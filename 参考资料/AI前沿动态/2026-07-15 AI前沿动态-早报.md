# 📱 深度研究 ｜ 27B 级 agentic 模型第一次跑进 iPhone：拆解 PrismML「Bonsai 27B」与端侧 agent 的临界点

> **一句话定性**：这不是又一个开源模型，而是一个**部署层的临界点**——一个带工具调用、视觉、262K 上下文的 **27B 级 agentic 模型，被压到 3.9GB 塞进 iPhone**，还保住了约 90% 的能力。它把"能干活的 agent 必须跑在云端前沿 API 上"这条隐含假设，第一次真正撕开一道口子。但**代价恰恰落在 agent 最吃紧的能力上**——工具调用掉得最狠。

## 一、为什么这一篇值得单独深读

过去一年，"agent"这个词几乎等价于"调云端前沿模型的 API"。做 agent 系统的默认前提是：能力越强越贵、越贵越只能放云上、越放云上越绑死某个供应商、数据越要出你的设备。Bonsai 27B 的意义，不在于它刷了什么榜，而在于它**同时撬动了这条假设链上的四个环节**：

- **能力**：它不是个玩具小模型，而是一个 **27B 级、多模态、带工具调用与结构化输出**的 agentic 模型（底座是阿里 Qwen3.6-27B）。
- **体积**：1-bit 版压到 **3.9GB**，第一次让"27B 级"这个量级**装进一部手机的可用内存**。
- **速度**：在 iPhone 17 Pro Max 上真实**能出词**（虽然不快）。
- **成本/隐私**：端上跑 = 边际推理成本≈0、数据不出设备、可离线。

极致低比特量化（1-bit / ternary，即 BitNet 一脉）过去两年一直被质疑"短基准好看、真用就崩"。Bonsai 的看点是：它**把这套方法一次性铺到 27B + 多模态 + agentic 全栈**，并公开了逐类别的能力保留曲线——让我们第一次能定量看清"极致压缩到底伤了 agent 的哪根筋"。对做多 agent 系统的团队，这既是机会窗口，也是一份该收藏的"端侧能力衰减表"。

## 二、核心事实（按可信度分层）

**A. 模型与方法（硬事实）**
- 底座 **Qwen3.6-27B 多模态**，架构不动。参数分布：语言网络约 **24.8B**、视觉塔 **0.46B**（保留 4-bit HQQ）、embeddings/LM head 约 **2.5B**。**262K** 上下文。
- 两个变体：
  - **Ternary（三值）**：权重 ∈ {−1, 0, +1}，每 128 个权重共享一个 FP16 缩放因子 → **1.71 有效 bit/权重**，**5.9GB**。
  - **1-bit（二值）**：权重 ∈ {−1, +1} → **1.125 有效 bit/权重**，**3.9GB**（约为 FP16 的 1/14）。
- 低比特表示**贯穿全网**——embeddings、attention、MLP、LM head，**没有留高精度"逃生舱"**。这点很关键：不是"只压不重要的层"糊弄基准。
- 方法口径有一处分歧（如实标注）：**CNBC 引 CEO Hassibi 称用了量化感知训练（QAT）**，让模型"从一开始就带着二值约束学"；而 MarkTechPost 把公开的这两个 build 描述为"对底座的低比特表示、非重新预训练"。二者不完全矛盾（IP 是 QAT，放出的是其产物），但**"到底多少来自训练、多少来自后处理"目前无法从一手页面证实**，是第一个该盯的存疑点。

**B. 能力保留曲线（自报基准，15 项套件，thinking 模式；基线=FP16 Qwen3.6-27B）**

| 类别 | FP16 基线 | Ternary(5.9GB) | 1-bit(3.9GB) |
|---|---|---|---|
| 数学(4 项) | 95.3 | 93.4 | 91.7 |
| 编码(3 项) | 88.7 | 86.0 | 81.9 |
| **Agentic / 工具调用** | **80.0** | **74.0** | **66.0** |
| 指令遵循 | 78.4 | 71.8 | 65.8 |
| 知识/STEM | 83.1 | 77.0 | 73.4 |
| 视觉 | 72.6 | 65.2 | 59.6 |
| **综合(15 项)** | **85.0** | **80.5(≈94.6%)** | **76.1(≈89.5%)** |

**C. 真实速度（decode / 出词速度，别被峰值数字骗）**
- **iPhone 17 Pro Max（1-bit）**：解码约 **11 tok/s**（prefill 约 111 tok/s）。
- **M5 Max（Ternary）**：解码约 **26 tok/s**（prefill 约 393 tok/s）。
- **H100（1-bit）**：解码约 **105 tok/s**（prefill 约 2755 tok/s）。
- ⚠️ 官方另有"163 tok/s（RTX 5090）/ 87 tok/s（M5 Max）"等**峰值宣称**——那是最优/prefill 口径。**多步 agent 循环真正卡的是 decode**，以手机 ~11 tok/s 为准更诚实。

**D. 部署与生态**
- 苹果设备经 **MLX**、NVIDIA 经带自定义低比特 kernel 的 **CUDA**；已在 **iPhone 17 Pro Max** 实机演示，iOS 侧可经 **Locally AI** app 体验。支持**投机解码**。
- **苹果在评估**：Hassibi 对 CNBC 称，苹果等公司正在测其模型的速度、能耗与端上表现——"They're really evaluating our technology right now."

## 三、机制拆解：为什么"agent 最需要的能力"掉得最狠

看那张表最该盯的不是综合分，而是**各类别的衰减斜率**。从 FP16 到 1-bit：
- 数学只掉 **3.7 分**（95.3→91.7），编码掉 **6.8 分**——**闭合式、答案唯一**的任务最抗压。
- 但 **agentic/工具调用掉了整整 14 分**（80.0→66.0）、指令遵循掉 **12.6 分**、视觉掉 **13 分**——**这些恰恰是 agent 干活的核心肌肉**。

原因不难理解：极致量化把权重的"表达分辨率"砍到只剩符号位，**误差是逐 token 累积的**。数学题一步错基本当场露馅、可被 thinking 模式纠回；而**工具调用/指令遵循是长程、结构敏感的**——一次参数名拼错、一个 JSON 字段跑偏、一步该调工具却没调，错误会沿 agent 循环**复利放大**，且往往到很后面才暴露。换句话说：**量化伤的不是"知识"，是"照章办事的精确度"**，而后者正是 agent 的命门。

所以真正可用的结论是分档的：**做 agentic 工作负载，选 Ternary（5.9GB，保 74）而非 1-bit（3.9GB，保 66）**；1-bit 更适合纯生成/摘要/离线问答这类容错高的场景。别被"3.9GB 塞进手机"这个营销点带着走。

## 五、正反观点

**支持方（这是真拐点）**
- **端侧 agentic 第一次"够用"**：27B 级 + 工具调用 + 视觉 + 262K 上下文跑在手机上，隐私（数据不出设备）、成本（边际≈0）、离线、低延迟——四个云端 agent 的结构性痛点一次缓解。
- **信誉不低**：Caltech 出身、信息论大牛挂帅、Khosla/Google/Samsung 背书，不是随手套壳的小作坊；苹果在评估进一步抬高了平台意义（呼应 6/8 已推的 Gemini-Siri 端上博弈）。
- **方法可迁移**：ternary/1-bit 全栈量化若稳，是把**任意开源前沿权重**下沉到端的通用管道，不止一个模型。

**质疑方（先别兴奋）**
- **伤在刀刃上**：如上，量化最狠地砍掉了 agent 最依赖的工具调用/指令遵循能力，长程任务里会复利放大——"跑得起来"≠"跑得可靠"。
- **真实速度慢**：手机 ~11 tok/s decode，一个多步、要读长上下文再多轮调工具的 agent 会很"肉"；持续负载下的**发热/降频/续航**官方未给数据。
- **内存账没算完**：12GB 的 iPhone 实际留给 app 的约 6GB，3.9GB 权重还要和 **KV cache + 激活**抢预算，**262K 上下文一开，长任务很快触顶**。
- **自报 + 衍生**：15 项基准均为 PrismML 自测、待独立复现；底座是 Qwen3.6（阿里开源），**权重来源/许可链**（Qwen 许可 vs 重新打包成 Apache 2.0）值得确认；方法是否真 QAT 也待坐实。

## 六、深度解读：对行业 + 对「做多 agent 系统的我们」

**对行业格局**：这条线的战略含义，是**推理的成本/隐私/延迟地板正在向端侧塌陷**。过去"能力=云端=绑定供应商"的链条，多了一个真实的旁路。它同时喂给两条我们一直在追的主线——**多模型冗余/抗断供**（端上有个离线兜底，就多一层不受出口管制、限流、监管下线影响的保险，见 Fable5 出口管制系列）与**推理成本地板下移**（Lindy 效率拐点、自研硅军备）。对苹果尤其性感：一个能在自家芯片上跑、还带 agentic 能力的 27B，是 Apple Intelligence"少求人、多本地"叙事的现成拼图。

**对做多 agent 系统的我们（落到可执行判断）**：
1. **把"端侧兜底档"纳入 agent 架构**：不是全量迁端，而是设计**云-端混合**——高价值/隐私敏感/离线场景走端上小 agent，复杂长程仍回云端前沿（正如 GPT-Live 用 GPT-5.5 兜底的思路）。端上这一档，现在有真实候选了。
2. **量化档位按"能力命门"选，别按体积选**：agentic/工具调用负载**默认选 ternary，不选 1-bit**；把这张"逐类别衰减表"变成你选端上模型的验收基线——**自己在真实工具链上重测工具调用成功率与指令遵循**，别信综合分。
3. **端上 agent 的瓶颈是内存预算不是模型体积**：262K 上下文是纸面数字，真跑要给 KV cache 留量；**上下文压缩/滚动窗口/工具结果裁剪**在端上比云上更是刚需。
4. **供应链要多问一句**：底座 Qwen（中国开源权重）→ PrismML 量化 → Apache 2.0 分发，这条链的许可与来源要盘清楚，别把不确定的许可引进产品（呼应我们对"AI 生成的依赖/来源需校验"的一贯口径）。

**一句话给团队**：Bonsai 27B 不改变"最强 agent 仍在云端"的现实，但它把"**够用的 agent 可以离线、在你口袋里、零边际成本地跑**"从 PPT 变成了可下载的权重——该做的不是立刻搬家，而是**现在就在真实工具链上量一次端上工具调用的可靠性**，把这一档提前排进架构。

## 七、接下来盯什么（信号）

- **独立复现**：第三方（社区/竞品）在标准 SWE/Terminal-Bench/工具调用套件上复测 Bonsai 的工具调用与指令遵循，看自报数字是否站得住。
- **方法坐实**：PrismML 是否公开 QAT 细节或论文，把"训练 vs 后处理"的口径说清。
- **苹果动向**：苹果"评估"是否转成集成/收购/授权——那会把端侧 agentic 从极客玩具推成平台默认（接 6/8 Gemini-Siri）。
- **管道通用性**：同套 ternary/1-bit 全栈量化是否被套到别的开源前沿权重（Llama/GLM/DeepSeek/Gemma），成为"把云模型下沉到端"的标准工序。
- **端上 agent 的真实工程账**：手机持续负载的发热/续航/内存触顶实测，以及长上下文下 decode 速度的真实体感。
