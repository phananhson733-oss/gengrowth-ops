# 🧠 深度研究 ｜ 苹果给漏洞收件箱装上闸门：AI 时代的瓶颈正式从「生成」搬到「验证」

> **一句话定性**：这不是一条苹果的产品新闻，而是**第一家有无限资源的大平台公开承认「人类分诊带宽已被 AI 产出打爆」**——并且它选择的解法（按人限流）在上线的同一周就把一个真实的、值 10–20 万美元的 macOS 漏洞挡在了门外。对所有做 agent 的团队，这是一份关于「产出多少不重要、能否被验证才重要」的提前判决书。

**来源**：Financial Times 首发（2026-08-02，Techmeme 同日收录为头条）；the-decoder 同日跟进补上关键个案；curl / OpenSSL 侧对照数据来自 2026 年 1 月的公开记录。

## 一、为什么这一篇值得单独深读

过去一年，「AI slop 淹没开源维护者」一直被当作小项目的苦水——curl 那种一个人扛安全队列的项目撑不住，可以理解。这次不一样：**扛不住的是苹果**。

苹果是这个星球上安全预算最充裕、分诊团队最专业的公司之一，最高赏金已经开到 200 万美元、链式攻击加奖金超过 500 万美元。它扛不住，说明这不是资源问题，而是**结构问题**：生成侧的边际成本被 AI 压到接近零，验证侧的边际成本几乎没变。任何一个「多方提交 → 少数人审」的系统，都会在某个时点被这条剪刀差撕开。

而这条剪刀差，正是我们做多 agent 系统时最容易忽略的那一半——我们花全部精力优化「让 agent 产出更多候选」，却默认下游有人接得住。

## 二、核心事实（按信源可靠度分层）

**A. 苹果做了什么（FT 一手，8/2）**
- 对 Feedback Assistant 的漏洞提交设置了**提交数量上限**，并加了**30 天冷却期**（cool-off period）。
- 公开理由：AI 辅助生成的漏洞报告泛滥（a deluge of AI-assisted reports）。
- 留了口子：研究者可以**申请更高配额**（higher quotas）。
- ⚠️ 具体额度数字苹果未公开，公开报道中也没有——这一点先别自己脑补。

**B. 闸门当周就误伤了什么（the-decoder，8/2）**
- 意大利初创 **Bynario** 用自家 Atlas 平台（由 GPT-5.5 驱动）发现一个 macOS **Screen Sharing** 漏洞：已通过认证的 VNC viewer 可以访问受保护数据，并以 **root 权限创建文件**。
- Bynario CEO **Alfredo Pesoli** 估计该漏洞黑市价值 **10 万–20 万美元**。
- 结果：提交额度已被封顶，**报不上去**。
- 后续：苹果事后**主动联系了 Bynario**。

**C. 苹果自己那一手（同日报道）**
- 苹果**自己在用 Anthropic 和 OpenAI 的模型**猎取漏洞，且效果显著：最近一次更新包含的修复数量是**平常的 5 倍**。
- 苹果同时引入 **target flags**：要求研究者客观证明漏洞真的触达了受保护区域，而不是停留在理论推演——这是**信噪比治理**，与配额限流是两种完全不同的思路。

**D. 对照组：更早撑不住的那些（2026 年 1 月公开记录）**
- **curl**：2026 年 1 月宣布关停 bug bounty，2 月 1 日起不再通过 HackerOne 收新提交，改走自有披露渠道。数据：约 **20% 的提交是 AI slop**；**2025 年全年提交里仅 5% 是真漏洞**；该项目自 2019 年运行以来累计支付 **9 万美元以上**、认定 **81 个真漏洞**。
- 同一个 Daniel Stenberg，也公开承认 AI 辅助工具帮 curl 修掉了 **100+ 个 bug**——那些 bug 熬过了多年激进 fuzzing、编译器告警、静态分析和多轮人工安全审计。
- **AISLE 的 OpenSSL 实验**（2026-01-27 公开）：AI 系统命中 OpenSSL 2026 年 1 月发布中的 **12/12 零日 CVE**，2025 年全年 **13/14**；其中 **3 个 bug 可追溯到 1998–2000 年**，潜伏 **25–27 年**，有一个甚至继承自 1990 年代的 SSLeay。curl 侧另有 5 个 CVE。
- ⚠️ 这份实验的**关键短板必须同时记住**：它没有公布用了哪些模型、检出率、**误报率**、单条发现的成本。没有误报率，「12/12」这个数字无法用于任何经济性判断。

## 三、机制拆解：这条剪刀差是怎么张开的

把漏洞市场拆成三段，就能看清失衡发生在哪：

| 环节 | AI 之前的成本 | AI 之后的成本 | 变化 |
|---|---|---|---|
| **发现**（找到候选） | 高，需专家时间 | 接近零，可无限并行 | ↓↓↓ |
| **验证**（证明它是真的、可利用） | 中 | **几乎没变**——仍需人读代码、搭环境、跑 PoC | → |
| **修复**（打补丁） | 中 | 略降（AI 辅助） | ↓ |

AISLE 那句「难的一直是发现，知道要修什么之后修复就容易扩展了」在 AI 之前是对的，**现在整句反过来了**：发现变成了最便宜的一段，而**验证成为唯一没有被自动化的瓶颈**，于是它成了整条流水线的限流阀。

苹果的两个动作，恰好对应两种截然不同的应对哲学：

- **target flags** ＝ 把验证成本**前移给提交方**。你必须自己证明触达受保护区域，我才受理。这是在提升单条提交的信息密度。
- **配额 + 30 天冷却** ＝ 把验证成本**用速率限制硬压下去**。它不区分提交质量，只区分「你今天还有没有额度」。

Bynario 的案例就是这两种哲学冲突的产物：那条漏洞**完全有能力通过 target flags 的检验**（root 权限创建文件，实打实触达），却死在了与质量无关的配额上。**用一个与信号质量正交的维度去过滤信号，必然误伤最强的信号。**

Sophos 的 **Rafe Pilling** 给出了行业侧的判断：漏洞发现的重心已经转向「**以机器速度验证它们**（validating them at machine speed）」。这句话点名的正是那个还没被填上的缺口。

## 四、正反两面

**支持苹果这么做的一方：**
1. 分诊是**真实的稀缺资源**，且无法靠加钱线性扩张——分诊质量依赖对系统内部的深度理解，不是可以外包的岗位。
2. 不加闸门的对照组结果已经摆在那里：curl 的做法是**直接关停整个 bounty 程序**。相比之下，配额 + 可申请提额，至少保留了通道。
3. 苹果并非只做减法：**最高赏金提到 200 万美元、链式超 500 万美元、引入 target flags**，这套组合的意图是「少而准」，不是「少就行」。
4. 5% 的真阳性率（curl 数据）意味着分诊团队 95% 的时间在处理噪声。任何工程系统在这个信噪比下都必须限流，否则真信号的响应延迟会趋于无穷。

**质疑的一方：**
1. **配额是钝器**。它按「人」限流而不是按「历史真阳性率」限流。一个从没提交过垃圾的团队，和一个刷了三个月 slop 的账号，吃同一套额度。Bynario 就是代价。
2. **双重标准刺眼**。苹果自己用 Anthropic 和 OpenAI 的模型找漏洞、把修复量拉到 5 倍，同时对外部的 AI 辅助报告限流。合理的解释是「我信任自己的验证流水线、不信任你的」——但这等于承认：问题不在 AI，在于**缺少一套跨组织的可信验证协议**。
3. **黑市不设配额**。一条 10–20 万美元的漏洞在合法渠道被额度挡住时，灰色渠道的相对吸引力是上升的。限流真正压低的可能不是噪声总量，而是**合法披露相对于私下变现的竞争力**。
4. **成本只是被转嫁，没有消失**。研究者要么等 30 天，要么去申请提额——后者又是一道人工审核。除非提额审核比漏洞分诊便宜得多，否则这只是把队列从一个窗口挪到了另一个窗口。

## 五、深度解读：对行业，以及对「做多 agent 系统的我们」

**对行业：**这是**第一次由一家不缺钱的大平台，用制度形式承认「AI 产出的接收端会崩」**。它会成为先例。凡是「多方提交 → 少数人审」的结构——bug bounty、开源 PR、应用商店审核、学术投稿、工单系统、内容举报——都在同一条剪刀差上，只是被撕开的先后不同。curl 在 1 月，苹果在 8 月，下一个是谁只是资源多寡的问题。

**对我们，六条可执行判断：**

1. **agent 的输出格式必须自带证据，而不是自带论证。** 苹果的 target flags 就是在强制这件事。我们的 agent 产出（无论是代码变更、诊断结论还是调研发现）如果只交付自然语言推理，接收端的验证成本就全落在人身上——而那正是马上要被限流的资源。**交付物里必须包含可机器执行的复现路径**：最小复现脚本、断言、可跑的环境定义。这条从「加分项」升级为「准入条件」。

2. **凡是把 agent 产出提交给外部人类系统的链路，现在就要按「有速率限制」来设计。** 别假设对面的收件箱是无限的。架构上把「提交额度」当作一等资源来建模：显式记账、优先级排序、失败可重投。同时设计**信誉累积路径**——先用低量高质换取配额与信任，再放量，而不是一上来就把管道打满。这跟我们此前在 harness 层做工具白名单是同一类工作：**把外部约束显式化，别让它以随机失败的形式暴露。**

3. **给 agent 的 KPI 如果是「产出条数」，就是在给自己造 slop。** curl 的 5% 真阳性率是所有「无验证的高吞吐 agent」的归宿。内部评估指标要换成 **verified-precision（经验证通过的比例）**，并且把未通过条目消耗的下游人力**显式计入成本**。一个产出 10 条、9 条经验证成立的 agent，价值远高于产出 200 条、真阳性 5% 的 agent——后者在今天的环境里是净负价值，因为它烧的是别人的分诊带宽。

4. **自动验证层是当前最值钱的中间件，比再加一个生成 agent 杠杆高得多。** 三方独立指向同一个缺口：curl 的 5% 真阳性、苹果需要 target flags、Sophos 说要「以机器速度验证」。如果我们要在 agent 基础设施上押注，**押验证与分诊，不要押生成**——生成侧已经是红海且边际成本趋零，验证侧还是空的。

5. **上游补丁节奏假设要更新。** 苹果单次更新的修复量已是平常的 5 倍，AISLE 一次挖出 OpenSSL 12 个零日、其中 3 个潜伏 25 年以上。这意味着**我们依赖的 OS 与基础库，漏洞披露速率在结构性上升，补丁窗口在缩短**。依赖更新的排期和 SLA 要按 2026 年的速率重算，别继续用 2024 年的假设——那套假设背后是「漏洞发现受限于专家时间」，而这个前提已经不成立了。

6. **和 8/2 那条 Ruflo 议题接上，构成完整图景。** 前天看到的是 agent 框架**自己成为攻击面**（未认证 MCP bridge、memory poisoning），今天看到的是 agent **作为发现方把防守方的分诊打爆**。同一批能力，两端同时施压。对我们的合并结论是：**agent 系统的安全预算必须双向配置**——既要防自己被打，也要防自己的产出成为别人眼里的噪声（后者会直接损耗我们与外部生态的信任额度，而信任额度一旦被限流就很难恢复）。

## 六、接下来盯什么

- **苹果是否公布具体配额数字与信誉分级机制。** 「按人限流」和「按历史真阳性率限流」是钝器与精准工具的分界线，也是判断这套制度会不会长期误伤高质量提交方的唯一信号。
- **Bynario 那个 Screen Sharing 漏洞的最终归宿。** 是否进入某次 macOS 安全更新、是否拿到赏金——这决定了这次是「个案已纠偏」还是「制度性失灵」。
- **HackerOne / Bugcrowd / GitHub 是否跟进配额或信誉门槛。** 一家＝苹果特例，三家＝行业新常态，后者意味着我们要把速率限制写进所有对外提交链路的默认假设。
- **是否出现被广泛采用的「可验证提交」标准**（target flags 式的证据格式）。这很可能会成为 agent 输出格式的事实标准来源——谁先定标准，谁就定义了 agent 产出的合格线。
- **curl 停收半年后的真漏洞数是否下降。** 2 月 1 日停收，8 月正好半年，这是唯一能量化「闸门到底挡掉了多少真信号」的自然实验。
- **有没有机构公布 AI 漏洞发现的误报率与单条成本。** AISLE 缺的正是这两个数。在它们出现之前，任何「AI 找到 12/12」的说法都只能当能力演示看，不能用来做投入产出判断。
