# 一张显卡装下会干活的 agent

**一句话定性：** 阿里把一个 27B、Apache 2.0、能装进一张消费级显卡的模型，推到了 Terminal-Bench 2.1 = 73.0 —— 这是本监测第一次看到「本地可跑」和「agent 能干活」这两件事出现在同一个模型上，而不是二选一。

**来源：** Qwen Team / 阿里云通义实验室（官方发布 + HuggingFace 模型卡）
**🔗 原始链接：** https://huggingface.co/Qwen/Qwen3.8-27B
**发布时间：** 2026-08-14 15:00 UTC（北京时间 8/14 23:00）

---

## 为什么值得深读 / 背景

8 月 3 日本监测推过一篇《阿里把 2.4 万亿参数交出去》：Qwen3.8-Max 转为全球可用，同时官方承诺「下周放开源权重」。8/14 这条就是那个承诺的兑现——但兑现的方式和多数人预期的不一样。

大家等的是 2.4T 那个旗舰的权重。真正落地的第一个开权重档位，是 **27B**。

这个错位恰恰是这条新闻的价值所在。过去一年本监测反复记录同一个结构性事实：开源权重的前沿档位在把「硬件准入线」越抬越高。7/31 wafer 那篇《Is memory the moat?》给过最硬的一组数——Kimi K3（2.8T）光权重就要 >1.5TB 显存，能单节点装下的只有 288GB/GPU 的 B300 与 MI355X；7/26 Kimi K3 那篇给的门槛是 1.4TB。也就是说，**「开源」这个词在前沿档位上已经和「你能跑」脱钩了**：权重是公开的，但只有云厂能跑。

Qwen3.8-27B 走的是反方向：把 agent 级能力压进 24GB 显存。如果这个压缩是真的，那么本监测追了半年的「开权重 = 只能托管」这个结论，第一次出现了缺口。

对做多 agent 系统的团队，这不是一条模型发布快讯，而是一次**部署形态的可行性重估**。

### 二、架构（这是它能压进单卡的原因）

64 层，采用 **3:1 混合解码器**，一个模式重复 16 次：

```
16 × ( 3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN) )
```

- **Gated DeltaNet（线性注意力）48 层**：V 头 48 / QK 头 16，头维 128
- **Gated Attention（全注意力）16 层**：Q 头 24 / KV 头 4，头维 256，旋转位置编码 64 维
- FFN 中间维 17,408
- 隐藏维 5,120
- 训练时带 **多 token 预测（MTP）**，用于加速解码

## 机制拆解：3:1 混合注意力为什么对 agent 特别重要

多数人看到「线性注意力」想到的是省算力。对 agent 工程，**真正省的是 KV cache，而 KV cache 才是长跑 agent 的死因**。

一个跑长任务的 agent，上下文里堆的是：系统提示 + 历史消息 + 每一次工具返回 + 每一段思考块 + 最终输出。这些东西只增不减。传统全注意力架构下，每增加一段工具返回，KV cache 就按上下文长度线性膨胀，且每层都要存。跑到第 30 轮工具调用，显存先崩，而不是模型先笨。

3:1 混合的做法是：**64 层里只有 16 层需要维护完整 KV cache**，另外 48 层用 Gated DeltaNet 的固定大小状态。全注意力层在这里扮演「精度校验点」——它们能对全上下文任意位置做精确打分，负责消歧和精确检索；线性层负责廉价地把上下文往前推。

这个设计在 Qwen 系列上是有历史读数的：同架构族的 Qwen3.5 上，40 层里只有 10 层用 KV cache，上下文从 4,096 拉到 65,536 只多吃约 800MB 显存。按公开的混合架构测算，1M 总上下文的 KV 成本约 25GB，比朴素全 transformer 估算低约 4 倍。若按 32 层里 4 层全注意力的比例，262K 上下文下注意力相关计算量约降到 1/8。

**对我们的直接含义：** 我们做多 agent 系统时反复撞的墙是「长会话把显存吃光」而不是「模型不够聪明」。3:1 混合是第一个在开权重侧、且带完整 agent 基准的解法样本。这个架构值得在我们的本地评分器 / 复核 agent 上做一次真实工作流实测——不是跑基准，是跑我们自己的 30 轮工具调用。

## 正反观点

### 支持方：这是「本地 agent」第一次不是玩具

- **纵向增幅是真的大**：DeepSWE 1.1 从 13.3 到 42.2，OSWorld-Verified 从 63.9 到 84.3。同体量、同团队、一代之隔，这种幅度不是调参能刷出来的。
- **横向压制同级开权重**：Terminal-Bench 2.1 上 73.0 vs Muse Glimmer 30B 的 51.7，差 21.3 分。8/10 我们把 Muse Glimmer 记进 backlog 时给的定位是「本地评分器候选」，四天后这个位置被换人了。
- **许可是干净的 Apache 2.0**：可商用、可自托管、可再分发。对有辖区约束的部署，这是硬条件。
- **它把 agent 评测的门槛降下来了**：一个 18GB 的 Ollama 包 + 一张 4090，团队就能跑真实的 agent 评测循环，而不是每次评测都烧 API 账单。

### 质疑方：这些数字全部是厂商自报，而且「装得下」不等于「跑得动」

1. **零独立复现。** 截至目前没有找到独立机构对这批基准的复现。QwenSWEBench 本身就是 Qwen 自家的基准——那个 +29.7 的最大增幅恰好出现在自家基准上，这个巧合需要被记住。
2. **技术报告缺席。** 本次发布**没有**模型专属技术报告：训练 token 数、数据集清单、知识截止日、训练算力、支持语种数、安全 / red-team 报告、官方延迟表、最低 GPU 矩阵，全部未披露。有评测站直接指出「fully open source」这个说法在没有训练数据和可复现训练包的情况下是夸大的。
3. **对照组不是当前前沿。** 官方对照表里的 Claude 档位标注为 Opus 4.6 / Opus 4.6 Max —— 而 Anthropic 当前旗舰是 7/24 发布的 Opus 5。拿上一代对标是常见做法，但读数时必须扣掉这一层。
4. **就算按这张表，前沿仍然领先。** Terminal-Bench 2.1 上 Opus 4.6 Max 是 78.2，领先 5.2 分；NL2Repo-Bench 上 47.6 vs 42.3。GPT-5.6 在 Terminal-Bench 上的口径是 88.8。再对照本监测 8/14 已核实的 DeepSeek V4-Pro-0813：Terminal Bench 2.1 = 87.9。**73.0 不是前沿，是前沿之下 5 到 15 分的一个新档位。**
5. **显存账没那么好看。** 权重文件不是账单全部。按 BF16 全精度 KV 估算，原生 262K 上下文的全注意力 KV 至少要 67.76 GiB；官方 BF16 权重 51.76 GiB 加上原生上下文缓存已超过 80GB。一张 24GB 卡装得下权重，装不下 256K 的真实 agent 会话——「能加载模型的笔记本，未必扛得住一次 256K 的 agent 会话」。
6. **量化敏感性未知。** 官方 FP8 卡宣称性能与 BF16 近乎一致，但这在同 prompt / 同 seed / 同视觉输入 / 同 agent harness 下被实测之前只是厂商说法。而 agent 任务对量化的敏感度显著高于单轮问答——工具调用格式、thinking 保留策略、chat template 在 Ollama / vLLM / SGLang 上各不相同，这些差异足以吃掉基准上的十几分。
7. **短板明确**：纯知识类任务（GPQA 系）落后，未发布 AIME / MATH 成绩，中英之外的语种表现无文档。

## 深度解读

### 对行业：开权重出现了「双头分叉」

到今天为止，开源权重这条线上同时存在两种完全相反的策略，而阿里一家把两种都做了：

- **上行**：Qwen3.8-Max（2.4T）、Kimi K3（2.8T）、openPangu 505B、K-EXAONE 750B —— 权重公开，但准入线是单节点 1.5TB HBM，实际只有云厂能跑。**开源在这里的含义是「你可以审计，但你得租我们的机器」。**
- **下行**：Qwen3.8-27B、Muse Glimmer 30B —— 权重公开，且一张卡能跑。**开源在这里的含义回到了原本的样子：你可以拥有它。**

过去半年本监测记录的几乎全是上行那一支，容易得出「开源正在变成托管的另一种说法」的结论。8/14 这条是下行支第一次拿出 agent 级基准。这两支不是竞争关系，而是在把闭源前沿从两头夹：上行支抢的是「最强」，下行支抢的是「够用且免费」。

被夹在中间最难受的，是**中等价位的闭源 API 档**。一个 73.0 的模型如果本地跑起来边际成本接近零，那么任何定价的闭源模型都必须证明自己那多出来的 5–15 分值这个钱。呼应本监测 8/13 那篇《前沿被挤成一条 3 分宽的线》：前沿内部已经挤成一条窄带，现在窄带下方又被开权重顶上来了一层。

同一周还有一个反向读数值得并读：DeepSeek 从 8/16 16:00 UTC 起涨价并首次启用峰谷分时定价（缓存命中价从标准输入价的 1/120 缩到 1/30，等于对长上下文多轮 agent 的定向加价）。**云端 agent 的单位成本在涨，本地 agent 的能力门槛在降 —— 这两条曲线正在同一周交叉。**

### 对「做多 agent 系统的我们」：五个可执行判断

1. **本地评分器 / 复核 agent 的候选换人。** 8/10 我们把 Muse Glimmer 30B 记为本地 LLM-as-judge 候选。按 Terminal-Bench 21.3 分和 OSWorld 18.4 分的差距，Qwen3.8-27B 应当取代它成为首选试点对象。这类任务（打分、复核、格式校验）恰好是**高频、低难度、对延迟敏感、对成本极敏感**的档位——把它从云端前沿档下沉到本地，是我们成本结构上最大的一块可动预算。

2. **别按权重体积做容量规划，按 KV 曲线做。** 24GB 能装 Q4 权重这件事在 agent 场景下几乎没有意义。真正要测的是：我们典型的 agent 会话（30 轮工具调用 / 多少 token）在目标量化下，显存曲线长什么样，什么时候崩。**行动项：在我们最长的一条真实 agent 轨迹上做显存打点，而不是跑基准。**

3. **量化档必须自己实测，不能抄官方。** 具体到我们最在意的三件事：工具调用的 JSON 格式在 Q4 下是否退化、thinking 块保留策略在不同 runtime 下是否一致、长会话下是否出现指令漂移。这三项在通用基准上完全测不出来，但每一项都能让一个 agent 系统变得不可用。

4. **多模型路由里给它开一个新档：`local-agent`。** 现有路由分档基本是「前沿 / 中端 / 廉价云端」。这条新闻要求加第四档：**本地、零边际成本、可离线、无辖区外传**。按 7/27 立场篇的字段约定，这个模型的归档是 `origin=CN / hosting_jurisdiction=self / license=Apache-2.0` —— 注意 hosting_jurisdiction 是 `self`，这是它相对所有云端中国模型的关键差异，也是它能进对数据出境敏感场景的唯一原因。

5. **口径纪律：73.0 不是「追平前沿」。** 对外表述必须写清楚「同级开权重最强 / 前沿之下 5–15 分 / 厂商自报未经独立复现」。本监测已经吃过一次亏的地方是聚合站会把「在部分基准上超过某个非当前旗舰」压缩成「超越 Claude」——这次的传播里已经出现了这种压缩，别跟着传。

## 接下来盯什么

1. **独立复现。** 第一个由非 Qwen 方在标准 harness 下跑出的 Terminal-Bench 2.1 / OSWorld-Verified 数字。如果独立值落在 65 以下，整篇解读的力度要下修一档。
2. **技术报告是否补发。** 训练 token 数、知识截止、安全评测。缺这三项，它在受监管场景里进不了正式依赖清单。
3. **量化后的 agent 质量实测。** 特别是 Q4_K_M 下工具调用成功率与格式稳定性的第三方数据。
4. **推理栈支持成熟度。** vLLM / SGLang 对 3:1 混合 + MTP 的支持是否稳定、chat template 是否统一。混合架构的历史包袱是 runtime 支持滞后。
5. **2.4T Max 的权重是否真的放出。** 8/3 的承诺是「下周」，现在放的是 27B。如果 Max 权重迟迟不来，说明「开权重」在阿里内部也已分层：小档真开、大档只是路线图。
6. **Meta 的回应。** Muse Glimmer 30B 才发布四天就被压过 21 分，看 Meta 是补一个版本还是换赛道——这决定 30B 级开权重是不是一条会被持续投入的战线。
7. **DeepSeek 分时定价的跟进者。** 若 OpenAI / Anthropic 任一跟进按时段卖 token，云端 agent 成本的时间结构就正式成立，本地档的相对吸引力会再上一台阶。
