# 那个被钉住的哈希，从来没有人回头核对

**一句话定性**：业界为 agent 插件生态建立的唯一一道主防线——SHA pinning（把插件锁死在某个经过审查的 40 位提交哈希上）——被证明在四家主流 coding agent 里**全部只做了前半截**：它们写下哈希、请求哈希、报告"已锁定在该哈希"，但从来没有在 checkout 完成后回头核对一句「我现在真的在这个哈希上吗」。缺的就是一行 assert。

**来源**：AIR Security 研究团队（一手）
🔗 **原始链接**：https://www.air.security/blog-posts/plugin4shell
**日期**：2026-09-18 公开披露（部分媒体标 9/17）；漏洞 2026 年 5 月发现，6 月通报厂商

---

## 为什么值得读 / 背景

这半个月我们追的 agent 安全线一直是"后果侧"的：9/10 PaperCut、9/11 RubyGems 的 2,000 个恶意包、9/18 CNN 那条军机升空。那些都是**已经发生的事故**，讨论的是"出事之后怎么办"。

Plugin4Shell 是另一类东西——它是**防线本身的设计缺陷**，而且是四家独立团队在互不相干的代码库里犯的同一个错。这种"共性错误"比任何单点事故都更值得停下来看，因为它意味着：整个行业对 agent 扩展生态的信任模型，建立在一个没人验算过的假设上。

时间线还有一层讽刺。AIR 在 **2026 年 5 月**做出可用 PoC，**6 月**协调披露给四家厂商。Anthropic 在 **6 月 17 日**随 Claude Code 2.1.179 修掉了——但 release notes 里只字未提。OpenAI 在 **8 月 12 日**随 Codex 0.146.0 修掉，并且在修复说明里公开描述了这个 bug。公众直到 **9 月 18 日**才知道有这回事。也就是说：**过去三个月里，你无法从任何 changelog 反推出自己那台机器是什么时候脱离危险的。**

而截至披露日，GitHub Copilot 仍未修补，Gemini CLI 则根本不会被修了。

## 核心事实

### 漏洞机制：git 的 refs 优先级

agent 安装插件时做的是标准操作——克隆仓库，checkout 到市场记录的那个提交哈希：

```bash
git clone <plugin repo> ./
git checkout aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

问题在于 **git 在遇到歧义时优先解析 refs（分支/标签名）而不是提交 ID**。攻击者只要在自己控制的插件仓库里创建一个**名字就是那 40 位十六进制字符串**的分支，并把它设为默认分支，这次 checkout 就会静默地落到恶意分支上。git 不报错，agent 不报错，配置文件里那个哈希看起来完全正常——但工作区里跑的是另一份代码。

Gemini CLI 走的是另一条路径，同一个病根：

```bash
git clone --depth 1 <plugin repo> ./
git fetch origin 41d0bc0a4aeb2fbf797dacea39e876d98c95024b
git checkout FETCH_HEAD
```

如果仓库的默认分支就叫 `FETCH_HEAD`，checkout 会解析到那个分支而不是刚 fetch 下来的提交，钉住的版本被直接丢弃。

### 完整攻击链（五步，零点击）

| 步 | 动作 |
|---|---|
| 1 | 攻击者发布一个**真正无害**的插件，提交在 `aaa...aaa` |
| 2 | 通过市场审查，用户安装，锁定在这个已审查版本 |
| 3 | 例行更新，市场把 pin 升到新的、同样无害的提交 `bbb...bbb` |
| 4 | 攻击者在自己仓库里创建一个**名为 `bbb...bbb` 的分支**，指向恶意代码，设为默认分支 |
| 5 | **后台自动更新**（Claude Code 与 Codex 的默认行为）触发 → 零点击 RCE，已安装的插件被静默掉包 |

AIR 的原话点出了第 5 步为什么是关键：

> "The same git checkout re-runs on background auto-update – the default in Claude Code and Codex – so when the marketplace bumps the pinned SHA, the swap reaches already-installed plugins with no user action."

### 爆炸半径

插件继承运行 agent 的开发者的**全部权限**：本地源码、云凭据、SSH 密钥、内部仓库、生产系统、各类 secret。AIR 的定性是"对 agent 及其宿主机的完全攻陷，以及该 agent 能触及的每一项资产与每一份数据"。

### 各厂商状态（截至 2026-09-18）

| Agent | 状态 | 细节 |
|---|---|---|
| **Claude Code** (Anthropic) | ✅ 已修 | 2.1.179（2026-06-17）；release notes **未提及**此修复 |
| **Codex** (OpenAI) | ✅ 已修 | 0.146.0（2026-08-12）；修复说明中**公开描述**了该 bug |
| **GitHub Copilot** (Microsoft) | ❌ 未修 | 6 月通报后至今无补丁；据 Pebblous，Microsoft "未作回应" |
| **Gemini CLI** (Google) | ⚠️ 不会修 | 产品已定于 **2026-06-18 退役**，引导迁移至 Antigravity CLI |

### 唯一正确的修法（必须在 agent 侧）

```bash
test "$(git rev-parse HEAD)" = "<pinned-sha>" || abort
```

一行。核对**实际解析出来的 HEAD**，而不是核对"我请求了什么"。

这里有个结构性的点：**市场方修不了这个洞**。锁的校验发生在用户自己的机器上，不在市场那一侧。无论 marketplace 的审查做得多严，补丁都只能由 agent 发。

### 背景：AIR 的系列研究与生态现状

- **2026-06**：AIR 演示一个假 skill 通过了所有公开安全扫描器（审查后改外链），触达约 **26,000 个 agent**。
- **2026-07-02 「SkillJacking」**：925 个 skill 坐落在"可被瞬间劫持"的依赖上（已注销的 GitHub 账号、未注册的包名、过期域名、被释放的云应用槽位），影响约 **134,000 个 agent**。研究者实际接管了 skills.sh 上最流行的视频生成 skill（**11,483 次安装**）——通过重新注册其已删除的所有者账号；**未向真实公开 skill 推送任何恶意内容**。
- **OWASP Agentic Skills Top 10 (AST10)**：1.0 (2026 Edition) 起草中，目标 **2026 Q4** 发布。十项里 **AST02 供应链攻陷**、**AST07 更新漂移（版本钉选与哈希校验）** 正是本条命中的两项；AST05 直接引用了 SkillJacking 的 925/134K 数字。

Plugin4Shell 与 SkillJacking 是可以串联的：后者提供"怎么拿到仓库控制权"，前者提供"拿到之后怎么把恶意代码推给**已经装好**的用户"。

## 正反观点

### 支持方（AIR 及多数安全媒体）的主张

1. **零点击**。不需要用户点击、批准、重装任何东西。默认开启的后台自动更新就是投递通道。
2. **四家全中**，说明这不是某家的疏忽，而是整个 agent 插件架构对"pin 即安全"的集体误读。
3. **打掉的是主防线**。SHA pinning 正是业界给出的、对抗插件供应链投毒的标准答案。这个答案在四个最主流的实现里都是空的。
4. **权限继承使后果无上限**。coding agent 天然握有开发者的全部凭据。
5. **市场侧无法自救**，只能等 agent 发补丁——而两家还没发。

### 质疑方 / 必须一起记的限制条件

1. **GitHub 平台级免疫**。GitHub 发言人：

   > "GitHub does not allow users to create branch or tag names that resemble commit SHAs, and this mitigation ensures the reported vulnerability cannot be exploited on GitHub."

   而 Anthropic 社区目录、Claude Code 与 Copilot 的默认目录里的插件**全部指向 GitHub**。也就是说主流路径上的绝大多数用户，被 GitHub 的一条分支命名规则挡住了。AIR 的反驳是市场也可托管在 Bitbucket 等平台，且 Copilot 支持这些外部源——成立，但这把风险从"所有人"收窄到了"用非 GitHub 托管插件源的人"。

2. **无在野利用，无 CVE**。截至披露日没有任何实际滥用报告，也尚未分配 CVE 编号。Pebblous 的措辞很克制：这是"一个研究团队做出了 PoC 的漏洞，而不是一起已经发生的事故"。

3. **"数百万 agent 受影响"是自报数字**。Pebblous 明确指出该规模估计"来自发现方自己，未经第三方验证"，而真实暴露面取决于是否安装了插件、插件托管在哪——"没有任何文档公布了这个分布"。

4. **利益冲突已被公开标注**。研究共同作者 Niv Hoffman 是 AIR Security 的联合创始人兼 CTO，而 AIR 销售相关的检测与修复产品。Pebblous 的原话值得原样引用：

   > "There is no basis for doubting the research itself, but the fact that the severity language and the reach estimate come from the side selling the remedy is information that travels with the numbers."

   技术发现本身无可指摘；**严重性形容词和覆盖面估计需要打折**。

5. **两家"未修"的性质不同**。Copilot 是真未修；Gemini CLI 是产品线本身在 6/18 就退役了。多家报道把后者写成"Google 选择弃用而非修补"，但退役 deadline（6/18）与 AIR 通报厂商（6 月）撞在同一个月——更可能是顺势处理而非专门回应。**这一点我无法从公开材料确证 Google 弃用公告与通报的先后，按存疑标注。**

### 一个两方都没说、但从两条独立事实能推出来的事

Gemini CLI 的退役条款里有一条豁免：**个人用户（AI Pro / Ultra / 免费版 Code Assist）在 6/18 之后 legacy CLI 直接停止响应，但购买了 Gemini Code Assist 许可证的组织可以继续使用 legacy CLI**，以保持既有工作流稳定。

把这条和"Gemini CLI 不会收到补丁"叠在一起：**被强制迁移到安全产品上的是个人用户，被允许继续运行永不修补版本的是付费企业客户**。这是一次典型的反向选择——未修补的攻击面被精准地留给了资产价值最高的那批目标。这不是阴谋，是兼容性承诺和安全承诺在弃用流程里没有对齐。任何做"长期支持版豁免"的产品决策都应该照这面镜子检查一次。

## 深度解读

### 对行业

**第一，这是 agent 扩展生态的 Log4Shell 时刻——但重要的不是严重性，是"共性"。** 四个由不同公司、不同语言、不同团队写的 agent，在同一个位置犯了同一个错。这说明大家是**互相抄的心智模型**，而不是各自独立推导的安全设计。"pin 住 SHA"在包管理器时代被反复验证过，于是被整体搬进 agent 插件系统——但没人注意到 npm/cargo 的 lockfile 校验是有**事后哈希比对**的，而 `git checkout <sha>` 没有。**从成熟生态借来的安全实践，在移植时丢掉了它赖以成立的那一半。**

**第二，"审查一次，自动更新无数次"是 agent 生态的结构性透支。** 传统应用商店的审查覆盖的是发布行为；agent 插件市场的审查覆盖的是**某一个提交**，而后台自动更新把这次审查的信用额度无限期地滚动到了未来所有版本上。第 3 步"例行更新到新的无害提交"之所以关键，是因为它证明了：**只要更新通道存在，任何一次历史审查都无法为当前运行的代码作保。**

**第三，安全研究的商业化正在成为信息本身的一部分。** AIR 既是发现者也是解药销售方，Pebblous 把这一点直接写进分析。这不削弱发现，但它提示一个正在形成的常态：**agent 安全领域的威胁情报，越来越多地由有商业动机的一方定价。**读这类报告时，技术机制照单全收，规模数字和严重性形容词单独核。

### 对「做多 agent 系统的我们」——可执行的六条

**① 今天就跑一遍版本核对，然后停止把"已修复"当成"我已安全"。**
Claude Code ≥ 2.1.179、Codex ≥ 0.146.0 即安全。这两个版本分别是 6 月和 8 月的，正常自动更新的机器早就过线了——**所以本条对我们的实际紧迫性很低，别当火警处理。** 真正要处理的是 Copilot：如果链路里有 Copilot 且插件源不在 GitHub 上，那是当前唯一的实际敞口。

**② 把「写下 ≠ 核对」升格成一条通用审计问句，扫一遍自己的全部 pin。**
这是本条最可迁移的东西，跟 agent 一点关系都没有。凡是我们系统里出现 pinned / locked / verified / immutable 字样的地方，都要能回答一个问题：**谁在操作完成之后，回头核对了实际结果等于预期值？**具体清单：
- 依赖 lockfile —— 安装后是否校验哈希，还是只记录哈希？
- **模型版本固定** —— 我们写死的是 `claude-opus-5` 这种别名，还是带日期的具体快照？别名是会漂的，等价于"写下但不核对"。
- prompt / skill / MCP server 配置版本 —— 部署后有没有回读校验？
- 容器镜像 —— 用的是 tag 还是 digest？
- 构建产物 —— 发布出去的那个 artifact，有没有和 CI 里构建出来的那个做过比对？

**③ 把 agent 的自动更新从"默认开"改成"有意识的选择"。**
不是建议关掉——关掉会让我们错过 6/17 那种静默安全修复，反而更糟。建议是：**生产链路上的 agent 走固定版本 + 有人值守的升级窗口；开发机上保留自动更新。**并且明确认知：自动更新同时是补丁通道和投毒通道，这两件事共用一根管子。

**④ 插件/skill 的"来源托管平台"必须进依赖台账，成为一个可查询字段。**
本条最反直觉的结论是：**救了大多数人的是 GitHub 的一条分支命名规则，不是四家 agent 做对了什么。**这意味着「这个插件托管在哪里」是一个真实的安全属性，而不是元数据。台账里至少要有：插件名 / 托管平台 / 仓库所有者 / pin 的 SHA / 最后核对时间。特别注意：**企业内部自建 plugin marketplace（通常跑在自托管 GitLab 或 Bitbucket 上）恰好没有 GitHub 那层运气**——而自建内部市场正是大团队被推荐的做法。安全建议和安全现实在这里是打架的。

**⑤ 把 SkillJacking 的"依赖是否可被瞬间接管"做成季度巡检项。**
925 个 skill 踩的坑是：已注销的 GitHub 账号、未注册的包名、过期域名、被释放的云应用槽位。这四类都是**可以脚本化检测**的。我们自己依赖的每一个 skill/plugin，其所有者账号是否仍然活跃、其引用的域名是否仍在有效期内——这是一个能跑 cron 的检查，不需要任何安全专业知识。**接上之前那条注入式测试的主线：这是"供应链侧"的同类动作。**

**⑥ 供应商的披露实践应当进选型评分。**
同一个漏洞，OpenAI 在修复说明里公开描述了 bug，Anthropic 在 release notes 里一字未提。两种做法都不违规，但对我们的运营含义完全不同：**静默修补意味着我们无法建立"我从哪天起是安全的"这一事实。**在事后取证、合规审计、客户问询三个场景下，这个差别是实打实的成本。建议把"安全修复是否在公开 changelog 中标注"加进供应商评估表——这条和 9/17 那篇「可观测性是销售前提」是同一个方向，只是从我们看系统，换成我们看供应商。

### 反向警告

我们过去一年把大量注意力放在"模型会不会做坏事"（对齐、越狱、幻觉）上。Plugin4Shell 提醒的是：**agent 系统当前最现实的失效面，根本不在模型里。**它在 git 的 refs 解析优先级里，在一行没写的 assert 里，在"自动更新默认开启"这个产品决策里。这些全是**普通软件工程问题**，用普通软件工程手段就能查、就能修——前提是我们得先承认它们归我们管，而不是归模型厂商管。

**在 agent 安全这件事上，我们目前的最大风险不是能力不够，是把注意力投错了地方。**

## 接下来盯什么

1. **Microsoft/GitHub 是否为 Copilot 发补丁**——距 6 月通报已逾三个月。若 90 天后仍无补丁，这是关于该厂商漏洞响应 SLA 的硬信号，直接进选型评分。
2. **是否分配 CVE**。目前无编号，意味着它进不了任何自动化漏洞扫描器的规则库——**在拿到 CVE 之前，这个洞对所有依赖 SCA 工具的团队是不可见的。**这本身是 agent 生态安全基建不成熟的量化指标。
3. **首例在野利用**。当前仅有 PoC。出现真实利用会把这条从"架构教训"变成"事故"，并大概率触发各家对插件自动更新的默认值调整。
4. **Anthropic 是否改变静默修补实践**——观察后续安全修复是否在公开 changelog 标注。这是可验证、可追踪的具体行为。
5. **OWASP AST10 正式发布（目标 2026 Q4）**。一旦落地，AST02/AST07 会成为可以直接抄进内部审计清单的现成条目，比我们自己攒一套快得多。
6. **企业自托管插件市场是否成为下一个披露主题**。GitHub 的免疫是平台级偶然，自托管 GitLab / Bitbucket 上的内部市场没有这层保护——如果 AIR 或其他团队去扫这一层，结论会比这次难看。
7. **Gemini CLI 企业豁免用户的处置**。Google 是否会因为这个不修的洞，改变对持 Code Assist 许可证组织继续运行 legacy CLI 的政策。这是检验"弃用流程里安全与兼容性如何排序"的一个具体观察点。
