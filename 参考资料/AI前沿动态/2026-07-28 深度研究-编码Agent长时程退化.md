# 🧪 深度研究 ｜ 24% 的天花板：SlopCodeBench 把「编码 agent 能不能无人值守」第一次量化了

> **一句话定性**：Opus 5 发布仅 3 天，一份第三方长时程实测把行业最爱的那个含糊问题钉死了——**在「需求分批下发、代码要反复演进」的真实开发形态下，当前最强模型的严格通过率只有 24%**。它不否定 Opus 5 的进步（相对 Opus 4.8 的 6% 是 4 倍），但它说明：**一次性刷榜的分数与「能托管给 agent 自己跑」之间，隔着一整个数量级。**

**来源**：HumanLayer（Dex Horthy / dhorthy）《Benchmarking Opus 5 on SlopCodeBench》，2026-07-27 前后发布，2026-07-28 登上 Hacker News 头版第 2 位（329 分 / 80 评论）。底层基准来自论文《SlopCodeBench: Benchmarking How Coding Agents Degrade Over Long-Horizon Iterative Tasks》(arXiv:2603.24755，Gabriel Orlanski、Devjeet Roy、Alexander Yun、Changho Shin、Alex Gu、Albert Ge、Dyah Adila、Nicholas Roberts、Frederic Sala、Aws Albarghouthi；v1 2026-03-25，v2 2026-05-07)。

## 一、为什么这一篇值得单独深读

这两天 AI 圈的头条是政策与资本（Anthropic 的开放权重立场、Nvidia 给 OpenAI 的融资担保）。但对**真正在生产环境跑 agent 的团队**，7 月 28 日 HN 头版透露的信号更硬——前三条里有两条指向同一件事：

1. #2《Benchmarking Opus 5 on SlopCodeBench》329 分
2. #3《一个 500 美元的 9B 开源模型 RL 微调，在目录审核任务上打败前沿模型》239 分
3. #1《用开源模型的感觉出奇地好》300 分

**共同潜台词是：旗舰模型的溢价正在被具体场景重新定价。** 而 SlopCodeBench 这条最关键，因为它回答的不是"哪个模型分高"，而是那个决定我们架构的问题：**agent 能不能在没人盯着的情况下，连续改同一个代码库好几天而不把它改烂？**

以前没有可信答案，因为几乎所有编码基准（SWE-bench 系）都是**一次性任务**：给定完整问题，给出补丁，判对错。而真实工程是"需求一段一段来、代码在自己的旧代码上长"。SlopCodeBench 正是针对这个缺口设计的。

## 二、核心事实（分层）

### A. 基准本身（来自论文，可信度最高）

- 规模：**36 个迭代式软件开发问题、共 196 个 checkpoint**，Python 语言。
- 设计原则：题目"**规定架构决策，但把内部结构留给 agent 自己定**"——这样后续 checkpoint 的表现就直接暴露早期设计选择的后果。
- 评测了 **15 个编码 agent**（开源 + 闭源）。
- 头条结论：**没有任何 agent 端到端完整解出任何一道题**；表现最好的 agent 的 checkpoint 通过率是 **14.8%**。
- 退化是系统性的：**77% 的轨迹出现结构侵蚀（structural erosion）上升，75.5% 出现冗长度（verbosity）上升**。
- 与人类对照：agent 产出的代码，相比 **473 个开源人类仓库**基线，**冗长度高 2.3 倍、结构侵蚀高 2.0 倍**。
- 一个重要且容易被忽略的发现：**给质量指引（quality guidance）能把「初始退化」压低最多三分之一，但不改变退化的速率**——也就是说，prompt 层面的"请写干净代码"能让你起点更高，**却救不了斜率**。

### B. HumanLayer 的 Opus 5 复测（子集，样本小，但时效性最强）

作者挑了 3 道题、共 **17 个 checkpoint** 的子集，跑了 Opus 5 / Opus 4.8 / Sonnet 5，**现场直播观察约 6 小时**：

- `circuit_eval`（易，8 checkpoint）、`database_migration`（中，5 checkpoint）、`dynamic_config_service_api`（难，4 checkpoint）
- 方法：每个 checkpoint **全新上下文窗口**、相同 prompt；"严格通过"= 新代码全部测试通过 **且** 继承的历史回归测试全部通过。

**严格通过率（17 个 checkpoint）**

| 模型 | 严格通过 | 通过率 |
|---|---|---|
| **Claude Opus 5** | 4 / 17 | **24%** |
| Claude Opus 4.8 | 1 / 17 | 6% |
| Claude Sonnet 5 | 1 / 17 | 6% |
| *(论文中 GPT-5.4)* | — | 11% |
| *(论文中 Opus 4.6)* | — | 17% |

**代码形态指标（最有信息量的一段）**

| 指标 | Opus 5 | Opus 4.8 | Sonnet 5 |
|---|---|---|---|
| 写出的源码行数 | **29,065** | ~9,000 | ~9,000 |
| 其中测试占比 | **51%** | 11% | — |
| 仅被调用一次的函数占比 | **14.9%** | 49.1% | 71.5% |
| 重复率变化 | 2.41% → 2.64%（几乎持平） | 4.6% → **16.8%** | — |
| slop 规则命中行占比 | 93% | 98% | 89% |
| 终态遗留缺陷（三题合计） | 2 / 3 / 4 | 10 / 5 / 7 | 3 / 2 / 4 |

- 圈复杂度：**所有模型都随 checkpoint 推进而上升**；Opus 4.8 在 8 个 checkpoint 内上升 70%。
- 成本侧作者原话："**every dollar bought correctness. nobody bought enough of it.**"（每一块钱都换来了正确性，但没人买够。）Sonnet 起初每 checkpoint 更贵，随着工作重心转向维护反而变成最便宜的。

### C. 官方叙事的对照（Anthropic，2026-07-24）

Anthropic 发布 Opus 5 时给出的是另一组数字，全部是**一次性/短时程**口径：

- Frontier-Bench v0.1：**超越所有其他模型，且以更低的单任务成本把 Opus 4.8 的成绩翻了一倍多**
- ARC-AGI 3：**分数是次优模型的三倍**
- CursorBench 3.2：最大 effort 下"**与 Fable 5 峰值分差 0.5% 以内，但单任务成本只有一半**"
- Zapier AutomationBench：通过率约为次优模型 **1.5 倍**（同等单任务成本）
- OSWorld 2.0：**超过 Fable 5 最好成绩，成本仅略高于三分之一**
- 定价：**$5 / 百万输入 token，$25 / 百万输出 token**（与 Opus 4.8 持平）；另有约 2.5 倍速的快档，价格翻倍

值得注意：**Anthropic 官方页面并没有宣称 Opus 5 能自主运行多长时间**，只强调"agency 与 thoroughness 的提升"。也就是说，"能长跑"这个印象很大程度上是生态自己脑补的——而这正是 SlopCodeBench 要校正的地方。

## 三、机制拆解：为什么"更强的模型"依然会把代码库改烂

把上面两张表放在一起看，Opus 5 的进步是**真实但有代价**的，而且代价的形状变了：

**1. 它用"写更多"换"错更少"。** 29,065 行 vs ~9,000 行，是 3 倍多的产出。但拆开看，**51% 是测试代码**（Opus 4.8 只有 11%）。这说明 Opus 5 学会了一种非常"资深工程师"的策略：**用测试把自己的修改锁住**，从而在后续 checkpoint 的回归测试上活下来。这直接解释了它为何严格通过率高 4 倍——严格通过的定义里，一半分数来自"别把以前的功能弄坏"。

**2. 它的抽象是真抽象，不是复制粘贴。** 单次调用函数占比 14.9%，远低于 Opus 4.8 的 49.1% 和 Sonnet 5 的 71.5%。后两者那个数字意味着：**它们创造的函数里有一半到七成只被用了一次**——典型的"为了写而写"的伪模块化。Opus 5 的重复率从 2.41% 到 2.64% 几乎不动，而 Opus 4.8 从 4.6% 飙到 16.8%，这是"复制粘贴式演进"的经典特征。

**3. 但复杂度对谁都在涨。** 这是论文层面的结论（77% 的轨迹结构侵蚀上升），也是这次复测的观察。换句话说，**"agent 写的代码会随时间变烂"不是某个模型的缺陷，而是当前范式的属性**。Opus 5 只是让斜率更缓，没有让斜率变负——**没有任何模型表现出自发重构、主动降复杂度的行为**。

**4. 所以真正的瓶颈是"没有回头看的机制"。** 每个 checkpoint 全新上下文，模型面对的是"一个陌生人写的、恰好风格像我的代码库"。它能读懂、能扩展，但没有任何动力去问"这个结构还撑得住下一轮吗"。HN 上 delbertty 一句话点破：**"Slop accumulates when the agent can touch anything."**（当 agent 什么都能碰时，垃圾就会堆积。）——这暗示**约束边界（harness 设计）可能比换模型更有效**。

## 四、关键原话

> "today's models can't be relied on to run lights-off without steering."
> ——报告作者的核心结论：**今天的模型无法在没有人为引导的情况下"关灯运行"。**

> 作者给出的可托管门槛：他愿意接受自主部署的标准是模型在"**一个（充分留出的）像 SlopCodeBench 这样的基准上拿到 80%+**"。
> 按这个尺子，**24% 距离"可无人值守"还有 3 倍以上的距离。**

> "every dollar bought correctness. nobody bought enough of it."

> 作者对三个模型的总评：**"none of them did a very good job."**

## 五、正反观点

### 支持方（这个基准抓住了真问题）

- **robbomacrae**：SCB "definitely an underrated benchmark"——因为它要求 agent 跨多个任务维持代码质量，而不只是解孤立问题。
- **Vgoose**：时机正好。"模型已经足够好到能解决大部分**时间点上的**问题"，所以**纵向的代码质量**才是决定能否上生产的变量。
- **WilcoKruijer**：**"Reducing complexity in generated code should be the number 1 priority"**，并希望各实验室把这个指标纳入 RL 训练目标。
- **piazz**：把"周期性重构轮次"与功能实现轮次交替插入，应该能显著改善结果。
- **delbertty**：问题出在 harness 而非模型——限制 agent 的可触碰范围。

### 质疑方（别过度解读这个数字）

- **mellosouls**（最重要的一条批评）：**基准缺少人类基线**。"很多人会以为 Opus 5 只有人类程序员四分之一的水平"——而实际上人类在同样的"分批下发需求 + 严格回归"设定下也未必及格。**没有人类对照，24% 这个数字无法被正确定位。**
- **样本量**：这次复测只有 **3 道题 / 17 个 checkpoint**。24% = 4/17，**差一个 checkpoint 就是 6 个百分点的波动**。它是信号，不是定论。
- **willsmith72 vs well_ackshually 的争论**：把 17% → 24% 说成"没高多少"是不公平的，这是 **41% 的相对提升**；但反方回应，**76% 的失败率无论相对提升多少都不可接受**。两边都对，取决于你是在评估"进步速度"还是"能否托管"。
- **4by4by4**：某些测试（如 `database_migration` 的 `default_value`）失败可能源于**需求解读歧义**，与模型能力无关。
- **patwolf**：过于苛刻的 review prompt 可能制造反馈环，**是 prompt 逼出了不必要的复杂度**，而非模型本身的倾向。
- **Gareth321**：版本间的表现差异可能反映的是**量化（quantization）**而非模型能力变化。
- **adamtaylor_13**：如果缺陷数低，代码丑一点真的重要吗？"slop 是否超出了我们的审美偏好"值得追问。
- **dan_gee**：对模型间微小差异的反复 benchmark 是 **"navel-gazing"（自我陶醉）**。

## 六、深度解读：对行业 + 对「做多 agent 系统的我们」的具体含义

### 对行业

**1. 基准竞赛的重心正在从"能力"转向"耐久"。** SWE-bench 类基准已经接近饱和，能区分模型的信息量在下降。SlopCodeBench 代表的这一类（长时程、迭代、含回归约束）会在未来半年成为新的兵家必争之地——**因为它才是"agent 产品能否卖出去"的直接代理指标**。谁先在这类基准上拿到 50%+，谁就掌握了"自主编码"叙事的定价权。

**2. 官方基准与生产现实之间出现了可测量的裂口。** Anthropic 报的是 Frontier-Bench 翻倍、ARC-AGI 3 三倍；独立实测报的是 24%。**两者都不假**，但它们衡量的不是一件事。这个裂口从今天起是公开的、可引用的——**采购方（尤其是企业 IT）会开始要求长时程口径的证据**。

**3. "质量引导救不了斜率"是对 prompt 工程的一次降级。** 论文那条结论（quality guidance 只降低初始退化最多 1/3，不改变退化速率）意味着：**靠往 system prompt 里塞"请写整洁代码"来解决 agent 代码腐化，是数学上无效的路径**。要改变斜率必须动结构——训练目标、harness 约束、或流程编排。

### 对我们（做多 agent 系统）

**这是本周最该直接改动作的一条。** 具体：

1. **把"无人值守跑多久"从信念改成一个数字，并且往下调。** 我们的默认假设应该是：**任何让 agent 连续演进同一代码库超过 ~4-5 个 checkpoint 的设计，都必须有人类检查点**。24% 严格通过率的含义是——每 4 个自主迭代里有 3 个会留下回归。别把 Opus 5 的发布当成放宽这个假设的理由。

2. **立刻把「测试代码占比」加进 agent 产出的监控指标。** Opus 5 的 51% 测试占比是它严格通过率领先的**机制性原因**，不是副作用。这给了我们一个可复制的做法：**在 agent 的 workflow 里显式要求"先补回归测试再改功能"**，把 Opus 5 自发学会的策略变成我们所有模型（包括更便宜的 Sonnet 档）的强制流程。这是把 6% 拉向 24% 的最低成本杠杆。

3. **加两个 CI 门禁：单次调用函数占比、重复率斜率。** 这两个指标在这份实测里最能区分"真抽象"和"伪模块化"：**单次调用函数占比 >45% 基本等于伪模块化**（Opus 4.8 49.1% / Sonnet 5 71.5%），**重复率在连续迭代中翻倍（4.6%→16.8%）就是复制粘贴式演进的报警**。这两个数都能用现成静态分析工具算，接进 CI 的成本极低，却是目前唯一有实测支撑的"agent 代码腐化"早期信号。

4. **把"周期性重构轮次"写进编排，不要指望模型自发做。** 论文和实测都显示：**没有模型会自己回头降复杂度**。所以在我们的 multi-agent 编排里，应该显式插入"每 N 个功能 checkpoint 强制一轮 refactor-only agent"——这个 agent 不允许改功能，只允许降复杂度并保证回归全绿。这是 piazz 的建议，也是唯一可能改变斜率（而非仅仅抬高起点）的干预。

5. **缩小 agent 的可写范围。** delbertty 那句"Slop accumulates when the agent can touch anything"值得当成设计原则：**给每个子 agent 明确的文件/目录白名单**，比换更贵的模型更可能改善长时程质量。这条也和成本对齐——限制范围同时缩小了上下文。

6. **成本模型要重算。** Opus 5 写了 3 倍的代码。在 $25/百万输出 token 的价位上，"更强的模型"在长时程任务里**未必更省**——它把成本从"重试"转移到了"体量"。我们的 agent 成本预估如果还是按"任务数 × 平均 token"，在长时程场景会系统性低估。**建议按 checkpoint 数 × 累计代码增量重新建模。**

7. **谨慎对待这份数据的强度。** 3 题 17 checkpoint，且无人类基线。**上面的动作 1-6 都是"低成本、即使结论被推翻也不亏"的类型**，可以直接做；但不要据此做"推迟某个自主 agent 产品线"这种不可逆决策——等更大样本的复现。

## 七、接下来盯什么（信号）

- **是否有更大样本的复现**：有人跑完整 196 个 checkpoint 的 Opus 5 结果（尤其含人类基线）——这是把 24% 从"信号"变成"定论"的关键。
- **实验室是否把长时程质量纳入 RL 目标**：如果 Anthropic / OpenAI 在下一次发布中主动引用 SlopCodeBench 类指标，说明 WilcoKruijer 的呼吁被采纳，行业优化方向真的转弯了。
- **SlopCodeBench 的污染风险**：它已经上了 HN 头版，题目公开。**下一代模型的高分要警惕训练集污染**——注意作者强调的是 "well-held-out" 基准。
- **GPT-5.6 / Gemini 3.6 系在同一基准上的成绩**：目前公开的只有论文里的 GPT-5.4（11%）。跨家横评出来之前，"Opus 5 在长时程编码上领先"只能算 Claude 家族内部的结论。
- **harness 侧的对照实验**：有没有人验证"限制 agent 可触碰范围"或"插入 refactor 轮次"能把 24% 推高——这直接决定我们该把工程预算投在换模型还是改编排。
- 呼应信号：**HN 同日第 3 名那条「$500 微调 9B 开源模型击败前沿模型」**。如果前沿模型在长时程上也只有 24%，那"用便宜模型 + 更好的编排"的性价比论证会进一步增强。
