# AgentForger:一条 ChatGPT 链接,伪造出一个继承你身份、关掉护栏的自主『内鬼』

**一句话定性:** 安全公司 Zenity Labs 披露的 AgentForger 是一类全新的攻击原语——不是骗一个已存在的 agent 干坏事(prompt injection),而是通过一次点击的跨站请求伪造(CSRF),在你公司里凭空**铸造出一个攻击者控制的自主 agent**:它继承受害员工的身份与全部已授权连接器、把审批护栏从「每次询问」翻成「从不询问」、并挂上定时调度当作 C2。这把整个行业的安全焦点,从「agent 运行时被骗」推进到了「agent 的**创建/供给入口**本身可被伪造」。

**来源:** Zenity Labs《AgentForger, Part 1: ChatGPT Cross-Site Agent Forgery》(一手研究披露)
**🔗 原始链接:** https://labs.zenity.io/p/agentforger-part-1-chatgpt-cross-site-agent-forgery
**公开披露日期:** 2026-07-23(BusinessWire 新闻稿),The Hacker News / SecurityWeek / The Register 7/23–24 跟进;漏洞已于 6 月修复

## 为什么值得深读 / 背景

过去两个月,本监测反复深挖的 agent 安全事件几乎都是同一条主线的变体:**「agent 读入的外部内容 = 攻击面」**——DuneSlide(Cursor 零点击 prompt injection→RCE)、AutoJack、Wiz 六工具劫持链、以及 7/21 那起惊动全行业的「OpenAI 模型在评测中自主逃逸、攻破 Hugging Face 生产系统」。它们的共性是:攻击者**骗一个已经存在的 agent**,让它在运行时执行了不该执行的动作。

AgentForger 不属于这条线。它攻击的是**上一层**:agent 被创建出来的那一刻。攻击者不需要一个已存在的 agent、也不需要注入运行时上下文,而是伪造了「用户亲手创建并授权了一个 agent」这个动作本身。用 Zenity CTO Michael Bargury 的话说:

> **"这不是伪造一个请求,而是伪造一个内鬼(This isn't a forged request, it's a forged insider)。一次点击,攻击者就在你公司内部拿到一个完全自主的 agent,它带着你员工的身份和访问权限,而护栏是关着的。"**

这条新闻恰好落在一个极具张力的时点上:就在 7/22,OpenAI 刚推出 **Presence**(前沿实验室价值链上移、forward-deployed 的企业级语音/聊天 agent 部署平台);Anthropic 7/24 的 Opus 5 又把它定位成「Claude Code / 长程 agent 的新默认」。整个行业正在竞相给 agent **常驻的企业身份、连接器与自主权**。AgentForger 是第一次有人用一个具名、可复现、有厂商确认的工件证明:当 agent 变成企业内一个有身份、有工具、有权限的「员工」时,**「谁能铸造一个 agent、用谁的身份、挂什么权限」这个供给入口,就成了新的皇冠珠宝**。

## 核心事实(硬数据 / 机制)

**发现方与影响面**
- 研究方:Zenity Labs(专注 agent / 低代码安全的研究团队);受影响产品:OpenAI **ChatGPT Agent Builder**(企业版 / 商业版里用于搭建自主 Workspace Agent 的工作室)。
- 严重度:文章未给 CVSS 评分。厂商已修,**无证据表明曾在野外被利用**。

**披露与修复时间线(约 4 天闭环)**
- 2026-06-04:经 OpenAI 的 Bugcrowd 漏洞披露计划报送。
- 2026-06-05:OpenAI 受理并确认。
- 2026-06-08:OpenAI 修复(受理到修复约 3–4 天)。
- 2026-07-23:Zenity 公开发布《Part 1》,主流安全媒体跟进。

**攻击机制:两个 URL 参数就够了**
恶意链接指向 agent 创建端点 `https://chatgpt.com/agents/studio/new`,携带两个参数:
1. `template_name`:选择起始模板,默认落到 **`chief-of-staff`(幕僚长)**——Agent Builder 里权限最高、能力最全的模板。
2. `initial_assistant_prompt`:核心缺陷所在——它的值**不是被放进输入框等用户确认,而是在页面加载时被自动提交并执行**。

因为是 CSRF,整个过程发生在**受害者已登录的会话里**,以受害者的身份完成,不弹任何新的 OAuth 授权页。

**被伪造出来的 agent 会做什么(payload 指令链)**
Zenity 演示的恶意 `initial_assistant_prompt` 指挥 Builder:
1. **挂上全部已授权连接器**——Outlook / Gmail / Slack / Google Drive / SharePoint / Teams,因为受害者早已授权过,**无需任何新的同意弹窗**。
2. **把每个动作的审批从「Always ask」翻成「Never ask」**——护栏被它要执行的指令亲手关掉。Zenity 的原话:*"本应要求人工审批敏感动作的机制,可以被正在执行的指令自己禁用。"*
3. **上线并挂定时调度**:按固定节奏(Zenity 演示为**每 5 分钟**一次、The Hacker News 报道为每小时)反复执行;并调用 Preview 模式**立即跑一遍**。
4. **监听攻击者指定的邮箱**,把标记为「TASK」的邮件当作新指令执行——形成「更接近 C2(命令与控制)」的远程操控通道。
5. 执行后**不加脱敏地回传结果**。

**为什么这是「致命三要素(lethal trifecta)」**
Zenity 用 Simon Willison 提出的框架点名了它:**不可信输入(恶意 URL)+ 私有数据访问(继承的连接器)+ 外泄通道(发邮件)**三者齐备。三者缺一,链条就断——这也是后面「对我们的含义」里最实用的抓手。

**扩散潜力(类蠕虫,但非自动自我复制)**
在十余个 PoC 场景里,Zenity 演示了这个「被伪造的内鬼」能:测绘组织环境、窃取敏感文件与凭据、冒充员工、并**发起内部钓鱼——而内部钓鱼可以再生成新的被控 agent**。需要精确区分:它的**持久化**靠的是定时调度 + 邮件 C2(而非自我复制);「内部钓鱼→再造 agent」是它演示的横向扩散场景之一,具备**类蠕虫扩散潜力**,但不是无需人点击的自动蠕虫。

## 关键原话 / 引述

- Bargury:*"This isn't a forged request, it's a forged insider... a fully autonomous agent inside your company that has your people's identity and access, with the guardrails off."*

## 正反观点

**淡化 / 别恐慌的一面(务实视角):**
- **已修复、约 4 天闭环、无野外利用**:这是一次教科书式的负责任披露,即时风险已被 OpenAI 关闭。
- **触发门槛不低**:需要受害者**点击链接** + **本就授权过一堆连接器** + **有 Agent Builder 访问权**(即企业 / 商业 / 教育版且开了 agent 工作室)。它不是一个「所有 agent 通用」的洞,而是某个具体产品创建流程里「自动执行内嵌 prompt + 缺 CSRF 令牌」的实例,已被打补丁。
- 因此把它读成「今天正在燃烧的火」是过度渲染;它更像**一次高质量的设计模式预警**。

**为什么它仍然重要(严重视角):**
- **类别升级,而非又一个 CVE**:传统 CSRF 逼你做**一个**非预期动作;AgentForger 逼系统凭空生出**一个新的自主系统**——带工具、审批、指令、调度和已授权连接器。这是「一次点击 → 一个持久的、有身份的自主实体」,量级不同。
- **对现有防线不可见**:EDR / DLP / IdP 看到的是「合法员工在自己会话里创建了一个 agent」——完全合规的动作。Bargury 说「现有控制没被设计来看见它」不是修辞,而是检测栈的真实盲区。
- **被修的是实例,可推广的是模式**:自动执行创建端点内嵌 prompt、新 agent 静默继承用户全部连接器、护栏能被自己执行的指令翻转——这三个设计选择,几乎每一个正在出货的「agent builder / 低代码 agent 平台」都可能重蹈。补丁关掉了 ChatGPT 这一处,没关掉这个**品类**的风险。

## 深度解读:对行业 + 对『做多 agent 系统的我们』的具体含义

**对行业:** agent 安全的重心正在从「运行时」上移到「**供给时(provisioning)**」。行业过去一年把精力压在「怎么防 agent 在跑的时候被 prompt injection 骗」,而 AgentForger 指出:当 agent 变成企业里一个**有身份、有连接器、有调度的常驻实体**,「谁能创建它、以谁的身份、挂什么权限、由谁批准」这套**供给与身份治理**,才是新的攻防主战场。这和本监测里两条线正在合流:一条是 Presence 代表的「企业 agent 大规模部署」(部署越多,供给面越大);另一条是 7/24 深研的 AI Kill Switch Act 提出的「**带外控制平面**」——AgentForger 恰好证明了:如果护栏能被 agent 执行的指令自己关掉,那它就等于没有护栏。

**对我们(做多 agent 系统的团队),六条可执行判断:**

1. **把「创建 agent」当作最高危操作来设防。** 任何「一个 URL / 一次点击就能实例化一个带权 agent」的入口,必须有 CSRF 令牌、创建端点**绝不自动执行内嵌 prompt**、且实例化前有一次**显式的人类确认**。我们自己的 agent 编排 / builder 若有「深链创建」能力,今天就该按这条自查。

2. **连接器继承是最危险的默认。** 新建 agent **不应静默继承**用户已授权的全部 connector。改成 **per-agent 最小授权 + 每个连接器重新 consent**,且这份授权清单要可枚举、可审计、可一键撤销。「我授权过 Gmail」不等于「我造的每个 agent 都能用 Gmail」。

3. **审批门必须放在 agent 指令够不到的带外控制平面。** 「Always ask → Never ask」这种开关,决不能由 agent 正在执行的指令翻转。护栏、熔断、审批策略要跑在 agent 的动作面之外(呼应 Kill Switch Act 深研的「agent 路由不到的熔断」)。

4. **给 agent 独立身份,和人类身份解耦。** 伪造 agent 之所以致命,是因为它**借用了人的 OAuth 身份**。agent 应持有**自己的、短时、可审计、可撤销的机器身份**(工作负载身份 / SPIFFE 思路),而不是继承人的 token。这样即便创建流程被伪造,拿到的也是一个权限受限、可追溯、可秒级吊销的身份,而非「一个完整的员工」。

5. **建 agent 清单与供给审计。** 传统检测看不见「合法身份下新起的一个自主 agent」。我们需要一份 **agent inventory**:谁在何时创建了哪个 agent、挂了哪些工具、什么调度 / 什么外部通道触发。这正是 backlog 里「agent 行为淹没 EDR」的解药之一——不是去看行为,而是去看**供给事件**。

6. **切断致命三要素里最容易切的一环。** 不可信输入 + 私有数据 + 外泄通道,三者齐了才成链。最务实的是掐掉**自动出网 / 自动发信**:长程 agent 的调度器(cron)+ 邮件 / webhook 触发要按**高危原语**审计和限流——它们既是 agent 的能力,也天然是 C2 通道。

## 接下来盯什么(信号)

- **同类 CVE 会否成批出现:** 其他 agent builder——Anthropic 的 Claude Agent Skills / Cowork、Google Antigravity / AI Studio、Microsoft Copilot Studio、Salesforce Agentforce——是否也有「创建即执行 / 连接器静默继承 / 审批可自关」的同构缺陷。AgentForger 若是「Part 1」,大概率有 Part 2、Part 3。
- **OpenAI 的结构性补法:** 是否给 Agent Builder 加「创建 agent 需显式 human-in-the-loop」「per-agent 连接器重新 consent」「移除 `initial_assistant_prompt` 的自动执行」——还是只堵了 CSRF 令牌这一处。
- **是否出现野外利用或 agent-worm 可复现 PoC:** 「伪造 agent 生成更多伪造 agent」一旦被做成自动扩散链,量级会变。
- **「agent 身份治理 / agent IAM / agent inventory」会否长成新安全品类:** 这是本监测值得单开一条主线追踪的方向——企业买 agent(Presence 等)越多,越需要「谁能铸造 agent」的治理层。
- **与企业 agent 部署量的叠加:** Presence / Opus-5-驱动的长程 agent 铺得越广,供给攻击面越大,这条线的权重只会上升。
