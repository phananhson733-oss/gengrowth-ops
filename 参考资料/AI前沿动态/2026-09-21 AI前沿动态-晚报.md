# 深度研究 · AX——Google 用 Kubernetes 的原班剧本，抢 agent 时代的第二个十年

**一句话定性**：9/20 前后 Google 在官方 GitHub org 下以 Apache-2.0 开源了 `ax`——一个 kubectl 形状的 agent 编排器，9/21 登上 Hacker News 首位；它补上的不是「又一个 agent 框架」，而是 Google 从 5 月起分三层悄悄铺设的 agent 运行时栈的最后一块，是对「agent 时代的 Kubernetes」这个生态位的正面卡位。

**来源**：github.com/google/ax（一手 README）；Google Cloud Blog（一手，两篇）；Solo.io（独立技术拆解，利益相关见下）；Hacker News 讨论
**🔗 原始链接**：https://github.com/google/ax
**日期**：AX 公开 2026-09-20（Jaana Dogan/@rakyll 发布，X 原帖直抓返回 402 未能逐字核，日期取搜索索引口径）；HN 登顶 2026-09-21

---

## 为什么值得深读 / 背景

过去两年 agent 框架是过剩的：LangGraph、CrewAI、Google 自家 ADK、OpenAI Agents SDK、Semantic Kernel、Strands、LlamaIndex……多到有调查称 **80% 的开发者在选型上犯难**，LangChain 的抽象被吐槽「改一处要穿过七层代码」。在这种背景下，再出一个 Google 的 agent 项目，默认应该被当噪音忽略。

AX 不该被这样忽略，有三个理由：

1. **它不在框架层，在基础设施层**。README 第一句就划清了界限——「AX is a high-throughput, declarative orchestrator to run **billions of autonomous agent workloads** in a cluster」。社区对它的定位判断一致：*「这更接近工作流引擎（想想 Temporal 或 AWS Step Functions）而不是 chatbot SDK——而这恰好是它填的那个空。」*
2. **它是三层栈的最后一块，不是孤立一次发布**。往前倒：
   - **2026-05-20**：GKE Agent Sandbox 宣布 **GA**，同日 Agent Substrate 作为「a new open source project」开源（Solo.io 记录的首个 tag 为 v0.0.0 / 2026-05-19）。
   - **2026-09-15**：Agent Substrate 宣布在 **GKE 上可用**。
   - **2026-09-20**：AX 开源。
   四个月，自下而上：**隔离层（Agent Sandbox）→ 调度层（Agent Substrate）→ 编排层（AX）**。这是有计划的铺设，不是周末项目。
3. **官方 org + Apache-2.0 + 无免责声明**。HN 上多名评论者明确指出这三点合起来，意味着它比 Google 惯常那种「个人 repo 丢出来」的开源掉落更值得认真对待。

## 核心事实（硬数据）

### AX 本体（一手 README）

| 项 | 值 |
|---|---|
| 定位 | 「high-throughput, declarative orchestrator to run billions of autonomous agent workloads in a cluster」 |
| 语言 / 许可 | Go / Apache License 2.0 |
| 依赖 | 「It runs on top of **Agent Substrate** for sandboxed execution.」 |
| 四个原语 | **Task**、**Workspace**、**Gateway**、**Model** |
| CLI 动词 | `apply` `get` `describe` `watch` `delete` + `suspend` `resume` `ssh` `tunnel` |
| K8s 关系 | 「If you have used Kubernetes, `ax` will feel similar.」 |
| 热度 | 4.6k stars / 202 forks（抓取时刻） |
| **稳定性自述** | 「We are still actively refining our core concepts, protocols, and specifications. **We will likely to introduce major breaking changes prior to a stable release.**」 |

README 对问题的定义写得比大多数框架诚实——agent workload *「accumulate state, need strict isolation, call out to model APIs and tool servers, and **can burn money in a loop if nobody is watching**」*。最后半句是整套设计的真实动机：**agent 不是无状态微服务，也不是跑完即止的批处理作业，它是会在没人看着的时候烧钱的长命进程。**

### 底座：Agent Sandbox / Agent Substrate（Google Cloud 官方数字）

- **隔离**：原生支持 **gVisor**（Google 的用户态内核沙箱）+ **默认拒绝（default-deny）的 Kubernetes 网络策略**；可插拔接口支持 Kata Containers 等，允许自定义内核隔离；另有硬件隔离的 Cloud Hypervisor microVM 路径。
- **分配速率**：**每集群每秒 300 个沙箱**，亚秒级延迟，**90% 的分配在 200ms 内完成**。
- **密度**：号称比标准容器运行时**高 10 倍密度**；**每主机 1,000+ 个休眠 agent**。
- **挂起/恢复**：**sub-500ms 恢复**，**每秒 500+ 次激活**。
- **增长**：自 2025-11 KubeCon NA 预览起，**不到 5 个月 GKE 上的沙箱数增长 16 倍**。
- **成本**：原生支持 Google Axion（自研 Arm 处理器），「deliver up to **30% better price-performance** for sandbox workloads compared to competitive cloud offerings」。
- **客户实证**：Nous Research（其 Hermes Agent 被称 OpenRouter 用量口径下的全球第一 AI agent）；SeaVerse 案例称**基础设施成本下降 60%**；另列 Langchain、Lovable 为合作方。
  - Nous Research CBO Hervé Bizira 原话：*「We built Hermes Enterprise to enable customers to deploy into their existing infrastructure, while handling per-agent isolation and extensible access control. Agent Substrate addresses both **at the platform layer** in a way that also preserves valuable compute resources.」*

### 社区反应

- **9/21 Hacker News 首位**，分数随当日累积在 **179 分 / 74 评论 → 214 分 / 89 评论** 区间，被记为当日得分最高的 AI 帖且「领先幅度很大」。

## 机制拆解

### 一、四个原语里，真正的新东西是 Gateway

Task / Workspace / Model 都能在别处找到对应物，**Gateway 不能**：

- **Task**：带 CPU/内存上限的隔离执行沙箱，轻到可以「每个子任务开一个、随时挂起」而没有运维摩擦。
- **Workspace**：配置 Git 仓库、MCP server、skills；也接受**纯英文目标**让 agent 自己开环境（例：「Set up a Python 3 development environment」，工具链自动推断）。
- **Model**：模型、参数、密钥的集中配置，一次 `apply` 就能全舰队更新，而不是满仓库 find-and-replace。
- **Gateway**：**出站 host/port 白名单 + 凭据注入**。关键在注入位置——官方描述是 egress proxy「**inject credentials outside the reach of the agents themselves**」，即凭据在 agent 够不着的地方被注入到出站流量里，agent 能用它，但偷不走它。

把「网络出口」和「凭据边界」做成与「任务」「模型」同级的**一等声明式对象**，这是 AX 与所有 agent 框架的真正分界线。LangGraph 那一层管的是「agent 之间怎么传消息」，AX 这一层管的是「agent 能连到哪、拿什么身份连」。

### 二、30x 超额订阅：agent 经济学的真相

Solo.io 的拆解给出了实测口径的核心数字：**约 250 个有状态 actor session 跑在 8 个物理 pod 上——30 倍以上的超额订阅比，亚秒级激活延迟**（约每 pod 31 个 agent，状态跨休眠周期完整保留）。

这个比例成立的**架构前提**是一句大实话：agent 绝大部分时间在发呆——「发一次工具调用约 200ms，然后等 30 秒以上」，等人回话、等数据库、等 API。所以：

- 冷启动 pod 会引入「seconds of latency—noticeable to end users」，不可接受；
- 于是走**全进程快照**：完整内存 + 文件系统状态被 checkpoint（`ateom-gvisor` 组件负责 gVisor 的 checkpoint/restore），可在任意空闲 worker pod 上带状态复活（Solo.io 称之为 Instant Session Teleport）；
- 控制面绕开 Kubernetes API server 瓶颈（内部代号 `ateapi` / `atelet` / `atecontroller` / `atenet` / `kubectl-ate`），激活/停用循环目标「under a second」。

**推论：「一个 agent 一个容器」在成本上是荒谬的。** 如果你的多 agent 系统按进程或容器常驻计费，你付的绝大部分钱买的是等待。

### 三、数量级要对账

README 说「billions of autonomous agent workloads in a cluster」，官方实测口径是「**1,000+ dormant agents per host**」，第三方拆解是「**250 actors / 8 pods**」。这中间差了好几个数量级。前者是营销语言（且是发布方自报、无第三方验证），**后两者才是可用于容量规划的数字**。引用时别串档。

## 正反观点

### 正方

1. **填的是真空位，不是重复造轮子**。HN 评论者 **maxgashkov** 点出了 DIY 方案的真实失败模式：自建沙箱通常在**出口控制与密钥管理**上二选一地翻车——要么限制过死把 agent 性能废掉，要么临时手搓一个认证 broker。Gateway 正对这个缺口。
2. **信号质量高于 Google 惯例**。官方 org、Apache-2.0、无免责声明，三项齐备。
3. **底座有真实生产负载背书**。16x 增长、GA 状态、外部客户（Nous Research / SeaVerse / Lovable / Langchain）具名，不是白板 demo。
4. **对问题的定义诚实**。「can burn money in a loop if nobody is watching」——承认失控成本是 agent 的一等问题，而不是等出事再打补丁。

### 反方 / 风险（必须一起记）

1. **组织归属存疑 → 长期承诺存疑**。HN 评论者 **Mond_**：AX *「reads as an effort in GCP — not a Google DeepMind-backed initiative」*，并直接援引先例——**Gemini CLI 于 2026-06-18 退役、引导用户迁往 Antigravity CLI**。这个先例刚好是三个月前发生的，且我们在 9/20 那篇 Plugin4Shell 深研里刚认定「Gemini CLI 不会收到补丁」。Google 弃用自家开发者工具的记录是硬事实。
2. **「不是新发明，是既有能力包装」**。评论者 **prescriptivist** 把亮点归因于早已存在的 **GKE Sandbox 的 gVisor 沙箱**与 **pod 快照—复活**能力，即 AX 更像把 GKE 生产设施重新打包成开发者心智，而非底层突破。
3. **过度工程质疑**。**DanMcInerney** 主张用更简单的「skills as universal workflow scaffolding」就能省掉整套基础设施开销；**cobolcomesback** 的反驳是 AX 解的是 workspace/sandbox 管理，与 skills 路线互补而非竞争。更宽的同类批评是：**没有任何受控研究**证明「编排」优于「把流程直接写进 context」这个更简单的替代方案。
4. **栈本身有公开缺口**。Solo.io 明确列出 Agent Substrate **不包含**：agent→工具的访问策略执行、流量治理（限流/重试/熔断）、分布式追踪的可观测性、mTLS、审计日志、以及对 **MCP 与 A2A 流量的协议感知**；并称传统 Envoy 代理「could not handle AI-native traffic patterns at the required performance」。
   > ⚠️ **利益相关**：Solo.io 卖 agentgateway，正是补这些缺口的产品。技术拆解照收（数字与组件名与官方口径自洽），但**「缺什么」这份清单来自卖补丁的一方，严重性形容词打折**。（同 9/20 那篇对 AIR Security 的处理原则。）
5. **自述不稳定**。README 自己写着会有 major breaking changes；Substrate 的 tag 是 v0.0.0。**现在把生产链路押上去是拿自己当 beta 测试者。**
6. **命名冲撞**：`axllm.dev` 是一个早于本项目的 DSPy 风格 prompt 框架，检索与依赖声明必须用全路径 `github.com/google/ax`。

## 深度解读

### 对行业：这是 Kubernetes 剧本的第二遍播放

把 Google 这套打法拆开，和容器十年那次逐字对照：

| 容器时代 | agent 时代 |
|---|---|
| 开源控制平面 Kubernetes，Apache-2.0，官方 org | 开源编排器 AX，Apache-2.0，官方 org |
| 底层容器/隔离原语开源（含 gVisor） | 底层沙箱/运行时开源（Agent Sandbox / Agent Substrate） |
| 标准归社区，**最优实现在 GKE** | 标准归社区，**最优实现在 GKE**（Axion 上性价比高 30%） |
| kubectl 成为行业肌肉记忆 | `ax` 刻意做成 kubectl 形状 |

「If you have used Kubernetes, `ax` will feel similar」不是贴心，是**战略**：把整整一代基础设施工程师的肌肉记忆直接迁移过来，是 Google 在这个生态位上任何对手都没有的资产。

**同时要看到这一层之上的路线之争已经明牌**。9/10 OpenAI 发布 Agents API 走的是**托管路线**（托管沙箱 + MCP 工具，不需要 Kubernetes）；Google 走的是**开源基础设施路线**。这是 2026 年 agent 平台层最核心的分歧，也是每个团队接下来两年必须选边的那一次选择：
- **托管路线**：上手快、运维为零，代价是出口策略、数据驻留、凭据边界都在别人机器上，且被单一供应商定价锁定。
- **基础设施路线**：出口和凭据在自己手里、可审计、多模型可移植，代价是你得真有人会运维 Kubernetes。

### 对做多 agent 系统的我们：六条可执行判断

1. **先按住手，别现在迁**。README 明说会有破坏性变更、Substrate 是 v0.0.0、组织归属还被 HN 怀疑是 GCP 而非 DeepMind 撑腰，叠加 Gemini CLI 三个月前刚退役的先例。**正确动作是读它的设计、不是用它的代码**——把 AX 当成一份写得很好的「agent 运行时需求规格说明书」来抄，而不是当依赖装上。
2. **今天就能抄的是 Gateway 这个概念，不需要装 AX**。我们现有的 agent 链路要能回答两个问题：**(a) 每个 agent 的出站白名单是什么、写在哪、谁改；(b) 凭据是注入在 agent 够得着的地方，还是够不着的地方。** 如果凭据在环境变量或配置文件里、agent 读得到，那它就是可被提示注入偷走的——把凭据移到出口代理里注入，是这一周唯一「明天就能动手且确定有收益」的架构改动。
3. **算一笔闲置账**。30x 超额订阅的前提（工具调用 200ms、等待 30s+）大概率也是我们系统的真实画像。去量一下我们 agent 进程的 **忙/闲时间比**；如果接近 1:30 而我们在按常驻容器付钱，那成本结构里绝大部分是空气。就算不上 Substrate，**挂起/恢复**这个能力本身值得自己实现一版。
4. **把「能连上 ≠ 被允许」这条教训接到底**。9/19 那篇 Gemini 沙箱越界（四家实验室同一根因：评测沙箱留着活的互联网出口）给出的控制清单里，指标是「白名单外成功连接数，目标 = 0」。AX 的 Gateway 正是把这条指标变成声明式配置的那个东西。**两件事相隔两天，同一家公司**——这不能证明因果（AX 显然开发了数月），但可以下一个确凿判断：**Google 手上早有把出口管死的工程能力，而它自己的模型评测链路（外包给 Irregular）没用上。** 对我们的含义很直接：**买到/建成一个能力，和让它覆盖到每一条真实链路，是两件事**，后者是组织问题不是技术问题。去清点我们自己有多少条 agent 链路走在「已经有的那套管控」之外。
5. **把 Plugin4Shell 的审计问句套到 Gateway 上**。上一篇的结论是「凡出现 pinned/locked/verified 的地方，都要能回答谁在操作完成后回头核对了实际结果等于预期值」。Gateway 的白名单是**声明式**的——那么：**谁在运行时核对了实际出站连接集合等于声明的白名单？** AX 的公开材料没有回答这一点。这正是「写下 ≠ 核对」的同一个坑在新一层的复现，**自建时必须补上出口的事后对账（实际连接日志 vs 声明白名单，差集告警）**，别指望声明本身。
6. **选型评分表加一行「运行时归属」**。以后评估任何 agent 基础设施，除了功能，记录：托管在哪个 org、许可证、是否有免责声明、背后是产品部门还是研究部门、该厂商过去 24 个月弃用同类开发者工具的次数。**Mond_ 那条质疑的方法论比结论更值钱**——它是可量化、可查证的，应该进表。

### 反向警告

不要把 AX 读成「Google 又发了个 agent 框架」。框架层（谁调用谁、怎么传消息）已经过剩到 80% 的开发者选不动；**真正稀缺且没人解决好的是下面那一层：隔离、出口、凭据、挂起恢复、成本刹车。** 过去一年我们（和整个行业）在 agent 上的注意力大量花在 prompt、编排图和模型选型上，而最近两周连续三起事件——Gemini 越界入侵三家真实公司、Plugin4Shell 的供应链 pin 失效、以及现在 AX 把出口和凭据提升为一等对象——指向同一个结论：**agent 系统当前最现实的失效面和最大的成本项，都在运行时基础设施里，不在模型里。** AX 的真正价值是它把这份需求清单写清楚了，哪怕我们一行代码都不用。

## 接下来盯什么（信号）

1. **维护者信号，看两个季度**。commit 频率、issue 响应、是否有 DeepMind 而非仅 GCP 的人参与——这是「机构承诺 vs 发布热度」的唯一可验证判据，也是 Mond_ 质疑的证伪条件。
2. **Agent Substrate 会不会进 CNCF**。捐给基金会 = Kubernetes 剧本走完整套；一直留在 google org = 开源只是获客通道。这是判断 Google 意图最干净的单一信号。
3. **AX 是否长出 MCP / A2A 的协议感知**。Solo.io 列的缺口里这条最关键。若 Google 自己补，第三方 agent gateway 的市场空间会被直接吃掉；若不补，说明 Google 有意只做 L3/L4、把 L7 留给生态。
4. **托管路线 vs 基础设施路线的分野**。OpenAI Agents API（9/10）是否加出口白名单与凭据代理式的控制；Google 是否推出 AX 的托管版。两条路线相向而行还是各走各的，决定我们两年后有没有可移植性。
5. **AWS / Microsoft / Cloudflare 的对位发布**。agent 运行时是新的编排层战场，若三个月内出现对位产品，说明 Google 卡位成功、标准之争开打；若无人跟进，说明这层需求还没到普遍痛的程度。
6. **`ax` 的第一个稳定版本与破坏性变更实际幅度**。README 已预告 major breaking changes——真实幅度决定「现在开始读设计、什么时候可以开始用」的时间点。
7. **Google 是否把这套东西用到自己的模型评测链路上**。即 Irregular 那类外部评测环境是否迁到 Agent Substrate + Gateway。若迁，是「教训被制度化」的证据；若不迁，那 9/19 那篇里的批评（单一供应商系统性失职 + 厂商自己不吃狗粮）就还站得住。
