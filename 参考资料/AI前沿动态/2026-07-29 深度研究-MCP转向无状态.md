# 🔌 深度研究 ｜ MCP 拆掉了 session：2026-07-28 规范是它诞生以来最大的一次自我否定

> **一句话定性**：这不是一次"加功能"的版本号更新，而是把 MCP 从「双向有状态协议」**削回「请求/响应无状态协议」**——删掉 session、删掉 initialize 握手、把 Roots/Sampling/Logging 三个核心能力打上弃用标签。代价是所有手写实现要返工、协议层唯一的文件范围强制点消失；收益是 MCP 第一次成为一个能扔进 serverless 和 round-robin 负载均衡后面的**普通 HTTP 工作负载**。对任何把 agent 往生产环境搬的团队，这是过去半年最该立刻读的一份文档。

**来源**：Model Context Protocol 官方博客《The 2026-07-28 Specification》（2026-07-28 发布，MCP 第五次规范发布）；同日 Anthropic 发布《MCP 2026-07-28 spec: stateless core, coming to Claude》。
🔗 官方规范公告：https://blog.modelcontextprotocol.io/posts/2026-07-28/
🔗 完整变更日志：https://modelcontextprotocol.io/specification/2026-07-28/changelog
🔗 Anthropic 侧公告：https://claude.com/blog/bringing-mcp-2026-07-28-to-claude

## 一、为什么这一篇值得单独深读

MCP 已经不是"某家实验室的一个开放协议"了。按官方口径，Tier 1 SDK 月下载量「接近五亿」，TypeScript 与 Python SDK 各自**累计突破 10 亿次下载**；Anthropic 侧的说法是 **400M+ 月下载、今年内 4 倍增长**，Claude 连接器目录里挂着 **950+ 个 MCP server**，社区侧的开源 server 数量按 HN 上网关运营者 punkpeye 的统计已达 **62,726 个**（其中约 30% 仍在活跃维护）。

也就是说：MCP 已经是 agent 接入外部世界的事实标准接口层。**在这个体量上做破坏性变更，本身就是一个战略事件**——它决定了未来一到两年 agent 基础设施的部署形态、计费形态和攻击面形态。

而这次改动的性质很特别：它不是往前加，是往回拆。Anthropic 技术成员、MCP 核心维护者 David Soria Parra 的定性是——这是**"自加入 authorization 以来，我们对规范做过的最实质性的改动"**。HN 上 progbits 的说法更刻薄但指向同一件事：MCP 当初是"a pile of anti-patterns"，现在在"一个一个地把错误撤回来"。

## 二、核心事实（按影响分层）

### A. 拆掉了什么（这是 breaking 的部分）

| 删除项 | 说明 | SEP |
|---|---|---|
| **协议级 session** | 移除 Streamable HTTP 上的 `Mcp-Session-Id` 头；`tools/list`/`resources/list`/`prompts/list` 不再随连接变化 | SEP-2567 |
| **initialize 握手** | 移除 `initialize`/`notifications/initialized`。每个请求自带协议版本与客户端能力，放在 `_meta` 里（`io.modelcontextprotocol/protocolVersion`、`clientCapabilities`、`clientInfo`） | SEP-2575 |
| **`ping` / `logging/setLevel` / `notifications/roots/list_changed`** | 直接移除。日志级别改为**每请求**通过 `_meta` 里的 `io.modelcontextprotocol/logLevel` 设置；未带该字段的请求，服务端 MUST NOT 发 `notifications/message` | SEP-2575 |
| **SSE 断点续传与消息重投** | 移除 `Last-Event-ID` 与 SSE event ID。**响应流一断，在途请求就丢了**，客户端 MUST 用新的 request ID 重发 | SEP-2575 |
| **HTTP GET 端点 + `resources/subscribe`** | 由单一长连 POST 流 `subscriptions/listen` 取代，客户端显式 opt-in 订阅类型 | SEP-2575 |

### B. 补了什么（新原语）

- **`server/discover`**：服务端 MUST 实现的 RPC，用于广播支持的协议版本、能力与身份。客户端 MAY 在任何请求前调用做版本选择，也可当作 STDIO 上的向后兼容探针。
- **Multi Round-Trip Requests (MRTR)**：**这是整套无状态设计的枢纽**。以前服务端要问客户端要东西（`roots/list`、`sampling/createMessage`、`elicitation/create`），得靠服务端发起请求，前提是有一条活着的双向流。现在反过来——服务端返回 `resultType: "input_required"` 的 `InputRequiredResult`，把要问的东西放进 `inputRequests`；客户端**重试原请求**，把答案放进 `inputResponses`。（SEP-2322）
- **所有结果必带 `resultType`**：`"complete"` 或 `"input_required"`。老服务端不带该字段的，客户端 MUST 当作 `"complete"`。
- **Header 路由**：Streamable HTTP POST 上强制带 `Mcp-Method`、`Mcp-Name` 头——**网关可以直接按 header 路由和计量，不用再解 JSON body**。（SEP-2243）
- **列表结果可缓存**：`tools/list`、`prompts/list`、`resources/list`、`resources/read`、`resources/templates/list` 的返回强制带 `ttlMs`（新鲜度提示）和 `cacheScope`（`public`/`private`，控制共享中间层能否缓存）。（SEP-2549）
- **tools/list 建议确定性排序**：官方明说目的是让客户端能缓存，并**提升 LLM 的 prompt cache 命中率**。
- **OpenTelemetry**：正式文档化 `_meta` 里 `traceparent`/`tracestate`/`baggage` 的 trace 上下文传播约定。（SEP-414）

### C. 弃用了什么（还能用，但至少 12 个月后消失）

- **Roots、Sampling、Logging 三件套弃用**（SEP-2577）。官方给的迁移路径：Roots → 改用工具参数 / resource URI / 服务端配置传目录；Sampling → **直接对接 LLM 提供商 API**；Logging → 写 `stderr`（stdio）或用 OpenTelemetry。
- **HTTP+SSE 传输**正式降级为 Deprecated（自 2025-03-26 起就是 deprecated 状态），迁 Streamable HTTP。
- **OAuth 2.0 动态客户端注册（DCR, RFC7591）弃用**，改推 **Client ID Metadata Documents (CIMD)**。
- Tasks 从核心协议里**搬出去**，变成官方扩展 `io.modelcontextprotocol/tasks`：阻塞式 `tasks/result` 被 `tasks/get` 轮询取代，新增 `tasks/update` 供客户端回传输入，删掉 `tasks/list`，且服务端可以**不经 per-request opt-in 就返回 task handle**。已经按 `2025-11-25` 实验版 Tasks 发过货的团队必须迁移。

### D. 授权硬化（企业侧的重点）

- 授权服务器 SHOULD 按 **RFC 9207** 在授权响应里带 `iss`；客户端 **MUST** 校验 `iss` 与记录的 issuer 一致后才能兑换 authorization code。（SEP-2468）
- 客户端凭证**绑定签发它的授权服务器**：MUST 按 issuer 标识存储、MUST NOT 跨授权服务器复用、授权服务器变更时 MUST 重新注册。（SEP-2352）
- DCR 时必须指定 `application_type`，避免 OIDC 重定向 URI 冲突。（SEP-837）

### E. 治理层（容易被忽略，但可能是最重要的一条）

规范首次采纳**功能生命周期与弃用政策**：定义 Active / Deprecated / Removed 三态，**最短 12 个月弃用窗口**，并维护一份「已弃用功能登记表」。同时把 SEP 流程正式化为 `seps/` 目录下的 markdown + PR 编号 + sponsor 责任制。

时间线也值得记：规范于 **2026 年 5 月 21 日锁定为 RC**，经 SDK 维护者与客户端实现方 **10 周**验证后，于 7 月 28 日正式发布。四个 Tier 1 SDK（TypeScript / Python / Go / C#）**当天即支持**，Rust SDK beta。Cloudflare 的 Agents SDK v0.20.0 在 7 月 27 日就发了 day-zero 支持。

## 三、机制拆解：为什么"无状态"是运维问题，不是美学问题

**旧世界的账**：一个远程 MCP server 要正确工作，你得同时准备三样东西——网关上的 **sticky routing**（同一 session 必须打到同一实例）、一个**共享 session store**（不然实例重启就断）、以及网关**解 JSON body 做深包检测**（因为方法名藏在 body 里，不解就没法路由/限流/计费）。这三样在本地 stdio 时代完全不存在，是 HTTP 传输引入的纯运维税。

**新世界**：任何实例可以处理任何请求，**普通 round-robin 负载均衡即可**，没有粘性路由、没有共享 session store；网关按 `Mcp-Method`/`Mcp-Name` 头做路由和计量；`tools/list` 可以被客户端和共享中间层缓存。这就是 Netlify 应用 AI 副总裁那句"**2026-07-28 规范里的无状态内核让 MCP 成为一等 HTTP 工作负载**"的实质含义。

**MRTR 是让这一切成立的那块砖**。只要还存在"服务端主动向客户端发起请求"，你就必须维持一条活的双向通道，也就必然要 session。MRTR 把这个方向翻转过来——服务端不再"推"，而是**返回一个未完成态**，让客户端带着答案重试。于是通道可以随时断，请求可以打到任何实例。

**但状态并没有消失，只是搬了家。** 变更日志里的原话是：需要跨调用状态的服务端，改用「**服务端铸造的 handle，作为普通工具参数传递**」。这是一次从"隐式协议状态"到"显式应用状态"的搬迁——好处是状态变得可见、可推理、可审计（InfoWorld 采访的 Kanerika AI 开发经理 Amit Jena 强调的就是这点）；坏处是**这些 handle 现在跑在模型的上下文里，也就跑在提示注入的射程内**。

**代价清单也要老实记**：官方自己承认新设计"**在 wire 上比以前更复杂了**"；SSE 断点续传被删意味着**流一断，在途请求整个作废**——对跑几分钟到几小时的长时程工具调用，这是实打实的退步，官方给的答案是"去用 Tasks 扩展轮询"。

> ——MCP 官方公告对本次改动的定性

## 五、正反观点

### 支持方

- **运维负担是真实的**：HN 上 btbuilder 称这是"Excellent improvement"，理由是"处理 session 所需的服务端复杂度，一直是基础设施和团队教育上的巨大负担"。网关运营者 punkpeye 说他**无法统计自己有多少 issue/bug 是因为要持久化服务端状态**造成的。
- **生态可达性提升**：punkpeye 认为这让"人们使用开源 MCP server 变得容易得多"——6 万多个开源 server 里只有约 30% 活跃维护，无状态降低了托管门槛。
- **状态显式化本身是好设计**：Amit Jena 认为把状态从协议 session 里的隐藏处挪到显式资源标识，让 AI 工作流在分布式环境中更可移植、更有韧性。
- **托管方已经用脚投票**：Cloudflare Agents SDK 提前一天发 day-zero 支持（可在 Workers 里直接跑无状态 MCP server 并兼容旧服务端），Netlify 公开背书，Microsoft 也发了 App Service 上的扩缩容解读。**基建层认为这解决了他们的真问题。**
- **迁移方向本来就该走**：多篇独立迁移指南的共同判断是——破坏性变更基本被限制在被弃用的能力（roots/sampling/logging）上，而规范推你去用的"显式 handle"模式，"**本来就是你早该在用的模式**"。

### 质疑方 / 风险

- **手写实现是硬伤**：官方自己承认自建实现要"a lot of uplift"。用官方 SDK 的团队升级成本低；**没骑 SDK 的，这是一次实打实的 breaking release**。
- **互操作性断层**：Stacklok 的企业就绪指南警告，2026-07-28 的服务端可能与旧客户端互不工作，反之亦然；弃用功能只保证 12 个月，"**兼容性要求双方共处同一协议世代，或有一方主动实现回退/翻译**"。
- **三个新攻击面**（Backslash Security）：① **Handle 劫持**——可移植的凭证串现在跑在对话里而不是服务端 session 里，拿到上下文的攻击者可跨用户/跨请求重放；恶意工具返回 `{"task_id": "t-ATTACKER-CONTROLLED"}`，模型会照单全收。② **文件范围真空**——Roots 是协议里唯一的结构性边界强制点，弃用后范围限制完全靠各家实现自觉；其举的例子是一个"生成使用报告"的例行任务顺手读了 340 个其他文件，包括 `.env`、数据库密码、Stripe 与 AWS 密钥。③ **MCP Apps 的 HTML 渲染**（SEP-1865）——服务端可以往 IDE 的沙箱 iframe 里投交互式 HTML，带来 XSS、点击劫持、UI 仿冒钓鱼与沙箱逃逸风险，"**这里的一次沙箱逃逸就是整个 IDE 沦陷**"。
- **Sampling 弃用改的是钱和信任边界，不是 API 名字**：Amit Jena 指出这改变了网络架构、认证模型和计费流向；更危险的是**你可能不知道自己依赖的第三方 MCP server 用没用 sampling**。
- **session 依赖藏得很深**：同上——"session 管理的复杂度往往散布在多个层：网关配置、部署脚本、监控看板"，排查要审基础设施而不只是代码。
- **老问题没解**：HN 上一个长期批评依然成立——工具的 metadata 在模型开始推理前就吃掉大量上下文窗口，**无状态传输对这个 context bloat 一点帮助也没有**。
- **协议价值本身仍被质疑**：HN 上 jongjong 主张多数场景 HTTP + curl 就够了；TZubiri 质疑参考实现过度复杂。这类声音在 6 万 server 的生态里已属少数派，但提醒我们 MCP 的"必要性"并非共识。
- **长跑退步**：SSE 断点续传被删，长时程调用的容错从传输层被推给了应用层（Tasks 扩展）。

## 六、深度解读：对行业，以及对「做多 agent 系统的我们」

### 对行业

**1）MCP 完成了从"开发者笔记本上的玩具"到"云原生工作负载"的身份转换。** 这次改动的每一条都指向同一个目标：让 MCP server 能像普通无状态 Web 服务一样部署、扩容、限流、计费。这直接**打开了一整层商业空间**——MCP 网关、多租户托管、按调用计量、边缘部署。Cloudflare 提前一天发支持、Netlify 公开背书、微软写扩缩容指南，说明基建厂商已经把这看成新的接入点之争。

**2）治理成熟度的信号，可能比技术改动更重要。** 功能生命周期政策 + 12 个月弃用窗口 + 弃用登记表 + PR 化的 SEP 流程 + "targeting 2026-07-28 的实现，未来升级不必重写传输和生命周期代码"的公开承诺——这套组合的意思是：**MCP 从"随时可能又改一遍"变成了一个可以押注的基础设施**。对我们这种要把 MCP 写进架构图的团队，这条比无状态本身更值钱。**押注风险下降了。**

**3）一个不该忽略的反向张力：状态往哪搬，是谁控制 agent loop 的商业问题。** MCP 在把状态**推出**协议、交还给应用；而 OpenAI 的 Responses API 在把状态**吸进**平台（服务端保留推理过程与会话历史，托管工具收进自家基建）。两条路的动机不同——MCP 的状态是"传输层意外混进来的、被生产环境逼着删掉"，OpenAI 的状态是**刻意的平台策略**。作为使用方，这两条路对我们的含义完全相反：**前者增加可移植性，后者增加锁定**。这是选型时该明确写进决策文档的一条轴。

### 对我们（可执行判断，按优先级）

**① 今天就做的分类审计：我们的 MCP server 是"骑 SDK"还是"手写"。**
骑官方 Tier 1 SDK（TS/Python/Go/C#）的，升级成本可控，四个 SDK 都已当天支持。**手写 HTTP 传输的，按 breaking release 排期**，别指望渐进。同时列出所有依赖 `Mcp-Session-Id`、initialize 握手、`ping`、`logging/setLevel` 的地方——注意这些依赖常常**不在代码里，而在网关配置、部署脚本和监控看板里**。

**② 清点 Sampling 依赖，把它当作"信任边界与计费流向变更"处理，不是当作 API 改名。**
凡是靠 server 反向调用客户端模型的路径，都要改成服务端直连 LLM 提供商 API。这意味着：**凭证放哪、谁付这笔 token 钱、出口网络怎么开**，三件事都得重新定。特别要查第三方 MCP server——我们可能在不知情的情况下依赖了它。

**③ Roots 弃用 = 文件范围白名单从"最佳实践"升级为"没人替你兜底"。**
这一条和我们昨天从 SlopCodeBench 那篇得到的结论**正面撞上了**：当时的行动项是"给子 agent 文件/目录白名单"，属于优化项；现在协议层唯一的结构性强制点被拿掉了，**它变成了必须项**。Backslash 那个"生成使用报告顺手读了 340 个文件、含 `.env` 和 AWS 密钥"的例子，就是我们不做这件事的默认结局。落到实处：在我们自己的 harness 里做路径白名单强制，不要相信任何 server 会自我约束。

**④ 服务端铸造的 handle，必须服务端校验、绑定调用方身份——绝不信模型回传的 ID。**
状态从 session 搬到工具参数之后，handle 就活在模型上下文里，也就活在提示注入射程内。工程红线：handle 必须与调用方身份绑定、服务端做归属校验、设短 TTL、拒绝任何格式合法但归属不符的 ID。**默认假设「模型传回来的每一个 handle 都可能是被投毒的」。**

**⑤ 零成本先收的收益：确定性排序的 `tools/list` + `ttlMs`/`cacheScope`。**
官方明确说排序确定性是为了提升 **LLM prompt cache 命中率**。我们的 agent 每轮都要塞工具清单，这是纯白拿的成本下降。要求：自家 server 的 `tools/list` 返回排序稳定、设合理 `ttlMs`；含用户私有数据的一律 `cacheScope: "private"`（**这条搞错就是跨租户串数据**）。

**⑥ 长跑工具调用不能再依赖长连接不断。**
SSE 断点续传被删，流断即请求作废。所有跑超过几十秒的工具，迁到 Tasks 扩展的 `tasks/get` 轮询模型。注意 Tasks 本身也被重构了——按 `2025-11-25` 实验版发过货的地方要重写生命周期，且服务端现在可以**不经 opt-in 就返回 task handle**，我们的客户端必须能处理这种"突然收到一个 task"的情况。

**⑦ 版本迁移策略：网关做双世代翻译，别两端同时切。**
Stacklok 的警告很实在——新服务端配旧客户端会互不工作。可行路径是在网关层做协议世代翻译，服务端先切、客户端跟上，用 `server/discover` 做版本探测。**12 个月弃用窗口给了我们时间，但不给我们"不做兼容层"的许可。**

**⑧ MCP Apps 默认关。**
让第三方服务端往我们 IDE 的 iframe 里投 HTML，收益不明确，风险是"沙箱逃逸 = IDE 全盘沦陷"。在有明确需求和白名单机制之前，企业环境里默认禁用。

## 七、接下来盯什么（信号）

1. **Claude 各产品线的落地日期**——Anthropic 公告只写了"support is being rolled out across Claude products soon"，**没有给 Claude Desktop / API / Claude Code 的任何具体日期**。这是我们排期的关键依赖，盯 claude.com/blog 与 docs 的 release notes。
2. **OpenAI / Codex、Cursor、VS Code 何时跟进 2026-07-28**。OpenAI 是 Agentic AI Foundation 联合创始方、MCP 指导委员会成员，它的跟进速度决定这次升级是"全生态换代"还是"Anthropic 阵营先行"。
3. **Java SDK 时间表、Rust SDK 何时出 beta**（HN 上 cidd 已在追问 Java）。企业侧大量集成卡在 Java。
4. **6 万+ 开源 server 的实际迁移率**。活跃维护率只有约 30%，意味着**大量 server 会永久停在旧协议上**——12 个月后的"生态断层"规模，现在就可以开始观察。
5. **Tasks 扩展会不会成为长跑 agent 的事实原语**。它现在是官方扩展而非核心，采用率决定了长时程 agent 的标准做法。
6. **CIMD 取代 DCR 的推进速度**，以及授权服务器侧（各 IdP）的支持进度。
7. **第一起基于 handle 劫持或 MCP Apps 的公开事件**。Backslash 已经把三个面画出来了，按 MCP 的部署体量，这是"何时"而不是"是否"的问题。
