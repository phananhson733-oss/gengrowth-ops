# 深度研究 · 把「开店」写成参考架构——Anthropic Commerce Agents 蓝图与 agentic commerce 的第三条路线

**一句话定性**：Anthropic 在假日购物季前夜（9/2）开源了一套生产级 commerce agent 参考架构——面向消费者的购物 agent + 面向商家后台的运营 agent，Apache 2.0、四个垂直行业可跑示例、八层安全模式、评测 harness、外加一个 Claude Code 插件。它不做协议（OpenAI ACP 路线）、不做托管结账（Instant Checkout 路线，OpenAI 自己已在 3 月弃用）、不做支付网络联盟（Google AP2 路线），而是把「怎么把 agent 建对」这件事本身产品化、开源化，当作分发武器。

- **来源**：Anthropic 官方博客《Building Commerce Agents with Claude》 🔗 https://claude.com/blog/claude-for-commerce-agents （2026-09-02）
- **代码**：🔗 https://github.com/anthropics/commerce-agents （Apache 2.0；发布约一天 1.2k stars / 185 forks）
- **交叉信源**：BigGo Finance 9/2（Angela Jiang 引语）、CommerceClarity（catalog 约束技术分析）、Digital Commerce 360（三巨头 agentic commerce 路线对照）

## 为什么值得深读 / 背景

agentic commerce 是过去一年半竞争最密集的 agent 落地战场之一。从 2025 年 4 月到 2026 年 1 月，行业先后出现六个协议/栈：OpenAI+Stripe 的 ACP、Google 的 UCP 与 AP2（联合支付网络）、Anthropic 的 MCP、Google 的 A2A、Visa 的 Trusted Agent Protocol——外加 Mastercard Agent Pay。但落地并不顺利：**OpenAI 的 Instant Checkout（agent 直接替用户结账）已于 2026 年 3 月弃用**，退回「发现 + 商家跳转」模式——agent 推荐，用户仍在商家站点完成购买。

Anthropic 此前在这条战线上显得「慢」：今年 4 月它公布的 Project Deal 只是 69 名员工在内部模拟市场里让 agent 代为谈判的小实验。而 9/2 这一发，是它第一次拿出完整的生产级答案——且打法与 8 月底我们深研过的 MHS（给物理世界装 USB 口）完全同构：**不抢协议、不做闸门，发布参考标准/参考实现，让生态在自己的架构假设上生长。**

时点也很直白：假日购物季（11-12 月）前两个月，正是零售商决定「今年上不上 AI 导购」的窗口。

## 核心事实

**发布物是什么**
- 一套开源参考蓝图（Apache 2.0），包含两个 agent：
  - **Shopping agent**（嵌入商家 App 面向消费者）：catalog 检索、多商品规划、比较、购物车构建、订单/政策问答、会话内渲染商品 UI（不是纯文本）、客户记忆。
  - **Merchant agent**（商家员工用的后台）：销售归因分析、库存/订单告警、定价与促销建议、营销 campaign 起草——**所有写操作一律 staged，须人工批准后才生效**。
- 三条运行时路径同构可选：Messages API 参考循环 / Claude Agent SDK / Managed Agents（走 MCP server）。同一套 prompt、skills、tool contracts 三处复用。
- 四个可直接跑的垂直示例，各带行业特化：零售（内置组件）、旅行（date-bound 库存、行程呈现）、电信（server-authored 费用披露、监管合规）、票务娱乐（限时锁座、waitlist、真实容量）。
- **Claude Code 插件 `commerce-builder`**：四个命令——`/scaffold-commerce-agent`（从描述生成项目）、`/add-commerce-flow`、`/author-commerce-evals`（生成评测 harness）、`/review-commerce-agent`。
- 部署跨云：Claude API / Amazon Bedrock / Microsoft Foundry / Google Vertex AI。

**数据与伙伴**
- Angela Jiang（Head of Product, Claude Platform）：「我们看到令人鼓舞的结果——某合作方购物车金额提升约 30–35%，客户完成购买的可能性提高约 60%。」（单一未具名伙伴自报口径）
- 伙伴名单横跨商务栈：Shopify、Priceline（其 agent「Penny」）、Accenture、Mastercard、Visa、Intuit、Klaviyo、Wix、Zomato、Fetch、Square。
- Accenture 调研：85% 消费者愿意与 AI agent 协作购物；Adobe Analytics 口径 AI 引流的零售转化显著高于其他渠道（各家报道给出 +42%～+60% 不等）。
- 值得注意：仓库明确标注 **"Not maintained; does not accept contributions"**——这是一份快照式发布，不是持续维护的框架。

## 机制拆解：八层安全模式才是真正的主角

蓝图最有含金量的部分不是购物流程，而是 `docs/safety.md` 里那张安全模式表——几乎每一层都对应一类已公开发生过的 agent 事故：

| 安全层 | 防什么 | 对应的真实事故类别 |
|---|---|---|
| Fencing（围栏） | 限制工具可达域 | agent 越权访问外部系统 |
| Provenance gates | 校验调用者身份、拦未授权写 | 间接 prompt injection 触发写操作 |
| Memory validation | 事实入库前校验 | 持久记忆投毒（如 8/18 Copilot「CoSnitch」CVE-2026-24301） |
| Approval gate | 商家写操作全部 staged 待人批 | agent 失控改价/改库存 |
| Caps | 金额上限、频率限制 | 失控循环刷单 |
| Grounding rules | 系统提示强制「never invent prices」+ 执行器校验 | 幻觉价格/幻觉商品 |
| Analysis budgets | 分析代理 token 上限 | 成本失控 |
| MCP loopback binding | MCP server 只绑本机回环 | 托管 agent 暴露公网面 |

两个架构决定尤其鲜明：

1. **模型永远碰不到支付。** checkout 工具只返回一个 URL，由宿主渲染、用户完成——「the model never sees」。这是对「agent 该不该碰钱」的明确回答：不碰。对照读，OpenAI 3 月弃用 Instant Checkout 正是撞了这堵墙之后的撤退；Google AP2 想用协议+支付网络给 agent 发「可信支付授权」；Anthropic 的答案最保守也最工程化：把最危险的环节从模型手里整个拿走。
2. **拒答边界长在架构里，不在提示词里。** grounding 规则由 prompt + 执行器双重强制，写操作由 staged approval 兜底——与本频道 8/10（auto mode）、9/3 早报（Astra Critical）反复出现的结论同轴：**提示词不是安全边界，架构才是。**

## 正反观点

**支持方**
- Priceline VP：「一次旅行是一个人买过的最复杂的东西之一……Penny 在一次对话里搞定全部。」
- CommerceClarity（独立技术分析）的判词：「agent 蓝图本身已是成熟基础设施（mature infrastructure）」——争论已经不在架构层。
- 转化数据方向一致：Adobe 口径 AI 引流转化更高，Accenture 口径消费者接受度 85%。

**质疑方 / 风险**
- **真瓶颈在 catalog 数据治理，不在 agent。** CommerceClarity 逐行读了代码后指出：`search_products` 的过滤器只看结构化字段（attributes/titles/option values），**埋在长文本描述里的事实对 agent 不可见**；单位不统一（254 g vs 2.1 kg）会让过滤器失效；更隐蔽的是 **filter dropout——过滤器匹配不到时后端会静默丢弃条件，返回「相关商品」而非用户要的商品**。原话：「A shopper condition remains enforceable only when the catalog holds it as a field.」
- **30–35% / 60% 是单一未具名伙伴的自报数字**，无第三方审计，且发布时点（假日季前）商业动机明显。
- **"Not maintained; does not accept contributions"** 意味着 fork 它起步的团队要自己承担长期维护——这是营销快照，不是社区框架。
- 学术侧（arXiv 2508.02630《What Is Your AI Agent Buying?》）已证明购物 agent 的选择存在模型依赖与呈现偏差——当采购决策交给 agent，商家侧必然催生「面向 agent 的 SEO」军备赛，蓝图对此没有答案。

## 深度解读：对行业 + 对我们

**对行业：竞争单位正从「协议」滑向「参考实现 + 分发」。** 协议大战打了一年半、六个协议并存，结果最激进的托管结账（Instant Checkout）反而先阵亡。Anthropic 此时押注的是另一个杠杆：谁的参考架构被 fork 得最多，谁的安全假设、工具契约、evals 就成为事实标准——协议可以中立，但蓝图自带世界观。这与 MHS（硬件）、Managed Agents（托管）是同一盘棋：Anthropic 在系统性地把「agent 工程最佳实践」变成自己的分发面。三巨头路线自此清晰分岔：OpenAI=流量入口+协议、Google=支付信任层、Anthropic=工程栈本身。

**对我们（做多 agent 系统的团队），有六条可执行判断：**

1. **把这个 repo 当官方架构范本读，别当商务新闻刷过。** 这是 Anthropic 迄今最完整的生产级 agent 公开实现——unified prompts / skills / tool contracts / safety gates 跨三种运行时复用的组织方式，直接回答了「多运行时 agent 代码怎么不写三遍」。
2. **八层安全表可平移到任何 agent 域，拿它审计自己的系统**：我们的 agent 有没有 provenance gate？写操作是否 staged？记忆入库有没有校验？分析型子 agent 有没有 token 预算？逐行对照，缺哪层补哪层。
3. **两条权限公理可以直接抄**：高危动作（支付级）→ 模型只产出 URL/意图，执行归宿主；持久写操作 → 一律 staged + 人批。这比任何「小心谨慎」的提示词都值钱。
4. **`commerce-builder` 是「领域知识 skill 化分发」的示范**：四命令模式（scaffold / add-flow / author-evals / review）把领域最佳实践打包成 Claude Code 插件。我们自己的领域蓝图（SEO 流水线、研究 agent 等）完全可以照此封装——这是把 know-how 变成可安装资产的模板。
5. **catalog-as-field 教训要泛化**：agent 只能执行结构化字段里的约束，长文本里的事实对工具层不可见，且约束失配会**静默降级**而非报错。任何 agent 产品接客户数据之前，数据治理先行；给自己的工具层加「filter dropout 必须显式告知用户」的规则。
6. **若真做商业侧 agent**：Apache 2.0 可直接 fork 起步（省掉几周架构设计），但按「上游永不更新」做预算。

## 接下来盯什么

- 假日季（11–12 月）是否有第三方复现 30–35% / +60% 的转化数据——这是「agent 导购」叙事的证伪点。
- OpenAI 是否以开放蓝图回应（ACP 生态侧），Google UCP/AP2 与此的互操作性动向。
- 蓝图的社区 fork 是否出现事实标准化（官方不维护 = 把演化权让给了生态）。
- Shopify / Square / Wix 是否把蓝图包装成一键产品——那才是分发真正起量的时刻。
- MCP 官方 commerce connector 是否补位（当前蓝图刻意不带 connector，全走后端接口）。
