# 🧠 深度研究 ｜ 一个未撤销的令牌，三层工具深：LiteLLM 供应链事件的曝光面终于被摊开

> **一句话定性**：三月那次只被当成「又一个 PyPI 投毒」的事故，在五个月后被重新称量——它打穿的不是一个 Python 包，而是**几乎所有多模型 agent 系统唯一那个同时握着全部供应商密钥的进程**；而攻击的入口，是 LiteLLM 自己 CI 里那个负责扫漏洞的安全扫描器。

**来源**：CloudSEK 研究报告《2,500+ Companies and 434,000 CI/CD Pipelines Exposed in the Largest AI Supply Chain Breach of 2026》（2026-08-11 发布，8-12 经 PRNewswire 正式发稿后全网扩散）。技术机制部分交叉 Snyk 逆向分析《How a Poisoned Security Scanner Became the Key to Backdooring LiteLLM》与 LiteLLM 官方安全公告；质疑侧交叉 SecurityWeek 与 The Hacker News。
🔗 原文：https://www.cloudsek.com/blog/ai-supply-chain-breach-2500-companies-434000-cicd-pipelines
📅 日期：2026-08-11（CloudSEK 报告）／2026-08-12（PRNewswire、SecurityWeek、The Hacker News）；事故本体发生于 2026-03-24

## 一、为什么这一篇值得单独深读

三月底 LiteLLM 被投毒时，主流叙事是"恶意包只活了 40 分钟"——听起来像一次被及时掐灭的未遂事件，绝大多数团队看一眼公告、确认自己没在那 40 分钟里 `pip install`，就翻篇了。

八月的这份报告把这个结论推翻了两次。

第一次是**规模**：CloudSEK 从情报渠道拿到了这场行动的战利品与日志，重建出的曝光面是 2,500 家以上组织、434,000 条 CI/CD 流水线，名单里有 AWS、三星电子、Cisco、Salesforce、ServiceNow、Siemens、S&P Global、FedEx、Deloitte、X Corp。

第二次、也是更重要的一次，是**攻击链的形状**。SecurityWeek 引述报告里最精炼的一句话：

> "Trivy, then the build system, then the LiteLLM release: one unrevoked token, three tools deep."
> （先是 Trivy，然后是构建系统，然后是 LiteLLM 的发布产物：一个未撤销的令牌，三层工具深。）

TeamPCP 从头到尾**没有攻击过 LiteLLM**。他们打的是 Trivy——一个安全扫描器。LiteLLM 的 CI 里那一步"跑个 Trivy 扫扫漏洞"，自己把发布令牌递了出去。

对本监测而言，这条新闻的位置很特殊：过去半年我们反复把「多模型路由」写进行动项，而 LLM 网关正是这个建议的物理实现。这是那条建议第一次收到反面账单。

## 二、核心事实（按可信度分层）

### A. 攻击链时间线（一手取证，可信度最高）

来自 Snyk 逆向分析与 LiteLLM 官方公告，两边互证：

| 时间（UTC） | 事件 |
|---|---|
| 2026-03-19 17:43 | Trivy 的 GitHub Action tag 被改写，指向恶意 release v0.69.4。利用 `pull_request_target` 工作流漏洞（GHSA-9p44-j4g5-cfx5）窃取 `aqua-bot` 凭据 |
| 2026-03-23 12:58 | TeamPCP 注册 `checkmarx.zone` 与 `models.litellm.cloud` 两个域名 |
| 2026-03-24 | LiteLLM 的 CI/CD 跑到那一步，**执行了未固定版本的 Trivy**；恶意 Action 从 runner 环境里抽走 `PYPI_PUBLISH` 令牌 |
| 2026-03-24 10:39 | 用合法凭据发布 v1.82.7 |
| 2026-03-24 10:52 | 十三分钟后发布 v1.82.8，换用"升级版 `.pth` 投递机制" |
| 2026-03-24 12:44–12:46 | **102 秒内**用 73 个此前失陷的开发者账号发出 88 条 bot 评论刷屏；并用被控维护者账号 `krrishdholakia` 把披露 issue #24512 关成 "not planned" |
| 2026-03-24 ~13:38 | PyPI 隔离两个版本 |
| 2026-03-30 | LiteLLM 用全新 CI/CD v2 流水线发布干净的 v1.83.0 |
| 2026-07-02 | FBI 发布 FLASH 通告 FLASH-20260702-01 |
| 2026-08-11 / 08-12 | CloudSEK 公开曝光面数据 |

**两个关键放大器**：
1. **令牌撤销失效约 20 天**。CloudSEK 指出，泄露的自动化令牌在"轮换之后"仍然有效了大约 20 天——即失陷发生在被发现之前很久，而补救动作没有真正生效。
2. **Trivy 的 tag 几乎全被改写**：77 个 trivy-action 版本 tag 里有 **76 个**被重写，7 个 setup-trivy tag **全部**中招。这意味着"我 pin 了版本号"在这次里等于没 pin——被改的正是 tag 本身。

### B. 恶意载荷的机制（Snyk 逆向，硬技术）

**两个版本用了两套完全不同的触发方式，第二套才是要命的那套：**

- **v1.82.7**：base64 载荷直接嵌在 `litellm/proxy/proxy_server.py` 里，**任何东西 import `litellm.proxy` 就执行**——也就是以 proxy 模式跑网关的标准路径。
- **v1.82.8**：往 `site-packages/` 里丢了一个 `litellm_init.pth`（34,628 字节，双层 base64）。`.pth` 文件的性质是——**每次 Python 解释器启动都执行，不需要任何 import**。Snyk 的原话是"包括 `pip`、`python -c`、或者 IDE 的语言服务器启动 Python 的时候"。

  更难受的是：这个 `.pth` 在 wheel 的 `RECORD` 文件里被**正确声明**了，因此**通过了 pip 的全部完整性校验**——因为攻击者用的是合法的发布凭据，产物在密码学意义上是"正版"。

**三阶段载荷：**

1. **侦察与凭据采集**——SSH 私钥、`.env`、Git 凭据、shell 历史里的 API key、Slack/Discord webhook、Jenkins/Travis/Terraform 配置、`/etc/shadow` 里的口令哈希；AWS/GCP/Azure 凭据与服务账号 JSON，并用符合 IMDSv2 的请求去够 AWS Secrets Manager 与 SSM Parameter Store；Docker registry 凭据、kubeconfig、Kubernetes 服务账号令牌与集群 secret；顺带还捞加密货币钱包与助记词（BTC/ETH/SOL/ADA/XMR）与 Ledger 配置。
2. **加密外传**——`openssl rand` 生成 32 字节 AES-256 会话密钥，AES-256-CBC + PBKDF2 加密数据，再用硬编码的 4096 位 RSA 公钥（OAEP）包住会话密钥，打成 `tpcp.tar.gz`，curl POST 到 `models.litellm.cloud`。**那把 RSA 公钥与 Trivy、KICS 载荷里的公钥完全相同**——这是归因链上最强的单条技术证据。
3. **持久化与横向移动**——在 `~/.config/sysmon/sysmon.py` 装后门，注册一个名叫 "System Telemetry Service" 的 systemd user service，每 5 分钟轮询 `checkmarx.zone/raw` 取下载地址。**Kubernetes 侧**：读服务账号令牌 → 枚举**所有 namespace 的全部 secret** → 在 `kube-system` 里给**每一个节点**部署名为 `node-setup-{node_name}` 的特权 pod（`alpine:latest`），挂载宿主文件系统，把后门装到节点本身。

### C. 曝光面数据（CloudSEK 重建，需打折看，见第五节）

- **2,500+** 组织、**434,000** 条 CI/CD 流水线
- 点名样本（含每家的 secret 计数）：X Corp **3,459** 个 secret、S&P Global **1,218** 个、Cisco **327** 个 secret / **1,900** 次 run
- 行业分布覆盖金融、电信、制造、国防、能源
- 恶意软件被 Google 以 **SANDCLOCK** 追踪；TeamPCP 别名 PCPcat / Persy_PCP / ShellForce / DeadCatx3，自 2025 年 12 月活动至今，LiteLLM 是其行动的 **"Phase 09"**

### D. 爆炸半径（为什么 40 分钟不等于低影响）

- LiteLLM 的下载量约 **340 万次／天**。
- **确认发了紧急补丁的下游项目**：DSPy、MLflow、OpenHands、CrewAI、Arize Phoenix——**全是 agent 与 LLMOps 框架**。也就是说，大量团队是通过传递依赖拉进 LiteLLM 的，他们**不知道自己在跑它**。
- LiteLLM 官方明确列出的**受影响路径**：未固定版本的 `pip install litellm`、窗口期内构建的自建 Docker 镜像、以及**"经由 agent 框架、MCP server 拉进来的未固定版本 LiteLLM"**。

**这次事件是怎么被发现的**，值得单独记一笔：FutureSearch 的 Callum McMahon 在测试一个 Cursor MCP 插件时，机器因内存耗尽卡死——`.pth` 载荷起了个 Python 子进程，子进程启动时又触发了 `.pth`，递归成了一个非预期的 fork bomb。**世界头号 AI 供应链攻击是被自己的 bug 抖出来的。**

## 三、机制拆解：为什么偏偏是 LLM 网关

把三条线并起来看，就明白这次为什么不是普通投毒。

**第一，网关是密钥的汇合点，这既是它的价值也是它的价格。**
多模型路由的全部工程收益——一个抽象层、一处限流、一份用量账、随时切供应商——来自同一件事：把 OpenAI、Anthropic、Google、以及各家开源托管的密钥**全部收进一个进程**。这个进程被攻破的那一刻，团队与所有模型供应商的关系同时归零。CloudSEK 的战利品清单里"LLM API keys 与 AI gateway 配置"是单独一类，不是顺手捞的。

**第二，攻击面是防御工具本身。**
Trivy 是扫漏洞的。LiteLLM 在 CI 里跑它，正是在做正确的事。链条的形状是：**安全扫描器 → 构建系统 → 发布产物**，每一跳都是被信任的、自动的、无人看的。而 76/77 的 tag 被重写这一细节，把"pin 版本"这条最常见的防御建议直接击穿——**tag 是可变引用，只有 commit SHA 是不可变的**。

**第三，agent 生态把间接依赖做成了默认。**
DSPy、MLflow、OpenHands、CrewAI、Arize Phoenix 集体打补丁说明了一件事：**在 agent 技术栈里，LLM 网关已经沉到了地基层**。你选的是 CrewAI，装进来的是 LiteLLM。这与三月之前大家对供应链的心智模型不一样——那时人们盯的是"我直接依赖了什么"。

**第四，时间结构才是真正的伤口。**
3/24 事故 → 7/2 FBI 通告 → 8/12 组织才在名单上看见自己。**中间隔了 141 天。** 在这 141 天里，被偷走的云凭据、K8s 令牌、模型 API key 一直是活的，除非团队在毫无理由的情况下主动轮换过。FBI 七月那份 FLASH 的核心警告正是：被盗凭据**仍可被用于未来的攻击**。

## 五、正反两面

### 支持方：这就是 2026 年最大的 AI 供应链事件

- 攻击链有**完整密码学归因**（Trivy、KICS、LiteLLM 三处载荷用同一把 RSA 公钥），不是猜的。
- `.pth` 这条投递路径把"我只是装了一下"变成了失陷——**没有安全的安装动作**。
- 下游 agent 框架集体打补丁，是爆炸半径的独立佐证，不依赖 CloudSEK 的数据集。
- FBI 在七月就发了 FLASH，说明执法侧已认定这批凭据具有持续危害。

### 质疑方：那个数字不是受害者名单

- **CloudSEK 自己划了线**：这些数字"描述的是重建出的曝光面"，**不应被读作"每一家被点名的组织都被成功攻破"或"每一份凭据都真的被偷走"**，并建议逐案独立核实。
- **数据来源是情报渠道拿到的战利品与日志**，不是从被点名组织那里采集的。CloudSEK 向 The Hacker News 承认了这一点。
- **置信度分级本身就说明问题**：高置信 = 该组织自有域名出现在被捕获的 CI runner 环境身份信号里；中置信 = **仅凭仓库命名空间**。CloudSEK 明确表示，两个标签**都不构成攻击成功的证据**；并拒绝讨论是否做过发布前告知、有没有组织提出异议。
- **数字口径不统一**：The Hacker News 的标题用的是 **2,100+**，而报告数据集是 2,500+；同一个 434,000 在不同报道里分别被表述为"CI/CD 流水线数"与"被捕获文件数"。这类不一致在传播中会被抹平成一个权威数字。
- **存在利益相关**：CloudSEK 售卖曝光监测平台 AIVigil，并为此事件专门上线了自查页 `exposure.cloudsek.com`。这不否定研究质量，但报告的传播强度里有商业动机的成分。
- **LiteLLM 官方的反面事实同样硬**：官方 Proxy Docker 镜像 `ghcr.io/berriai/litellm`（固定了 requirements.txt）、LiteLLM Cloud 用户、从 GitHub 仓库安装的用户、以及停留在 v1.82.6 及更早的用户，**均不受影响**。换句话说，**按最佳实践部署的那批人真的躲过去了**——这不是运气，这是 pin 依赖的直接回报。

**我的判断**：把 2,500 当成"2,500 家公司被黑了"是误读；但把它当成"至少 2,500 家公司需要立刻做凭据审计"是**完全站得住**的。这两个结论的行动成本差不多，而只有第二个在错的时候不会害死人。

## 六、深度解读

### 对行业

**1. AI 基础设施层第一次被证明是最优攻击位。** 不是因为它防守弱，而是因为它**连着所有东西**：模型供应商密钥、云凭据、K8s、CI。CloudSEK 那句"未来的攻击很可能就是冲着 AI 这一层来的"不是修辞，是从这次的战利品结构里读出来的。

**2. 防御工具的信任链是行业级盲区。** Trivy、Checkmarx（被冒名注册域名）、KICS——这次被串起来的全是安全工具。CI 里跑的安全扫描器拥有 runner 的完整环境访问权，却几乎从不被当成攻击面来审。

**3. "不可变引用"要从建议变成硬要求。** 76/77 个 tag 被重写这一条，应该终结关于"pin 到 tag 够不够"的讨论。PyPI/npm 的 trusted publishing 与 attestation 会不会从可选变成生态强制，是这次事件最值得追的制度后果。

**4. AI agent 已经出现在攻击方的工具链里。** `openclaw` 做自动化目标筛选这条，比这次泄了多少密钥更值得记住——它与本监测既有的「模型自主逃逸」「Unit 42 自主网络攻击」两条线合流：**agent 同时在防守侧和进攻侧规模化，而进攻侧不需要通过任何安全评估。**

### 对「做多 agent 系统的我们」——可执行判断

**① 今晚就做的三件事（不需要等任何结论）**

- 在所有开发机、CI runner、容器镜像里跑一遍：
  `find / -name "litellm_init.pth" 2>/dev/null`
  以及检查出站到 `models.litellm[.]cloud` 与 `checkmarx[.]zone` 的历史流量。
- 审计依赖历史：不只看 `requirements.txt` 现在写的是什么，要看 **3 月 24 日前后有没有构建过任何镜像**、锁文件里 litellm 曾经解析到哪个版本。**传递依赖是重点**——如果我们用过 CrewAI / OpenHands / DSPy / MLflow / Arize Phoenix 中的任何一个，就必须查。
- **不管查出什么，轮换全部模型供应商 API key。** 141 天的暴露期里，"没证据被偷"和"被偷了但没被用"看起来完全一样，而轮换的成本是几分钟。

**② 把网关的单点性质写进架构文档，而不是只享受它的好处**
多模型路由的收益依旧成立，但要为它配一条对冲：网关进程的凭据**不应是长期静态密钥**。可行方向是让网关只持有短时效凭据（供应商支持的话）或把密钥托管在外部 secret 管理器并按调用取用——目标是把"网关失陷"的爆炸半径从"所有供应商关系归零"压到"一个短窗口"。

**③ CI 里所有第三方 Action 全部 pin 到 commit SHA，不接受 tag**
这是本次事件唯一一条**零成本、零争议、立刻可做**的加固。同时给 CI 的发布令牌加两条约束：最小权限（发布令牌不该能读环境里的其他 secret）与短有效期。别忘了那 20 天——**轮换之后旧令牌仍然有效**才是真正的失败点，所以轮换必须验证撤销生效，不能只做签发。

**④ 按"这个进程迟早会被攻破"设计 agent 的运行时权限**
Kubernetes 那段横向移动（读服务账号令牌 → 枚举全 namespace secret → 给每个节点部署特权 pod）是一份现成的威胁模型。如果我们的 agent 跑在 K8s 上：服务账号令牌不该默认挂载、secret 访问要按 namespace 收窄、`kube-system` 的 pod 创建权限必须走准入控制。这与我们此前记下的 NHI（非人身份）治理和 agent 运行时白名单是同一件事，这次事件只是给它标了价。

**⑤ 依赖清单要加一个字段：`is_credential_aggregator`**
我们此前给依赖加过 `retirement_date`、`origin/hosting_jurisdiction`。再加一个布尔字段，标记"这个组件是否同时持有多个系统的凭据"。网关、CI、secret 管理器、MCP server 都该被标红——**它们不按代码量或重要性排优先级，按失陷后的爆炸半径排。**

**⑥ MCP server 是下一个同形状的位置**
LiteLLM 官方公告把"经由 MCP server 拉进来的未固定版本 LiteLLM"单独列为受影响路径。MCP server 的性质与网关同构：进程内持有多个外部系统的凭据，被 agent 自动加载，几乎没人审依赖树。7 月底的 MCP 新规范把授权收进 OAuth/OIDC 是对的方向，但**它管的是 server 与外部系统之间，管不了 server 自己的供应链**。

## 七、接下来盯什么（信号）

1. **TeamPCP 的 "Phase 10"**——LiteLLM 是第 9 阶段。下一个被打的如果又是 AI 基础设施包（向量库、MCP server 注册表、agent 框架本体），就说明这是一条被选定的赛道而非机会主义。
2. **被点名的大厂是否公开反驳 CloudSEK 的归因**。AWS、Cisco、Salesforce、Siemens 若出面否认或修正，这份名单的可信度会被重新定价；若集体沉默，则反向印证。
3. **`openclaw` 那条线是否出现第二例**。AI agent 用于供应链攻击的实战化，一旦有第二个独立案例，就该单开一篇《进攻侧的 agent：不需要通过评估的那一半》。
4. **PyPI/npm 是否把 attestation 或 trusted publishing 从可选改成强制**，以及 GitHub 是否对 Action 的 tag 可变性做出机制性回应。
5. **LiteLLM 的 CI/CD v2 + cosign 签名镜像会不会成为 AI 基础设施包的新基线**——如果其他 agent 框架跟进签名与校验和发布，这次事故的行业收益才算兑现。
6. **是否出现第一起由此引发的、可归因的下游生产事故**。141 天的暴露期意味着后果可能才刚开始显现；这与本监测「agent 造成的生产事故：谁赔、赔什么」的追踪位直接相接。
