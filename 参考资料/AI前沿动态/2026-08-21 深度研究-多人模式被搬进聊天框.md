# 🧠 深度研究 ｜「多人模式」被搬进聊天框：Slack Code 把 agent 编排层做成了免费基建

> **一句话定性**：真正的新闻不是 Slack 又接了几个 AI；而是它把「agent 拉起工作空间 → 展示 diff 与预览 → 团队围观并给反馈 → 人类签字才准上线 → 完事自动归档成审计日志」这一整套**我们这行自己在造的编排与治理层**，做成了一个**所有套餐（含免费版）都白送**的原生频道类型——并且 Claude Code、Devin、Copilot、Vercel 四家（多家媒体另计入 OpenAI）在同一天以「首发伙伴」身份接了进去。

**来源**：Salesforce / Slack 官方发布《Introducing Slack Code: Agentic Coding for Teams》；官方开发者侧文章《How Coding Agents Work in Slack》；SlackHQ 官方 X 长文标题《Agentic coding is now multiplayer: Introducing Slack Code》

## 一、为什么这一篇值得单独深读

这条线我们已经跟了两个季度，而且是**我们自己每天在干的事**：

- **2025-12**：Claude Code 以 research preview 形态进入 Slack 线程（Unite.AI 梳理的时间线）
- **2026-02**：Slack 放出 **MCP server** 与 Real-time Search API——agent 第一次能把 Slack 当结构化上下文源读
- **2026-06-23**：我们推过 **Claude Tag 公测**——agent 从「单用户助手」变成「每频道常驻、有自有服务账号身份、跨频道记忆、可主动插话」的团队成员
- **2026-06**：Slackbot MCP Client 上线，Slack 反过来当 MCP 客户端
- **2026-08-14**：backlog 里记过 Claude Tag 升级（用完整频道上下文 + memory 自行判断何时插话、何时沉默，不额外收费）
- **2026-08-20**：**Slack Code**

前面每一步都是「某一家 agent 厂商把自己接进 Slack」。这一步反过来了：**Slack 定义了一种新的原生对象（code channel），让所有 agent 厂商来适配它**。

对做多 agent 系统的我们来说，这比任何一次跑分更该停下来看。因为它动的不是模型能力，是**我们产品的边界**：过去半年我们（以及一大批 agent 创业公司）投入最多工程量的三样东西——**任务级工作空间、人在环审批、执行审计**——被一个装机量以亿计的协作工具，在同一天，免费送了出去。

顺带一个把这条新闻的量级钉住的数字：Forbes 引用 **Anthropic 对 500 位美国技术负责人的调研，近 90% 的组织今天已在用 AI 辅助编码**。也就是说，这不是在开辟需求，是在给一块**已经饱和的既成需求**装上默认的治理外壳。

## 二、核心事实

### A. 产品形态：一种只有 agent 能创建的频道

| 项 | 事实 | 出处 |
|---|---|---|
| **触发方式** | 在任意对话里 @ 一个编码 agent（如 Claude Code、Devin），**agent 自己 spin up 一个任务专属的 code channel** | 官方口径，Unite.AI / Techzine 引述 |
| **频道内的 Tab** | 对话 / 任务计划 / 代码 diff（前后对比）/ HTML 实时预览 | The Next Web、Techzine、SiliconANGLE 一致 |
| **参与者** | 工程师、PM、设计师、非技术同事在**同一个空间**看同一份上下文 | 官方口径 |
| **完成后** | 频道**自动归档**，历史保留为**审计日志**（请求、变更、审批全链路） | Techzine、Unite.AI |
| **可用范围** | **每一个 Slack 套餐都可用**（含免费工作区），发布当日生效 | Techzine、Unite.AI 一致 |
| **收费口径** | Slack Code 本身不额外收费；**agent 的使用权仍需向各厂商单独购买** | The Next Web、Techzine |

The New Stack 的标题把这件事的性质说得最准：**Slack 多了一种新频道类型，但只有 agent 能创建它。**

### B. 治理机制：三道闸（这是本次发布真正的技术内容）

**① 强制人类签字**
高风险动作——明确点名的是**把代码合并/推送到生产**——必须由「channel expert」授权。Slack 发言人 **Gianna Dimick** 对 Gizmodo 的原话：平台要求 *"human sign-off on high-stakes actions like merging code to production, all governed by Slack's built-in enterprise security model."*

**② 任何人可急停（kill switch）**
频道里的**任何成员**都可以在任务执行途中暂停、改道或终止 agent（The Next Web）。注意这个设计的非对称性：**发起需要@，叫停不需要权限**。

**③ 身份复用，不新增攻击面**
agent 继承**已有的 Slack 权限与管理员控制**；IT 不需要为它单独 provision 新身份（The Next Web）。这一条延续了 6/23 Claude Tag 的路线——服务账号而非冒用用户身份——但现在是平台级默认。

### C. 生态：谁在里面

**首发伙伴（founding partners）——各家口径不完全一致，如实记录：**

- Techzine、Unite.AI 记为 **4 家**：Claude Code（Anthropic）、Devin（Cognition）、Vercel Agent、GitHub Copilot
- The Next Web、Cryptobriefing 记为 **5 家**：上述四家 + **ChatGPT（OpenAI）**
- SiliconANGLE 的列法是 Claude Code / ChatGPT / Vercel **v0** / Devin + 「其他可通过自定义 API connector 接入的 agent」

> *这个分歧很可能来自「code channel 原生首发伙伴」与「Slack 生态内可用 agent」两个口径的混用；官方页面 403 未能直取原始名单，标注为待核。*

**更外圈**：OpenAI、Google、Perplexity、Writer、Dropbox、Notion、Cognition、Vercel、Cursor 都在往 Slack 生态送 agent；Slack 现有**2,600+ 第三方应用**；另有 Lovable、n8n、LangChain、Superhuman 等集成（The Next Web）。

**下一步**：Slack 表示会把 **code channel 底层 API 开放给广大开发者社区**（Techzine、The Next Web）——即第三方可以做自己的 agent 来占据这个新频道类型。

## 三、机制拆解：code channel 其实是一个「运行时」

把营销词剥掉，Slack Code 提供的是一套**任务级 agent 运行时**，它的四个组成部分正好对应我们自己 harness 里的四个模块：

| Slack Code 的东西 | 在我们的系统里叫什么 | 谁提供 |
|---|---|---|
| @ 触发后自动开的 code channel | **任务级 session / workspace 隔离** | 现在是 Slack，免费 |
| 计划 tab + 对话 tab | **plan 展示与中途纠偏通道** | 现在是 Slack，免费 |
| diff tab + HTML 预览 | **产物 review surface** | 现在是 Slack，免费 |
| 签字闸 + kill switch + 归档审计日志 | **HITL 审批 + 可观测性 + 合规留痕** | 现在是 Slack，免费 |
| **模型/agent 本身** | policy | **仍然要向 Anthropic / OpenAI / Cognition / GitHub 付费** |

结论很直接：**Slack 免费送掉了整条编排与治理链路，唯独没送 agent 本身。** 这是典型的「把互补品商品化」——被商品化的那一层，恰恰是过去 12 个月里大量 agent 工具创业公司用来做差异化的那一层。

还有一处结构性变化值得单独指出：**review 的受众被扩大了**。传统 code review 发生在 GitHub PR 页面、受众是工程师；Slack Code 把 diff 放进了一个 PM、设计师、非技术同事都在的频道。这是**能力扩散**（更多人能发起并验收软件变更），同时也是**风险扩散**（下面会讲）。

## 五、正反观点

### 支持方：这是 agent 从「个人生产力」跨到「组织生产力」的必要一步

1. **上下文本来就在这儿**。Cat Wu 的论点最有说服力：工程工作**本来就是从 Slack 里的一句话开始的**。把 agent 的工作台搬到需求诞生的地方，省掉的是「把上下文从聊天搬到工具再搬回来」的全部损耗。
2. **单人 AI 生产力提升是不可累积的**。Gavin 的「solo player sport」抓住了一个真问题：一个人用 Claude Code 干得再快，那份上下文与判断力**留在他本地**，组织拿不到复利。默认公开的频道把它变成资产。
3. **治理是先于速度设计的**。签字闸、kill switch、自动归档审计日志——这三样在发布日就是默认开启，而不是企业版加购项。对受合规约束的团队，这可能是第一次能把 agent 编码**合法地**放进流程。
4. **对 agent 厂商是纯增量**。Slack 不卖模型，只做承载层，所以 Anthropic / OpenAI / Cognition / GitHub 全都乐意接——这解释了为什么首发能凑齐几乎所有主要玩家。

### 质疑方：治理形式做足了，治理实质未必

1. **审批会退化成社交动作**。The Next Web 直接点出这个风险：在一个热闹的频道里，approve 按钮很容易变成**社交性的点头**而不是严肃的技术审查。传统 PR review 之所以有效，一部分正来自它的「摩擦」和专属受众；把它搬进聊天流，摩擦被移除的同时，注意力也被稀释了。
2. **失败案例是真的存在的**。Gizmodo 在报道里挂了两起 agent 抹掉代码库的旧账（OpenAI 模型删文件、Replit 的 agent 在 vibe coding 过程中清空客户代码库），并对 Slack 的护栏加了一句刺人的括注——*"(Assuming it works)"*。护栏只覆盖「合并到生产」这类被显式列举的高危动作；agent 在 sandbox 内部能造成的破坏并不在这道闸的射程内。
3. **Gizmodo 的整体定性是「套路」**。标题里的 *"of course"* 和把这归入企业软件「拼命向 B 端兜售 AI」的常规剧本，代表了相当一部分开发者的态度：这不是突破，是渠道。
4. **治理边界模糊**。Forbes 的分析在肯定 Slack「要做企业里 agent 的操作层」这一定位的同时，明确点出它面临**治理挑战**——当非技术人员也能在频道里发起并验收代码变更，责任归属和变更管控如何界定，发布材料并没有答案。
5. **竞争层面并未解决根本问题**。Forbes 的标题问句本身就是质疑：*"But Can It Take On Teams?"* Slack 用「agent 中立的操作层」来对抗 Microsoft 的全栈捆绑，是一条真实但脆弱的差异化——微软手里同时握着 Teams、GitHub、Copilot 和 VS Code。

## 六、深度解读：这对行业、对「做多 agent 系统的我们」意味着什么

### 对行业

**1. agent 竞争的战场，正式从「模型层」下移到「承载层」。**
这一周的其他新闻其实指向同一件事：Stripe 以 75 亿美元买下 OpenRouter（**路由层**）、Anthropic 用 2.5 亿美元订单把 Fractile 顶到 65 亿估值（**推理硅层**）、现在 Slack 免费送出**编排治理层**。模型能力在 8 月已经被挤成一条很窄的带（我们 8/12 推过「前沿被挤成一条 3 分宽的线」），于是价值开始沿着栈上下逃逸。**承载层的归属，正在成为比模型排名更重要的变量。**

**2. 「agent 中立」是继「云中立」之后的新站位。**
Slack 的赌注是：企业不会只用一家的 agent，所以谁能当**所有 agent 的公共客厅**，谁就拿到控制点。这与微软的垂直整合是两条明确对立的路线。值得注意的是，**Anthropic 同时站在两边**——它既是 Slack Code 的首发伙伴，又与 Salesforce 有扩展合作，还在自己做 Claude Tag。

**3. 编码 agent 的「团队化」是产品形态的收敛点，不是 Slack 独有。**
8/12 的 Cursor、8/12 的 Zed「Delta」（人与 agent 协作的 multiplayer 编码环境）、7/31 的 YC 开源 harness「QM」（云优先、原生 Slack、每人每 room 各自作用域的 memory/files）、以及现在的 Slack Code——**四个独立团队在两个月里收敛到了同一个形态**：任务级隔离空间 + 多人围观 + agent 常驻 + 审计。这种收敛速度通常意味着这个形态是对的。

### 对我们（做多 agent 系统的团队）——三条可执行判断

**判断一：别再自己造「任务频道 + diff 展示 + 审批 + 审计」这四件套了，除非它是你的核心差异化。**
这四样今天在 Slack 里是零成本的默认能力。我们如果还在这上面投工程量，需要能明确回答「比免费的那个强在哪」。**更划算的做法是把我们的 agent 做成能进 code channel 的一等公民**——Slack 已经宣布会开放 code channel 底层 API。这是一个明确的、有时间窗的接入机会，早接的人吃到分发红利。

**判断二：把「非技术同事也在 review 现场」当成产品需求，而不是意外。**
Slack Code 最被低估的变化是**验收者的构成变了**。一个纯 diff 视图对 PM 是无效信息，所以 Slack 才要加 HTML 实时预览。我们的 agent 输出如果只有代码 diff、没有**可直接判断对错的产物形态**（预览、可点的样例、before/after 对比、变更的自然语言摘要），在这个新场景里就是不可验收的。**「让非工程师能在 30 秒内判断这次改动对不对」应该成为我们输出层的硬指标。**

**判断三：正视「审批社交化」这个批评——它对我们同样成立，而且我们有能力做得比 Slack 好。**
The Next Web 的质疑是这次发布里最有价值的一条外部意见。Slack 的闸门是**按动作类型**设的（合并生产 = 高危）。但真实风险不是按动作类型分布的，是按**变更影响面**分布的。我们可以做 Slack 不会做的事：**按 blast radius 分级审批**——碰到迁移脚本、鉴权逻辑、计费路径、删除操作时，要求指定的人签字并附理由；纯文案改动一键放行。同样地，**kill switch 要设计成任何人可按、且默认可回滚**，Slack 只做到了前半句。

**一句话总结我们的定位调整**：**编排层已经不值钱了，值钱的是「让人类在 30 秒内做出正确批准/否决判断」的那一层**。

## 七、接下来盯什么（信号）

1. **code channel API 什么时候开放、门槛多高。** 这是我们能否把自家 agent 送进这个新分发渠道的唯一入口。开放的形态（是 Slack app 框架，还是走 MCP）会决定接入成本。
2. **官方首发伙伴名单的确切构成。** ChatGPT 到底是不是 code channel 原生首发伙伴（4 家 vs 5 家的分歧）——这直接反映 OpenAI 与 Salesforce 的合作深度。
3. **第一起「Slack Code 里 agent 造成真实事故」的公开案例。** Gizmodo 的 *"(Assuming it works)"* 会不会被证实。这将决定这套治理机制是不是真的、还是只是 UI。
4. **微软的对应动作。** 如果 Teams 在 Q4 出一个绑定 GitHub Copilot 的等价物，「agent 中立 vs 垂直整合」这场对决会立刻具象化。
5. **Anthropic 会不会把 Claude Tag 与 Slack Code 合并口径。** 如果 Claude Tag 的能力被吸收进 code channel，说明 Anthropic 接受把承载层让给 Slack；如果继续并行，说明它想自己保留一份。
6. **审批数据。** 半年后如果有人统计出 code channel 里的 approve 中位耗时（比如 <10 秒），「审批社交化」的批评就被实证了。
