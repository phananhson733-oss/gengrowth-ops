# 🔌 深度研究 ｜ 调用者不再是人：MCP 新路线图把整个协议重造给无人值守的 agent

> **一句话定性**：8 月 22 日，MCP（Model Context Protocol）核心维护者 David Soria Parra 与 Den Delimarsky 发布新一版官方路线图（未来 6–12 个月）。表面看是一份工程排期，实际是这个「AI 接万物」事实标准的一份**三重自白**：①请求-响应模式装不下要跑几分钟、需要中途改道的 agent 工作负载；②整套授权模型建立在「一个坐在浏览器前的人当场点同意」之上，而现实中的调用者越来越多是**云端无人值守的 agent、以及需要比父 agent 更窄权限的子 agent**；③连上一个 100 个工具的 server，模型要在用户问出第一个问题之前就为整个工具面付 token 成本。五大优先区（agent 消息原语 / HTTP 传输统一 / **Agent Identity** / 原语重做 / SDK 生成化）每一条都在回应生产环境的真实伤口——而其中 Agent Identity 是 2026 下半年 agent 工程最值得押注的一条线：**协议层第一次要给「agent 本身」发身份证，并让子 agent 拿到比父 agent 更窄的授权**。对做多 agent 系统的我们，这份文件不是新闻，是施工图。

## 一、为什么值得深读

过去两周本栏目追的几条线——8/19 收入易主、8/22 harness 打穿 ARC-AGI-3、8/23 Mythos 5 的接口闸门与 FelonyBench 的越界记分牌——共同指向一个判断：**竞争与治理的重心正在从「模型」移向「模型外面的那一层」**。harness、闸门、审计、编排，全都长在协议层之上。而协议层此刻只有一个事实标准：MCP。

所以当 MCP 的核心维护者用一份路线图宣布「我们要把协议从『为聊天窗口里的人类设计的插件规范』重造成『为无人值守 agent 设计的基础设施』」时，这不是一条工具链新闻，而是整个 agent 生态的地基要换梁。三个理由值得单独深读：

1. **它是方向性文件，不是功能清单**。路线图明说：落在五大优先区内的 SEP（规范增强提案）获得加速评审，区外的「排更长的队、过更高的门槛」——这决定了未来一年整个生态往哪长。
2. **它包含一次罕见的静默翻案**。2026-07-28 版本删掉了协议级 session 与初始化握手——MCP 发布时最受诟病的有状态设计被整个拆除，远程 MCP server 从此「与任何 HTTP 工作负载无异」。承认走错，然后当着全生态的面拆掉重来，这在一个已被三大实验室采纳的标准上极少见。
3. **Agent Identity 第一次成为一级公民**。「pasted API keys and long-lived tokens」被点名为要淘汰的现状；接替它的是一整套与 IETF OAuth / WIMSE 工作组协同的标准栈。谁先吃透这条线，谁就先拿到企业级 agent 部署的门票。

## 二、核心事实

### 2.1 已经落地的：2026-07-28 规范版本（理解路线图的前提）

- **无状态化**（SEP-2575 / SEP-2567）：删除协议级 session 与初始化握手，server 可水平扩展、无需状态层；
- **`server/discover`**：连接前先探明对方支持的版本与能力；
- **列表结果可缓存**（SEP-2549）：list 结果与资源读取加 `ttlMs` / `cacheScope`；
- **Tasks 转为官方扩展**（SEP-2663）：长任务生命周期按早期采用者反馈重做；
- **MRTR（Multi Round-Trip Requests，SEP-2322）**：取代「server 主动发起请求」，与无状态架构兼容；
- **授权强化**：issuer 校验、issuer 绑定的客户端凭据、CIMD（Client ID Metadata Documents）、Enterprise-Managed Authorization 成为稳定扩展;
- **治理**：正式 Contributor Ladder、各工作组自行分诊 SEP、特性生命周期与弃用政策。

### 2.2 五大优先区（未来 6–12 个月，各区列明责任维护者与工作组）

**① Agentic Messaging Primitives**（Caitie McCaffrey / Clare Liguori / Peter Alexander）
问题：Tasks、`subscriptions/listen`、progress notifications 三套「server 还没做完」的答案分属不同工作组，**不共享生命周期、取消模型和错误面**。本期交付：**server 主动事件**（channels + 订阅 + webhooks，让 server 在任务完成时通知 client，替代昂贵的客户端轮询）；Agents / Transports / Triggers & Events 三工作组联合做**组合性评审**；Tasks（SEP-2663）继续向并入核心协议推进。

**② HTTP-Native Transport 统一与硬化**（Kurtis Van Gent / Nick Cooper）
问题：每个 HTTP 原生特性都得为 stdio 再设计一遍，SDK 维护两条传输管线，协议元数据在 HTTP header 与消息字段间重复且需交叉校验。本期交付：**「HTTP over stdio」**——Streamable HTTP 成为唯一绑定，本地 server 用 **HTTP/2 over stdio** 获得多路复用，同时保留子进程的安全与生命周期保证；**缓存扩展到 ETag**，给原语结果（尤其 tool call 结果）做版本化。

**③ Agent Identity 与企业级安全**（Paul Carleton / Den Delimarsky；Agent Identity WG 本期组建）
问题原话级表述：「MCP 授权假设 consent 时有一个带浏览器的人在场。而调用者越来越多是 agent：有自己身份的云工作负载、替一个不在场的用户行事、或者派生出**应当拿到比父 agent 更窄权限的子 agent**。现存 MCP server 依赖粘贴的 API key 和长命 refresh token。」本期交付:**DPoP**（Demonstrating Proof of Possession，RFC 9449）定稿并推广采用；**agent 身份与委托**——Workload Identity Federation（SEP-1933）+ ID-JAG（Identity Assertion JWT Authorization Grant，Enterprise-Managed Authorization 的底层）+ RFC 8693 token exchange，与 IETF OAuth 和 WIMSE 工作组协同。讨论中：**human-presence attestation**——在协议层区分「交互式客户端」与「无人值守 agent」。

**④ Improved Primitives**（Kurtis Van Gent / Peter Alexander / Den Delimarsky；Core Primitives WG 本期组建）
本期交付：**重做 `tools/call` 结果形状**——现规范允许同时返回 `content` 与 `structuredContent`，server 与 client 作者双双困惑、实现已经分叉；**progressive discovery**——server 先给一个小入口目录，随对话收窄按需展开，与 ETag 缓存联动；**content annotations 生死判定**——声明内容受众/优先级的注解几乎无人采用，「如果没用就该考虑弃用」。另有 File Uploads WG 继续做范围读取、层级列举等类文件系统语义。

**⑤ SDK 开发者体验**（Den Delimarsky / David Soria Parra）
背景判断：**「agent 越来越多地直接从库文档生成 MCP client/server 代码」**。本期交付：定义扩展契约（扩展绑定哪个角色、SDK 必须原生支持什么、如何打包与版本化）；**生成化实验**——从规范 + 人审一致性测试套件生成一个候选 Tier 1 SDK 与配套 quickstart，验证后发布结论，包括「哪些层该确定性 codegen、哪些层该模型辅助生成」。

### 2.3 规则变化：路线图即资源分配

官方明说：**优先区内的 SEP 加速评审；带着工作组支持来的提案走得最快**；任何工作组可先在 `experimental-ext-` 仓库做实验性扩展（SEP-2133）再走正式提案。路线图同时声明「反映当前思路而非硬承诺」。

## 三、机制拆解：三个「承认」，一次翻案

**承认一：请求-响应死了，但三套替代品不能各自为政。** MCP 已经长出 Tasks / 订阅 / 进度通知三套异步机制，路线图罕见地自曝风险：「三个对『server 还没做完』的回答，不共享生命周期、取消模型和错误面」。把 server 主动事件（webhook/channel）扶正，本质是承认 agent 工作负载的主形态是**长任务 + 事件驱动**，轮询是要被计价淘汰的过渡形态。

**承认二：授权模型的隐含前提已经失效。** OAuth 同意页的全部语义建立在「人在场」上。当调用者是 cron 拉起的 headless agent、当一个 orchestrator 派生五个子 agent 各干一摊活，「把整串权限原样下传」就是今天多数系统的现实——也是 FelonyBench 那 15 起越界事件共同的暗面配置。ID-JAG + RFC 8693 token exchange 的组合，目标正是让**每一级委托都能收窄一次授权**；human-presence attestation 则要在协议层把「有人看着」和「没人看着」变成可声明、可校验的属性。这与我们 8/23 深研的结论（治理重心从「模型拒绝什么」转向「环境允许什么」）严丝合缝：**MCP 正在把「环境闸门」标准化**。

**承认三：工具目录是有价格的。** 原话：「连上一个有一百个工具的 server，意味着模型在用户问出第一个问题之前就要为整个表面付费。」progressive discovery + ETag 缓存是同一枚硬币的两面：前者少载入，后者不重复载入。协议层第一次把 **token 成本**当作设计约束写进路线图。

**一次翻案：有状态设计被整体拆除。** 2024 年首发的 MCP 是有状态协议——session、初始化握手、SSE 长连接，部署方为此搭持久层、做会话粘滞。07-28 版本把这些全删了。HN 上最高赞的方向性评价来自 rco8786：「引入一个自造的新协议是 MCP 初版最愚蠢（bone-headed）的决定之一」——而这次翻案恰恰是对该批评的全盘接受。接下来的「HTTP/2 over stdio」是同一逻辑推到底：**连本地子进程都说 HTTP，一个传输模型走天下**。

## 五、正反观点

**支持方（含建设性辩护）**：
- **无状态化方向广受肯定**：多位部署过 MCP 的评论者（huksley 等）指认 v1 有状态设计「对部署极不友好，需要一个复杂的持久层」，本次修正是对的；
- **动态工具面是 REST 给不了的**（HN @youre-wrong3）：「MCP 可以按这个用户想要、且有权限的范围下发工具，而不是一份把所有 endpoint 全列出来撑爆上下文的 REST 文档」；
- **无沙箱场景刚需**（HN @MikhailTal）：不是所有 agent 都有代码执行环境去「写代码调 API」，MCP 让工具调用不依赖沙箱——有沙箱的场景确实可以走 code mode（Cloudflare 路线）；
- **从 OpenAPI 单源生成**（HN @davidrichards，Parallel AI）：维护一份高质量 openapi spec，MCP 从其自动生成，UI/API/MCP 三面对齐、零额外维护——与路线图第五区「从规范生成 SDK」同构。

**质疑方**：
- **「REST + skills.md 为什么不够」**（HN 最热评论，@cube00，16 条回复）：agent 直接读一份文档、打普通 HTTP endpoint，为什么需要一个平行协议？@peterlk 补充实测：「一个文档良好的 openapi.yaml 对 agent 非常有效」；
- **规范翻烧饼的迁移税**（@jdw64 / @mmaunder）：Wordfence 创始人 mmaunder 的控诉最重——「从第一天起就是多套标准来回转向、一个吞上下文的特性、感觉像个拼凑物（kludge）。这烧掉了我对 MCP 的信任，本地工具 + API 用得太顺了，要我回来得拿出真东西」；
- **progressive discovery 迟到**（@skinfaxi）：「已经在好几个 harness 里自己实现过 MCP 懒加载了，现在正把一切改成 code mode」——协议标准化的速度落后于一线自救的速度；
- **身份栈的落地率存疑**（@izend）：DPoP + WIF + ID-JAG + token exchange 是一套相当重的企业级组合拳，「很好奇有多少 MCP server 会真的实现这些」；
- **根本性否定**（@DarmokTanagra）：「MCP 的整个前提就是误入歧途——为非人类维护一个平行 web」。

**公平校准**：质疑方的「REST+文档就够」在有沙箱、有代码执行能力的 harness 里基本成立（我们自己的实践也印证）；但在无沙箱的消费级/企业级表面（聊天应用、办公套件、Slack Code 这类），协议化的工具下发 + 权限继承没有现成替代。两条路线更可能长期并存，而非一方吞掉另一方。

## 六、深度解读：对行业，对我们

### 对行业

1. **协议层在追认 harness 层已经发生的事实。** 懒加载工具（progressive discovery）、结果缓存（ETag）、长任务事件化（server-initiated events）——每一项都是过去一年各家 harness 里早就自己做过的私有实现。MCP 现在做的是把这些私有解法收编为标准。含义：**协议不再引领创新，而在固化共识**——这恰是一个标准走向成熟（而非衰落）的标志，参照 HTTP/2 对 SPDY 的收编。
2. **Agent Identity 是 2026H2 最重要的基建暗线。** 本栏目最近四篇深研（Daybreak 身份闸门、Mythos 接口闸门、FelonyBench 责任归属、SB 53 训练期监控）全部卡在同一个缺口上：**没有标准化的 agent 身份，一切治理都只能在应用层各自造轮子**。MCP 把 ID-JAG/WIF/DPoP 这套栈推成标准后，「子 agent 权限必须窄于父 agent」将从最佳实践变成协议能力，进而变成企业采购的合规检查项。留意：这套栈与 IETF WIMSE（Workload Identity in Multi System Environments）协同——agent 身份正在和云原生工作负载身份**合流**，而不是另起炉灶。
3. **「code mode vs MCP」的路线竞争公开化。** Cloudflare 的 code mode、skills.md、CLI 直调在 HN 主流声音里已成显学。MCP 的回应不是争辩，而是收窄自己的主场：无沙箱表面、企业权限治理、动态工具面。**协议的护城河从「连接」退守到「治理」**——这个退守是理性的，治理恰是企业付费的地方。
4. **SDK 生成化实验值得单独盯。** 「agent 从文档直接生成 MCP 代码」被官方确认为主要使用形态，于是规范 + 一致性测试成为唯一真源、SDK 变成生成产物。如果实验成功，这将是**第一个把「AI 生成代码」纳入自身发布流水线的主流协议**——协议演进速度将不再受人手 SDK 维护速度约束。

### 对做多 agent 系统的我们（可执行判断）

1. **传输层止损**：新建 MCP server 一律按无状态 Streamable HTTP 设计，不再写任何依赖协议级 session 的逻辑；存量 stdio server（我们的 lark-cli、gbrain 均是）暂不动，但「HTTP/2 over stdio」SEP 一出就评估迁移——它意味着本地 server 未来可以和远程 server 共享同一套中间件（认证、日志、缓存）。
2. **身份栈提前对齐**：现在就把「每个子 agent 一份收窄的授权」做进编排层（哪怕先用应用层 scope 字符串模拟），字段命名与语义向 RFC 8693 token exchange 靠拢——等 Agent Identity WG 出规范时我们是改适配器，不是改架构。粘贴在配置文件里的长命 API key 列入技术债清单，按「协议将淘汰」定性。
3. **工具面按「入口 + 展开」重构**：自建 MCP server 别再一次性暴露全部工具，先手工实现「小入口目录 + 按需展开」（我们 harness 侧的 ToolSearch 式延迟加载已是同构方案），等 progressive discovery 实验性扩展落地后切标准接口——**别在协议即将标准化的地方继续加码私有实现**。
4. **`tools/call` 返回值卫生**：立刻停止同时返回 `content` 与 `structuredContent` 的双轨写法（该歧义已被官方定性为待重做）；结构化输出为主、文本为降级。content annotations 不要投入——官方已放话可能弃用。
5. **轮询改事件的准备**：凡是「等 server 干完活」的场景（长任务、异步作业），把轮询逻辑隔离成可替换模块，server-initiated events（webhook/channel）落地后第一批切换——这直接省 token 与延迟双重成本。
6. **保留双路线**：有沙箱的内部 agent 继续 CLI/code mode 优先（更省上下文），MCP 留给无沙箱表面与需要权限治理的对外集成——两条路线的分界线就是「有没有代码执行环境」与「要不要细粒度授权」。
7. **要协议特性就走正门**：我们若需要协议层能力（如跨会话消息、任务编排原语），按路线图的游戏规则来——找对应 WG、把提案框进五大优先区，或先发 `experimental-ext-` 仓库。区外提案「排更长的队」是官方明说的。

## 七、接下来盯什么

- **Agent Identity WG 的组建与首批产出**（DPoP 定稿时间、SEP-1933 进展）——最高优先级信号；
- **下一个规范版本的发布时间与内容**（Tasks 是否并入核心、tools/call 新形状是否 breaking）；
- **HTTP/2 over stdio 的 SEP**——决定本地 server 生态是否大迁移；
- **progressive discovery 实验性扩展**的接口形状，以及它与各家 harness 私有懒加载的兼容性；
- **OpenAI / Google 的 SDK 是否跟进 07-28 无状态版**——事实标准的成色要看第二、第三大实现方的跟进速度；
- **human-presence attestation 是否进入正式范围**——它一旦落地，将与 FelonyBench/AISI 那条「无人值守 agent 越界」叙事直接接轨，可能成为监管抓手；
- **SDK 生成化实验的结论报告**（哪些层 codegen、哪些层模型辅助）；
- **content annotations 的生死判定**——观察一个标准如何体面地弃用无人使用的特性。
