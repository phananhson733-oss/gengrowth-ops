# dramafinds.com 旧站优化 · 技术 SEO 与流量执行方案

## 零、先说清楚：这份和上一份不是同一个题目

| | 上一份（8/15） | 本份 |
|---|---|---|
| 题目 | 我们**新建一个和它一样的站** | 我们**优化它本身** |
| 那 27,515 个剧集页 | **负债**——内容与旧站 100% 相同，我们是副本，不会被索引 | **资产**——我们就是原件，已有部分收录 |
| 主线 | 只能做视频端 + 品类词 blog | **先修架构，把已有的 2.7 万页盘活** |

**这个区别是决定性的。** 上一份说"剧集页不用抱期望"，前提是我们做副本。**在旧站上这句话不成立——那 2.7 万页是这个项目最大的一笔存量资产，而它现在几乎没在产生流量，原因不是内容薄，是架构错。**

---

## 一、核心诊断：同一部剧有两套 URL 在互相打架，而站内链接和 sitemap 各指一套

**这是本次审计最重要的发现，也是上一轮审计漏掉的。**

### 1.1 实测：同一部剧同时存在于三/四套 URL

以剧 ID `31490`（泰语）和 `21840`（韩语）为例，逐个请求：

| URL                    | HTTP | canonical | 在 sitemap 里 | 收到站内链接    |
| ---------------------- | ---- | --------- | ----------- | --------- |
| `/th/detail/31490`     | 200  | **自指**    | ✅ 是         | ❌ **0 条** |
| `/th/video-play/31490` | 200  | **自指**    | ❌ 否         | ✅ **全部**  |
| `/ko/detail/21840`     | 200  | **自指**    | ✅ 是         | ❌ **0 条** |
| `/ko/video-play/21840` | 200  | **自指**    | ❌ 否         | ✅ **全部**  |

**两套 URL 标题完全相同、内容相同、都是 `index, follow`、都自我 canonical。** 没有任何一方告诉 Google "我才是正版"。

### 1.2 站内链接一条都不指向 sitemap 里的那套

实测首页和详情页的全部 `href`：

```
首页  →  /video-play/9787, /video-play/40505, /video-play/37806 ... （共 40+ 条）
首页  →  /detail/*        0 条
首页  →  /{lang}/detail/* 0 条

详情页 → /video-play/9787, /video-play/9781 ...（推荐位）
详情页 → 其他剧的 /detail/*  0 条
```

**结论：sitemap 里提交的 27,515 个 URL，全部是孤儿页——站内没有任何一条链接指向它们。**

### 1.3 而 Google 两套都收了

搜索实证，同时出现在结果中的有：
- `dramafinds.com/ko/detail/21840` ← sitemap 里的那套
- `dramafinds.com/th/video-play/31490` ← 不在 sitemap 里的那套

**两套都在索引里，互相稀释。**

### 1.4 外加一个只影响英语的错

`/en/` 是 21 个语言里唯一的例外：

| 语言 | URL | canonical 指向 |
|---|---|---|
| **en** | `/en/detail/7875` | **`/detail/7875`** ← 去掉了语言前缀 |
| de | `/de/detail/7870` | `/de/detail/7870` 自指 ✅ |
| es / ja / th / zh-TW / ar / ru | 同上 | 全部自指 ✅ |

而 `/detail/7875`（无前缀）**是活的、200、自我 canonical，但不在任何 sitemap 里，也没有任何站内链接**。

**即：3,580 个英语页（占 13%）告诉 Google「真正的页面在另一个地址」，而那个地址既没提交也没链接。英语是最大的语言分区，却是唯一配错的。**

> ✅ 这一条我这次跨 8 个语言逐个验证过，不是从单一样本推的。上一轮我只测了 `/en/` 就写"13%"，结论碰巧对，但方法不对。

### 1.5 这解释了什么

**月访 600–1,000 这个数字，此前我们归因为"内容薄、程序化不奏效"。现在看，更可能的解释是架构：**

| 后果 | 说明 |
|---|---|
| **抓取预算对半分** | Google 要抓两套等价 URL，实际覆盖率减半 |
| **提交的 2.7 万页拿不到站内权重** | 零内链 = 零内部权重传递，全靠 sitemap 硬推 |
| **重复内容判定** | 两套自指 canonical，Google 只能自己挑，挑错就白做 |
| **分类层完全不存在** | 见 T4 |

**这几条都是可修的，而且修完影响面是 27,515 × 21 语言。这是这个项目里性价比最高的一块。**

## 二、技术 SEO 操作清单

**共 13 项，按影响面 × 修复成本排序。每项都写了现状实测值、改成什么、怎么验收。**

### P0 · 修 URL 架构（影响全站 99.8% 的页面）

#### T1 —— 二选一，定一套正规 URL

**现状**：`/{lang}/detail/{id}` 与 `/{lang}/video-play/{id}` 并存，各自指。

**改成**：**保留 `/{lang}/detail/{id}` 作为唯一正规 URL。**

**为什么选它而不选 video-play**：
1. 它已经在 sitemap 里，27,515 条，改动面小
2. `detail` 语义上是"剧集信息页"，可以承载简介 / 演员 / 集数 / 观看方式等完整内容；`video-play` 是播放器页，内容天然单薄
3. 已有收录（`/ko/detail/21840` 实证在索引中）

**具体做法**：
```
/{lang}/video-play/{id}          → canonical 指向 /{lang}/detail/{id}
/{lang}/video-play/{id}?episodesNum=N → canonical 指向 /{lang}/detail/{id}
/detail/{id}（无前缀）            → 301 到 /en/detail/{id}
```
⚠️ **不要给 video-play 加 noindex** —— 它承载真实的播放功能，加 noindex 会连带影响用户可达性判断。**用 canonical 归并，不用 noindex 屏蔽。**

**验收**：随机抽 20 个 `video-play` URL，canonical 全部指向对应 detail 页；无前缀 `/detail/*` 全部返回 301。

---

#### T2 —— 修 `/en/` 的 canonical

**现状**：3,580 个 `/en/detail/{id}` 的 canonical 指向 `/detail/{id}`。

**改成**：自指 `/en/detail/{id}`，与其余 20 个语言一致。

**这是一行模板改动**，因为其他 20 个语言的逻辑已经是对的——只有英语走了另一条分支。

**验收**：`curl -s https://dramafinds.com/en/detail/7875 | grep canonical` 返回 `/en/detail/7875`。

---

#### T3 —— sitemap 与站内链接对齐

**现状**：
```
sitemap-index.xml
  ├── sitemap.xml         44 条（9 静态 + 35 blog）
  └── drama-sitemap.xml   27,515 条，全部 /{lang}/detail/*
站内链接                    全部 /{lang}/video-play/*
```

**改成**：**把首页、详情页推荐位、分类页的链接，全部改指 `/{lang}/detail/{id}`。**

**这一项和 T1 必须一起做，单做任何一个都无效**：
- 只改 canonical 不改链接 → 2.7 万页仍是孤儿
- 只改链接不改 canonical → 两套 URL 仍在竞争

**另外**：`drama-sitemap.xml` 单文件 3.2MB / 27,515 条，**已接近 Sitemap 协议的 50,000 条 / 50MB 上限**。建议现在就按语言拆成 21 个子 sitemap 挂在索引下，便于后续在 GSC 里**按语言看收录率**——这是判断"哪个语言值得投入"的唯一可靠数据来源。

**验收**：GSC → 网页索引编制 → 按 sitemap 筛选，21 个语言各自的「已编入索引 / 已提交」比值可单独读出。

### P1 · 建可索引的分类层（现在是 0）

#### T4 —— 分类页从查询参数改为独立路径

**现状实测**：
```
/genre            HTTP 200，标题「Short Drama Genres | Romance, Thriller & More」
                  但页面里指向具体分类的链接 —— 0 条
/genre?tag=8      HTTP 200，canonical 指向 /genre
/genre?tag=3      HTTP 200，canonical 指向 /genre
```

**即：分类页全部被 canonical 归并到了一个空的 `/genre`。这个站没有任何一个可索引的分类页。**

**为什么这是大问题**：一个 2.7 万页的站，分类页是"把权重从首页分发到详情页"的唯一现实路径。现在这一层是断的——**首页 → ？ → 详情页，中间没有桥。**

**改成**：
```
/genre/{slug}         例：/genre/werewolf-romance、/genre/revenge、/genre/ceo
/{lang}/genre/{slug}  21 个语言各一套
```
- 每个分类页自指 canonical
- 列出该分类下的剧集，**链接指向 `/{lang}/detail/{id}`**
- 加入 sitemap
- 分类页做分页，每页 24–36 部，分页自指

**为什么值得**：`werewolf romance short drama`、`revenge short drama` 这类**品类词**才是这个站能排上去的词（见第四节），而承接品类词的落地页现在根本不存在。

**验收**：分类页可被直接访问、自指 canonical、在 sitemap 中、且每个分类页至少含 24 条指向详情页的链接。

---

#### T5 —— 分类页要有真实内容，不能只是一个列表

**现状**：不存在，无从谈起。

**改成**：每个分类页顶部 150–250 词的介绍（这个品类是什么、典型情节、代表作），下面是剧集网格。

**理由**：纯列表页在 Google 眼里是薄内容，容易落进"已抓取—尚未编入索引"。**这一步的成本很低（21 语言 × N 分类，可以先只做 en/es/pt/id 四个大语言），但决定分类层能不能被收录。**

### P2 · 页面级修复

#### T6 —— 给 27,515 个剧集页加结构化数据

**现状实测**：跨 8 个语言逐个检查，**剧集页 `application/ld+json` 数量一律为 0**。

**对照**：他们的 blog 页有完整的 `BlogPosting` + `Organization` + `WebPage`。

> **说明这不是不会做，是没在占全站 99.8% 的页面上做。**

**改成**，每个剧集页输出：

| Schema 类型 | 作用 |
|---|---|
| `TVSeries` | 声明这是剧集，带 `numberOfEpisodes`、`inLanguage`、`genre` |
| `VideoObject` | **最关键**——让页面有资格进搜索结果的「视频」区块 |
| `BreadcrumbList` | 首页 → 分类 → 剧名，同时强化 T4 的分类层 |
| `AggregateRating`（如有评分） | 争取星级富媒体展示 |

**🔴 `VideoObject` 是这一项里回报最高的。** 第四节的实测显示，剧名词的搜索结果**九成是视频区块**——而一个没有 `VideoObject` 的页面，连进入那个区块的资格都没有。**这是目前唯一一条"从视频结果里抢位置"的技术路径。**

**验收**：Google 富媒体结果测试通过；GSC → 增强功能 → 视频，出现有效项。

#### T7 —— hreflang（有架构障碍，单独见第三节）

**现状实测**：21 个语言，`hreflang` 标签数**全部为 0**，首页也是 0。

**这一项不能直接做**，原因见第三节。

---

#### T8 —— 修双 H1

**现状实测**：跨 8 个语言，每个剧集页都有**两个内容完全相同的 `<h1>`**。

```
<h1>The Lady Boss CEO is My Daughter</h1>
<h1>The Lady Boss CEO is My Daughter</h1>
```

**改成**：保留一个 H1，第二个降为 H2 或去掉。

**优先级实话**：这一项**对排名的实际影响很小**，Google 早已能处理多个 H1。列出来是因为它是模板 bug、改动成本几乎为零，**但不要指望它带来排名变化**。

---

#### T9 —— 首页 H1 是一部剧名，而且每次刷新都变

**现状实测**：
```
8/14 请求 → <h1>The Luna's Second Choice</h1>
8/16 请求 → <h1>Ms. CEO's Baby Daddy Is the Merchant of Death</h1>
```

**这不是写错了一次，是首页 H1 绑在了轮播组件上，跟着内容轮换。**

**后果**：首页没有稳定的主题声明。Google 每次抓取看到的都是不同的一部剧名，**无法建立"这个站是做短剧聚合的"这个认知**。而首页是全站权重最高的页面。

**改成**：固定 H1，例如 `Watch Free Short Dramas Online — Full Episodes`（与现有 title 一致），轮播里的剧名降为 H2/H3。

**验收**：连续 5 次请求首页，H1 一致。

---

#### T10 —— meta description 328 字符，而且是剧情简介直接截断

**现状实测**（`/en/detail/7875`）：

```
长度 328 字符（Google 桌面端约 155–160 字符后截断）
内容：After Matilda's only daughter, Elodie, is rescued from her kidnapper by
      local police - she is turned over to foster care and never to be seen
      again. Matilda and her son, Carson, never stopped searching for her -
      spending every last penny on posters and PI invesitgations till they
      starved. Then, after twenty long years...
```

**三个问题**：
1. 超长两倍，摘要必被截断
2. 是剧情简介，**没有任何"在哪看 / 多少集 / 免费"这类会促成点击的信息**
3. 原文有拼写错误 `invesitgations`（原始素材带进来的）

**改成模板**：
```
Watch {剧名} full episodes free online. {集数} episodes, {类型}.
{一句话钩子，≤60 字符}
```
控制在 150–158 字符。**这一项 27,515 页一次性生效，是这份清单里唯一直接影响点击率的改动。**

---

#### T11 —— 剧集页之间零内链

**现状实测**：详情页指向**其他剧详情页**的链接 = **0 条**。推荐位全部指向 `/video-play/*`。

**改成**（与 T1/T3 一并）：
- 推荐位改指 `/{lang}/detail/{id}`
- 每页增加「同类型剧集」12–16 条，链接指向同分类下的详情页
- 加面包屑：首页 → 分类 → 本剧

**这一项和 T4 是配套的**：T4 建分类页把权重往下分，T11 让详情页之间横向流通。**两个都做，2.7 万页才真正连成一张网；只做一个，效果打对折。**

### P3 · 抓取与性能

#### T12 —— 首页 462KB HTML / 222 张图

**现状实测**：
```
首页 HTML  462,087 字节
<img> 标签  222 个
原始图源    357 jpg + 159 png
next/image  516 处引用 ✅
preload     3 处
```

**这里要更正上一轮审计的一条**：我此前写"webp/avif 0 张、仅 14 张走 next/image"。**这次实测是 516 处走 next/image**——图片优化管线是接着的，Next.js 会按浏览器协商输出 webp/avif。**上一轮那个数字是错的，不作为问题项。**

**真正的问题是首屏塞了 222 张图**：移动端占该站流量约 65%，首屏一次性渲染 222 张图会明显拖慢 LCP。

**改成**：首屏保留 12–18 张，其余懒加载或改为分页 / 无限滚动。

**现状实测**：

## 三、hreflang：这一项现在做不了，得先补一张表

**21 个语言、零 hreflang，表面看是"加个标签"的事，实际上加不了。**

**原因是同一部剧在不同语言下用的是不同的数字 ID：**

```
/de/detail/7870   =  /es/detail/7876   ← 同一部剧，ID 不同
```

hreflang 要求每个语言版本互相声明对方的 URL。**而这个站的 URL 结构里没有保存"哪几个 ID 是同一部剧"这个信息**——从 URL 上看不出来，从页面上也拿不到。

**要做 hreflang，必须先有一张跨语言剧集映射表：**

| drama_key | en | de | es | th | ko | … |
|---|---|---|---|---|---|---|
| the-luna-second-choice | 7875 | 7870 | 7876 | … | … | |

**这张表在哪**：大概率在他们的内容管理库里（同一部剧引进 21 个语言时必然有一个源 ID）。**这是第五节要向对方确认的第一件事。**

- **如果有** → hreflang 是模板层的事，1–2 天
- **如果没有** → 要靠剧名 + 时长 + 集数做模糊匹配，2.7 万条，工作量以周计，且会有错配

**在拿到答案之前，T7 不排期。** 我不建议为了赶进度用模糊匹配硬上——**hreflang 配错比不配更糟**，会让 Google 把不同语言的页面判成同一页并只留一个。

## 四、流量怎么拿

### 4.1 一个重要更正：剧名 blog 是能排上去的，我上一份写错了

**上一份文档里我写过「对方的 blog 一次都没进前十」，据此建议"不要写剧名 blog"。这个结论不成立，我这次测出了反例。**

**这次的实测：**

| 查询                                                       | 他们的 blog | 位置        |
| -------------------------------------------------------- | -------- | --------- |
| `When Forever Fell Apart`（裸剧名）                           | ❌ 不在前十   | —         |
| `when forever fell apart ending`                         | ❌ 不在前十   | —         |
| `"When Forever Fell Apart" full episodes where to watch` | ✅ **在**  | **第 6 位** |
| `"Star Prison" short drama full episodes`                | ✅ **在**  | **第 9 位** |

**分界线很清楚**：

| 词型 | 前十长什么样 | 他们能不能进 |
|---|---|---|
| **裸剧名** | YouTube / Dailymotion / ReelShort 官方 + IMDb | ❌ 进不去 |
| **剧名 + `ending`** | 同上 | ❌ 进不去 |
| **剧名 + `full episodes` / `where to watch`** | 仍以视频为主，**但有内容站的位置** | ✅ **第 6–9 位** |

**机制解释得通**：他们那篇的标题是 `When Forever Fell Apart Full Episodes: She Finally Leaves...`——**标题里带了 `Full Episodes` 这个修饰词，就能排 `full episodes` 类的词；没带 `ending`，就排不了 `ending` 类的词。**

> ⚠️ **样本量说明**：修饰词形态测了 2 部剧，裸剧名 / ending 形态测了 3 个查询。**样本小，但方向一致且机制可解释。** 上一份的错误正是出在样本上——那次我只测了裸剧名和 ending，没测 `full episodes`，就下了全称结论。

**这条更正直接改变了 blog 线的判断**：不是"不要写剧名"，而是**"写剧名，但标题必须带意图修饰词"**。

### 4.2 由此得出的 blog 选题规则

**他们现在 35 篇 blog 的命名已经部分踩对了**（`bound-by-duty-full-episodes`、`god-of-pain-full-drama-cast-episodes` 都带修饰词），**但也有一半没带**（`when-the-moon-hides-her-crown`、`hate-to-love-you` 是裸剧名）。

**规则**：

| 做 | 不做 |
|---|---|
| `{剧名} full episodes` | 裸剧名做标题 |
| `{剧名} where to watch` | `{剧名} ending`（前十是视频，进不去） |
| `{剧名} cast and episodes` | |
| `{剧名} full drama free online` | |

**标题模板**：`{剧名} Full Episodes: {钩子} — Where to Watch Free`

### 4.3 品类词：这是承接量的一层，但落地页还不存在

实测 `best free short drama apps`：前十是应用商店占 5 席 + 论坛问答类结果，**但有一个内容站进去了**（Magiclight.AI）——**说明窗口存在，只是窄。**

他们已经写了一篇 `best-free-short-drama-apps`。**方向对，但只有一篇。**

**品类词的问题在于：现在没有页面承接它们。** `werewolf romance short drama` 这种词，理想落地页是分类页 `/genre/werewolf-romance`，而这个页面**根本不存在**（T4）。

**所以品类词这条线要等 T4 做完才有意义** —— 这也是 T4 排在 P1 而不是 P3 的原因。

**候选品类词方向**（每个仍须过选词三问再定）：
```
best free short drama apps        werewolf romance short drama
short drama apps without coins    revenge short drama full episodes
how to watch reelshort for free   billionaire ceo short drama
free short drama app no payment   {平台A} vs {平台B}
```

### 4.4 视频端：这条线的判断不变

同名 YouTube 频道 `@DramaFinds-q3z` 7 个月做到 **1.09 万订阅、342 个视频、4 个语言分身**，而网站月访只有 600–1,000。

**而且我逐条查过他们的视频描述——里面只有合规声明和话题标签，没有一条站链接。**

**这是一个现成的、没被利用的流量源。** 如果这个频道确实是同一方（**待确认，见第五节**），在描述里加站链接是**当天就能做、零成本**的一件事。

⚠️ **如果不是同一方**，那问题反过来：一个同名频道正在这个品类里积累认知，而域名叫 dramafinds.com——**得先弄清楚谁在蹭谁。**

### 4.5 剧集页本身：目标是收录和长尾，不是排名

那 2.7 万个剧集页，**不要指望靠它们排剧名词**（4.1 已证明裸剧名是视频主场）。

**它们的价值在于**：
1. **收录规模本身**——2.7 万页被正常收录，站点在这个品类的主题覆盖度就建立了，这会反过来抬升 blog 和分类页
2. **长尾**——21 个语言 × 剧名的各种小语种变体，单页流量极低但基数大
3. **`VideoObject` 之后的视频区块位置**（T6）——这是唯一能从视频结果里抢位的技术路径

**所以剧集页的 KPI 是收录率，不是排名。** 这一点要在立项时说清楚，否则第二个月看到"2.7 万页没排名"会被误判成失败。

## 五、开工前必须向对方确认的六件事

**前三件是阻塞项，拿不到就有工作做不了。**

| # | 要什么 | 不给会怎样 |
|---|---|---|
| **1** 🔴 | **代码库的改动权限**（或对接他们的开发） | **T1–T13 全部做不了。** 这份文档的价值 90% 在技术线上 |
| **2** 🔴 | **跨语言剧集 ID 映射表** | hreflang（T7）无法做，21 个语言各自为战 |
| **3** 🔴 | **GSC 权限** | 收录率无法测量，做完不知道有没有用 |
| **4** | **`@DramaFinds-q3z` 是不是同一方** | 决定视频端是"直接接手"还是"从零建号" |
| **5** | 内容分发权（第三方平台） | 决定视频端能不能做 |
| **6** | 他们现在 blog 的产出节奏和人手 | 决定 4.2 那套规则由谁执行 |

**第 3 项的具体用法**：拿到 GSC 后第一件事不是看流量，是看**「网页索引编制」里 27,515 个提交 URL 落在哪个桶**：

| 如果大量落在 | 说明 | 对应动作 |
|---|---|---|
| 「重复网页，Google 选择的规范网址与用户指定的不同」 | **第一节的诊断被证实** | T1/T2/T3 直接是解药 |
| 「已抓取—尚未编入索引」 | 内容被判为薄 | 需要在详情页加内容，不只是修架构 |
| 「已发现—尚未编入索引」 | 抓取预算不够 | T3 拆 sitemap + T11 建内链 |
| 大部分「已编入索引」 | **我的诊断错了** | 需重新归因，问题不在架构 |

**这一步是整个项目的分诊台，建议排在所有动作之前。**

## 八、证据强度

| 结论 | 强度 | 依据 |
|---|---|---|
| 双 URL 家族并存、互相竞争 | ✅ **高** | 4 个 URL 逐个请求，canonical / robots / 标题全部实测 |
| 27,515 个提交页零站内链接 | ✅ **高** | 首页 + 详情页全部 href 提取，0 条命中 |
| `/en/` 是唯一 canonical 配错的语言 | ✅ **高** | 跨 8 个语言逐个验证 |
| 剧集页零 Schema / 零 hreflang / 双 H1 | ✅ **高** | 跨 8 个语言，结果一致 |
| 分类页不可索引 | ✅ **高** | `/genre` 零链接，`?tag=N` 全部 canonical 到 `/genre` |
| 剧名 + 修饰词能进前十 | ⚠️ **中** | **2 部剧、2 个查询**，方向一致且机制可解释，但样本小 |
| 裸剧名进不去 | ⚠️ **中** | 3 个查询、2 部剧 |
| 品类词有窗口 | ⚠️ **中低** | **仅 1 个查询** |
| 架构问题是低流量的主因 | ⚠️ **中** | 推断合理且证据链完整，**但未经 GSC 验证**，第五节第 3 项就是为了验它 |
| 月访 600–1,000 | ⚠️ **中低** | SimilarWeb 估算，该站全球排名一千二百万开外 |

**最后一行要特别说明**：整份方案的核心论点——"低流量主因是架构不是内容"——**是推断，不是实测**。它的证据链是完整的（双 URL + 零内链 + 零分类层，任何一条都足以压制收录），**但真正的裁判是 GSC 的索引桶分布**。所以第五节第 3 项排在所有动作之前。

**如果 GSC 显示 2.7 万页大部分「已编入索引」，那我的诊断就是错的，这份方案的 P0 部分要推翻重做。** 这个可能性我认为不高，但必须先验。
