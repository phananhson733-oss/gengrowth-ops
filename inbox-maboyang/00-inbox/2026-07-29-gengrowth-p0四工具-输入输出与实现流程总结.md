# P0四工具——输入 / 处理过程 / 输出结果

## 零、先说一个分类问题（整理时发现，需要确认）

网站架构文档3.3节把P0-2（内链检查器/孤岛页面检查器）和P0-1、P0-3一起归为"GSC驱动"，这次重新梳理发现**这个分类很可能不准确**：

- P0-1（曝光/点击/CTR数据）、P0-3（历史周期对比）都是Google Search Console的Performance报表数据，**必须**走GSC OAuth，这个没问题
- P0-2要看的是"哪些页面链接到哪些页面"——这是网站自己HTML里的公开信息，不是用户的私有数据。参考团队自己给astrologywiki做的两份内链审计报告（7/13、7/23），方法都是**爬取+提取href**，不是从GSC里读的。GSC虽然也有一个内链报表，但覆盖度和更新频率都不适合做实时检测

**结论**：P0-2大概率应该跟P0-4（免费SEO审计）归成一类——**爬取型，不需要OAuth，输入URL就能跑**，不是GSC驱动。这个如果成立，P0-2的产品定位会变（可以像P0-4一样做免登录的低摩擦入口），需要工程确认爬取型方案是否可行、覆盖度够不够，再改文档。

另外还发现P0-5的输入机制跟前四个都不一样——它不需要URL/域名，需要的是关键词/主题种子词（**2026-07-29更新：加了竞品对比之后不完全成立了，见四、P0-5**）。所以五个工具实际分三类输入机制，不是文档里写的两类：

| 输入机制                         | 工具        | 需要什么                                     |
| ---------------------------- | --------- | ---------------------------------------- |
| GSC OAuth驱动                  | P0-1、P0-3 | 用户自己网站的Search Console历史表现数据              |
| 爬取驱动（免OAuth）                 | P0-2、P0-4 | 一个公开URL，抓取页面本身                           |
| 关键词库驱动 + 爬取（混合，2026-07-29更新） | 6P0-5     | 种子关键词/主题（必填）+ 用户网站URL/竞品URL（选填，用于内容缺口分析） |

**2026-07-29补充：五个旗舰工具的"一套后端、多个前端入口"模式，其实有两种不同的拆分依据，不能混为一谈**：

| 拆分依据 | 例子 | 说明 |
|---|---|---|
| 按SEO主词拆分 | P0-2（2a/2b）、P0-5（5a/5b/5c） | 后端能力完全相同，只是每个前端入口对应一个独立的真实搜索词，避免一个页面塞多个主词互相稀释排名。用户体验和输出结构基本一致，只是落地页不同 |
| 按用户心态拆分 | P0-1 / P0-3 | 底层检测引擎相同（曝光/CTR/排名异常检测），但两个工具面向的是**不同心理状态的用户**——P0-1面向"我想让网站变得更好"的主动优化型用户，P0-3面向"我发现数据掉了，想知道为什么"的被动排查型用户。这种拆分不只是SEO落地页层面的事，**产出的语气、结构、甚至具体检测重点都应该不同**，不能只是换个标题 |

以下按这个更新后的理解整理四个工具。

---

## 一、P0-1：SEO Quick Wins

### 输入（2026-07-30更新：去掉demo模式，就是一个独立工具）
- **GSC OAuth只读授权**，读取用户自己网站的Search Console Performance报表（最近28-90天，按页面+搜索词维度）——没有免登录的demo/预览模式，用户接入GSC是唯一入口

**为什么去掉demo（团队拍板，2026-07-30）**：这个设计是在主页免费SEO审计（P0-4）出现之前定的，当时的逻辑是"不想让用户先接入GSC就看不到任何东西"。现在P0-4已经承担了"接入任何数据前先证明GenGrowth有用"这个职责，而且做得更彻底——不用点进工具页、用的是用户自己的真实数据，比看别人的例子更有说服力。P0-1不需要再重复这个职责，就是一个干净的独立工具：讲清楚是什么、连接GSC、看结果，不需要demo这一层。

### 处理过程
1. 拉取GSC Performance报表，按页面聚合曝光/点击/排名/CTR
2. 计算全站曝光均值，以及"按排名区间的期望CTR曲线"作为基准（Sistrix曲线：P1~28%、P3~11%、P10~2%，AIO风险高的词按约腰斩折算）
3. 识别两类机会页面：
   - **高曝光低CTR**：排名4-20 + 曝光高于站内均值 + 实际CTR明显低于该排名区间应有水平
   - **接近突破**：排名11-20 + 近期曝光呈上升趋势
4. 对每个命中页面，生成四段式产出（见下方输出）

### 输出结果
- 机会页面清单（可排序/导出）
- 每个页面的四段式：
  - Observation：URL + 排名 + 周曝光 + 点击 + CTR（如Lamine Yamal案例：排名8.9/曝光3259/点击4/CTR 0.12%）
  - Diagnosis：为什么会这样（如"CTR远低于该排名区间正常水平，大概率Title/Meta未命中意图"）
  - Recommendation：参照同集群里CTR表现好的对标页面，给出具体改法
  - Artifact：一键生成的Title/Meta草稿 + 可导出清单
- 结果页延伸：分享扫描结果、横向推荐内链检查器、订阅"CTR变化提醒"

## 二、P0-2：内链检查器 / 孤岛页面检查器（2a/2b，同一套后端能力两个入口）

### 输入
- 一个URL/域名（按上方"零"的判断，不需要OAuth验证网站所有权）

### 处理过程
1. 从首页+sitemap.xml（如有）出发爬取站内页面，建立完整URL清单
2. 对每个页面提取所有站内`<a href>`链接（方法论参照7/13、7/23两份内链审计报告的"爬取+grep href"逻辑，只是从人工抽样改成自动化全量）
3. 建立"页面→被谁链接"的关系图，统计每个页面的入链数量
4. **孤岛检测**（2b）：入链数为0的页面标记为孤岛，按内容集群/URL模式分组（参照astrologywiki报告里"celebrity集群孤岛比例最高"这种按集群拆解的呈现方式）
5. **断链/错链检测**（2a）：爬取时发现的404断链，以及（如果能建立"内容主题↔目标页面"映射规则）内链指向不匹配的错链——错链检测的准确率依赖有没有清晰的主题分类规则，比通用断链检测更难做到高置信度，第一版可能只做断链检测，错链检测留到有更完整的内容分类体系之后

### 输出结果
- 2a（内链检查器）：断链清单 + 内链密度不足的页面清单，可导出
- 2b（孤岛页面检查器）：零入链页面清单，按集群分组，附带"建议从哪些页面补充链接过去"
- 两者都可以配四段式呈现：Observation（哪个页面、入链数多少）→ Diagnosis（为什么重要——权重传递/抓取预算浪费）→ Recommendation（建议哪些页面加链接过去）→ Artifact（内链补充建议清单）
- 承接到四步工作流"网站结构与内链"这一步

## 三、P0-3：Organic Traffic Drop Diagnosis（自然流量下降诊断）

### 输入
- GSC OAuth只读授权，且需要**至少两个时间段的对比数据**（不像P0-1只看单一时间段）——比如最近28天 vs 前28天，或者今年同期 vs 去年同期（判断季节性要用）

### 处理过程
（这套逻辑其实已经写进了Blog文章"Why Is My Organic Traffic Dropping?"的正文结构里，两边应该保持一致）
1. **排除季节性**：同期年同比，判断是不是正常的需求波动
2. **区分排名下降 vs 点击下降**：同一批搜索词对比两个周期的排名和曝光——排名没变但点击掉了，说明是CTR/意图匹配问题（跟P0-1共享同一套检测引擎，见下方"跟P0-1的关系"）；排名确实掉了，才是真正的排名下降
3. **检查可抓取性**：页面是不是变成了孤岛、或者内链被断开（这一步如果用户也开了P0-2，可以直接复用内链检查器的数据）
4. 综合归类：季节性 / 排名下降 / CTR-意图不匹配 / 抓取权限下降，四选一或组合

### 输出结果
- 受影响页面/搜索词集群的根因归类
- 四段式：Observation（下降的具体数字）→ Diagnosis（属于哪一类根因）→ Recommendation（按根因给对应的修复方向，不是统一话术）→ Artifact（可导出的诊断报告）

### 跟P0-1的关系（2026-07-29已确认，不再是待澄清问题）
P0-1和P0-3底层是**同一套检测引擎**（曝光/CTR/排名异常检测），拆成两个产品不是技术拆分，是**用户心态拆分**：
- **P0-1（SEO Quick Wins）**：面向主动想让网站变好的用户——"我想优化，找机会"，产出语气是"这里有几个容易改善的地方"
- **P0-3（Traffic Drop Diagnosis）**：面向发现数据下滑、想搞清楚原因的用户——"我的数据掉了，帮我查一下"，产出语气是"我们查了三种可能，结论是……"

两者共享检测引擎，但**入口问题、结果呈现的语气和结构应该不同**，不是同一套UI换个标题：P0-1可以是一个持续可查的"机会清单"，P0-3更适合是一次性的"诊断报告"（有明确的根因结论，不是清单式罗列）。文案团队写这两个工具的落地页/结果页时要按这个区分来写，不能照抄同一份文案改几个词。

## 四、P0-5：关键词研究/聚类/话题集群（5a/5b/5c，同一套后端能力三个入口）

### 输入（2026-07-30再更新：从"对比竞品内容缺口"改成"从产品卖点AI发散"，机制换了）
- **种子关键词或主题描述**（选填——如果提供了网站URL，AI可以直接从网站内容出发，不强制要求先给种子词）
- **用户自己网站URL**（核心输入，2026-07-30起从"选填的缺口比对信号"升级为主要输入）——用来让AI理解产品/服务到底在卖什么、差异化在哪
- **竞品网站URL**（选填，降级为辅助参考信号，不再是核心机制——原因见下方）
- 不需要OAuth；URL相关的部分走爬取，跟P0-2/P0-4是同一类机制

### 为什么把"对比竞品内容缺口"降级、换成"从产品卖点AI发散"（2026-07-30，团队顾虑后调整）
Ahrefs/Semrush已经把"Content Gap"做成独立命名功能在卖多年，这个品类的搜索词大概率也是红海——跟"free seo audit tool"当年被Semrush博客占位、"striking distance keywords"被证实无量是同一种结构性问题（执行计划3.0节反复验证过的结论：跟大品牌拼同一个品类名，新进入者结构性打不过）。更关键的是，**对比竞品内容缺口这个机制本身天花板也低**——找到的都是"竞品已经想到、已经做过的东西"，没有真正的差异化，只是抄得比较快。

**改成的机制**：AI爬取用户网站后，提取的不是关键词，是**产品卖点/差异化功能/目标用户群体**这类更高层的信息，然后基于这些卖点反向发散关键词和自然语言问法——找的是"这个产品的独特角度，还没人系统性地在内容里覆盖过"，不是"竞品覆盖了但你没有"。这才是原名"关键词+**Prompt**机会地图"里"发散"两个字真正应该做的事，也更贴合GenGrowth不做红海通用工具的定位。竞品URL还可以留着，作为"确认这个角度确实还没人做"的辅助校验，不再是主机制。

### 处理过程
1. 爬取用户网站，提取页面文案/产品说明
2. **AI分析步骤（核心，新增）**：从爬取内容里提炼产品的卖点、差异化功能、目标用户群体、典型使用场景——这一步不是关键词提取，是理解"这个产品跟别人有什么不一样"
3. **AI发散步骤（核心，新增）**：基于第2步提炼出的卖点，发散候选搜索词和自然语言问法（既有传统Google式短词，也有人会问ChatGPT/Perplexity的自然语言问法，呼应GEO定位）
4. （可选）如果提供了竞品URL，爬取后做粗粒度覆盖比对，作为"这个角度是否已经被别人占了"的参考信号，不作为发散的主要来源
5. **强制校验（不可省略）**：第3步AI发散出来的所有候选词，必须过真实搜索量/KD/CPC数据校验，过滤掉零搜索量的臆造词——这一步照搬"seo quick wins"七轮查证里第2轮的教训（"GSC quick wins finder"这类内部造词，无论听起来多合理，没有真实搜索行为支撑就不能用）
6. 通过校验的词，按语义相似度/搜索意图聚类分组（5b：关键词聚类工具的输出）
7. 聚类结果映射成建议的网站结构（哪些该做主题页、哪些该做支撑内容、彼此怎么互链）（5c：话题集群工具的输出，通常是可视化的气泡图或层级树）

### 输出结果
- 5a：带搜索量/难度/CPC的优先级关键词清单，**每条都带"发现依据"标签**（传统关键词扩展 / 基于产品卖点AI发散 / 竞品参考），可导出——这个标签本身也是一种可信度设计，用户能看到"为什么AI觉得这个词值得做"，不是黑箱推荐
- 5b：关键词按集群分组，附建议集群名
- 5c：可视化话题地图/建议站点结构
- 承接四步工作流的"关键词库"+"网站结构与内链"两步

### ⚠️ 需要确认的问题一：AI发散出的候选词，校验环节的数据源和成本
第5步"强制校验"需要真实的关键词数据源（搜索量/KD/CPC），这是这个工具的核心边际成本来源——AI发散候选词本身成本可控，但每个候选词都要查一次真实数据，量一大成本会上升。需要产品/工程确认数据源用哪家、免费层每次扫描允许发散+校验多少个候选词。

### ⚠️ 需要确认的问题二：P0-5要不要用四段式结果模块
P0-5是**生成/规划类工具**，不是"发现问题"的诊断类工具——跟P0-1/P0-2/P0-3那种"扫描出一个具体问题"的逻辑不一样。四段式结果模块（Observation/Diagnosis/Recommendation/Artifact）是不是也适用于P0-5，还是应该用一套不同的输出结构？参照之前跟aimusic.fm对比时的结论（7.4节）：生成类工具本来就不需要四段式，这一点在P0-5上可能也适用——"发现依据"标签某种程度上承担了Observation的角色（AI从哪里看出这个机会），但不需要完整套用Diagnosis/Recommendation/Artifact这套诊断类工具的结构。
