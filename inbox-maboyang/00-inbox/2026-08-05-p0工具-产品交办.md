### 第 3 条的细节 · P0-1 的三层命名（上司 2026-08-06 已定）

**背景**：命名调研确认 `SEO Quick Wins` 的 SERP 是「快速提升 SEO 的技巧清单」类文章，不代表用户在找一个 GSC 数据分析工具。已实测的搜索量：

| 词 | 月搜索量 |
|---|---|
| `gsc quick wins` | **0** |
| `google search console quick wins` | 零自动补全 |
| `google search console tool` | 约 390 |
| `search console tool` | 约 8,100（过于宽泛） |
| **`high impressions low clicks`** | **约 70 / KD 0 —— 目前唯一已验证能打的任务词** |

**决策：三层分开，各司其职。**

| 层 | 内容 |
|---|---|
| **产品卡片 / 正式名** | `GSC Opportunity Finder` |
| **SEO Title** | `High Impressions, Low Clicks in GSC? Find Pages to Fix` |
| **H1** | `Find SEO Opportunities in Google Search Console` |
| **辅助文案** | `Turn high-impression, low-click queries and positions 8–20 into a prioritized action list.` |

`SEO Quick Wins` **保留在社媒标题、内容专题与卖点中**，例如：*Find your SEO quick wins from real Search Console data.*

**与当前线上的差异：**

```
Title  当前  SEO Quick Wins from Search Console — GenGrowth
       改为  High Impressions, Low Clicks in GSC? Find Pages to Fix

H1     当前  High impressions, low clicks
       改为  Find SEO Opportunities in Google Search Console

卡片   当前  SEO Quick Wins
       改为  GSC Opportunity Finder
```

> ⚠️ **一处需要留意**：主词 `high impressions low clicks` 目前只在 H1 与正文里，改动后**移到 Title**（更强的信号），但 H1 里不再有精确匹配。这是净改善，但上线后建议观察该词的排名变化。

> 📌 页面卡片改名的理由是**功能理解、ICP 筛选与产品命名统一，不是因为这个名字搜索量更大**（`GSC Opportunity Finder` 的 exact volume 预计很低）。未来可补测 `striking distance keywords`——它已是多个工具使用的成熟任务表达（Aergos、GSCdaddy），但目前缺本项目的可靠搜索量数据，**不宜直接替换主标题**。

### 第 7a / 7b 条的细节 · 让 P0-4 成为授权漏斗的第一级

**背景**：P0-4 明确声明不给评分、不给修复清单、不给优先级（落地页 + FAQ 03/04 + 结果区各申明一次）。**这个立场是对的，不建议改**——「先修哪三个」里的"哪个最重要"需要知道哪些页面真的有排名和流量，而 P0-4 结构上不连 GSC，说了就是编。

**但「先修哪三个」有两种含义，只有一种需要 GSC：**

|---|---|---|
| 修哪三个能带来最多流量 | 排名、曝光、点击 | ❌ 结构上不可能 |

**7b 的收尾文案**（放在结果区末尾，替代当前直接进入 FAQ）：

```

我们无法告诉你先修哪一个 —— 那需要知道哪些页面真的有排名
和流量，而那只存在于你的 Search Console 里。
```

### 第 8 条的细节 · 重复检测必须看 canonical ⚡这是正确性缺陷

**实测（2026-08-06，astrologywiki 630 页）**：P0-4 报 `Repeated title text 105 / 630`。逐条核实后，**105 个全部是假阳性**：

| 分类 | 数量 | 实际状态 |
|---|---|---|
| `/wiki/X` + `/en/wiki/X` 配对 | 约 96 | ✅ canonical 已收敛到 `/en/wiki/X` |
| 共用首页标题的 URL | 7 | ✅ canonical 已收敛到 `/` |
| **真实的重复标题问题** | **0** | |

核实命令：

```bash
for u in aries jupiter house-1; do
  for p in "/en/wiki/$u" "/wiki/$u"; do
    echo -n "$p → "
    curl -sL "https://www.astrologywiki.com$p" \
      | grep -oE '<link rel="canonical" href="[^"]*' | sed 's/.*href="//'
  done
done
# 两者均输出 https://www.astrologywiki.com/en/wiki/<u>
```

旁证：sitemap 只含 `/en/wiki/`（395）与 `/zh/wiki/`（126）；首页 12 条 wiki 内链全部指向 `/en/wiki/`；Google 实际收录的也是 `/en/wiki/aries`（已在 GSC 确认）。

**关键点：工具自己有一条 `Canonical target differs 70/630` 的记录**——它知道这些页面 canonical 指向别处，**但重复检查没有用这个信息**。

**修法**：

| 方案 | 做法 |
|---|---|
| 最低限度 | 分开计数：`105 observed, of which 105 canonicalised elsewhere` |
| **推荐** | 检测重复前先按 canonical 归并；仅当多个 URL **各自 canonical 指向自己**且标题相同时才计为重复 |

推荐方案**不改变产品立场**——按 canonical 归并仍是"记录观察到的事实"，只是把 Google 已声明的规范关系纳入观察范围。

`Repeated meta-description text 107/630` 几乎肯定同源，须一并修。

> **为什么这条比排序、徽章那些严重**：那些让人看不清，这条让人看到假的。一个产品把"只记录实际观察到的事实"当立身之本，却在一个处理正确的站点上报出 105 个不存在的问题。

### 第 9 条的细节 · 页面级证据按分组渲染

展开 `Repeated title text` 后，每个 URL 单独成块：

```
https://www.astrologywiki.com/en/wiki/aries
  TITLE TEXT      Aries
  MATCHING PAGES  2

https://www.astrologywiki.com/wiki/aries
  TITLE TEXT      Aries
  MATCHING PAGES  2
```

**105 行只对应 50 个不同标题**，每行把相同标题与相同计数重复一遍。

`MATCHING PAGES: 2` 证明**分组已经算出来了**，只是展示时拍平。按组渲染应为 50 行：

```
Aries                                    2 pages
  /en/wiki/aries  ·  /wiki/aries
```

**后果**：这条记录里最重要的信息——「每个词条页存在两个 URL」——在当前展示下看不出来。这个模式是把 105 行提取出来做分组之后才发现的。

### 第 5c 条的细节 · 折叠状态绑定到已有标签

**不需要引入新的判断标准。** 产品在结果区已经给每一块内容打好了证据标签，直接把折叠状态绑上去：

| 产品已有的标签 | 折叠状态 |
|---|---|
| `Observed` | 默认展开 |
| `Hypothesis` | 默认折叠（标签已经在了，只是现在和 Observed 一样铺开） |
| `Data boundary` / `Cannot check` / `did not run` | 收进统一折叠区「我们没能查的（N 项）」 |

## 二、需要确认的三个状态问题

### Q-A · OAuth 应用当前是 Testing 还是 In production？（建议优先，两分钟）

P0-1 页面文案写的是「consent screen is published」，据此应为 production。但需在 Google Cloud Console 中确认。

**如果实际仍在 Testing 状态，问题严重得多**：Testing 模式限 100 个白名单测试用户，且 refresh token 7 天强制过期——「7 日留存 10 人」这一核心指标会从机制上无法达成。

**这是唯一一个可能推翻推广方案指标层的确认项。**

### Q-B · `webmasters.readonly` 被 Google 归入哪一档？

核查授权跳转，我们请求的 scope 为：

```
openid + email + profile + https://www.googleapis.com/auth/webmasters.readonly
```

Google 的权限分三档，审核成本差异极大：

| 档位 | 例子 | 审核要求 |
|---|---|---|
| Non-sensitive | email、profile | 无需审核 |
| **Sensitive** | **Search Console** | 人工审核 + 演示视频，数天至数周 |
| Restricted | Gmail、Drive 全量 | 上述全部 + 第三方安全评估（CASA），数月 + 数千美元 |

`webmasters.readonly` 应属中间档，即**无需 CASA 的较快路径**。但请在 Cloud Console 中确认实际归档——若被归入 restricted，时间与预算量级完全不同，整个种子招募排期需要重排。

### Q-C · P0-3 里「Average position is impression-weighted」这句措辞对吗？

P0-3 结果区的 `Do not do` 有一条：

> **Do not chase a rankings recovery because average position went up**
>
> **Average position is impression-weighted.** When high-ranking queries disappear the number rises on its own, without any of your pages having moved.

**建议的动作是对的**，而且对当前 astrologywiki 的处境完全适用（曝光 -76%，大量查询消失）。

但 `impression-weighted` 这个定性**与我们此前的记录冲突**——我们记的是 GSC 均位为按查询平均而非按曝光加权，并且当时把它列为「我们踩过的统计陷阱」。

**我无法确定哪一边对，因此不下结论。请对着 Google Search Console 官方文档核一次这句措辞。** 这是产品里一条明确的「不要做」，措辞错了会误导用户，而核实成本极低。

## 四、🔴 OAuth 持续授权（第 10 条的细节）

**2026-08-06 状态变更**：本节原标题为「一项不必改、但需知晓其代价的设计」。**上司已判定它属于产品启动门槛，须在扩大招募前处理**，因此升级为必做项第 10 条。

### 4.1 现状

核查授权跳转参数：

```bash
curl -s -i "https://gengrowth.ai/api/auth/google/start?scope=gsc&next=%2Ftools%2Fseo-quick-wins" \
  | grep -i "^location"
```

Location 中含 **`access_type=online`**，即**不签发 refresh token**。access token 约一小时后失效且不可续期。

**实测印证**：2026-08-05 授权后跑通 P0-3，约一小时后再访问，页面已回到未授权门。

### 4.2 为什么是门槛

用户下次访问须从头再走一遍完整授权流程，**包括那个 Google 未验证警告页**。

这直接决定第四个核心指标：

> **7 日留存人数**：首次使用后 7 天内回来，完成第二次有效运行、复查或保存动作 —— 目标 10 人

第 7 天回访的用户面对的不是"打开即用"，而是完整重新授权 + 再点一次 `(unsafe)`。

### 4.3 需要产品侧判断的取舍

`access_type=online` 与产品「什么都不存」的定位是自洽的——不留存数据，自然不需要长期凭证。改为 `offline` 会引入 refresh token 的存储与吊销管理。

**两条路，请产品侧选：**

| 方案 | 做法 | 代价 |
|---|---|---|
| **A** | `access_type=offline`，服务端加密存储 refresh token，提供显式断开入口 | 需要凭证存储与吊销管理，与"什么都不存"的对外表述需要重新措辞 |
| **B** | 保持不存 token，但延长会话有效期 / 在会话内静默续期，仅在跨天回访时才要求重新授权 | 实现较轻，但无法完全消除 7 日回访的重新授权 |

**上司的判定是"应在扩大招募前处理"，没有指定方案。** 建议按 A 做——B 无法真正解决 7 日留存这个指标场景。
