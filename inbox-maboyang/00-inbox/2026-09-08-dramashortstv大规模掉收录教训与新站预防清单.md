# 一、发生了什么（简要还原）

dramashortstv.com 当时在做一次 URL 结构迁移：旧结构 `/detail/[id]`、`/video-play/[id]` 换成新结构 `/[locale]/drama/[slug-哈希]`、`/[locale]/watch/[slug-哈希]/[集数]`。迁移切换后出现三个叠加的问题：

1. **Google 已收录、正在拿真实点击的旧 URL 直接返回 HTTP 500**（不是 404，不是重定向，是应用报错）。受影响最重的是当时贡献全站约 90% 点击的一部剧的播放页和详情页
2. **两个 sitemap 同时返回 500**，Google 没法用 sitemap 重新发现或验证任何页面
3. **即便后来 URL 修好了，播放页（真正承载 63% "视频"类型点击的页面类型，约 30 万条）从一开始就没有进过 sitemap**，Google 只能靠从详情页的集数链接一层层爬过去发现，收录速度天然更慢

三个问题叠加的结果：GSC 数据显示故障期间 24 小时窗口点击从平时的量级跌到接近零。流量当时高度集中在极少数页面上（一部剧占了九成），这几个页面一旦出问题，几乎等于全站失血。

# 二、技术根因：核实到的部分 vs 无法核实的部分

## 2.1 表面结论（同事报告原话）

500 故障的说法是：`permanentRedirect()` 往 `Location` 响应头里塞了非 ASCII 字节（西里尔字母、泰文、日文等 slug），触发 Node.js 的 `ERR_INVALID_CHAR` 报错。

这个机制本身是真实、可查证的通用规律，不是编出来的——**HTTP 头的取值范围本来就被 RFC 7230 限制在 ASCII 可见字符 + 空格/制表符**，任何非 ASCII 字符不经编码直接塞进 `Location` 这类头，本来就是不合规的响应。Node.js 的 `http` 模块碰到这种情况会直接抛 `ERR_INVALID_CHAR` 拒绝发送，这是运行时在正确拦截一个本就不合规的响应头，不是 Node 挑剔或者这个项目特有的怪癖——**任何语言、任何框架，只要把没编码的 Unicode 字符串塞进 Location 头，都会撞上同一类问题**，只是有的运行时选择直接报错（比如 Node），有的选择静默发送畸形字节（更隐蔽、更难排查）。这一条是可以放心当作通用工程常识来用的。

## 2.2 核实后发现：表面结论没能解释全部现象

重新查了原始故障清单和实测记录，发现一个和"非 ASCII 触发报错"这个说法对不上的矛盾：

| URL | 语言/文字系统 | 当时是否 500 |
|---|---|---|
| `bg/detail/38000` | 保加利亚语，西里尔字母 | ✅ 500 了 |
| `vi/detail/59699` | 越南语，拉丁字母+变音符号 | ✅ 500 了 |
| `ar/detail/41112` | 阿拉伯语，阿拉伯字母 | ❌ 没有 500，308 正常跳转 |
| `it/detail/34803` | 意大利语，拉丁字母 | ❌ 没有 500，308 正常跳转 |

阿拉伯字母显然也是非 ASCII 字符，如果"非 ASCII 触发报错"这个说法是全部真相，阿拉伯语这条不应该是例外。

进一步核实：现在重新测阿拉伯语这条，重定向目标是 `/ar/drama/%D8%A5%D8%BA%D9%88...`——**percent-encoding 是正确的，而且这个正确性在故障期间就已经是这样，不是修复之后才变对的**。同时抽查了全站非拉丁语言页面（保加利亚语、阿拉伯语、韩语、越南语）的 canonical、hreflang、正文内链，**这几类页面渲染路径上的编码从故障期到现在，一直都是正确的，没有出过问题**。

**这说明真正的故障面比"非 ASCII 字符触发报错"这个笼统结论窄得多**：页面渲染这条路径用的 URL 构造逻辑，和触发 500 的旧版重定向逻辑，走的根本不是同一套代码；前者从头到尾正确，后者只在部分记录上出错，而且出错与否和"是不是非拉丁语言"没有干净的对应关系。

**无法核实的部分**：具体哪些记录会触发、哪些不会，现在故障现场已经不在了（记录已修复，也拿不到服务端日志），没法百分百还原当时的字节级细节。比较合理的猜测是重定向逻辑是后补的兼容层，写的时候没有复用页面渲染那边已经验证过的编码函数，自己重新拼了一遍 URL 字符串，具体哪批数据踩中和数据本身的历史（比如是不是经过某次特定的迁移脚本）有关——但这一层猜测没有证据支撑，不写成结论，只作为下面防范措施的参考方向。

# 三、新站怎么彻底避免

不管当时具体是哪个字节触发的，"重定向逻辑自己拼 URL 字符串、不复用页面渲染那套已验证的编码工具"这件事本身就是错误做法。新站要从架构上直接堵死这条路，不能指望"记得测非英文字符"这种容易被漏掉的人工检查项。

1. **全站只能有一个函数负责"把 locale + slug + 集数拼成 URL"**。页面渲染、sitemap 生成、canonical/hreflang 标签、以及未来任何可能出现的重定向/兼容逻辑，全部必须调用同一个函数，不允许任何代码路径自己用字符串拼接的方式单独构造 URL。dramashortstv 这次出问题的根子，大概率就是重定向这条路径没有复用主渲染路径已经验证过的那个函数

2. **这个唯一的 URL 构造函数内部强制调用 `encodeURIComponent()`**（或框架对应的编码方法），对每一个动态拼进 URL 的片段都编码，不允许"这个字段应该是安全的所以跳过"这种侥幸判断

3. **CI / 发布前检查必须包含真实非英文 slug 的重定向端到端测试**，不能只单元测试编码函数本身。这类问题在本地跑一次真实的西里尔文/阿拉伯文/泰文重定向请求就能 100% 复现，不需要等上生产环境才发现——既然 Node 会直接报错而不是静默出错，这本来就是一类"测了就一定能抓住"的问题，抓不住只是因为没测

4. **未来如果新站也需要做类似的旧 URL 兼容重定向（改版换 slug 规则大概率会发生），这类"补丁性质"的代码要格外小心走查**。从这次的经验看，故障不是发生在主流程里，是发生在这种事后补的兼容层里——写的时候最容易图快、绕开已有工具函数，代码评审时应该把"是否复用了统一的 URL 构造函数"当成这类改动的强制检查项
