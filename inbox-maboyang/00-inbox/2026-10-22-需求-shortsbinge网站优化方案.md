# 需求 · shortsbinge.com 网站优化方案

## 一句话结论

基础技术扎实：SSR 内容完整、canonical 基本干净、404 正确、schema 覆盖广、图片基本都有 alt、移动端无横向溢出。当前最优先要处理的是**抓取量骤降**和**响应时间异常**这两个关联问题，其次是**国际化**（hreflang 缺失、本地化半翻译），但国际化相关的几项工作需要先确认**剧目版本映射关系是否准确**（见第 8 项），不要跳过这一步直接批量生成互链。部分条目标注了"待确认"，提交审核时请重点核实这几项再排期，不要直接按字面执行。

## 一、抓取健康与响应时间（P0，最高优先级）

### 1. 抓取量骤降

抓取请求量从 10-11 起从日均千余次骤降到个位数到几十次，截至 10-19 GSC 导出仍未恢复：

| 日期 | 抓取请求 |
|------|----------|
| 10-09 | 8,365 |
| 10-10 | 1,301 |
| 10-11 | 59 |
| 10-12 | 78 |
| 10-13 | 80 |
| 10-14 | 7 |
| 10-15 | 24 |
| 10-16 | 11 |

**已确认**：
- 不是 Vercel Bot Protection 拦截 Googlebot——Live URL 测试通过，首页抓取、渲染、索引均正常。
- 4XX 明细 954 条样例全部是 `/api/play/{剧目ID}/{集数}/` 请求锁定付费集（集数 8、12、17、27 这类），时间戳集中在 10/8（10/9 修复 PR #142 上线之前），属于历史遗留，不是当前持续发生的问题。
- robots.txt 的 `Allow: /api/play/` 例外**保留，不要删除**——这是免费第 1 集视频能被 Googlebot 渲染识别的必要条件，删掉会连第 1 集视频也一起挡住。

**需要技术同事确认**：
- 非授权 403 命中率在 10/9 修复后是否已降到接近 0（排除团队自己写 blog 时的调用：10/16 No More Backing Down `nh3qscvkdwig` 第1–7集、10/19 Taming My Bullies `djfncnmzxyam` 第1–18集、How to Tame Your Bully `gl7brtsjuo2w` 第1集、Where My Love Went Wrong `chfxhaefilog` 第1–11集）。
- 按路由拆分的函数响应时间长尾是否准确、是否是抓取量骤降的真正原因（见下方第 2 项）。

### 2. 响应时间异常

GSC 测到的"平均响应时间"从事发前（09-16~10-05 加权平均约 **171ms**，61,220 次请求）飙升到 10-12~10-19 区间普遍 900~2,400ms：

| 日期 | 请求数 | 平均响应时间(ms) |
|---|---|---|
| 10-09 | 8365 | 338 |
| 10-10 | 1301 | 200 |
| 10-11 | 59 | 371 |
| 10-12 | 78 | 1019 |
| 10-13 | 80 | 1971 |
| 10-14 | 7 | 964 |
| 10-15 | 24 | 2374 |
| 10-16 | 11 | 439 |
| 10-17 | 46 | 922 |

**已确认**：
- Vercel 边缘 ISR 缓存实际在生效（`x-vercel-cache` 实测 HIT/STALE，age 最高超 10,000 秒），不是"没有 CDN 缓存"的问题；`cache-control: max-age=0` 只是面向浏览器的指令，不代表后端每次都裸查数据库。
- 响应慢集中在页面的下载/流式传输阶段，不是 TTFB（首字节前等待）。页面解压后体积约 300~800KB，其中 Next.js RSC 流式载荷占比可达 50%+，是渲染需要陆续"流"过来的内容。
- 跟 NetShort（同架构、同页面体量的竞品）对比，方向上 shortsbinge 明显更慢更不稳定，但精确倍数样本不足，不能作为量化承诺引用。

**需要技术同事确认**（这是目前最具体、最可能直接定位根因的线索）：

按路由拆分的 Vercel 函数响应时间（10/13~10/20 窗口，UA 过滤 `Googlebot/2.1`）：

| 路由 | 函数调用数 | TTFB p50 | TTFB p95 |
|---|---:|---:|---:|
| `/sitemap/[shard]` | 136 | 3.3秒 | **47.5秒** |
| `/[lang]/best-short-dramas/[slug]`（blog文章页） | 7 | 23.8秒 | 28.9秒 |
| `/[lang]/drama/[slug]/episode/[episode]`（单集页） | 54 | 0.8秒 | 18.9秒 |
| `/[lang]/drama/[slug]`（剧目详情页） | 14 | 1.0秒 | 1.7秒 |
| `/api/play/[dramaId]/[episode]` | 64 | 0.05秒 | 0.35秒 |

如果这组数字准确，**sitemap 分片生成和 blog 文章页才是真正的慢路由**，`/api/play/` 反而是最快最稳定的一个。代码排查入口：`sitemapShardResponse` 调用 `sitemapShards` 构造全站分片集合。请彪哥先确认这组数据准确性，再决定是否作为排查主线。

另需核实：抓取量骤降（10-11）和响应时间明显跳升（10-12）的先后顺序——现有数据显示降速先于延迟暴涨一天，需要按小时粒度核实真实顺序，决定两者是因果关系还是共同的上游原因。

### 3. 抓取请求构成核查

10-19 导出的文件类型分布：HTML 39.51%、其他文件类型 30.14%、JSON 9.55%、JavaScript 3.41%、未知（请求失败）16.91%。HTML 只占四成。

**需要技术同事确认**：这些"其他文件类型/JSON"请求具体是什么——按内部日志的另一个窗口（9/20-10/5）看，单集模板请求 8,655 次、`/api/play/` 播放接口 7,548 次、剧目详情模板只有 138 次，说明抓取量主要消耗在观看链路（单集页+播放接口）上，这部分本身就是正常的渲染依赖，不是"非 HTML = 预算浪费"。在没有查清具体 URL 模式之前，**不要直接加 `Disallow: /*?_rsc=` 这类规则**，避免误伤播放页渲染需要的正常请求。

**需要做的事**：在 Vercel 日志里按 URL 模式拆分这部分请求（RSC 请求 `?_rsc=`、API、静态资源各占多少），确认有没有真正无意义的重复/冗余请求，再决定要不要新增抓取限制规则。

### 需要做的事（按优先级）

1. 核实第 2 项的函数响应时间长尾数据，确认 `/sitemap/[shard]` 和 blog 文章页是否为真正瓶颈，这一步优先于下面几项
2. 查服务端日志，按小时粒度核实抓取量骤降和响应时间跳升的先后顺序
3. 按 URL 路由类型和状态码拆分响应时间分布，不要只看全站聚合均值
4. 按第 3 项的要求，在 Vercel 日志里拆分非 HTML 请求的具体构成
5. 如确认 `/sitemap/[shard]` 是瓶颈，排查分片生成逻辑；检查高流量页面的数据拉取是否可并行化（`Promise.all` 替代串行等待）
6. 检查数据库查询索引、是否有冗余字段拉取；检查 Vercel 函数区域和数据库区域是否一致
7. 对比真实用户（Vercel Speed Insights/GA4）和 Googlebot 的响应时间，判断问题是否只发生在爬虫侧

### 验收标准

- GSC 平均响应时间回落到 171ms±20% 附近（p75 口径），并标注样本量
- 同一高流量页面固定方法重复采样（同测试机/时段/至少20次），下载阶段中位数明显收窄，不再频繁出现 2,000ms 以上异常值
- 抓取请求总量 2-4 周内逐步回升（滞后观察指标，不单独作为达标依据）

## 二、国际化（P0-P1）

### 4. 详情页缺 hreflang 标注

剧集详情、单集详情、文章页、语言列表页**没有 `<link rel="alternate" hreflang>`**，只有 `<a hreflang>`（语言切换链接，Google 不认这个做 hreflang 集群）：

| 页面类型 | `<link hreflang>` | `<a hreflang>` |
|----------|-----|----|
| 首页/trending/browse/genre | 20条（19语种+x-default） | — |
| best-short-dramas 列表 | 11条 | — |
| 剧集详情 | 0条 | 20条 |
| 单集详情 | 0条 | 19条 |
| 文章页 | 0条 | 19条 |
| 语言列表页 | 0条 | — |

语言切换链接本身也不完整：EN 剧集详情 18 个链接指向各语种首页而非对应译文；JA 单集详情的 `en` 链接指向首页而非对应英文单集。

本地化规模（sitemap 实测）：EN 4,715部/9,430条URL，JA 2,018部/4,036条URL，PT 1,672部/3,344条URL。

**影响范围待重新评估**：此前曾用 10/5-10/11 的 GSC 展示数据（日语那周只有3个页面/4次展示）来论证"hreflang 缺失已造成展示量归零"，但核对日语剧目 sitemap 发现 84%（3,906/4,660条）的 lastmod 是 10/13——测量那一周大部分日语页面还没上线，不能用来证明 hreflang 缺失的后果。**缺 `<link hreflang>`、语言切换链接指错地方这两个现象本身属实**，但具体业务影响需要用新的 GSC 数据重新评估。

**需要做的事**（前端，1–3天，**开始前请先确认第 8 项版本映射关系核查已完成**）：

在剧集、单集、文章模板里输出完整的 `<link>` 集群，只包含真实存在的译文：

```html
<link rel="alternate" hreflang="en" href="https://shortsbinge.com/drama/xxx/" />
<link rel="alternate" hreflang="ja" href="https://shortsbinge.com/ja/drama/yyy/" />
<link rel="alternate" hreflang="x-default" href="https://shortsbinge.com/drama/xxx/" />
```

要求：每个页面包含自己（self-referencing）；所有译文互相指向（否则整对被忽略）；只列 200、可索引、canonical 自指的译文；`x-default` 指向英文页；修复语言切换到对应译文详情页而非首页；用 Rich Results Test 验 3-5 个页面。如果维护成本太高，至少给"已翻译且有点击"的剧集加，其余译文考虑 `noindex` 或 canonical 到英文。

建议和下面第 5 项合并排期。

### 5. 本地化模板半翻译

19 个 locale 首页 title/H1 内容仍是英文（示例：`/ja/` title "ShortsBinge for Japanese Viewers — The Short Dramas Worth Your Time"，H1 "Your Next Binge Is Already Here"）；剧目详情页的页脚、面包屑、"Watch episode 1 free" 按钮、类型标签（Romance/Taboo 等）也是硬编码英文。

**需要团队先确认这是不是当前仍然有效的产品决定**：title 实际按受众语言做了模板化差异（"for Japanese Viewers" vs "for Portuguese Viewers"），英文 UI 本身可能是此前已有的产品方向。但不论归类为哪一种，**正文核心内容未翻译成目标语言**这个事实本身没有争议。

**如果确认要做，修复范围**（内容+前端，先做4个优先语种）：

1. 优先语种：**日语（ja）、繁体中文（zh-TW）、西班牙语（es）、阿拉伯语（ar）**——业务侧已确定，且和 GSC 数据吻合（zh-TW 有表现最好的单页之一；阿拉伯语 CTR 全站最高但排名最差，供给不足需求强）
2. 本地化范围：`<title>`、meta description、H1、副标题、导航、按钮、"Episode N"、"X episodes"、页脚、面包屑、类型标签
3. 保留品牌名 `ShortsBinge`，只翻译价值主张
4. 同步 `og:locale`、`html lang`、schema `inLanguage`
5. 没有流量、翻译质量差的语种考虑 `noindex`，不要为了覆盖语种数量而铺薄页

### 6. hreflang 输出逻辑核查 + Sitemap 承载方式确认

同一站点，hreflang 只在静态页/best-short-dramas 列表输出，详情/文章/语言列表页完全没有；41 个子 sitemap 的 `xhtml:link` 数量为 0。

**需要技术同事先核对现状，不要直接按"统一组件"去开发**：彪哥方反馈 `seo.ts` 里已经有一套按"栏目+可用语言集合"生成 hreflang 的共享构造，详情/文章页没有输出，不一定是遗漏，可能是页面不在语言集合内、noindex 或集合不足这几种情况下的设计内行为——如果是这样，直接要求"每页统一输出 N 条"会跟已有的两条规则冲突（纯英文补位列表和自有内容列表的索引资格不同；分页页面不发 hreflang）。

**需要技术同事做的事**：
1. 确认现有共享构造的输出规则（哪些情况下应该有、哪些情况下不该有），核对详情/文章页"没有输出"是不是真的符合预期
2. 如果核对后发现有本该生成却遗漏、或互链关系断开（A 指向 B 但 B 没指回 A）的情况，按具体缺口修，不是整站推翻重做
3. Sitemap 的 `xhtml:link` 和 HTML `<link>` 两种承载方式，确认是否需要都做，还是选一种作为主要机制——如果只选 HTML，这条可以降为低优先级，不强制要求 sitemap 也补
4. 同次采样发现 sitemap 存在小幅数据快照不一致（比如英文语言首页描述的部数和对应剧目分片的实际 URL 数对不完全上），需要确认这类差异是不是正常的缓存刷新周期内波动，不是漏收或数据损坏，不需要额外处理，只需要确认结论

### 7. 语言列表分页索引策略

`/browse/languages/{lang}/page/N/` 全部自 canonical + `index, follow`，sitemap 收录约 741 条语言 URL，和实际分页规模对不上。

**这一条的具体规模和处理方式需要彪哥确认**：规模数字（原估算约 1,881 页）和实际采样（约 797 页，各语种不均匀）有出入；"第二页起 noindex" 这个修复方向，如果和已有的内部决定（语言聚合分页保持可索引）冲突，实施前需要先确认这条决定是否还成立，不要直接按字面执行。另外结合第 3 项的抓取构成数据——实际抓取量集中在单集/播放链路，不是分页本身，"分页占用大量抓取预算"这个判断的紧迫性可能被高估了，排优先级时可以往后放。

### 8. 剧目版本映射关系核查（前置条件，建议最先做）

第 4、5、6、7 项（hreflang、本地化、内链互链）要正确工作，前提是"哪些页面是同一部剧的不同语言版本"这个映射关系本身是准确的。

**需要技术同事确认**：目前平台关系存在把不同作品、不同制作/剪辑版本错误关联在一起的已知情况，代码里已有一些防护（`version-groups.ts`），但仍保留"不在库 ID 作为连接桥"这类限制；另外也有记录显示，保留另一个英文版本之后，部分作品的其他语言页反而不再链到英文版。

**需要做的事**：在大规模生成 hreflang/内链之前，先核实版本映射的准确性——哪些剧目的多语言版本组是对的、哪些连错了或断开了（不能仅凭标题相似就判定是同一部剧的不同语言版本）。这一步没做完之前，第 4、6、7 项的批量实施建议暂缓，先在小范围（比如已确认版本关系正确的剧目）做试点。

## 三、结构化数据与视频索引（P2）

现有覆盖已经较全：`TVSeries`、`TVEpisode`、`VideoObject`、`BreadcrumbList`、`Article`、`Organization`/`WebSite`/`SearchAction` 均已输出。缺口：

| 类型 | 缺什么 |
|------|--------|
| Organization | `logo`、`sameAs` |
| Article | `image`（部分文章有自己的主图，但 schema 只取关联剧封面，有图不等于 schema 有图，这是一个比"整个模板不支持"更具体、可独立修的缺口） |
| VideoObject | `contentUrl`、`duration` |

**`VideoObject.contentUrl`（mp4 直链）这一条需要彪哥先确认是否和内部工程合同冲突**，不要默认可以直接加——如果视频地址不允许直接写入页面/JSON-LD，这条要么取消要么换成其他方案（比如只对免费集单独评估）。`logo`、`sameAs`、真实 `image`、`duration` 这几项用真实资产补，不编造。

**视频索引现状（10/22 GSC 导出，已核实）**：已编入索引的视频数从 09-21 的 210 条到 10-21 的 253 条，**一个月基本冻结在 250~254 这个区间，几乎没有净增长**——同期网站剧库明显在扩张（日语剧目 10/13 单天就新增 3,906 条）。未编入索引的数量则从 09-20 的 23 条涨到 10-21 的 604 条，其中 **10/08 当天从 181 条跳到 591 条**，跟这份文档第 1 项抓取量骤降的起始时间点（10-09 起）很接近，建议一并核查是否相关。失败原因高度集中：604 条里 603 条都是"视频不在观看页面上"这一个原因，占比 99.8%。

**10/16 的 `<video>` 外壳修复效果，目前看不乐观**：10/15 针对 599 个失败页面提交过 Search Console 验证请求（对应这次修复），截至 10/22，**589 条仍是"待定"，已经出结果的 11 条全部仍是"失败"**——目前为止 0 条通过验证。待定的大头还没有最终结论，但已复核的这 11 条全部没过，需要关注。

**补充线索（已核实）**：599 条失败 URL 里，380 条（63%）的"上次抓取日期"都是 **10-10**——抓取量骤降（10-11起暴跌到59）前的最后一天。这说明崩溃发生后这批页面基本没再被重新抓取确认过，时间线上和抓取量骤降直接衔接；但这不能单独证明两者是同一个根因（也可能只是全站最后一次大规模抓取恰好落在10-10，不是针对视频页面的特殊信号，需要有全站URL的上次抓取日期分布做对照才能排除）。

**需要技术同事做的事**：
1. 抽这 380 条里的几个具体 URL，查服务端日志，核实 10-10 当天 Googlebot 实际请求这些页面时的响应时间/状态码——如果当时就响应慢或渲染超时，可以把"响应慢→视频元素未渲染→索引失败"这条因果链坐实
2. 查 Vercel 部署记录，核实 10-07~10-09 之间有没有发生过可能同时影响抓取响应速度和视频渲染的部署/配置变更
3. 关注 Search Console 里那 589 条"待定"验证的后续结果，如果大批量仍然失败，说明 10/16 的修复没有真正解决"视频不在观看页面上"这个根因，需要重新排查——而不是直接假设"补完 `contentUrl`/`duration` 这两个 schema 字段=问题解决"，因为失败原因本身就是"页面上没有 `<video>` 元素"，不是 schema 字段缺失

### 剧目版本单集解锁试点（10/25，已验证可执行，建议优先排期）

**背景已验证**：用Rich Results Test分别测过`the-great-and-powerful-genie-hncnwbcubtta`这部剧的ep1和ep6——

- ep1（可被抓取）：检测到3项有效内容（路径/组织/视频），视频标记有效
- ep6（当前noindex+robots禁抓）：把它的JSON-LD原文粘进RRT"代码"模式单独测（绕开抓取限制），**检测到1项有效内容：视频，有效**

**结论**：ep6当前"网址无法编入索引"这个状态，根因是抓取/索引权限（noindex + robots.txt的`Disallow: /drama/*/episode/`），**不是结构化数据写错了**，`embedUrl`自指页面本身不会导致视频识别失败。这个判断已经有两轮独立RRT结果背书，不是推测。

**试点方案（只动这一集，不动全站）**：

1. robots.txt 加一条精确路径：`Allow: /drama/the-great-and-powerful-genie-hncnwbcubtta/episode/6/`——Google robots规则按最长匹配优先，这条字面路径比`Disallow: /drama/*/episode/`更具体会赢；**不支持用通配符写区间（比如"6到12"），只能精确路径逐条加**
2. 这一页的meta robots同步改成`index, follow`——robots控制"抓不抓得到"，meta robots控制"收不收录"，两层必须一起改，只改一层没用
3. （可选但建议）同步给这一集补上专属帧缩略图，把`thumbnailUrl`/`og:image`从现在的通用封面图换成真实的第6集截帧——这样验证的是"最终形态"，不是半成品，参考上一轮已经确认的"og:image从ep2到ep12全部共用同一张封面"这个缺口

**需要我们自己跟进验证的**（不需要彪哥做，到时候我来跑）：
4. 改动上线48小时后：用网址检查工具看ep6是否从"无法编入索引"变成可索引，再用RRT测真实URL（不是代码模式）看是否出现"3项有效内容"
5. 再过1周：盯GSC"搜索结果呈现"维度里ep6有没有出现"视频"这一行的曝光——这是视频结果真正落地的最终判定，比前面几步都更关键，前面步骤达标不代表这步一定达标

选这部剧这一集做试点还有个好处：它的JSON-LD全文已经被完整记录在这次核实过程里，改完之后能直接做修改前后的逐字对比，不用重新猜现状是什么样。

## 六、做得好的地方

- **SSR 内容完整**：不依赖 JS 也能拿到标题、正文、链接
- **canonical 基本干净**：抽样页面大多自指，尾部斜杠统一；**但大写路径、`?page=2` 这类场景会指向其他页面**，不是所有场景都自指，这部分不需要额外处理，只是备注准确范围
- **404 正确**：真 404 + noindex，不是 soft 404
- **付费集不进入索引**：robots 对 episode 2+ 做了禁抓；**这不保证所有形式的 URL 收录绝对为零**（比如被外链的 URL 仍可能以纯网址结果出现在搜索里），这是预期内的代价，不需要额外处理
- **schema 覆盖广**：TVSeries / TVEpisode / VideoObject / Breadcrumb / Article / Organization / WebSite，已经超过大多数同行
- **图片**：基本都有 alt，部分做了懒加载
- **移动端**：390px 无横向溢出，viewport 正确
- **压缩与安全**：Brotli、HSTS、CSP `frame-ancestors 'none'`
- **sitemap 索引规范**：41 个子 sitemap、有 lastmod；**但剧目和该剧第 1 集目前混在同一个 dramas 分片里，不是分开存放**，索引文件目前只给剧目分片写了 lastmod，pages 分片没有写，这部分不需要改，只是备注准确现状
