# 2·A1 / 2·A2 核查结果

完整改动清单把这两条列为 P0-2 组里「建议优先排」的最高优先级，并要求「若 2·A1 确认成立，须同时检查 P0-4」。因为 P0-4 的改动正在 PR #89 里发布，这个检查现在做了。**结论是两条都不成立。**

## 前置事实：P0-2 与 P0-4 确实共用爬虫

交接索引的记载属实。两个工具的 `scan.ts` 都 import 同一个 `crawlPublicSitePreview`（`packages/sources/src/crawl/public-preview.ts`），URL 规范化、同源判断、链接提取是**同一份代码**，差异只在拿到抓取结果之后的建模层。所以任一 bug 若成立，两个工具必然同时中招——反过来，两条都不成立，两个工具也就都干净。

## 2·A1（HTML 实体不解码）· 不成立

提取方式确实是正则而非 HTML 解析器（`parse-page.ts` 文件头明确写着不引入 cheerio），所以「解析器帮你解码了」这条辩解不存在。但**代码自己做了解码**，而且 href 与 canonical 两处都做了：

```
parse-page.ts:274-280   canonicalizeUrl(decodeHtml(href), pageUrl)
parse-page.ts:387-389   canonicalizeUrl(decodeHtml(canonicalHref), pageUrl)
```

`decodeHtml` 覆盖具名实体与十进制/十六进制数字引用。回归测试 `parse-page.test.ts:95-115` 不仅测了解码，还测了**不能重复解码**（`%26amp%3B` 必须原样保留）。

实跑验证：`href="/a?x=1&amp;y=2"`、`&#38;`、`&#x26;` 三种写法归并为同一个 URL，无幻影。对照组（跳过 `decodeHtml` 直接调 `canonicalizeUrl`）确实产出 `?a=1&amp%3Bb=2` 这个幻影参数——**说明这个 bug 的机制是真实的，只是已经修掉了**。

**时间线**：修复在 commit `271ad35`（2026-08-05 21:56，"ship actionable internal-link audit (#70)"），早于 2026-08-06 的审计报告。审计所依据的应是修复前的状态。

## 2·A2（`endsWith` 同源判断）· 不成立

抓取范围判断全部是精确 origin 相等，没有任何后缀匹配：`parse-page.ts:282-288`、`engine.ts:146-151` 及其五处调用、`sitemap.ts:69-75`。入口重定向判断更是显式注释拒绝后缀启发式（`public-preview.ts:67-101`：*"intentionally does not use a suffix or registrable domain heuristic, so sibling subdomains and look-alike domains stay blocked"*）。

回归测试 `parse-page.test.ts:117-131` 钉了子域名被排除。实跑把审计点名的那类 host 直接喂进去，`https://evilexample.com/pwn` 与 `https://app.example.com/` 都没有进入内链集合。

SSRF 防护是正交的另一套代码（DNS 解析 + IP 分类 + IP pinning，`url-safety/guard.ts:49-79`），也没有后缀匹配。全仓库涉及 host 的 `endsWith` 只有两类，方向都安全：带点前缀的黑名单（`.localhost` 等，属过度拦截不会漏放），以及 `host === d || host.endsWith("." + d)` 这个正确写法（且不在爬虫路径上）。

## 顺带确认：PR #89 的 canonical 归并逻辑没有隐藏缺陷

本次一并验证了新加的自 canonical 判据是否会因实体问题失效（`subjectUrlOf(canonicalTarget) === page.subjectUrl` 是否可能永远不相等）。**不会**，两条独立证据：

1. 两边经过同一条规范化管线，不存在不对称——`subjectUrl` 来自传输层 URL（根本不经过 HTML），`canonicalTarget` 已 `decodeHtml` + `canonicalizeUrl`。
2. 12 组实跑用例全部符合预期：实体/数字引用/十六进制/相对路径/斜杠变体/查询重排/utm 七类都正确判为自 canonical，真实迁移与真正不同的 canonical 正确排除；另有 19.3 万组随机 URL 的幂等性模糊测试零 mismatch。相关测试套件 12 文件 153 用例全绿。

一个值得知道但不是缺陷的行为：`/a → 301 → /b` 且 canonical 指向 `/b` 的页面会被判为非自 canonical、排除出重复检测。这是保守且正确的——该页本来就会被 `canonical_differs` 报出来，两处用的是同一个判据；而 `/a → /a/` 这类斜杠重定向被正确吸收，仍判为自 canonical。

## 唯一值得修的：sitemap 的数字引用（新增条目，低危）

`packages/sources/src/crawl/sitemap.ts:20-22` 的 `decodeXml` 只解 `&amp;` / `&lt;` / `&gt;`，不解 `&#38;` / `&#x26;` / `&apos;` / `&quot;`。实测 `&#38;` 尤其危险：`https://x/b?a=1&#38;c=2` 会被当成 fragment 截断成 `https://x/b?a=1`，导致 sitemap URL 与实际抓到的页面对不上——**P0-2 的 `orphan_candidate` 与 P0-4 的 `sitemap_page_without_observed_inlink` 会同时误报**。

影响面很窄：XML 文本节点只强制转义 `&` 和 `<`，主流 sitemap 生成器都输出 `&amp;`，数字引用极罕见。

修法：把 `parse-page.ts` 的 `decodeHtml` 提取成共享模块两边复用，或就地补齐 XML 五个预定义实体 + 数字字符引用。两个注意事项：必须只解码一次（sitemap 侧要补同类断言），且 `packages/sources` 受 vendor 哈希锁约束，改动需同步更新 `signalframe-manifest.json`，否则 `verify:spec` 会红。

## 对清单的建议

- **2·A1、2·A2 请改标为「不成立 / 已于 271ad35(2026-08-05) 修复并有回归测试」**，而非「未能证实也未证伪」。P0-2 那 28 条的排期可以据此重排——A 组两条不再是最高优先级。
- **新增一条窄口径条目**替代它们：sitemap 数字引用解码。
- 方法论上有一点值得留下：这两条的代码路径可以**静态 + 离线证伪**，不需要真实站点。当时因目标站 robots.txt 屏蔽参数路径而停在「未触达」是不必要的——直接调 `parsePage` 喂构造的 HTML 就能定论，成本几分钟。
