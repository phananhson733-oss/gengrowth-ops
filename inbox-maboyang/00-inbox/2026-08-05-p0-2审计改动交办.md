# 第一部分 · 工具侧（24 条）

## A · Bug 修复（2 条，都是 🔴）

### A1 · 爬虫不解码 HTML 实体

**现象**：12 条 findings 里 11 条是 `/blog?amp%3Bcategory=…` 这种 URL。

**根因**：站点 HTML 写的是 `href="/blog?category=case_study&amp;pillar=attribution"`（**正确的转义**），爬虫没解码 `&amp;`，把它当字面量，于是参数名变成了 `amp;pillar`。

**修法**：href 提取后先做 HTML 实体解码（`&amp;`→`&`、`&lt;`→`<`、`&#38;`→`&`），再做 URL 规范化。

> ⚠️ **要修的是爬虫，不是站点。** 站点 HTML 是对的。

**影响面**：`&amp;` 是 HTML 里写 `&` 的**标准正确写法**，**任何有筛选 / 分页 URL 的站都会中招**。

**验收**：对 gengrowth.ai 重跑，findings 里不应再出现 `amp%3B`。

---

### A2 · 子域名被当成同源路径

**现象**：树里有个 `app` 节点，入链 48、出链 0、标题「404: This page could not be found.」

**根因**：站上**没有任何** `/app` 同源链接，全是 `href="https://app.gengrowth.ai"`（子域名）。爬虫把子域名解析成了路径。推测同源判定用了 `endsWith('gengrowth.ai')`。

**修法**：同源判定改成**精确 host 匹配**（`hostname === seedHostname`）。

**影响**：违反工具自己声明的 `SAME ORIGIN` 契约；**风险不止误报——意味着爬虫可能爬到本不该爬的域名上**。

**验收**：

```bash
curl -s "https://gengrowth.ai/" | grep -coE 'href="/app[/"]'   # → 0
# 重跑后树里不应有 app 节点
```

## B · 核心指标定义（2 条，都是 🔴）

### B1 · `depth` 拆成两个口径

**现状**：一个视图里混了三套逻辑——

| 展示要素 | 现在用的逻辑 |
|---|---|
| 缩进（主） | URL 路径层级 |
| 缩进（回退） | 路径父页未采集时才用链接关系 |
| Depth 列 | 爬虫遍历层数，**且 sitemap 条目算爬取种子** |

**为什么是问题**：同样是 `/blog/xxx`，URL 路径深度全是 2，实际点击深度差很多——

| 页面 | URL 路径深度 | 实际点击深度 |
|---|---:|---:|
| `/blog/bounded-internal-link-crawl` | 2 | **1** |
| `/blog/affordable-seo-tools` | 2 | **3** |
| `/blog/marketing-attribution-for-saas` | 2 | **≥4** |

**修法**：抓取时可以用 sitemap 补全覆盖，**但计算 depth 时只能沿真实链接走**。

```
发现（可用 sitemap） ≠ 可达性（只能靠链接）
```

---

### B2 · 新增核心输出「点击深度分布」

```
点击深度分布（沿真实链接，不含 sitemap 种子）
  1 跳    25 页
  2 跳    27 页
  3 跳    51 页
  ≥4 跳   ⚠️ N 页   ← 这些拿不到多少内链支撑
  不可达  ⚠️ N 页   ← 只在 sitemap 里
```

**「≥4 跳」和「不可达」两栏才是可行动的输出。**

> 📌 现在 findings 里那条 `/blog/marketing-attribution-for-saas has limited observed internal support`——说了"内链支撑少"，**但没说它埋在 4 跳外**，而后者才是能拿去动手的信息。

## C · 检测能力（2 条）—— 性价比最高的一组

### C1 · 🟠 读已抓 HTML 的 `robots` meta 与 `canonical`

**爬虫已经把 167 页的完整 HTML 抓下来了，却只用了里面的 `<a href>`。**

读这两个标签是**零额外请求**的：

```html
<meta name="robots" content="...">
<link rel="canonical" href="...">
```

**能新增的检测**：
- 筛选 / 分页 URL 是否可索引
- canonical 指向是否异常（如分页页 canonical 指向第一页）

**这一条是本次审计里投入产出比最高的。**

---

### C2 · 🟠 内容指纹比对，识别「不同 URL 相同内容」

**实测**：`/blog?page=4` 与 `/blog?category=methodology&page=4` 返回**完全相同**的 12 篇文章。

现在工具把它们当两个独立页面收进计数，**没有识别出这是重复内容**。

**修法**：对已抓 HTML 做主体内容指纹（如正文链接集合的哈希），相同指纹的 URL 聚合报出。

---

### 💡 C 组背后的产品结论

工具给出的 12 条 findings **全部只有两类**：`crawl depth` 和 `inbound count`——**恰好是爬虫遍历时零成本产出的副产品**。

而站点侧实测出的四个真问题（见第二部分），**一条都没报**。

**当前的能力边界是「爬取时顺手能算的东西」，而用户要的"审计"主要由需要额外分析的部分构成。**

## H · 与其他工具的联动（5 条 · 2026-08-05 新增）

> 📌 **溯源说明**：`00-inbox/2026-07-31-前后端交接索引.md` 4.3 节写过 *"**P0-4** 各类发现→其他工具的交接，需确认数据能真的传过去，不能只是链接跳转"* —— **原文主语是 P0-4，不是 P0-2**。原则通用，但 **P0-2 的联动是本次审计新提的，此前未交接过**。

### ⚠️ 先说一个前置条件

产品评审已判定：**三个工具都停在「观测」，没走到「判断」**。

**在这个状态下加一堆工具入口，用户体验会变成：每个工具给我一堆数据，然后让我去下一个工具再拿一堆数据。**

**建议顺序：先做 B2（点击深度分布）和 E2（一句话结论），再做 H 组。** 联动不能替代单个工具的完整性。

### 联动的判定标准

| | 弱联动 | 强联动 |
|---|---|---|
| 形态 | 报告末尾一排"你可能还需要"的工具卡片 | **一个工具的输出，正好是另一个的输入** |
| 用户感受 | 广告 | 顺理成章 |
| 实现 | 加几个链接 | **传数据** |

**H1–H4 按价值排，只有 H1 / H2 值得做；H5 是指向主产品的 CTA，能力边界已确认。**

---

### ⭐ H1 · 🟠 P0-2 → P0-4：复用已抓 HTML，零额外等待

**依据**：交接索引"容易踩的坑"第 2 条明确写过 **「P0-2 与 P0-4 共用爬虫基础设施」**。

而实测显示 **P0-2 已经把 167 页的完整 HTML 抓下来了 —— P0-4 需要的就是同一批 HTML**。

```
现在：跑 P0-2 等十几秒 → 想看全站审计 → 跑 P0-4 再等十几秒（重抓同样的页）
应该：跑 P0-2 →「用这次已抓的 167 页做全站技术审计」→ 立即出结果
```

**这不是跳转，是「同一次抓取的两种解读」。**

> 🔗 **与 C1 强相关**：如果爬虫开始读 `canonical` 和 `robots` meta，**P0-4 的核心检测项在 P0-2 跑完时就已经算出来了**，边际成本接近零。

**验收**：从 P0-2 报告点进 P0-4，**不触发新的抓取请求**，结果立即呈现。

---

### ⭐⭐ H2 · 🟠 P0-2 × P0-1：交集才是可行动的

**这条价值最高，因为它给出的东西两个工具单独都给不出来。**

| 工具 | 知道什么 |
|---|---|
| P0-2 | 哪些页面**内链弱、埋得深** |
| P0-1 | 哪些页面**曝光高、点击少** |

**交集的判定逻辑：**

```
页面 曝光高 + 点击少 + 内链支撑弱
  → Google 已经在给它机会，但站内没给它支撑
  → 加内链是明确有回报的动作            ✅ 优先修

页面 内链少 + 根本没曝光
  → 修内链也没用，问题在别处            ❌ 不用管
```

**现在 P0-2 报「51 页埋在 3 跳外」，用户无法判断哪些值得修。加上 GSC 数据就能排序。**

⚠️ **门槛与机会**：P0-1 需要 GSC 授权，而 P0-2 是免登录的。所以这条同时是**从匿名到授权的转化点** —— 与北极星指标（续接率）方向一致。

---

### H3 · 🟡 P0-3 → P0-2（注意方向）

**方向要反过来**，`P0-3 → P0-2` 比 `P0-2 → P0-3` 自然：

```
✅ P0-3 诊断出「某批页面曝光崩塌」→ 这批页面是不是内链出了问题？→ 带 URL 跳 P0-2
❌ P0-2 说你内链有问题 → 要不要看看流量降没降？（无因由的推荐）
```

**这条应该在 P0-3 那边实现，不在 P0-2。**

---

### H4 · ⚪ P0-2 → P0-5：暂不做

从"内链弱的页面"提主题词去找关键词机会 —— **链条太绕，用户不会这么想。**

---

### 具体设计：不是「你可能还喜欢」，是「下一步该查什么」

报告末尾**不放工具卡片**，放**由本次结果触发的问题**：

```
┌──────────────────────────────────────────────────
│  你的站有 51 页埋在 3 跳以外
│  它们可能拿不到足够的内链支撑 —— 但值不值得修，
│  取决于它们在 Google 那边有没有曝光。
│
│  [ 连接 Search Console，看这 51 页的实际表现 ]  → P0-1
├──────────────────────────────────────────────────
│  抓取时我们还发现 66 个页面的 canonical 指向别处
│  这可能是分页/筛选的正常现象，也可能是配置错误。
│
│  [ 用这次已抓的 167 页做全站技术审计 ]  → P0-4 · 无需重新等待
└──────────────────────────────────────────────────
```

**三个设计要点：**

| # | 要点 | 说明 |
|---|---|---|
| 1 | **有条件触发** | 没有深层页面就不显示第一条；没有 canonical 异常就不显示第二条 |
| 2 | **说清为什么** | 不是"还有个工具"，是"**你这个结果引出了一个新问题**" |
| 3 | **标明成本差异** | P0-4 那条写「无需重新等待」—— 这是真实的差异化，不是营销话术 |

---

### H5 · 🔴 CTA 指向主产品 —— 已确认能力边界（2026-08-05）

**已确认**：主产品**能给出内链建设建议，但不能代替用户执行**（无法自动往站上加链接）。

#### 这不是缺陷，是分工

回看痛点报告里那句 Reddit 原话，出处帖标题是 **《How to *find* your orphan pages… without paying for Screaming Frog》** —— **那个"下午"花在「发现」上，不是花在「修」上。**

| 步骤 | 谁做 | 现状 |
|---|---|---|
| **① 发现**：哪些页面孤岛 / 埋太深 | **P0-2，15 秒** | ✅ 已经省掉了那个下午 |
| **② 决策**：从哪个页面链过去、锚文本写什么 | **主产品（给建议）** | ← **真正的脑力活** |
| **③ 执行**：去 CMS 插入链接 | 用户自己 | 每条几分钟 |

**第 ② 步恰恰是最难的一步**，它需要**页面主题相关性**和**源页面自身权重**——这两样 P0-2 都没有，正是主产品的增量所在。

> 📌 另外：**自动改站本身有风险**（需 CMS 权限、可能出错、难回滚）。不少专业 SEO 会主动拒绝这类功能。「只给建议」对目标用户反而更可接受。

#### CTA 措辞：去掉"自动"

```
❌ [ 用 GenGrowth 自动生成内链方案 ]     ← "自动"会被读成自动执行，承诺大于能力
✅ [ 让 GenGrowth 告诉你从哪些页面链过去 ]
```

**关键是说清建议的具体形态**，而不是笼统说"方案"：

```
/blog/marketing-attribution-for-saas 埋在 4 跳外，只有 1 条入链

建议从这 3 个页面加链接：
  /blog/9-best-marketing-attribution-tools   主题最相关，且自身有 68 条入链
  /blog/saas-seo-expert                      主题相关
  /blog                                      列表页，权重高

锚文本建议：marketing attribution for SaaS
```

**用户看到这个才知道"下一步具体做什么"，而不是"你有 51 个问题"。**

#### 与 H1 / H2 的关系：三步是连贯的

```
P0-2  找出内链弱、埋太深的页面        ← 发现
 ×
P0-1  哪些页面有曝光（值得修）        ← 排序（H2）
 ↓
主产品 从哪链、锚文本写什么           ← 决策（H5）
 ↓
用户  去 CMS 加链接                   ← 执行
```

**这条链条完整，而且每一环的分工都是诚实的。**

#### ⚠️ 对审计文档 5.5 节的一处修正

审计文档写过"我们把手工翻 100 页变成了翻 167 行表格，下午没省掉"。

**这句批评的对象要收窄**：**抓取那部分确实省掉了一个下午**（15 秒 vs 手工翻 100 页）。没省掉的是**读报告、判断优先级**这一段——**批评的是输出呈现，不是抓取能力**。

对应的改动仍然是 B2（点击深度分布）+ E2（一句话结论）+ F1（表格默认视图），**不影响那几条的优先级**。

# 第二部分 · 站点侧（4 条，改 gengrowth.ai）

> 这四条与工具无关，是审计时顺带查出的 gengrowth.ai 自身的 SEO 问题。**两条有 Google 官方文档逐字对应。**

## S1 · 🔴 ✅ 分页页 canonical 全部指向第一页

**现状**：

```
/blog          canonical → https://gengrowth.ai/blog
/blog?page=2   canonical → https://gengrowth.ai/blog   ⚠️
/blog?page=3   canonical → https://gengrowth.ai/blog   ⚠️
```

**但三页内容完全不同**——page1 与 page2 的 12 篇文章**零重复**。

**✅ 官方文档逐字对应**（[Pagination best practices](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)）：

> **"Don't use the first page of a paginated sequence as the canonical page. Instead, give each page its own canonical URL."**

**影响**：这个站 63 篇 blog 只有 12 篇在第一页，**其余 51 篇全靠这批 canonical 错误的分页页承接内链**。

**修法**：`/blog?page=N` 的 canonical 改为**自引用**。

**验收**：

```bash
curl -s "https://gengrowth.ai/blog?page=2" | grep -oE 'canonical" href="[^"]*"'
# 期望：https://gengrowth.ai/blog?page=2
```

---

## S2 · 🔴 ✅ 8 个空结果筛选组合返回 200

**实测**：15 种 `pillar × category` 组合里，**8 种返回 0 篇文章，且都是 HTTP 200**：

```
?pillar=attribution&category=case_study
?pillar=attribution&category=weekly_review
?pillar=customer_stories&category=methodology
?pillar=customer_stories&category=weekly_review
?pillar=experiment_driven&category=case_study
?pillar=growth_automation&category=weekly_review
?pillar=seo_content&category=case_study
?pillar=seo_content&category=weekly_review
```

**✅ 官方文档逐字对应**（[Faceted navigation](https://developers.google.com/crawling/docs/faceted-navigation)）：

> **"Return an HTTP 404 status code when a filter combination doesn't return results.** … This should also be the case if the URL contains duplicate filters or **otherwise nonsensical filter combinations**, and nonexistent pagination URLs."

**修法**：筛选组合无结果时返回 **404**（不要 302 到通用错误页，要在原 URL 上返回 404）。

---

## S3 · 🟠 `category` 筛选在有分页时不生效

**实测**：

```
/blog?page=4                        → 12 篇（agency-rank-tracking…）
/blog?category=methodology&page=4   → 12 篇（agency-rank-tracking…）  ← 完全相同
```

**不同 URL、相同内容、都可索引** = 真重复内容。

**修法**：修分页与筛选的参数组合逻辑，或对这类组合明确 noindex。

---

## S4 · 🟠 筛选 URL 全部可索引，robots.txt 无参数规则

**实测**：`?category=`、`?pillar=`、`?page=` 全部**无 robots meta**，robots.txt 里也没有参数相关规则。

**官方警告的两条危害**：

> **Overcrawling**：爬虫无法在抓取前判断 URL 有没有用，会先抓一大堆才发现没用
> **Slower discovery crawls**：抓取预算花在无用 URL 上，新的有用 URL 就发现得慢

**官方推荐的处理优先级**：

```
1. robots.txt 屏蔽参数模式（最有效）
2. 用 URL fragment（# 而非 ?）承载筛选 —— Google 不抓 fragment
3. canonical / nofollow —— 官方原话："generally less effective in the long term"
```

**建议**：robots.txt 加

```
disallow: /*?*category=
disallow: /*?*pillar=
```

分页 `?page=` **不要屏蔽**（那 51 篇文章靠它承接内链）。

---

### 📌 关于「任意参数都返回 200」

顺带澄清一个可能被误解的点：

```
/blog?这是我随便编的=12345  →  HTTP 200，内容与 /blog 相同
```

**这是 HTTP 的普遍行为，不是本站缺陷，不需要改。** 查询字符串不是路径的一部分，绝大多数网站都是这样。

**需要改的只有 S2**（空结果组合应返 404）**和 S4**（控制抓取范围）。
