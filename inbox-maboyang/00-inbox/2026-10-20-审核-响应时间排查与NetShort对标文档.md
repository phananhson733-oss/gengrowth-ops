# 审核意见 · 响应时间排查文档

## 0. 结论

这份文档的**方向是对的**：把“抓取量骤降”从单纯的 403 扩展到响应时间/后端性能，并尝试用竞品做对照，这是有价值的新线索。

但按严格标准，它目前**还不能作为“已定位到后端 RSC 数据层”的诊断**，原因有三类：

1. **3 个事实错误**（ReelShort 架构、ReelShort 缓存、NetShort 时延可复现性）；
2. **因果顺序不成立**：抓取量 collapse 发生在响应时间暴涨之前，文档却把后者当成前者的原因；
3. **测量口径混在一起**：GSC 平均响应时间是全站聚合值，样本极小、请求类型每天在变；外部 Resource Timing 又可能是 fetch/RSC 而不是页面导航。

下面逐条说，附可复核的证据。

---

## 1. 事实错误（必须改）

### 1.1 ReelShort 不是“非 Next.js”

文档写：

> ReelShort（非Next.js架构），`server: istio-envoy`

`server: istio-envoy` 只能说明前面有 Istio 代理，**不能说明应用框架**。实测响应头和 HTML：

```text
x-powered-by: Next.js
_next/static 资源：19 个
__NEXT_DATA__：1 个
self.__next_f：0 个
```

结论：**ReelShort 是 Next.js（Pages Router），不是“非 Next.js”**。它没有 App Router/RSC，但不等于“不是 Next.js”。

### 1.2 ReelShort 不是“无缓存”基线

实测响应头：

```text
cache-control: public, s-maxage=3600, stale-while-revalidate=7200
```

这说明它至少有 CDN/边缘缓存，TTFB 822–868ms 可能包含缓存命中/回源不同状态。文档把它当作“非 Next.js 的对照组”，却没有说明它的缓存状态，**架构和缓存两个变量都没有控制住**。

### 1.3 NetShort 的 247–254ms 不可复现，不能支撑“3–18 倍”

我在同一台机器、同一时段（2026-10-20）对两个首页各跑了 3 次：

| 站点 | TTFB 3 次 | 总耗时 3 次 |
|------|-----------|-------------|
| NetShort | 1.084s / 1.142s / 1.101s | 1.94s / 1.65s / 1.56s |
| ReelShort | 1.061s / 1.092s / 1.074s | 1.77s / 2.56s / 2.28s |

这和文档里的 NetShort 247–254ms、ReelShort 822–868ms 差了一个量级。可能是测试网络/边缘/时间不同，但结论是：**单次手工测试不足以支撑“3–18 倍”这种精确倍数**。

另外，文档表格里三个指标的倍数并不一致：

- TTFB：200–800ms vs 247–254ms → 约 0.8–3.2 倍；
- 下载/流式：2000–6351ms vs 60–98ms → 约 20–106 倍；
- 总耗时：约 2.2–7.2s vs 0.35–0.37s → 约 6–20 倍。

“3–18 倍”没有说明是哪个指标、怎么算的。

### 1.4 “NetShort 每次请求都是重新生成”不成立

`cache-control: no-store` + `cf-cache-status: DYNAMIC` 只能证明：

- Cloudflare 边缘没有缓存这个 HTML 响应；
- 不能证明 origin 没有数据缓存（Redis、Next.js Data Cache、内存缓存、ISR 等）。

文档后面又建议“加 Redis”，这本身就说明“数据层缓存”是可能存在的。准确说法应该是：**没有边缘 HTML 缓存**，而不是“没有缓存/每次重新生成”。

### 1.5 “10/11 起暴涨”不准确

按文档自己的表：

- 10-11：59 请求，371ms；
- 10-12：78 请求，1,019ms；
- 10-13：80 请求，1,971ms。

真正跳升是 **10-12**，10-11 只是从 200ms 回到 371ms。时间线差一天，会影响“谁先谁后”的判断。

---

## 2. 因果与统计问题（影响最大）

### 2.1 时间顺序反了：先 collapse，后 latency

文档的核心因果是“响应时间暴涨 → Google 降低抓取限额 → 抓取量骤降”。但按日数据：

| 日期 | 请求数 | 平均响应时间 |
|------|--------|--------------|
| 10-10 | 1,301 | 200ms |
| 10-11 | 59 | 371ms |
| 10-12 | 78 | 1,019ms |
| 10-13 | 80 | 1,971ms |

**抓取量在 10-11 已经 collapse，响应时间在 10-12 才明显跳升。** 至少从日粒度看，不能证明“延迟在前、降速在后”；也可能是：

- 抓取量先因别的原因（403、抓取需求、robots、站点状态）下降；
- 请求量变小后，请求类型结构变化，平均值被少数慢请求拉高；
- 两者有共同原因（后端过载、发布、边缘问题）。

文档应该把“延迟导致降速”写成**待验证假设**，并明确需要小时级/服务端日志来定先后，而不是直接说“这正是触发条件”。

### 2.2 GSC 平均响应时间是聚合值，不是页面渲染时间

GSC 的“平均响应时间”覆盖 Googlebot 抓到的**所有文件类型**（HTML、JSON、JS、CSS、API 等）。10-20 导出里：

```text
HTML 39.50% · 其他文件类型 30.12% · JSON 9.55% · JS 3.43% · 未知失败 16.90%
```

每天请求量从 8,365 掉到 7–80，**请求类型结构会剧烈变化**。10-15 的 2,374ms 只有 24 个请求，一两个慢请求就能把平均值拉上去。文档把这条曲线直接当作“页面路由/流式传输变慢”，中间缺了：

- 按文件类型拆的响应时间；
- 按 URL/路由拆的响应时间；
- 按状态码拆的响应时间；
- p50/p75/p95，而不是平均值；
- 样本量标注。

没有这些，**“响应时间暴涨”是事实（平均值确实涨了），但“页面路由变慢”只是推断**。

### 2.3 基线选错了

文档拿 10-09 的 338ms、10-10 的 200ms 当基准。但按 10-20 导出重算：

| 区间 | 请求数 | 加权平均响应时间 |
|------|--------|------------------|
| 09-16 ~ 10-08（事发前） | 65,002 | **176.8ms** |
| 10-09 ~ 10-10 | 9,666 | 319.4ms |
| 10-11 ~ 10-17 | 305 | 1,213.2ms |
| 10-12 ~ 10-17 | 246 | 1,415.2ms |

10-09 本身是 8,365 次请求的异常高峰，338ms 不代表日常。**事发前加权平均是 176.8ms**，不是 338ms。验收标准写“回落到 400ms 以下”比事发前基线还高 2 倍多，定得太松；建议用 200–250ms 或 p75，并说明样本。

### 2.4 Resource Timing 的测量对象可能不是页面导航

文档说用 `performance.getEntriesByType('resource')` 拆页面路由。问题是：

- **`resource` 条目不包括主文档导航**；主文档在 `navigation` 里；
- 如果测的是 `fetch()` 或 RSC 请求，那和 Googlebot 抓 HTML 不是同一个东西；
- 静态资源 1–3ms 很可能是**浏览器缓存命中**，不是网络传输；需要 `cache: 'no-store'` / 加随机参数 / 新无痕上下文。

这三条不澄清，“静态资源稳定、页面路由慢，所以不是网络问题”的推断就不成立。正确做法：

- 用 `performance.getEntriesByType('navigation')[0]` 测页面 HTML；
- 每次带 cache-buster；
- 至少 20 次，报 p50/p75/p95；
- 同时记录 `transferSize`、`encodedBodySize`、`decodedBodySize`、`nextHopProtocol`。

### 2.5 竞品对比没有控制变量

文档的比较缺了至少五个控制项：

1. **具体 URL**：NetShort 是哪个页面？首页还是剧集页？和 shortsbinge 的 trending 是否同类？
2. **压缩/解压口径**：395KB 是 decoded 还是 compressed？我两次抓取 NetShort HTML 约 405,901B / 406,986B（响应头未见 content-encoding，基本未压缩）；ReelShort 约 592,306B。
3. **网络/边缘**：测试机在哪个地区、走哪条网络、是否同一 DNS/边缘节点？NetShort 和 shortsbinge 的 CDN/边缘位置不同，TTFB 不可直接比。
4. **样本量与分布**：3 次还是 30 次？p50 还是最好值？
5. **数据复杂度**：同样 395KB，不代表同样数量的 DB 查询、同样 personalization、同样第三方调用；NetShort 可能数据源更简单。

### 2.6 没有对比“真实用户”和“Googlebot”

如果真实用户的 TTFB 正常、只有 Googlebot 慢，那问题可能在爬虫侧（challenge、地区、抓取环境），不一定是后端。文档完全没有用 Vercel Speed Insights / GA4 / RUM 做对照。**这是判断“后端问题”还是“爬虫侧问题”的关键一步。**

### 2.7 把 403 和延迟当成两条独立线索，依据不足

10-19 的交办文档已经查明：4XX 样例 954 条**全部是 `/api/play/{id}/{集数}/` 的 403**，且首页 GSC 实时抓取成功，Vercel challenge 基本被排除。

这份文档说“403 不在 Google 的名单里”，但：

- Google 那段引文说的是 **crawl capacity limit**，不是 crawl demand；
- 403 如果发生在 HTML 上，会影响抓取需求/索引；发生在 `/api/play/` 上，影响小，但仍是抓取浪费；
- 403 和慢响应可能来自**同一个后端过载**，不一定是两条独立线索。

文档应该明确写出“4XX 的已知根因是 `/api/play/` 深集数 403”，再讨论延迟，而不是把 403 放在一边。

## 3. 遗漏

1. **没有按 URL/路由拆**：trending、drama、episode、API、RSC 哪一类慢？GSC 的聚合值不能回答。
2. **没有按状态码拆**：4XX/200/301 各自的响应时间；403 快还是慢？
3. **没有 Vercel 函数区域/数据库区域**：serverless 跨区访问 DB 是常见 1–3s 延迟源。
4. **没有冷启动/并发**：Vercel 冷启动、实例复用、并发限制都会造成“忽高忽低”。
5. **没有第三方调用**：版权方 API、翻译、图片处理、搜索服务都可能阻塞 RSC。
6. **没有 Suspense 边界/串行 waterfall**：不只是“查询是否并行”，还可能是多个 `<Suspense>` 顺序 resolve、`await` 瀑布、N+1。
7. **没有 `Server-Timing` / OpenTelemetry / APM 片段**：外部黑盒只能定位到“这一层”，内部需要 span 才能定位到“哪个调用”。
8. **没有真实用户监控（RUM）对照**：见 2.6。
9. **没有说明 GSC 数据延迟**：10-18/10-19 可能不完整，10-14 之后样本极小。
10. **没有定义“什么结果会推翻这个假设”**：例如，如果 NetShort 与 shortsbinge 同区域、同数据源，或慢只发生在 trending 一个路由，结论就要改。

## 4. 做得好的地方

- Google 官方引文准确（我核对了原文，措辞一致）；
- 明确区分了“外部黑盒能定位到什么、定不到什么”；
- 把“并行查询 / 数据缓存 / 索引”列为待验证方向，而不是直接下结论；
- 承认测试是一次性手工测试；
- 提出了验收标准（虽然口径需要修正）。

---

## 5. 建议怎么改

### 5.1 先改定位

把标题/结论从“响应时间暴涨 = 根因”改成：

> **待验证假设：Googlebot 平均响应时间上升，可能与抓取量下降相关；需要按 URL/文件类型/状态码拆分，并用服务端日志确认因果顺序。**

### 5.2 补三张表

1. **GSC 按文件类型/URL 的响应时间**（服务端日志或 Vercel 日志）：HTML vs JSON vs RSC vs API；
2. **按状态码的响应时间**：200/301/403/404 分别多快；
3. **同一 URL 的 20 次采样**：p50/p75/p95，cache-bust，记录边缘节点/函数区域。

### 5.3 修正竞品对比

```text
ReelShort：Next.js（Pages Router），CDN 缓存 s-maxage=3600
NetShort：Next.js（App Router + RSC），Cloudflare 边缘 no-store，但 origin/data cache 未知
shortsbinge：Next.js（App Router + RSC），Vercel，HTML max-age=0
```

并固定：同一测试机、同一时段、同一页面类型、20 次采样、报 p50/p95。

### 5.4 补内部排查项

- Vercel 函数 region vs 数据库 region；
- 冷启动率、并发、实例复用；
- DB 查询计划/索引/N+1/连接池；
- 第三方 API 调用耗时；
- Suspense 边界与 `await` 瀑布；
- `Server-Timing` 或 OpenTelemetry span。

### 5.5 修正验收标准

- 事发前基线：**176.8ms 加权平均**（不是 338ms）；
- 目标：p75 回到 200–250ms，或至少回到事发前 ±20%；
- 抓取量回升是**滞后观察指标**，不是硬性验收项；
- 明确“多长期限、多少样本、哪个页面”。

## 6. 事实核查表

| 文档说法 | 核查结果 | 证据 |
|----------|----------|------|
| ReelShort 非 Next.js | ❌ 错误 | `x-powered-by: Next.js`、`__NEXT_DATA__`、`_next/static` 19 个 |
| ReelShort 无缓存/非缓存基线 | ❌ 未控制 | `cache-control: public, s-maxage=3600, stale-while-revalidate=7200` |
| NetShort 247–254ms | ⚠️ 不可复现 | 本机 3 次 1.08–1.14s |
| NetShort 每次重新生成 | ⚠️ 证据不足 | 只证明 Cloudflare 边缘 DYNAMIC；origin/data cache 未知 |
| 3–18 倍 | ⚠️ 口径不清 | TTFB/下载/总耗时倍数不同 |
| 10/11 起响应暴涨 | ⚠️ 应为 10/12 | 10-11 371ms，10-12 1,019ms |

| 403 不在 Google 名单 | ⚠️ 只适用于 crawl capacity | 引文是 capacity limit，不是 crawl demand |

## 7. 一句话

**这份文档可以当“下一步排查的假设清单”，但不能当“已定位后端数据层”的结论。**  
先把 ReelShort 的事实错误、时间顺序、聚合指标和竞品测试方法修掉，再交给彪哥；否则后端会按一个没被证实的因果去优化，浪费一轮。
