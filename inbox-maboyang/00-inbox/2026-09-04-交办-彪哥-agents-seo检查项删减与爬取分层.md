# 交办 · /agents/seo 检查项删减 + 爬取范围分层

## ⚡ 一分钟摘要

| #   | 事项                                                                   | 类型  | 成本  |
| --- | -------------------------------------------------------------------- | --- | --- |
| 1   | 删除"Title contains the target query"类单页单词检查，改成一句引导语指向 On-Page Checker | 删除  | 低   |
| 2   | 爬取范围分层：免费/轻量档只跑"关键页"深度检查；全站爬取收窄成可选/付费档，只服务真正需要全站视角的检查                | 简化  | 中   |

## 一、删除"Title contains the target query"类检查

### 现状（实测证据）

`/agents/seo` 检查目录里编号 **2.3 "Title contains the target query"**，Decision rule 原文：

> Contains the confirmed target query as a token sequence; otherwise Warning; **2× check weight**. No synonym or stemming set is applied.

本次对 gengrowth.ai 实测，这条检查的范围是 **"tested 1 · affected 1"**——Stage 01 只填了1个目标query（"seo website audit"），且只绑定给了首页1个页面。也就是说，**这条检查天生就是单页单词的判断，不是全站视角的东西**。

### 为什么要删

同一件事，`/tools/on-page-seo-check` 做得更深：本次实测同一个页面 + 3个query，"Keyword placement"这一类给出的是标题/子标题/开头正文/URL/密度**五个维度**的独立分数（本次跑出来是0/28），还带精确到像素的标题宽度、Google结果预览。`/agents/seo`这条2.3检查只是个"含不含"的二元判断，深度上明显更弱，留着只会让用户觉得"两个工具在查同一件事，我该信哪个"。

### 改动内容

1. **删除**检查目录里的 2.3 "Title contains the target query"。
2. 原位置（或 Meta 类目结尾）**加一句纯引导文案**，不做任何判断，例如：

   > Want to know if a specific page actually covers your target keywords? Use the [On-Page SEO Checker](/tools/on-page-seo-check) for word-by-word placement, density, and a SERP preview.

3. **别只改这一条就收工**：麻烦彪哥把89项检查目录整体过一遍，凡是符合"只绑定1个query、只测1个页面"这个模式的（备注里会写类似"tested 1"这种字样），按同样逻辑处理——要么删掉改引导语，要么明确说明它跟2.3不是一回事、必须留。目前只确认了2.3这一条，不确定还有没有同类的。
4. **连带影响，别漏了**：2.3被删除后，它原来"2× check weight"占的权重需要从总分公式里去掉，不然总分计算会对不上。

## 二、爬取范围分层：免费/轻量档 vs 付费/全站档

### 现状（实测证据）

本次对 gengrowth.ai 跑`/agents/seo`：214页爬取，耗时约2分钟（工具自己文案写的上限是4分钟/约950页）。

但把这次46条issue的完整明细逐条翻过一遍后发现：**绝大多数检查根本不需要214页**。

| 检查范围标签 | 覆盖的检查 | 数量级 |
|---|---|---|
| **"X/12 key pages"** | Title length、Meta description length、Render-blocking resource count、Markup document size、Modern image format share…… | 本次逐条翻查的30+条issue，**几乎全部**是这个标签 |
| **"Site-level scope"** | Impression share in positions 1–6、Average response time | 本次只有**2条** |
| **"SOURCE GATED"**（跟爬取深度无关，是另一个维度：卡在没连Search Console） | Index coverage rate、Deprecated URL impression share、Discovered currently not indexed rate、Time-sensitive content impression share | 5条，**不受本次分层改动影响，解锁条件是接GSC不是爬多少页** |

也就是说，产品内部其实**已经把"214页发现"和"12页深度检查"分开了**，只是现在两者被强制打包在一次运行里，对用户不可见、不可选。

### ⚠️ 需要彪哥确认一件事

落地页文案（`00-inbox/2026-07-30-落地页文案-p0-4-seo-audit.md`）里承诺的 **"Broken internal links"、"Orphan pages"** 这两项检查，本次46条issue完整明细里**一条都没找到**（用JS在页面全部DOM文本里搜"orphan"、"broken link"，两个都是NOT FOUND）。

这两项按定义必须爬完整站的链接图才能判断（判断一个页面是不是孤岛，前提是爬过所有可能链接到它的页面），是"真正需要全站视角"这一类里最典型的代表。**麻烦确认一下这两项现在到底实现了没有**——如果还没做，正好，直接按下面的方案设计成付费专属，不存在"已经免费给用户、现在要收回"这个问题。

### 关键页选取规则（不是12，是下面这套规则——直接照此实现，不需要再等产品拍板）

现在的12页，看实测结果，像是"从首页广度优先爬，爬到前12个不重复页面就停"这种发现顺序决定的，不是按页面重要性挑出来的。这个逻辑如果直接照搬到免费档，会有明显漏洞：如果一个网站首页导航链了20个工具页，广度优先爬到12个就停，意味着**有8个工具页永远不会被免费档检查到，而且用户不知道少查了哪些**。这不是"轻量"，是"随机漏检"。

**候选页按下面四条规则收集，不设一刀切的页面数量上限，靠规则本身控制规模：**

1. **首页**：永远包含。
2. **导航直链页**：站点主导航（header）里直接出现的每一个链接，**全部包含，不受数量限制**——包括定价页（URL含`pricing`/`plans`/`price`的页面通常也会被导航直链命中，双重保险）。
3. **同类页面集群，整簇收，不是收前N个**：爬取过程中，只要发现某个URL路径前缀（如`/tools/`、`/products/`、`/agents/`、`/features/`、`/solutions/`）下**聚集了3个以上页面**，判定为"产品/功能页集群"：
   - 集群规模 **≤20页**：整簇全收（这就是解决"20个工具页"这个场景的关键——不管导航菜单里显示了几个，只要是同一路径前缀下的页面，爬到几个收几个，不按发现顺序砍）。
   - 集群规模 **>20页**：视为"内容型集群"而非"产品型集群"（走第4条的规则，不整簇收）。
4. **Blog/内容类页面，按站内内链数量取前15**：`/blog/`、`/posts/`、`/news/`这类路径前缀，或第3条里被判定为"内容型"的集群，**不整簇收**——按"被站内其他页面链接的次数"（纯粹从这次爬取本身能算出来，不依赖GSC）排序，取前15篇。这15篇代表"网站自己通过内链投票认为重要"的内容，不是"最新发布"或"爬虫先碰到的"。
5. **黑名单直接跳过**（除非该页面本身也被导航直链命中，导航直链的优先级最高，能覆盖黑名单）：URL含`about`、`contact`、`privacy`、`terms`、`cookie`、`careers`、`jobs`、`team`的页面。这类页面对SEO健康诊断的价值低，不占用免费档配额。

**安全阀，不是主控制手段**：以上规则收集完的候选页总数，正常情况下落在"导航页(通常个位数到二十几) + 产品集群(≤20) + 内容页(≤15)"这个量级，一般不会超过50页太多。如果确实超过50（比如产品集群本身就有40个页面 + 导航还有一堆），**优先压缩第4条的内容页数量**（15→10→5），**不动第2、3条**——导航页和产品集群页是"网站主人明确表达重要性"的页面，不能因为数量超标就砍。

**用户可以手动追加**：如果规则选漏了某个用户关心但没被导航/内链命中的页面，跑之前允许手动加几个URL进候选池。

**报告里必须显示候选页是怎么选出来的**，不能是黑箱：列出"导航页N个 / 产品集群N个（来自路径`/tools/`等）/ 内容页N个（按内链数取前15）"，让用户知道免费档到底查了哪些页面、为什么是这些。

### 建议方案：两档分别列出检查项目 / 检查范围 / 输出内容

**免费/轻量档**

| 维度 | 内容 |
|---|---|
| **检查范围** | 只爬"关键页候选池"（见上五条规则：首页+导航直链页+产品集群整簇+内容页按内链取前15+黑名单排除，安全阀50页）。**不做站内发现式爬取**——不追踪候选池规则之外的任何链接 |
| **检查项目** | 现有89项里所有标"X/12 key pages"的部分，逐页跑：Meta（标题/meta description长度与唯一性、canonical、robots指令、viewport、字符编码、HTML lang）、Content（静态HTML是否已含正文、HTML体积）、Links（本页出站链接是否可达，**不做全站链接图**）、Images（格式、alt等）、Social & structured data（schema/OG）、Technical & crawl（单页HTTP状态/响应时间/HTTPS/robots.txt可达性/是否在sitemap里/URL形态） |
| **明确不做** | 孤岛页面、断链扫描（全站范围的）、跨全站标题/meta重复检测、全站索引覆盖率扫描、CWV全站分布——这些都需要看过整站链接图或大量页面样本，放在付费档 |
| **输出内容** | 1）候选池里每个页面一行的评分卡（URL/总分/各类目小分，跟现在的展示方式一样）；2）如果候选池被截断，列出"未纳入检查的页面清单"；3）结尾一句话引导："想查全站孤岛页面、断链、跨站重复内容？升级到全站档" |
| **预期耗时** | 几秒到几十秒（页面数从214降到候选池量级，不是2–4分钟） |

**付费/全站档**

| 维度 | 内容 |
|---|---|
| **检查范围** | sitemap.xml + 站内爬取发现的全部页面，上限维持现状约950页/4分钟（这个上限本来就是产品已有的，不用改） |
| **检查项目** | 免费档的全部逐页检查，覆盖范围从候选池扩大到全部发现的页面 **+** 真正需要全站视角的检查：孤岛页面（爬到但没有任何内部链接指向的页面）、断链扫描（全站范围内部链接的404/redirect链检测）、跨全站标题/meta重复检测、索引状态全站扫描、CWV在全站的分布（不是单页数字，是按页面模板/类型分组的分布） |
| **输出内容** | 1）全站健康度总览（总分/等级）；2）按问题类型聚合的清单，不是逐页罗列（例如"7个断链，涉及23个页面"）；3）孤岛页面清单；4）CWV分布（按页面模板/类型分组，指出哪一类页面普遍慢）；5）免费档那份关键页深度报告，作为全站报告里的一个子集展示，不用重复算一遍 |
| **预期耗时** | 维持现状，2–4分钟 |

**不属于本次分层范畴，但顺带说明一下避免混淆**：
- "SOURCE GATED"那5条不受此次改动影响，它们要解锁得连Search Console，跟选哪个爬取档位无关，两个开关是独立的
- Business Competitor Frame（DataForSEO竞品建议）那部分不在检查项目录里，不受影响

### 好处

免费档的逐页检查逻辑不用重新设计——89项检查现在已经天然分成"关键页级别"和"必须全站"两组，只是被强制打包成一次运行、而且现在决定"关键页是谁"的逻辑本身有缺陷。这次要做的是：**把候选页选取规则换成上面这五条（首页/导航直链/产品集群整簇/内容页按内链取前15/黑名单排除）+ 把两组检查拆成两档运行**，不是从零开发新检查逻辑，选取规则也不需要再等产品拍板，按这份文档直接实现。
