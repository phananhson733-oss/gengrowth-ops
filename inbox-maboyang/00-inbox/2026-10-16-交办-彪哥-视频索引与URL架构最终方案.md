# 交办 · shortsbinge.com 视频索引问题与URL架构——最终方案

## 两个问题，现在的结论

| 问题 | 结论 |
|---|---|
| 1. 579条episode/1页面被GSC判定"视频不在观看页面上" | 根因是播放器间歇性加载失败，不是页面结构问题，也不是`/api/play/`接口慢——现场复现实锤，详见下面"问题一" |

## 问题一：579条episode/1页面加载失败（CDN层面，需要彪哥查内部监控）

### 已经验证清楚的部分，不用再查

- 不是页面结构/视频展示位置的问题：现场核查过DOM位置、展示尺寸，播放器在视口内、不需要滚动，没有被其他内容挤占
- 不是`/api/play/`接口的问题：失败发生时，直接`fetch`这个接口返回200，响应正常
- 不是CDN文件本身不存在：失败发生时，直接`fetch`视频文件（`v-mps.crazymaplestudios.com`，Range请求）返回206，文件可读
- 不是JS代码崩溃：失败发生时浏览器Console没有任何报错

### 现场复现的真实情况（真实浏览器，挂`<video>`官方标准事件监听器，拿到毫秒级时间线）

在一个免费首集页面（579条统计范围内的典型页面类型）上完整复现了一次失败，时间线：

| 时间 | 事件 | 含义 |
|---:|---|---|
| 288ms | `loadstart` | 浏览器开始请求视频 |
| **3523ms** | **`stalled`** | **readyState仍是0，3.5秒内一个字节视频数据都没收到** |
| 16465ms | `abort`+`emptied` | 播放器自己放弃第一次尝试，重置 |
| 16472ms | `loadstart`（自动重试） | 第二次尝试 |
| 19749ms | `stalled`（第二次） | 第二次尝试同样卡住 |
| 32130ms | `<video>`元素从DOM移除 | 彻底放弃，切到"This episode couldn't load"错误态 |

两次`stalled`出现的时间点（约3.5秒、重试后约3.3秒）精确对应WHATWG HTML官方规范定义的"media element stall timeout"（规范原文："should be about three秒"）——这证明浏览器如实报告了"CDN请求发出后，视频数据持续3秒以上没有到达"这个底层事实，不是测试工具的巧合。MDN对`stalled`事件的官方定性是"网络问题、服务器问题、连接超时"，不是客户端代码的判断失误。

对照测试了另一部剧的episode/1页面，当场没有复现失败——**确认是间歇性问题，不是100%必现**，这和579条占599条97%、但不是全部100%失败的统计特征吻合。

### Google官方对这个问题的权重说明

Google官方视频SEO文档原文：

> "Google needs to successfully fetch the actual bytes of a video file..."
> "The host of the video watch page and the server streaming the actual video must have enough server resources to support crawling."

Google明确要求"承载视频的服务器"（这里是`v-mps.crazymaplestudios.com`，Akamai CDN）必须有能力支撑抓取。我们现场复现的正是这台服务器间歇性在字节传输阶段卡住——这足以单独解释"视频不在观看页面上"这个判定。

### 需要彪哥做的事

1. **查Akamai后台这条路径的缓存命中率、边缘节点响应时间、是否存在限流策略**——现场测试只能证明"间歇性卡在字节传输阶段"这个现象存在，卡顿背后是cache miss回源慢、限流、还是连接数争抢，需要内部监控数据才能定位，这是本次最核心的待办
2. **修复"Try again"按钮**——现在点击后只是重新调用`/api/play/`接口，没能让播放器真正恢复，用户必须整页刷新才能恢复，这个按钮目前对用户是失效的
3. **验收标准**：抽查几个episode/1页面，用Google[富媒体搜索结果测试工具](https://search.google.com/test/rich-results)重新测试，确认视频能被识别为页面主体内容

## 问题二：非第1集页面——确认维持"只让Google抓第1集"策略，方案从canonical升级为robots.txt禁抓

### 背景澄清：10/12那次URL架构改动，不是为了加载速度，是为了控制爬虫成本

此前文档推测"10/12这次改动可能是为了解决视频加载慢的问题"，**这个推测是错的，彪哥已经澄清：10/12那次改动是为了控制爬虫渲染费用，不是加载速度**。彪哥给的数据：如果每集都是独立页面，全库约230万个选集地址；10/12之前片库约3000部时，选集页一天渲染最多2.7万次（九成以上是第2集以后的页面）；现在片库是当时的十倍多；按每千次$0.06-0.1算，Google爬一遍全部选集地址要$130-230。**这个成本数据直接决定了下面的方案选择，予以采信。**

### 最终方案：不追求第2集以后独立收录，用robots.txt彻底禁抓（彪哥方案"甲"）

业务侧已确认：第2集以后的页面**不需要**被Google独立搜到/进入视频搜索结果，优先级是把有限的抓取资源集中到"每部剧的第1集"这个入口上，扩大剧目覆盖广度，不追求单部剧多集同时被收录。这个决定本身符合Google官方抓取预算指南对万级以上页面站点的建议（原文："Consolidate duplicate content...focus crawling on unique content rather than unique URLs"）。

在这个前提下，**不需要再折腾canonical/og:url/JSON-LD这些标签**，直接在robots.txt里把第2集以后的页面对常规爬虫也禁抓即可——站内对AI爬虫（GPTBot等）已经用的是一模一样的模式，这次只是把这个规则也套用到`User-Agent: *`（覆盖Googlebot等常规爬虫）：

```
Disallow: /drama/*/episode/
Disallow: /*/drama/*/episode/
Allow: /drama/*/episode/1/
Allow: /*/drama/*/episode/1/
```

（具体规则顺序和写法请彪哥按站内robots.txt现有的AI爬虫那段模式套用，已经过验证的写法，不是新模式）

**这个方案的代价，确认过Google官方文档，需要提前说清楚、不是以后才发现的意外**：

1. **爬虫成本归零**——disallow之后Google根本不会再请求这些页面，这是彪哥方案"甲"的核心优点
2. **GSC那11条失败记录（episode/10、36等）、以及这份599条报告里任何涉及非第1集的记录，会永久停留在"失败"状态，不会再变成"通过"**——Google官方robots.txt文档原话："blocked by robots.txt...crawler will never see...the page can still appear in search results"，disallow不是"从索引里删除"，是"不再抓取"，已经被发现过的URL可能还会以"无描述、仅标题"的形式残留一段时间，这是预期行为，不是bug，不需要再派人去查
3. **之前方案里"修正JSON-LD让它别谎称自己是第1集"这条，现在不需要做了**——既然这些页面以后Google根本不会再抓取，结构化数据写什么Google都看不到，这条可以从待办里拿掉，减少彪哥的工作量
4. 这11条失败记录、以及未来任何同类"非第1集页面视频不在观看页面上"的GSC记录，**请内部统一定性为"预期内、不需要处理"，避免以后被当成遗留bug反复追查**

### Sitemap——确认不用改

已核实sitemap现状本来就只收录每部剧的落地页和`episode/1/`播放页，第2集以后从未进过sitemap，这和上面的策略天然一致，不是需要彪哥处理的项。

### 给技术的行动项清单（最终版）

1. **问题一**：查Akamai CDN后台数据定位间歇性卡顿根因；修复"Try again"按钮的重试逻辑
2. **问题二**：在robots.txt里给`User-Agent: *`加上"只允许抓第1集"的规则（参考站内AI爬虫那段现有写法）；不需要改canonical/og:url/JSON-LD；不需要改sitemap
3. 内部对齐：GSC视频索引报告里涉及非第1集的失败记录，统一定性为预期内状态，不再作为待办追踪
