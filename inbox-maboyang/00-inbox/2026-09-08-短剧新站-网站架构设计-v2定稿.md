# 零、v2 改了什么，为什么要改

v1 是对着 pinedrama.com 反推出来的方案，判断依据全部来自"别人家的站长什么样"。这几周 dramashortstv.com 完整走了一遍"设计新 URL 结构 → 上线 → 出故障 → 修复 → 验证生效"的全过程，等于用真实生产数据把 v1 里几条"建议"变成了"已验证"，也发现了几条 v1 完全没考虑到的硬约束。v2 只改这几块：

1. **新增一条不可协商的架构红线**：URL 构造方式，直接决定会不会重演 dramashortstv 那次大规模掉收录
2. **Sitemap 架构从"建议"升级为"已验证的具体做法"**，包括一个 v1 没提到的实操细节：不建议做 sitemap 总索引文件
3. **Schema 矩阵补全播放页的 VideoObject 具体写法**，包括"contentUrl 拿不到时怎么办"这个 v1 没遇到过的真实工程问题
4. **新增分类标签治理规则**，防止重蹈 dramashortstv 分类标签滥出到 468 个/标签的覆辙
5. **新增 Bing Webmaster Tools + IndexNow 接入**，第一次上线就做，不要等有了流量再补
6. **新增 sitemap 分批放量规则**：不能一上线就把全部 URL 暴露给 Google，新站从零信任起步，风险比 dramashortstv 这次更大
7. **v1 遗留的三个决策点**，本文档不替你拍板，原样列在最后，需要你确认

其余部分（站点地图、页面骨架、meta 标题公式、内链权重分配逻辑）v1 已经讲清楚了，v2 不重复，直接继承。

# 一、新增红线：URL 构造方式（这条不是建议，是强制要求）

dramashortstv 那次大规模掉收录的根因，最后查到是重定向逻辑里把没编码的非 ASCII 字符（西里尔文、越南语变音符号等）直接塞进了 HTTP 的 `Location` 响应头，触发 Node.js 报错，导致大量已收录页面直接 500。详细复盘见 `2026-09-08-dramashortstv大规模掉收录教训与新站预防清单.md`。

新站从第一行代码开始就要满足：

1. **全站只允许一个函数负责"把 locale + slug + 集数拼成 URL"**。页面渲染、sitemap 生成、canonical/hreflang 标签、未来任何重定向逻辑，全部调用同一个函数，不允许任何代码路径自己拼接 URL 字符串。这条在架构评审阶段就要定下来，不要等有人写"临时"重定向代码的时候才发现没有统一入口
2. **这个函数内部强制对每个动态片段调用 `encodeURIComponent()`**，没有例外
3. **CI 里必须有一条测试，用真实的非拉丁字母 slug（西里尔文/阿拉伯文/泰文/韩文样例各一个）走一遍完整的 URL 生成和请求流程**，不能只单测编码函数本身。这类问题本地测一次就能 100% 复现，新站不该在生产环境里第一次撞见它

多语言是新站从 v1 就定下的必做项，这条红线比 dramashortstv 当时更重要——dramashortstv 是后来才加的多语言，新站是一开始就要扛住全部语种，这个函数从项目第一周就要写对。

# 二、Sitemap 架构：v1"建议"升级为"已验证做法"，并新增一条反直觉的实操结论

v1 说"按内容类型分片，单文件不超 3 万条"，这条方向是对的，dramashortstv 重建时也是这么做的，实测结果：

| 家族 | 内容 | 分片数 | 单片容量策略 |
|---|---|---|---|
| index | 首页/分类页/分页 hub/固定页/blog | 1 片 | 全部塞一起，量小 |
| drama | 剧集详情页 | 到量就切下一片（实测约 2 万条一个阈值，最后一片是余数，不是每片都严格等分） | 简单按条数切 |
| watch | 播放页（量最大，只收免费集，付费集页面本身是 noindex，不进 sitemap） | 按剧数切（每 2,000 部一片），不按 URL 条数切 | 见下方"为什么按剧数切" |

**为什么播放页要按剧数切，不是按 URL 条数切**：如果按条数切（比如每 3 万条一片），生成逻辑需要先对全库做窗口函数求累积和，才能定位第 N 条 URL 属于哪部剧——如果 sitemap 路由是实时动态生成（不是预生成静态文件），这个查询每次抓取都要重新跑一遍，是不必要的数据库开销。按剧数切（比如每 2,000 部剧一片）不需要这个计算，直接按剧的创建顺序分段，性能可预测。新站如果 sitemap 也走动态生成，直接采用这个切法，不用重新踩一遍这个坑。

**一条框架特定的权衡，不是通用最佳实践，新站要按自己的技术栈重新判断**：dramashortstv 重建时决定不做 sitemap.xml 总索引文件，直接在 robots.txt 里逐条列分片。这个决定的前提是他们用 Next.js 的 `generateSitemaps` 生成分片，这个工具**不会自动生成索引文件**，要索引就得自己再写一个路由手动拼 XML——多一层容易漂移的东西（分片数量变化时索引文件要跟着同步更新，多一个出错点）。`robots.txt` 里逐条声明 `Sitemap:` 效果和索引文件是一样的，Google 支持任意多条声明，不需要包一层索引，这是他们选择跳过索引文件的直接原因。

**这个理由不适用于所有技术栈**：如果新站走静态预生成 sitemap，或者用的框架/工具本身就能顺手生成索引文件，加一层索引完全没有额外成本，那时候索引文件的"统一入口、方便人工检查"这些好处就该拿回来，不用照抄"不做索引"这条。新站架构评审时应该先确认自己的 sitemap 生成方式，再决定要不要索引文件，不要不假思索抄这条。

**robots.txt 逐条列的规模上限也要提前想清楚**：dramashortstv 现在是 19 条 `Sitemap:` 声明，如果新站内容量级更大（尤其是小说层如果真的上线），这个数字可能涨到几十甚至上百条。建议提前定一个触发点（比如超过 30-50 条时）就要重新评估要不要换回索引文件模式，不要等 robots.txt 变得难以维护了才回头处理。

# 三、Schema 矩阵：播放页 VideoObject 的具体写法（v1 只提了要补，没给方案）

v1 第六节写"新站按 dramashortstv 方案把 VideoObject 补全"，但当时 dramashortstv 自己也还没做这个。现在做完了，遇到的真实工程问题和解法一并记下来，新站直接抄：

**问题**：`VideoObject` 需要 `contentUrl` 或 `embedUrl` 才有意义，但短剧站的真实视频直链通常是带签名的临时 URL（不能落库，也不能进搜索引擎的缓存），播放器本身也可能是嵌入第三方（比如通过分销关系接入 ReelShort 等上游平台的播放源）。

**解法**：
1. `contentUrl` 一律不给——硬编一个签名过期的直链只会换来"视频无法抓取"的报错，比不给还差
2. `embedUrl` 指向自己站内的播放页 URL 本身（和 canonical 一致），**不要指向上游平台**——如果指向上游，等于告诉 Google"这个视频的规范位置在别的域名"，把好不容易能拿到的视频搜索结果拱手让给上游
3. 免费集（noindex 之外的正常可索引集数）才输出 `VideoObject`，付费引导页（本身就是 noindex）不输出——两段 Schema 只在真的有内容可看的页面上出现，不为不可索引的页面硬造结构化数据

**`uploadDate` 是已知弱项，新站规划内容同步节奏时要考虑这条**：如果内容是批量导入的（比如一次性同步几万部剧），且上游数据没有真实的首次发布时间，唯一能用的替代字段是"本站首次收录时间"，而这个时间如果集中在铺库的那一两天，几万条页面会声明同一个日期，这个信号大概率会被 Google 判定为无效（不是有害，只是没用）。**新站如果决定分批、错峰同步内容（而不是一次性全量导入），这个字段反而能天然分散，是更划算的做法**，值得在排产能计划时提前考虑，不是纯技术问题。

# 四、分类标签治理：新增规则，防止重蹈覆辙

v1 没有这条，因为写 v1 的时候还没观察到 dramashortstv 分类标签失控的规模。后来审计发现，dramashortstv 一个 `Bullying` 标签下面挂了 468 部剧，多数是自动打标签打出来的剧情元素词（不是观众会搜的题材词），乘上多语言之后是几千个几乎零搜索量的页面。

新站上线前就要定这条规则，不要等标签堆到几百个才回头治理：

1. **区分"题材词"和"剧情元素词"**，只有题材词（billionaire、mafia、revenge 这类观众会主动搜的类型）才生成独立可索引的分类页
2. **剧情元素词（写实设定，比如 apartment、hospital、caught-cheating 这类）默认不生成独立 URL**，作为纯前端筛选参数存在，或者生成页面但标记 `noindex`
3. **新增标签是否升级为"可索引分类页"，要过一遍最低搜索量门槛**，不是打标签系统自动生成就自动可索引——这条建议在 CMS/打标签流程里做成一个人工确认步骤，不要让它变成全自动的

# 五、新增：Bing Webmaster Tools + IndexNow 要在第一次上线时就接好，不要等有了流量再补

dramashortstv 这边是网站已经跑了一段时间之后才补的 Bing 验证和 IndexNow 接入（需求文档见 `2026-09-03-dramashortstv-bing-indexnow-接入需求.md`），等于错过了这段时间里 Bing/DuckDuckGo 本可以拿到的收录。新站是从零开始，这个成本极低（半天到一天的开发量），没有理由不在第一次正式上线时就一起接好：

1. **Bing Webmaster Tools 站点验证 + 提交 robots.txt**（不用逐条提交 sitemap，Bing 支持从 robots.txt 自动发现）
2. **IndexNow 协议**：生成 key、部署 key 文件、把批量提交接到内容同步流程上（不是接到"人工点发布"这个动作上）——具体接入方式和踩过的坑，直接照抄 dramashortstv 那份需求文档，不用重新设计一遍

这条本质上是"反正要做，早做比晚做省事"，不涉及任何需要你拍板的产品决策，架构定稿时直接列进第一阶段的开发任务里就行。

# 六、新增：sitemap 不能一上线就把全部 URL 一次性交给 Google，必须分批放量

**这条是从 dramashortstv 一次真实故障里学到的，新站的风险比它当时更大，必须写进架构里，不是运营建议。**

## 6.1 发生过什么（供理解风险，不是重复记流水账）

dramashortstv 修完 sitemap 后一次性把新增的几十万条 URL（主要是播放页家族）全部暴露给 Google。Google 发现后触发了一次补抓高峰：日抓取请求从平时的 1,500-8,000 次，两天内冲到 44,081 次（**平时的 5-30 倍**），平均响应时间同步从 225ms 爬升到 404ms。紧接着第三天，Google 的抓取量断崖式跌到 724 次（**比故障前的正常水平还低**），并持续多日没有回升——这是 Google 的算法检测到站点扛不住负载后自动收紧抓取预算的典型表现。表现出来的后果是：新页面进不去索引，老页面也因为长期得不到重新抓取验证而逐步掉出索引。

**新站的处境比这更危险**：dramashortstv 好歹在故障前有几个月的正常抓取历史，Google 对这个域名已经建立了基础信任，"扛不住就收紧"这个反应本身还算温和。新站是从 0 次已知抓取历史直接跳到 sitemap 里塞几十万条 URL，等于在 Google 对这个域名毫无信任基础的情况下，第一天就制造一次同等量级的抓取冲击——大概率不是"抓取量先冲高再回落"，而是从一开始就被判定为不稳定站点，压根不给冲高的机会，起步阶段的信任建立会比 dramashortstv 这次修复更慢。

## 6.2 新站上线时必须做的事

1. **sitemap 分批放量，不是一次性全量提交**。首次上线只暴露一个较小的初始集合（比如首页、分类枢纽页，加一批经过挑选的剧集详情页，不是全部）,让 Google 先建立起"这个域名正常、值得信任"的基础认知，再按周为单位逐步扩大 sitemap 覆盖范围，每次扩量之间观察抓取统计信息，确认服务器响应稳定了再扩下一批
2. **sitemap 相关的动态路由必须做缓存，不能是每次请求都实时查库**。这条不只是这次事故的教训，是从根上降低"同样抓取量对服务器的真实压力"——新站从设计阶段就该把这一条定成硬性技术要求，不要等出了问题才发现 sitemap 路由是 `force-dynamic`
3. **上线前必须做一次压测，模拟 Google 真实补抓时的并发量级**（参考这次的真实数字：平时基线的 5-30 倍），不能只测"平时正常访问量下没问题"就上线
4. **从第一天开始监控"抓取统计信息"**，不要等 Performance 报表里流量下跌了才回头查——抓取量异常永远先于流量异常出现，这次的真实时间线是抓取量 9/3 崩、展示量 9/4 才开始跌，中间有一天的窗口，只要盯着抓取统计信息，这个窗口是能提前预警的

# 七、v1 遗留的决策点（原样保留，不替你决定）

1. **新站是否要做小说层**，还是先把短剧+博客跑扎实
2. **博客是否要包含"AI 短剧行业趋势"这类面向创作者/媒体的选题**
3. **播放页视频承载方式**——自建 CDN+播放器，还是走可嵌入的第三方播放源（这条决定了第三节 VideoObject 方案里"embedUrl 指向自己"这个前提是否成立——如果视频源完全来自第三方且无法自建播放页面承载真实播放器，这个方案需要重新评估）

第 3 条现在比 v1 写的时候更紧迫——dramashortstv 的解法是"播放页自己承载一个前端播放器组件，内部再去调用/嵌入实际视频源"，如果新站也走分销/嵌入模式，这个产品形态需要提前和工程确认能不能做到，不是内容侧能单方面拍板的事。
