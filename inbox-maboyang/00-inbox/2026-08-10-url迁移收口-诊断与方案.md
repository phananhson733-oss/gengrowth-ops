# URL 迁移收口 · 诊断与方案

## 零、一句话结论

**迁移本身做对了，没有配置错误可修。** 真正的问题是：**我们把所有指向旧 URL 的路径都删干净了，导致 Googlebot 没有任何理由再去访问 `/en/*`，也就永远发现不了那个 308。**

**解决方式不是"修跳转"，是"临时给它一条抓取路径"。**

---

## 一、诊断：六项全部正确，所以不用改

2026-08-10 逐项实测：

| 检查项 | 结果 | 判定 |
|---|---|---|
| 旧 URL 跳转类型 | `308` 永久跳转，直达终点，无跳转链 | ✅ 正确 |
| robots.txt 是否禁止抓取 `/en/` | 未禁止，`Allow: /` | ✅ 正确 |
| sitemap 是否残留旧 URL | 99 条，含 `/en/` 的 **0 条** | ✅ 干净 |
| 站内是否仍有指向 `/en/` 的链接 | 首页 / /blog / /tools / 文章页 **均为 0** | ✅ 干净 |
| 新 URL 的 canonical | 自指 | ✅ 正确 |
| hreflang 是否仍指向 `/en/` | 已无 hreflang 标签 | ✅ 已修（8/5 审计报的问题已解决） |

**结论：没有一处配置需要改。** 这一点很重要——**如果按"排查配置错误"的思路去动，会白花时间，而且有很大概率把已经正确的东西改坏。**

## 二、那为什么 Google 还在索引旧 URL

因为**抓取路径被我们自己清空了**：

- sitemap 里没有旧 URL → Googlebot 不会从 sitemap 发现它
- 站内没有任何链接指向旧 URL → Googlebot 不会从内链爬到它
- 于是 Googlebot 只能靠**自己索引队列里的历史排期**慢慢轮回来重访

而 **gengrowth.ai 是 DR=0 的新站，抓取预算极低**。这个轮转可能要几个月。在轮到之前，Google 手里保存的仍然是迁移前那份索引——所以它继续用旧 URL 参与排名，占掉了 68.9% 的曝光。

**这不是 bug，是迁移的正常中间态。但它可以被明显加速，而且成本很低。**

## 三、🔴 需要工程做的（两件）

### 3.1 建一份临时的「迁移 sitemap」，只放旧 URL —— 最高杠杆

这是 Google 在站点迁移文档里明确推荐的做法，专门用于这种情况。

**做法：**
1. 新建 `/sitemap-legacy-en.xml`，列出全部历史 `/en/*` URL（至少覆盖 GSC 近 90 天有过曝光的那 46 个）
2. 每条的 `<lastmod>` 设为**迁移发生的日期**，不要设成今天
3. **不要**并进主 sitemap，要独立一份
4. 我在 GSC 里单独提交这一份

**原理**：给 Googlebot 一条明确的抓取路径 → 它去抓旧 URL → 拿到 308 → 把排名信号转移到新 URL → 旧 URL 退出索引。

> ⚠️ **收口后必须删掉这份 sitemap。** 长期留着等于持续声明旧 URL 是有效 URL，会变成新的问题。判断标准见第五节。

### 3.2 处理 7 个「308 跳到 404」的旧 URL

这 7 个是真正的缺陷，不是等待问题。它们**排名极好但跳过去是 404**：

| 旧 URL | 曝光 | 排名 |
|---|---:|---:|
| `/en/blog/9-best-marketing-attribution-tools-for-saas-in-2026` | 36 | 12.28 |
| `/en/blog/ai-marketing-automation-for-saas` | 11 | 6.64 |
| `/en/blog/gengrowth-vs-improvado` | 5 | **3** |
| `/en/blog/astrologywiki-zero-to-5000-users` | 2 | **1** |
| `/en/blog/gengrowth-vs-blaze` | 2 | **4** |
| `/en/blog/gengrowth-vs-cometly` | 1 | 7 |
| `/en/blog/gengrowth-vs-okara` | 1 | 8 |

曝光合计只有 58，量不大，**但排名第 1、第 3、第 4 的位置白白扔掉了**，而且 `308 → 404` 这种跳转链会被 GSC 报成重定向错误、浪费抓取预算。

**分两种情况处理：**

- **内容还想要的**（`astrologywiki-zero-to-5000-users` 排第 1、`gengrowth-vs-improvado` 排第 3，都是高意图词）→ 把内容恢复到新 URL 上，让 308 有个真实终点
- **确实不要了的**（旧定位的对比页）→ **直接返回 `410 Gone`**，不要保留 `308 → 404` 的链条

> **为什么用 410 而不是 404**：410 是明确的"已永久删除"信号，Google 会更快把它从索引里清掉；404 只是"现在没有"，Google 会反复回来试。

## 四、我这边做的（GSC 操作）

- 提交 `/sitemap-legacy-en.xml`
- 对曝光最大的旧 URL 用「网址检查 → 请求编入索引」手动催抓（每天有配额，按曝光排序做前 10 个）：
  `why-use-a-backlink-monitor-tool` 173 · `all-in-one-seo` 55 · `seo-starter-package` 36 · `manual-seo-service` 33 · `saas-seo-platform` 22 · `best-white-label-seo-tool` 13
- 每周记录 `/en/` 曝光占比，作为收口进度指标

---

## 五、❌ 不要做的四件事

1. **不要把旧 URL 加回主 sitemap** —— 那是永久声明它有效，和我们的目标相反。只能用独立的临时 sitemap
2. **不要在 robots.txt 里 `Disallow: /en/`** —— **这是这类问题最常见也最致命的错误**。一旦禁止抓取，Googlebot 永远看不到那个 308，旧 URL 会**永久卡在索引里**，情况比现在更糟
3. **不要给旧 URL 加 noindex** —— 跳转 URL 上加 noindex 是自相矛盾的指令，还会阻断权重传递
4. **不要因为"八篇文章新旧并存"就去改 canonical** —— 那是迁移处理中的正常现象（见第六节）

---

## 六、⚠️ 对 W32 周报里一处措辞的修正

周报 §2 写过：「旧 URL 排名（50.45）比新 URL（54.99）还好，权重滞留的那一份还更强」。

**这个说法要收一下。** GSC 是按它**当前索引的那个 URL** 归因的，新旧两条记录同时存在，说明 Google 还没把它们合并，**不代表两个页面在真的互相抢排名**。它们不是两个活着的重复页——旧的那个只是一条尚未被重新抓取的索引记录。

**收口完成后会自动合并，不需要为此单独做什么。** 这一条不影响方案，但影响我们怎么描述问题的严重性——**它是"等待中"，不是"正在互相伤害"。**

## 七、预期与验证

| 指标 | 现状 | 预期 |
|---|---|---|
| `/en/` 曝光占比 | **68.9%**（1,302 / 1,890） | 提交迁移 sitemap 后 2–4 周应单调下降 |
| GSC 网页索引「网页会自动重定向」 | 待取数 | 应先上升（说明 Google 在处理），再下降 |
| 308 → 404 的旧 URL | 7 个 | 修完应为 0 |

**如果 4 周后 `/en/` 占比没有明显下降**，说明抓取预算是更深的瓶颈，那就变成另一个问题（需要靠外链和内容更新提升抓取频率），届时再议。
