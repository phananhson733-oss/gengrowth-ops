# GenGrowth Discord 社区 0→1 建设与运营 SOP

> 目标：把对 GenGrowth 感兴趣、正在试用或已经使用产品的用户，沉淀为一个能获得帮助、交流 SEO/GEO 实战经验、参与产品共创的高质量社区。
>
> 原则：先建立“加入后立刻有价值”的最小社区，再邀请用户；不要先拉一批人进空服务器。

## 1. 当前状态 / 风险 / 建议

### 当前状态

GenGrowth 适合服务已有网站、希望提升自然增长效果的站长、营销人员、独立 SEO 从业者和小团队。社区内容可围绕 SEO Quick Wins、自然流量下降诊断、内链与孤岛检查、网站审计、关键词和 SEO/GEO 机会展开。

Discord 应承担三个角色：

1. **用户成功中心**：帮助用户完成首次使用并获得结果；
2. **产品反馈中心**：收集 Bug、需求、障碍和用户原话；
3. **用户关系中心**：交流案例、展示成果，形成长期留存。

### 风险

- 频道很多但没有负责人和稳定内容；
- 只发公告，社区变成单向广播群；
- 用户尚未获得产品价值就被要求加入另一个平台；
- 支持、Bug、建议混在一起，团队无法跟进；
- 批量拉冷用户造成低活跃、垃圾信息和品牌反感；
- Discord 活跃无法与产品激活、留存、付费关联。

### 建议

先用 **30–50 名种子用户、8–10 个频道、1 名明确 Owner** 跑 30 天，再扩大邀请。

首月北极星指标：**每周至少 10 名非团队成员完成一次有价值行为**。有价值行为包括提出真实问题、分享网站或数据、提交反馈、参与讨论、分享成果或帮助其他成员。

## 2. 社区定位

### 一句话定位

**GenGrowth Community 是面向站长、SEO/GEO 从业者和小型增长团队的实战社区：获取产品支持、诊断网站增长问题、交流可执行经验，并参与 GenGrowth 产品共创。**

### 用户加入的理由

- 更快解决产品使用问题；
- 获得网站 SEO/GEO 问题的诊断思路；
- 第一时间知道产品更新；
- 直接向产品团队提交建议；
- 学习其他用户的真实用法；
- 参加 Office Hours、网站诊断和社区挑战；
- 获得 Beta 功能、模板或早鸟权益。

### 社区不做什么

- 不做纯广告群；
- 不承诺免费代做完整 SEO；
- 不允许无关推广或私信骚扰；
- 不在公开频道收集账号凭据和敏感数据；
- 不以成员数、消息数代替真实用户价值。

## 3. 首批用户

| 优先级 | 用户类型 | 最佳邀请时机 |
|---|---|---|
| P0 | 已使用核心功能的用户 | 首次获得结果后 |
| P0 | 主动反馈 Bug、需求或问题的用户 | 问题解决后 |
| P1 | 完成审计但未持续使用的用户 | 首次审计后 |
| P1 | Waitlist、Newsletter、社媒高互动用户 | 表现出明确兴趣后 |
| P1 | SEO/GEO 从业者、站长、小团队 | 一对一邀请 |
| P2 | 泛营销或冷流量用户 | 暂不批量邀请 |

首批 30–50 人建议由：10–15 名产品用户、10 名高意向/反馈用户、5–10 名合作伙伴或同行、5–10 名愿意访谈/共创的用户组成。

| 角色 | 权限 |

| Community Manager | 公告、频道、成员和活动 |

## 8. 怎么把用户邀请进来

原则：**先提供价值，再邀请；说明加入理由，不强迫加入。**

### 产品内邀请

最佳触发点：首次审计完成、看到诊断结果、导出报告、连续使用两次、提交反馈、遇到问题或申请 Beta。

CTA：

> Want help interpreting your results? Join the GenGrowth Community to ask the team, share feedback, and learn from other site owners.

不要在注册前或首页首屏强推 Discord。

### 邮件邀请

优先发给完成首次价值动作、主动反馈、参加 Waitlist/Beta/访谈或近 30 天活跃的用户。邮件应说明邀请原因、加入价值、首个动作，使用可归因链接，并允许用户忽略。

### 一对一邀请模板

```text
Hi [Name]，感谢你最近使用 GenGrowth / 给我们反馈。

我们刚建立了一个小型 Discord 社区，主要给正在做 SEO、GEO 和网站自然增长的用户使用。你可以直接向产品团队提问、参与新功能共创，也可以和其他站长交流实际问题。

如果你愿意加入，这是邀请链接：[Discord link]

加入后可以在 #introductions 发一下你的网站和目前最想解决的问题，我会亲自跟进。
```

### 支持结束后的邀请

```text
很高兴这个问题已经解决。我们在 Discord 里有 #product-help，也会发布产品更新和 Office Hours。如果你希望以后更快联系团队，可以从这里加入：[Discord link]
```

### 入口优先级

1. 产品结果页；
2. Lifecycle Email；
3. 客服/访谈后的一对一邀请；
4. 官网 Footer / Community 页面；
5. X、LinkedIn 和 Blog CTA。

CTA 要说明具体价值，如 Get help with your audit、Join the next website review、Test new SEO/GEO features，而不是只有 Join Discord。

## 9. 冷启动内容与节奏

邀请前准备：欢迎帖、5 分钟产品入门、增长问题讨论、匿名/自有网站诊断示例、Roadmap 问题、Office Hours 时间、Wins 模板和 FAQ。

| 星期 | 内容/活动 | 目标 |
|---|---|---|
| 周一 | 本周增长问题 / Poll | 激活讨论 |
| 周二 | 产品技巧 / 5 分钟教程 | 提升使用 |
| 周三 | Office Hours / 网站诊断 | 建立信任 |
| 周四 | Build in Public / 产品反馈 | 促进共创 |
| 周五 | Community Wins + 更新 | 强化成果感 |

首月每周 3–4 个高质量动作即可，不必每天刷屏。

## 10. 首月活动

### GenGrowth Website Clinic

每周一次、30–45 分钟、每次 2–3 个网站。每个网站只输出 1 个优先问题、1 个建议、1 个下一步，明确不是完整咨询或代运营。

### 7-Day SEO Quick Win Challenge

用户用 GenGrowth 找到一个机会，记录修改前数据，完成一次优化，7 天后汇报过程和早期结果。SEO 可能需要更长时间，活动不承诺 7 天排名上涨。

### Build With Us

每两周讨论一个产品问题；结束后公开“听到了什么、决定做什么、暂时不做什么及原因”。

## 11. 职责与回复 SLA

Community Owner 每天欢迎成员、确保问题有人接、清理垃圾、分配问题、记录用户原话；每周发起讨论、组织活动、发布摘要并复盘数据。

产品/工程团队负责回应升级问题、标记状态、不在未确认前承诺日期、修复后回原帖闭环。负责人每月至少参加一次 AMA 或 Office Hours。

| 类型 | 首次回应目标 |
|---|---|
| 一般讨论 | 24 小时内 |
| 产品使用问题 | 工作日 12 小时内 |
| 严重 Bug | 工作时段 4 小时内 |
| 功能建议 | 48 小时内确认收到 |
| 违规内容 | 发现后尽快处理 |

无法立即解决时，说明已收到、谁在处理、下次更新时间和所需补充信息。

## 12. 指标与归因

```text
被邀请 → 点击 → 加入 → 完成身份/介绍 → 首次价值行为
→ 7 日活跃 → 30 日活跃 → 产品激活/留存/付费/案例
```

| 指标 | 首月目标 |
|---|---|
| 种子成员 | 30–50 |
| 完成介绍率 | ≥ 40% |
| 7 日内首次价值行为率 | ≥ 35% |
| 提问 24 小时内回应率 | ≥ 90% |
| 每周非团队发言人数 | ≥ 10 |
| 每周有效产品反馈 | 3–5 条 |
| 案例线索 | 2–3 个 |
| 违规处理率 | 100% |

分别创建 product-result、lifecycle-email、support、founder-outreach、x、linkedin、blog、partner 邀请链接。记录 invite_source、join_date、user_segment、product_stage、first_value_action、feedback_theme、case_study_candidate、30_day_status。

## 13. 反馈闭环与风控

| 类型 | 处理方式 |
|---|---|
| Bug | 进入问题跟踪，记录严重度和状态 |
| 使用障碍 | 更新 onboarding、FAQ、文案或体验 |
| 功能建议 | 合并同类需求，保留用户原话和上下文 |
| 成果/案例 | 取得授权后进入案例跟进 |

反馈要记录用户想完成的任务、当前方案、困难、频率、不解决的影响、是否愿意访谈，以及对激活/留存/付费的可能影响。

违规处理：轻微偏题则引导；重复推广则删除并警告；骚扰、诈骗、仇恨或恶意行为则禁言/封禁；发现敏感数据则删除并升级；产品事故或集中投诉时暂停常规宣传，统一更新状态。

## 14. 30 天上线计划

### 第 1 周：搭建

- [ ] 指定 Owner 和升级联系人；
- [ ] 创建最小频道、角色和权限；
- [ ] 配置欢迎、规则和安全；
- [ ] 准备 FAQ、模板和冷启动内容；
- [ ] 创建渠道邀请链接；
- [ ] 团队完整走一遍 onboarding。

### 第 2 周：内部试跑

- [ ] 邀请 5–10 名团队成员和熟悉用户；
- [ ] 测试权限、通知、Bot 和模板；
- [ ] 模拟产品问题、Bug、建议和违规；
- [ ] 检查责任是否清晰；
- [ ] 删除没人使用的频道。

### 第 3 周：种子用户

- [ ] 一对一邀请 20–30 名高意向用户；
- [ ] 每位新用户获得人工欢迎；
- [ ] 举办第一次 Office Hours；
- [ ] 发起第一次产品共创；
- [ ] 每天记录加入、激活和问题类型。

### 第 4 周：复盘扩展

- [ ] 统计邀请转化、价值行为和 7 日活跃；
- [ ] 访谈 5 名活跃和 5 名不活跃成员；
- [ ] 找出最有价值和最冷清的频道；
- [ ] 汇总 Bug、需求和案例；
- [ ] 决定是否扩大产品内和邮件邀请；
- [ ] 发布“我们听到了什么 / 接下来做什么”。

## 15. 扩大邀请前的验收

- [ ] 至少一名 Owner 能稳定投入；
- [ ] 每个频道用途清楚；
- [ ] 新用户 5 分钟内知道下一步；
- [ ] 产品问题有明确接手人；
- [ ] Bug 和建议能闭环；
- [ ] 至少 5 条高质量内容；
- [ ] 已排期首次活动；
- [ ] 权限和敏感数据规则已检查；
- [ ] 数据归因已确定；
- [ ] 团队承诺连续运营至少 30 天。

## 16. 负责人需确认

1. 首要目标是什么？建议：**用户成功 > 产品反馈 > 社区增长**；
2. 首批邀请哪些具体用户，谁负责筛选？
3. Owner 每周能投入多少时间？
4. 哪些问题允许公开讨论？
5. Beta、Office Hours 或早鸟权益是什么？
6. 主要语言是什么？不要一开始拆多个语言频道；
7. Discord 身份如何与产品账户对应，同时避免过度收集信息？
8. 30 天后用哪些指标决定继续、调整或暂停？

## 17. 最终执行原则

1. 社区价值来自高质量互动，不来自复杂结构；
2. 用户获得一次产品结果后，是最佳邀请时机；
3. 每个问题都要有人回应，每个反馈都要有去向；
4. 先服务好 30–50 名种子用户，再追求规模；
5. 每月公开反馈闭环，让用户看到自己的声音产生影响；
6. Discord 必须回流到产品激活、留存、案例和用户洞察，不能成为独立孤岛。

## 18. Discord 实际搭建需要准备什么

你过去做过运营，所以内容、活动和成员互动不是主要难点。第一次搭建时，真正需要补齐的是以下六类底层工作：

1. **账号资产**：服务器归谁、用什么邮箱、谁能恢复；
2. **服务器结构**：频道、分类、角色和权限；
3. **安全系统**：2FA、验证等级、AutoMod、日志和备份；
4. **成员路径**：从邀请链接到选身份、看规则、进入频道；
5. **工作流**：问题、Bug、建议如何流转和闭环；
6. **上线验收**：用普通用户身份完整测试，而不是管理员视角检查。

### 18.1 搭建前需要向团队拿到的材料

| 类别 | 需要的东西 | 说明 |
|---|---|---|
| 品牌资产 | Server 名称、Logo、Banner、品牌色、简介 | 初期 Logo 可以直接使用 GenGrowth 品牌头像 |
| 账号资产 | 公司控制的注册邮箱、恢复方式、2FA | 不建议长期绑定运营者私人邮箱 |
| 负责人 | Server Owner、Admin、Community Owner、产品/技术联系人 | Owner 不等于每天运营的人 |
| 用户信息 | 首批用户名单、用户阶段、语言、来源 | 不需要把完整客户数据库导入 Discord |
| 社区文案 | Welcome、Rules、FAQ、频道说明、邀请文案 | 上线前全部准备好 |
| 支持规则 | 服务时间、首次回复 SLA、紧急升级方式 | 避免用户默认社区提供 24/7 支持 |
| 产品材料 | 产品入口、Getting Started、帮助文档、反馈入口 | 所有链接上线前逐个测试 |
| 权益 | Beta、Office Hours、模板、早鸟权益 | 至少准备一个明确的入群价值 |
| 数据方案 | 分渠道邀请链接、周报表、指标 Owner | 用于判断哪个入口带来有效用户 |

如果这些材料没有准备齐，最低限度也必须先确认：**公司邮箱、Server Owner、Community Owner、产品联系人、Logo、欢迎语、规则和首批用户。**

## 19. 搭建顺序：从空服务器到可邀请用户

### Step 1：确定服务器所有权

建议结构：

- **Server Owner**：公司负责人或长期稳定的公司账号；
- **备用 Admin**：1 人，防止 Owner 无法登录；
- **Community Owner**：负责日常运营，可以有管理权限，但不必持有服务器所有权；
- **产品/技术成员**：只开放回答和管理反馈所需权限。

必须完成：

- 使用公司控制的邮箱；
- 开启 2FA；
- 保存恢复码；
- 记录 Owner、备用 Admin、创建日期和恢复方式；
- 不多人共用一个 Discord 账号。

> Discord 的 Server Owner 权限最高。运营人员离职或角色变化时，如果 Owner 是私人账号，后续交接会很麻烦，所以所有权要在第一天设计好。

### Step 2：创建服务器并完成基础设置

在 Discord 中选择 **Add a Server → Create My Own**，然后完成：

1. Server Name：`GenGrowth Community`；
2. Server Icon：使用清晰的方形品牌 Logo；
3. Description：一句话说明用户和价值；
4. 默认通知：建议设为 **Only @mentions**，避免新成员被大量消息打扰；
5. 系统消息：不要放进核心讨论频道，可单独放到内部或关闭不必要提示；
6. 地区/语言：以首批真实用户的主要语言为准。

首期不必追求复杂视觉装修。服务器图标、名称、简介和统一频道命名清楚即可。

### Step 3：开启 Community 功能

在 Server Settings 中启用 **Community**。启用后通常需要指定：

- Rules / Guidelines Channel；
- Community Updates Channel；
- 安全扫描或验证设置；
- 默认通知规则。

开启 Community 的价值：

- 可以使用规则筛选、Onboarding、公告等社区功能；
- 更适合公开或半公开运营；
- 为后续活动、发现页或更完整的社区功能留出空间。

注意：具体界面名称可能随 Discord 版本调整，但你要找的核心模块始终是 Community、Safety、Onboarding、Roles 和 Invites。

### Step 4：先建立角色，再建立频道权限

推荐角色顺序（由高到低）：

```text
Server Owner
Admin
Community Manager
Moderator
Automation Bots（按需要放置）
Product Team
Beta Tester
Community Contributor
Active User
Trial User
Prospect
@everyone
```

搭建角色时需要注意：

- Discord 的角色有层级，高层角色才能管理低层角色；
- Bot 角色必须低于 Admin，高于它需要管理的普通成员角色；
- 不要给 Bot `Administrator`，除非功能明确要求且已经评估风险；
- `@everyone` 只保留最基础的查看和互动权限；
- Admin 控制在 1–2 人；
- “贡献者”“Beta 用户”等身份不应自动获得管理权限。

### Step 5：创建频道分类和频道

按以下顺序建立即可：

```text
START HERE
#welcome
#rules
#introductions
#choose-your-role

PRODUCT
#announcements
#getting-started
#product-help
#bug-reports
#feature-requests

COMMUNITY
#seo-geo-discussion
#wins-and-results
#website-feedback

TEAM — PRIVATE
#community-ops
#user-escalations
#voice-of-customer
#moderation-log
```

频道权限建议：

| 频道 | 谁能看 | 谁能发 |
|---|---|---|
| #welcome / #rules | 所有人 | 仅团队 |
| #announcements | 所有人 | 仅团队，用户可按需回应 |
| #introductions | 已通过规则的成员 | 所有成员 |
| #product-help | 成员 | 成员和团队 |
| #bug-reports | 成员 | 成员和产品团队 |
| #feature-requests | 成员 | 成员和产品团队 |
| TEAM — PRIVATE | 指定团队角色 | 指定团队角色 |

搭建时优先在“分类”层设置权限，再让频道继承；只有特殊频道单独覆盖。这样以后调整不会逐个频道改。

### Step 6：配置安全和审核

至少配置以下项目：

- 开启管理员 2FA 要求；
- 提高成员验证等级，减少刚注册小号直接发言；
- 开启 Discord AutoMod；
- 屏蔽明显诈骗词、恶意链接和高频垃圾消息；
- 限制 `@everyone` 和 `@here` 的使用；
- 限制普通成员创建 Webhook、管理频道或管理角色；
- 设置 Moderator 可执行的 Timeout、删除消息和封禁权限；
- 建立 #moderation-log；
- 定期检查 Active Invites、Integrations、Bots 和 Webhooks。

AutoMod 不要一次设置得太激进。先拦截明显诈骗、辱骂和刷屏，再根据实际误杀情况调整。

### Step 7：配置新成员 Onboarding

用户第一次加入时，只让他完成少量选择：

1. 我是：正在了解 / 正在试用 / 已在使用；
2. 我的身份：Founder / SEO / Marketer / Agency；
3. 我最关注：SEO Quick Wins / Traffic Drop / Internal Links / SEO-GEO / Keyword Research。

这些回答可用于：

- 自动分配身份；
- 推荐相关频道；
- 让运营人员知道如何欢迎；
- 后续按用户阶段组织内容。

首期不要问超过 3 个问题，也不要要求用户提交邮箱、公司规模等过多资料。加入摩擦越大，完成率越低。

### Step 8：准备频道首帖和置顶内容

每个频道上线前至少要有：

- 一句话用途；
- 允许发什么；
- 不允许发什么；
- 提交模板；
- 谁会回应；
- 预计回复时间。

例如 #bug-reports 的首帖应该明确：不要发送密码、OAuth Token、GSC/GA4 凭据；如需私密信息，由团队通过官方方式另行收集。

### Step 9：决定是否需要 Bot

初期建议只使用 Discord 原生功能。只有明确问题时再加 Bot。

| 需求 | 首选方案 |
|---|---|
| 欢迎和身份选择 | Discord 原生 Onboarding |
| 垃圾信息与敏感词 | Discord AutoMod |
| 活动创建 | Discord Events |
| 规则确认 | Community / Membership Screening |
| 复杂工单 | 先人工处理，量上来后再评估 Ticket Bot |
| 数据统计 | Discord Insights + 手工周报起步 |

添加 Bot 前检查：

- 谁开发和维护；
- 它需要读取什么数据；
- 要求哪些权限；
- 是否能访问私密频道；
- 停止维护后如何移除；
- 是否真的比原生功能更省事。

首月通常不需要等级、积分、签到、经济系统或多个自动化 Bot。

### Step 10：创建分渠道邀请链接

不要全渠道共用一个永久链接。分别创建：

- `product-result`；
- `lifecycle-email`；
- `support`；
- `founder-outreach`；
- `x`；
- `linkedin`；
- `blog`；
- `partner`。

每个链接记录：名称、创建人、投放位置、有效期、使用次数和对应用户质量。

对于一对一邀请或小范围 Beta，可使用有期限或次数限制的链接；官网长期入口再使用稳定链接。发现垃圾用户集中来自某个链接时，可以单独撤销，不影响其他渠道。

### Step 11：内部测试

至少使用两个测试账号：

- **管理员账号**：检查管理、升级和处理流程；
- **普通新用户账号**：检查真实加入体验。

普通用户视角逐项测试：

- 邀请链接能否打开；
- 是否能看到 Welcome 和 Rules；
- Onboarding 是否容易完成；
- 是否错误看到内部频道；
- 是否能在正确频道发言；
- 是否不能使用危险权限；
- 模板、链接和 @mention 是否正常；
- 手机端是否好用；
- 退出后重新进入是否正常。

尤其要测试“普通用户看不到什么”。很多权限问题在管理员视角下无法发现。

### Step 12：软启动，而不是直接公开

建议顺序：

1. 团队内部 5 人测试；
2. 邀请 5–10 名熟悉用户试跑；
3. 修复权限、文案和流程；
4. 一对一邀请 20–30 名种子用户；
5. 跑完第一次活动和一周支持；
6. 再决定是否开放官网和产品内入口。

## 20. 一个人搭建时的实际工作量

如果品牌材料和文案已经准备好，一个熟悉 Discord 运营但第一次搭建的人，可以按以下预算排期：

| 工作 | 预计时间 |
|---|---|
| 服务器、角色和频道 | 2–3 小时 |
| 权限和安全设置 | 2–3 小时 |
| Welcome、Rules、频道首帖 | 3–5 小时 |
| Onboarding 和邀请链接 | 1–2 小时 |
| 普通用户测试与修正 | 2–3 小时 |
| 冷启动内容和首场活动准备 | 3–5 小时 |
| 合计 | 约 2 个工作日 |

真正耗时的不是点击创建频道，而是：权限测试、文案准备、团队责任确认和问题闭环设计。

## 21. 最容易踩的搭建坑

1. **直接用私人账号持有服务器**：后续交接和恢复风险高；
2. **给太多人 Admin**：任何账号被盗都可能影响整个服务器；
3. **给 Bot 过高权限**：第三方 Bot 是常见安全风险入口；
4. **先建二三十个频道**：用户被空频道吓退；
5. **只用管理员账号测试**：看不到普通用户权限错误；
6. **所有渠道共用一个邀请链接**：无法归因，也无法单独阻断垃圾来源；
7. **欢迎流程问题太多**：新成员还没看到价值就退出；
8. **没有回复 SLA**：用户以为没人管，团队以为别人会回；
9. **把 Discord 当客服系统替代品**：敏感问题和复杂工单仍需私密、可追踪的处理方式；
10. **上线当天才准备内容**：首批用户进入后看到空服务器。

## 22. 搭建完成验收表

### 资产

- [ ] 服务器由公司长期可控账号持有；
- [ ] Owner 和备用 Admin 已开启 2FA；
- [ ] 恢复方式已安全保存；
- [ ] 品牌名称、Logo、简介正确。

### 权限

- [ ] Admin 不超过 2 人；
- [ ] Bot 无不必要的 Administrator 权限；
- [ ] @everyone 无管理频道、角色和 Webhook 权限；
- [ ] 普通成员看不到 TEAM — PRIVATE；
- [ ] Moderator 能处理消息和违规，但不能改核心设置。

### 用户体验

- [ ] 邀请链接可用；
- [ ] 规则和 Onboarding 可完成；
- [ ] 新成员知道第一步做什么；
- [ ] 每个频道都有说明和模板；
- [ ] 手机端测试通过；
- [ ] 普通测试账号权限正确。

### 运营

- [ ] 至少准备 5 条冷启动内容；
- [ ] 首次 Office Hours 已排期；
- [ ] Support、Bug、Feature Request 都有负责人；
- [ ] 回复 SLA 已对团队确认；
- [ ] 分渠道邀请链接已登记；
- [ ] 首周值班安排已确定。

## 23. 你作为搭建负责人的最短执行清单

如果只看一份清单，就按这个顺序做：

1. 找负责人确认 Owner、Admin、Community Owner；
2. 拿到公司邮箱、Logo、简介、产品链接和首批用户；
3. 创建 Server，开启 Community 和 2FA 要求；
4. 先建角色并排序；
5. 再建分类和 8–10 个公开频道；
6. 在分类层设置权限，内部频道单独限制；
7. 配置 AutoMod、验证等级和 @everyone 限制；
8. 配置 Onboarding、身份选择和频道推荐；
9. 发布 Welcome、Rules、Getting Started、FAQ 和反馈模板；
10. 建立不同来源的邀请链接；
11. 用普通账号和手机完整测试；
12. 先邀请 5–10 人软启动，修正后再邀请首批用户。
