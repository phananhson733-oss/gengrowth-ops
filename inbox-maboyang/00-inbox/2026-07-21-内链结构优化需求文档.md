# AstrologyWiki 内链结构优化需求文档

---

## 一、问题背景

自动化博客系统当前存在两个导致内链不严谨的系统性问题，直接影响 Google 对页面集群权重的判断，需在 v2 内容全速生产（7/27 起）前完成修复。

已确认的线上案例：`/en/wiki/venus-in-gemini`（7/18 发布，KD=1，月搜索量 3,100）目前排名第 69 位，曝光仅 5 次，根因即为集群归属错误导致零入链。

---

## 二、根本原因分析

### 问题一：集群错误分配

系统在处理执行表关键词时，无法在主题集群表中找到对应集群定义，因此退回语义推断，将关键词归入最相似的已有集群。结果是：

- `venus in gemini` → 被归入 `worldcup2026_astro`（世界杯集群）
- `moon in capricorn` / `moon in cancer` → 被归入 `nakshatras_27_stars`（印度占星集群）
- `mars in scorpio` → 被归入 `lunar_nodes_path`
- `saturn return guide`（应为独立集群主页）→ 被归入 `transit_events`（行星过运大集群）
- 实验六-九所有关键词 → 均无正确集群定义，系统行为不可预期

内链按错误集群规则生成，页面之间没有形成正确的 Hub-Spoke 结构，PageRank 无法在正确集群内传递。

### 问题二：时序内链缺失

同一集群内，若文章 A、B 先于文章 C 发布：

| 链接方向 | 是否存在 |
|---------|---------|
| A → 主页（已发布）| ✅ |
| B → 主页（已发布）| ✅ |
| 主页 → A、B（发布时 A/B 不存在）| ❌ |
| A ↔ B（同天生成，互不知晓）| ❌ |
| C → A、B（C 发布时可写入）| ✅ |
| A、B → C（A/B 发布时 C 不存在）| ❌ |

结果是：所有 spoke 页面都能指向 Hub，但 Hub 无法向下分发权重，同日发布的 spoke 之间也没有横向链接。

---

## 三、解决方案

**方案：提前提交发布计划 + 发布后精准回填（Smart Backfill）**

与其让系统事后盲目扫描，改为在发布任何文章之前，先将完整执行计划（含集群归属、slug、角色）提交给系统，系统维护一张"待发布链接图"，每次文章发布时按图执行精准回填。

```
执行表（提前提交）
    ↓
系统解析 → 集群地图（cluster_id / slug / 角色 / 内链规则）
    ↓
文章 X 发布
    ├── 生成时：注入指向同集群已发布文章的内链
    └── 发布后触发回填：在同集群已发布文章中追加指向 X 的内链，重新部署
```

**数据来源**：主题集群表（内链规则）+ 选题登记表（cluster_id / slug / 角色）。系统读表，不做语义推断。

## 五、系统层需求

### 5.1 集群地图加载

系统在处理任何执行表之前，必须先完整加载主题集群表和选题登记表，构建内存中的集群地图：

```
cluster_map[cluster_id] = {
  pillar_slug: string,
  internal_link_rule: string,
  pages: [{ slug, page_role, artist_group? }]
}
```

**禁止语义推断**：若关键词在选题登记表中找不到对应 cluster_id，系统应抛出异常并中断，而不是自动推断。

### 5.2 文章生成时的内链注入规则

生成文章 X 时，按以下优先级注入内链：

| 规则 | 适用集群类型 | 链接目标 |
|------|------------|---------|
| R1：Spoke → Pillar 强制链接 | 所有集群 | X 所在集群的 Pillar 页（若 Pillar 已发布） |
| R2：Pillar → 已发布 Spoke | 所有集群 | 同集群所有已发布 Series 页 |
| R3：同行星交叉链接 | `planetary_placements_natal` | 同行星的其他已发布页面 |
| R4：同艺人 Series → Pillar | `pop_music_birthchart` | 相同 artist_group 的 birth chart 页 |
| R5：同 IP 角色交叉链接 | `fiction_*` | 同集群其他已发布角色页（最多 3 条） |

**内链数量上限**：每篇文章正文内链不超过 8 条（不含组件级链接，如工具推荐卡、相关文章卡）。

### 5.3 发布后回填机制（Smart Backfill）

文章 X 发布后，系统执行以下回填流程：

1. 查询同集群所有已发布文章列表（从选题登记表 + 结果复盘表联合查询）
2. 对每篇已发布文章，判断是否需要追加指向 X 的内链：
   - Pillar 文章：追加指向新 Spoke X 的链接（R2 规则）
   - 同平级 Spoke：按 R3/R5 规则判断是否追加交叉链接
3. 修改对应 MDX/内容文件，追加内链
4. 触发重新部署（建议批量合并同批次修改，单次 PR，避免频繁部署）

**回填触发时机**：每日发布完成后统一触发一次，而非每篇发布后立即触发。

### 5.4 已有错误集群的存量修复

对已发布的实验三-五页面（共约 34 篇），在数据层完成 cluster_id 修正后，系统执行一次全量回填，重建正确的内链网络。

优先级最高：`venus in gemini`（已上线 3 天，零入链，需立即修复）。
