# gengrowth.ai 操作页设计方案 v1

## 一、先说清楚我们现在有什么（2026-08-12 实测）

| 能力 | 状态 | 对应工具 |
|---|---|---|
| **SEO 诊断** | ✅ 已上线 | GSC Opportunity Finder · Traffic Drop Diagnosis · Internal Link Audit |
| **Technical SEO** | ✅ 已上线 | Free site-wide SEO audit（meta / 标题结构 / 断链 / 孤岛 / 索引 / CWV / Schema） |
| **GEO（AI 搜索可见度）** | ❌ **无工具** | 只有 6 篇 blog 文章 |
| **内容写作** | ❌ **无工具** | — |
| 关键词机会 | ⏸ Waitlist | `/tools/low-competition-keywords`（609 词，无输入框） |

> **能驱动界面的只有四个工具，且全部是一次性诊断——跑完就结束，没有持续产出。这是本方案最大的约束。**

**顺带记录两个变化**：`/tools/hidden-keywords` 已改名为 `/tools/low-competition-keywords`，主词从自造产品名换成了真实搜索词（`find low competition keywords` 全页 8 次）——这是 8/10 提出的建议，已落地。但工具本身仍是 Waitlist。

## 二、核心设计原则

> ### **Okara 的主区域是「今天有 9 件事可做」，我们的主区域应该是「现在做这 1 件」。**

**排除逻辑放在 Diagnosis 层，不占主区域。**

| | 用户看到 | 问题 |
|---|---|---|
| Okara | 今天有 9 件事可做 | 不告诉你哪件值得，**选择瘫痪** |
| ❌ 早期草案 | 这 9 件里 7 件别做 | 没有可执行的下一步，**打击积极性** |
| ✅ **本方案** | **做这 1 件——另外 8 件已替你排除，原因可展开** | **既有动作，又有信心** |

**排除的价值不在于被展示，而在于让那一个推荐变得可信**——用户知道这不是随便挑的。

### 唯一的例外

**当用户即将投入大成本做一件注定无效的事时，主动打断。**

例：他准备围绕 `internal link checker` 写十篇文章——该词前七名全是 DR 73–99，**写完也进不去**。这时"别做，原因在这"比任何正向建议都值钱，因为省下的是几周。

**规则：默认给正向的下一步；只在能证明用户要踩大坑时才主动说「别」。**

## 三、四栏布局

### 3.1 左栏 · 项目上下文

```
[站点选择器]  gengrowth.ai

📄 项目文档（单一事实源）
   ├ 站点画像             自动生成
   ├ 目标关键词            ⭐ 我们独有
   ├ 已排除关键词 + 原因    ⭐ 我们独有
   └ 竞争对手（SERP 实测）  ⭐ 我们独有

🎯 竞争对手
   实测 SERP 前十，不是推测
```

**「文档先行、单一事实源」这一层值得从 Okara 抄，而且我验证过它的生成质量是真的**——它给 AstrologyWiki 生成的产品文档准确抓到了"把星盘当自我认知工具而非算命"这个定位，连定价档位和支付渠道都扒对了，不是套模板。

**而这恰恰是我们最缺的一层**：两天内产出 22 份文档、三份互相打补丁、工具命名三套口径并存——没有单一事实源。

#### ⭐ 三处 Okara 完全没有的

| 我们独有 | 为什么重要 |
|---|---|
| **已排除关键词 + 原因** | Okara 只给机会，不记录否决。**否决记录防止团队反复讨论同一个已经死掉的词** |
| **竞争对手用 SERP 实测** | Okara 给 AstrologyWiki 识别的对手是 `costarastrology.com` 和 `astro.com`——**而实测真正的对手是 Astro-Seek（13.62M 月访）、Astrotheme（2.21M）、Cafe Astrology（5.57M）、AstroLibrary、BirthChart.net，一个都没识别出来** |
| **目标词的 AI Overview 覆盖度** | 见 3.5 |

### 3.2 中栏 · 审计模块（对标 Okara 分析面板 + AITDK 插件后重设计）

#### 3.2.0 先说两个对标对象各自做了什么

**Okara「分析」面板（2026-08-12 实测五个 tab）**

| Tab | 内容 | 数据源 |
|---|---|---|
| Traffic | GSC 曲线：Clicks / Impressions / CTR / Position，7 天 / 30 天切换 | GSC（GA 未连接） |
| SEO | Lighthouse 四项评分（移动 78/96/100/100，桌面 94/96/100/100）+ Core Web Vitals + **SIGNAL/VALUE 信号表** + Top issues | Lighthouse + 页面解析 |
| Links | — | — |
| Technical | **On-Page Score 100** + 服务器配置（Server: Vercel / Status 200 / Encoding br / Page Size 54KB / DOM Size / Cacheable） | HTTP 头 + 页面解析 |
| GEO | 🔒 **锁定**（"Unlock to see AI mentions, competitor visibility"）。模糊层下可见是一张 **Yes/No 检查表** | — |

**AITDK 插件（官方功能清单）**

TDK（Title/Description/Keywords + Canonical）· H 标签层级 · 图片（无 alt/title 的）· 内外链比例与 dofollow/nofollow · 关键词密度 · 流量估算（月访/跳出率/停留/全球排名/来源/Top 词/Top 地区）· WHOIS（注册商/注册与到期日/域名状态）· sitemap 与 robots.txt 校验

#### 3.2.1 🔴 关键判断：它们做的是「页面级信号」，我们做的是「站级诊断」

> **Okara 的 SEO/Technical tab 和 AITDK，本质都是「打开一个 URL，告诉你这一页的各项指标」。**
>
> **而我们四个工具做的是「爬全站，找出跨页面的结构问题」**——孤岛页、内链断裂、URL 迁移未收口、跨页重复元数据。

**这不是谁更好，是两个不同的层。而且我们缺的恰恰是页面级那一层：**

| 层 | 谁有 | 我们的状态 |
|---|---|---|
| **页面级信号**（这一页的 TDK / H 标签 / 图片 alt / 内外链 / 密度 / CWV） | Okara ✅　AITDK ✅ | ❌ **P0-4 有部分，但没有单页视图** |
| **站级结构**（孤岛页 / 迁移收口 / 跨页重复 / 内链图谱） | Okara ❌　AITDK ❌ | ✅ **这是我们的独有资产** |
| **判断与排序**（哪个该先修） | 两者都 ❌ | ⚠️ **也没有，见 4.1 ①** |

#### 3.2.2 审计模块的三层结构

```
┌─ [站级] ────────────────────────────────────┐
│  87 个 URL · 66 条发现 · 已排除 38 · 队列 28  │
│  [全站体检] [内链结构] [流量诊断] [快速机会]   │
└─────────────────────────────────────────────┘
        ↓ 点某条发现，钻取到涉及的页面
┌─ [页面级] ──────────────────────────────────┐
│  /tools/seo-audit                           │
│  TDK · H 层级 · 图片 alt · 内外链 · CWV      │
│  ← 这一层我们现在没有，是要补的               │
└─────────────────────────────────────────────┘
        ↓
┌─ [判定] ────────────────────────────────────┐
│  该不该修 · 优先级 · 预计耗时                 │
│  ← 这一层 Okara 和 AITDK 都没有              │
└─────────────────────────────────────────────┘
```

#### 3.2.3 评分体系：为什么不能只给一个总分

**先看 Okara 的一个自相矛盾（8/12 实测）：**

> 它给 AstrologyWiki 打了 **`On-Page Score 100`**，而同一个面板下面列着 **3 个 Warning**（render-blocking resources、low content-to-code ratio、主关键词 `birth chart calculator` 缺失）。
>
> **满分和三个问题同时存在。这个分数掩盖了问题，而不是揭示问题。**

**所以我们给两个数，不给一个：**

```
┌──────────────────────────────────────────┐
│   健康度  82 / 100        🔴 阻断项  2     │
│   ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░░                    │
│                                          │
│   只要阻断项 > 0，健康度一律灰显           │
│   —— 分数不能盖过"这页进不了索引"这件事    │
└──────────────────────────────────────────┘
```

| 概念 | 定义 |
|---|---|
| **阻断项**（红） | 会直接导致**页面无法被索引或无法参与排名**的问题。**任何一个 > 0，健康度就不再是主指标** |
| **健康度**（0–100） | 加权通过率，只在阻断项为 0 时才有意义 |
| **分组得分** | 每组独立打分，**因为用户修复时是按组行动的** |

#### 3.2.4 九组详细检查表

**每项都给「实测值 → 阈值 → 判定」，不给模糊的"良好/一般"。**

##### 🔴 组 1 · 索引与可抓取（唯一包含阻断项的组）

| 检查项 | 阈值 | 判定 | 我们现状 |
|---|---|---|---|
| HTTP 状态码 | 200 | 非 2xx = **阻断** | ✅ P0-4 |
| `robots.txt` 是否放行 | 允许 | 被禁 = **阻断** | ✅ P0-4 |
| `noindex` 标签 | 无 | 存在 = **阻断** | ✅ P0-4 |
| Canonical 指向 | 自指或有效目标 | 指向 404 = **阻断** | ✅ P0-4 |
| 是否在 sitemap 中 | 是 | 否 = 警告 | ✅ P0-4 |
| 跳转链长度 | ≤1 跳 | ≥2 跳 = 警告；终点 404 = **阻断** | ✅ P0-4 |
| hreflang 目标有效性 | 全部 200 | 指向 404 = 警告 | ✅ P0-4 |

> **这一组决定"这页存不存在"，所以单独成组、且是唯一能产生阻断项的组。** 我们自己站上出现过全部四种阻断情况（308→404、hreflang 指向 404、软 404、canonical 到列表页）。

##### 组 2 · TDK

| 检查项 | 阈值 | 判定 |
|---|---|---|
| Title 长度 | 30–60 字符 | <30 或 >60 = 警告（>60 会被截断） |
| Title 唯一性 | 全站唯一 | 与其他页重复 = 警告 |
| **Title 含主词** | 包含 | 不含 = **警告（高权重）** |
| Meta description 长度 | 120–158 字符 | 超出 = 提示 |
| Meta description 唯一性 | 全站唯一 | 重复 = 警告 |
| Open Graph 完整性 | og:title / og:description / og:image | 缺失 = 提示 |

> **「Title 含主词」给高权重**——我们自己刚吃过两次亏：P0-5 落地页主词全页出现 **0 次**、P0-3 的 Title 被换成了自造产品名。**Okara 的 "Main keyword missing" 查的就是这个。**

##### 组 3 · 标题结构

| 检查项 | 阈值 | 判定 |
|---|---|---|
| H1 数量 | 恰好 1 | 0 或 >1 = 警告 |
| H1 是否含主词 | 包含或近义 | 不含 = 提示 |
| H 层级是否跳级 | H1→H2→H3 连续 | 跳级（如 H2→H4）= 提示 |
| H2 数量 | 5–8 | 偏离 = 提示 |
| H3 数量 | 15–25 | 偏离 = 提示 |
| **每个 H3 下的平均字数** | ≥80 词 | <50 = **警告** |

> **最后一条是我们自己审计时发现的问题，两个对标都没有**：P0-4 落地页有 27 个 H3 但全页仅 935 词，**平均每个小标题只有 35 词**——骨架搭齐了但内容没跟上。**只数 H3 个数会给出"结构良好"的错误结论。**

##### 组 4 · 内容

| 检查项 | 阈值 | 判定 |
|---|---|---|
| 正文字数 | 参照同 SERP 前十中位数 | 显著低于 = 警告 |
| **主词密度** | 0.5%–2.5% | <0.5% = 警告；>3% = 堆砌警告 |
| 主词首次出现位置 | 前 100 词内 | 靠后 = 提示 |
| 内容/代码比 | ≥10% | <10% = 提示（Okara 有此项） |
| 相似度（与站内其他页） | <70% | ≥70% = 警告 |

##### 组 5 · 图片

| 检查项 | 阈值 | 判定 |
|---|---|---|
| 无 alt 的图片数 | 0 | >0 = 警告 |
| 无 alt 图片占比 | 0% | 按比例扣分 |
| 单图体积 | <200KB | 超出 = 提示 |
| 现代格式（WebP/AVIF）占比 | ≥80% | 偏低 = 提示 |
| 首屏图是否 lazy-load | 否 | 是 = 警告（拖慢 LCP） |

##### 组 6 · 链接

| 检查项 | 阈值 | 判定 |
|---|---|---|
| **入链数**（站内指向本页） | ≥1 | **0 = 孤岛页，警告（高权重）** |
| 出站内链数 | 3–15 | 0 = 警告 |
| 断链数 | 0 | >0 = 警告 |
| 外链 dofollow/nofollow 比 | — | 仅展示 |
| 点击深度（距首页几跳） | ≤3 | >4 = 提示 |

> **入链数是站级数据，页面级工具（AITDK）拿不到——这是 P0-2 的独有能力。**

##### 组 7 · 结构化数据

| 检查项 | 阈值 | 判定 |
|---|---|---|
| 是否存在 JSON-LD | 是 | 无 = 提示 |
| 类型是否匹配页面 | 工具页→SoftwareApplication；文章→Article | 不匹配 = 提示 |
| 必填字段完整性 | 全部 | 缺失 = 警告 |
| FAQPage 与页面 FAQ 是否一致 | 一致 | 不一致 = 警告 |
| BreadcrumbList 与可见面包屑一致 | 一致 | 不一致 = 提示 |

##### 组 8 · 性能（❌ 需补引擎）

| 检查项 | 阈值（**2026-08-12 联网核实**） | 判定 |
|---|---|---|
| **LCP** | <2.5s 良好 · 2.5–4.0s 待改进 · >4.0s 差 | 按档扣分 |
| **INP** | <200ms 良好 · 200–500ms 待改进 · >500ms 差 | 按档扣分 |
| **CLS** | <0.1 良好 · 0.1–0.25 待改进 · >0.25 差 | 按档扣分 |
| TTFB | <800ms | 超出 = 提示 |
| 页面体积 | <2MB | 超出 = 提示 |
| 渲染阻塞资源 | 0 | >0 = 提示 |

> **口径必须写清楚**：CWV 是 **CrUX 真实用户数据、第 75 百分位、28 天滚动窗口**，而 Lighthouse 是实验室模拟。**两者会不一致，界面上要分开标注，否则用户会拿实验室分数去解释真实排名。**
> **来源**：[corewebvitals.io](https://www.corewebvitals.io/core-web-vitals) · [Core Web Vitals 2026 Guide](https://www.digitalapplied.com/blog/core-web-vitals-2026-inp-lcp-cls-optimization-guide)

##### ⭐ 组 9 · 搜索机会（两个对标都没有，我们独有）

| 检查项 | 判定 | 依据 |
|---|---|---|
| **该词是否被 AI Overview 完整覆盖** | 是 = **标红：排上去也拿不到点击** | astrologywiki 实测：9 词中 6 个被覆盖，1,330 曝光 → 1 次点击 |
| **SERP 前十有无近两年注册域名** | 全无 = 赛道锁死 | 选词规则三问之一 |
| **SERP 前十有无十万月访以下的站** | 全无 = 赛道锁死 | 同上 |
| **有无 UGC 位**（Reddit/Quora/Medium） | 有 = 有缝 | 同上 |
| 当前排名所处区间 | 1–6 / 7–10 / 11+ | 7–10 = 全行业低点击区（2026 基准 0.65–0.78%） |

> **这一组是我们相对 Okara 和 AITDK 的真正差异**：它们给的是"你这页做得怎么样"，**我们给的是"这页值不值得做"。**

#### 3.2.5 分组权重与评分公式

**权重按「对能否拿到流量的影响」排，不按检查项数量：**

| 组 | 权重 | 理由 |
|---|---:|---|
| 索引与可抓取 | **阻断制** | 不参与加权——有问题直接压过一切 |
| 搜索机会 | 25% | 决定这页值不值得投入 |
| TDK | 20% | 直接影响点击 |
| 内容 | 15% | |
| 链接 | 15% | 孤岛页 = 白写 |
| 标题结构 | 10% | |
| 性能 | 8% | |
| 结构化数据 | 4% | |
| 图片 | 3% | |

**每组得分 = Σ(通过项权重) / Σ(全部项权重) × 100**

**三条硬规则：**

1. **阻断项 > 0 时，健康度灰显，界面主位显示阻断项数量**
2. **不显示"100 分"**——满分只在所有项都通过且无待补项时出现，否则最高显示 99，避免 Okara 那种"满分带三个警告"
3. **每个扣分项必须能点开看到：实测值、阈值、影响、怎么改**——分数不可解释就是噪音

#### 3.2.6 现状盘点：哪些能立刻做

| 组 | 引擎状态 | 说明 |
|---|---|---|
| 索引与可抓取 | ✅ **P0-4 全覆盖** | 只差单页视图 |
| TDK | ✅ P0-4 有，**缺"含主词"判定** | 主词判定需接入目标词 |
| 标题结构 | ✅ P0-4 有，**缺"H3 平均字数"** | 计算成本极低 |
| 内容 | ⚠️ 部分 | 字数有，密度与相似度需补 |
| 图片 | ✅ P0-4 有 | 缺格式与体积检查 |
| 链接 | ✅ **P0-2 全覆盖** | 入链数是我们独有 |
| 结构化数据 | ✅ P0-4 有 | |
| 性能 | ❌ **需接 PageSpeed Insights API** | 免费，成本低 |
| **搜索机会** | ⚠️ **方法已验证，未产品化** | SERP 实测目前是手工，自动化是独立技术问题（见 4.3） |

> **能立刻做的：把已有的六组组织成单页视图 + 补两个低成本判定（Title 含主词、H3 平均字数）。**
> **需要立项的：性能（接 API）和搜索机会（SERP 自动化）。**

#### 3.2.4 ⭐ 我们该加、而两个对标都没有的三项

| 检查项 | 为什么只有我们能做 |
|---|---|
| **目标词的 AI Overview 覆盖度** | 已在 astrologywiki 实测验证：9 个词中 6 个被 AI Overview 完整覆盖，1,330 曝光只换 1 次点击。**Okara 的 GEO tab 锁着，AITDK 完全没有** |
| **目标词的 SERP 竞争者密度** | 前十有没有近两年域名 / 十万月访以下的站 / UGC 位——**这是我们选词规则的核心，两个对标都是给指标不给判断** |
| **该不该修的判定** | Okara 给 "3 Top issues" 但不说先修哪个；AITDK 给一堆数值不给结论 |

#### 3.2.5 每条发现仍按四段式呈现



```
[Tab] 快速机会 │ 流量诊断 │ 内链结构 │ 全站体检

每条发现按四段式呈现：

  Observation     你的这个页面：排名 8.9 / 曝光 3,259 / 点击 4 / CTR 0.12%
  Diagnosis       为什么会这样
  Recommendation  具体怎么改
  Artifact        ← 可直接拿走的东西（Title/Meta 草稿、内链补充清单）
```

**Artifact 那一段是我们和大厂工具的真实差别**——别人给指标，我们给能直接用的东西。

### 3.3 右中栏 · 下一步（主区域，只放一件事）

```
┌──────────────────────────────────┐
│  下一件                     3/28  │
│                                  │
│  修 7 个跳转到 404 的旧 URL         │
│                                  │
│  为什么是它                        │
│  排名第 1 / 3 / 4 的位置正在白扔     │
│  预计 30 分钟                      │
│                                  │
│  ▸ 为什么不是别的（点击展开）        │
│                                  │
│  [ 标记完成 ]   [ 换一件 ]   [ 跳过 ]│
└──────────────────────────────────┘
```

**四个设计要点：**

| 要点 | 理由 |
|---|---|
| **完成驱动，不是时间驱动** | 标记完成才出下一件。节奏由用户执行速度决定，**不会积压**（见 4.1 ③） |
| **`3/28` 进度而非"今天的任务"** | 让用户知道队列有多长，但**不把 28 条全摊开** |
| **标注预计耗时** | ICP 是兼做 SEO 的创始人，**"这件要花我多久"直接决定他做不做** |
| **「为什么不是别的」默认折叠** | 排除逻辑是可信度来源，不是主区域内容 |

- **「换一件」**给用户否决权——我们的推荐可能不符合他当下处境
- **「跳过」和「换一件」要分开**：跳过 = 这件我不做（应记录原因，是产品信号）；换一件 = 现在不想做这个

### 3.4 右栏 · 对话

接住"为什么是这条不是那条"的追问。**这是排除逻辑真正该被讲出来的地方**，而不是主区域。

### 3.5 GEO：不做完整 agent，只做一个检测项

**建议先不在界面上放 GEO 和内容写作的入口，连占位都不放。**

理由：这两块**没有任何引擎**。放上去就是死格子或假 demo——**我们刚在 P0-5 上吃过这个亏**（Coming soon 页挂了很久，主词还丢了）。

**但 GEO 有一条现在就能做、成本极低的路径：**

> 我们已经在 astrologywiki 上实测过 AI Overview 的行为（9 个词，6 个被 AI Overview 完整覆盖答案）。**这套方法可以直接变成一个检测项**——用户输入关键词，我们告诉他：**这个词的答案会不会被 AI Overview 完整回答掉。**
>
> **如果会，那么排上去也拿不到点击**——这是我们在自己站上用 1,330 次曝光只换来 1 次点击验证过的。

**这比做一个完整的 GEO agent 现实得多，而且它正是我们已经验证过的能力。**

## 四、⚠️ 三个必须标明的风险

### 4.1 ✅ 「持续产出」有解了 —— 但解法不是新引擎，是分发队列

**原文写"这是本方案最大的缺口，需要产品侧补一个持续产出机制"。这个判断过于悲观，收回。**

关键在于：**我们不缺内容，缺的是分发节奏。**

| 一次诊断实际产出多少 | 数量 |
|---|---:|
| gengrowth.ai 全站审计 | **66 条改动条目** |
| astrologywiki P0-4 一次扫描 | **180 个孤岛页** + 200+ 处重复元数据 |
| gengrowth URL 迁移 | 95 个待收口 URL + 7 个断链 |

> **一次 P0-4 就能产出几十条。问题从来不是"没东西可做"，是我们一次性把 66 条全倒给用户——而他看完就关掉了。**

**所以机制是：一次诊断 → 进入队列 → 按优先级每次只放出一件。不需要任何新引擎，用现有数据就能做。**

#### 但这带来三个必须解决的问题

**① 排序变成核心能力，而我们现在没有。**

每次只给一件，意味着**第一件必须是最该做的**。而 P0-5 的实测证明我们目前不做排序——`CHECK BEFORE ACTING` 那一列对 KD 73 和 volume 10 的词给出**逐字相同**的建议（见 `01-product-feedback/2026-08-12-p0-5-...-实测审计.md` 3.1）。

**排序逻辑不解决，队列就是随机派发。**

**② 队列会耗尽。** 一次审计 66 条，按天派发约两个月。之后需要重新诊断或新数据源触发。**这买到了时间，不是永久解法。**

**③ 🔴「每天」这个节奏，我不同意 —— 应该由用户的执行速度决定，而不是我们的推送频率**

**Okara 能做每天，是因为它卖的是"AI 替你做"，用户只需审批**——审批一条推文几十秒。

**我们卖的是"告诉你做什么"，用户要自己动手。** 修 7 个跳转、改一批 Title、补内链——每一件都是几十分钟到几小时。

**而我们的 ICP 是 1–10 人团队、创始人兼做 SEO，不会每天登录一个 SEO 工具。**

> **每天推一件、用户每周只能做两件 —— 一个月后队列积压 30 条、完成 8 条。这又回到了"一次性倒 66 条"的同一个问题，只是延后了一个月。**

**建议改为「完成驱动」而不是「时间驱动」：**

```
任何时候打开 → 只看到当前这一件
标记完成    → 下一件出现
没完成      → 打开还是它，但可以「换一件」
```

**节奏由用户自己的执行速度决定。** 好处有三：

- **回访理由自然**：不是"今天该来了"，而是"我做完了，下一件是什么"
- **不会积压**：队列长度对用户不可见，也就不构成压力
- **顺带产出留存数据**：完成间隔天数 = 用户真实执行节奏，**这个数据我们现在完全没有**

**可以保留一个可配置的提醒频率（每天/每周/关闭），默认每周**——但那是通知层，不是产出层。

> ⚠️ **「每天 vs 每周 vs 完成驱动」这三种形态，本周 10 个种子用户能直接给出答案。** 建议在访谈里问一句：**"你多久会真的动手做一次 SEO 改动？"**

### 4.2 「用户要不要每日节奏」未经验证

右中栏该不该存在，取决于用户要的是**"每天一件事"的节奏感**，还是**"需要时跑一次"的工具感**。

**这两种形态差别极大，而我们没有任何数据。** 本周 10 个种子用户的反馈会给出方向。

### 4.3 左栏三份「我们独有」的文档，目前全是手工产出

36 词 SERP 实测表、竞争对手实测清单、否决词清单——**都是我一条条搜出来的**。

> **要进产品必须先解决自动化，否则只是把我的手工工作搬到界面上。** 而 SERP 实测能不能自动化（Google 反爬、成本、准确率）是个独立的技术问题，需要单独评估。

## 五、和 Okara 的关键差异（一句话总结）

| | Okara | 我们 |
|---|---|---|
| 产品形态 | **任务分发器**——每天给你 N 件事 | **判断器**——每次给你 1 件事 + 为什么是它 |
| **节奏** | **时间驱动**（每天 2+1+2+1，用户只需审批） | **完成驱动**（做完才出下一件，因为我们的任务要用户自己动手） |
| 排除逻辑 | 无 | **核心资产**，且被记录复用 |
| 竞争对手 | 算法推测（实测不准） | **SERP 实测** |
| 付费墙 | 9 个 agent 锁 7 个 | 免费工具是获客层，不锁 |
| **真正的弱点** | 评测普遍反映"加速判断，不替代判断" | **排序能力缺失**——P0-5 实测证明我们对 KD 73 和 volume 10 的词给出逐字相同的建议（见 4.1 ①） |
