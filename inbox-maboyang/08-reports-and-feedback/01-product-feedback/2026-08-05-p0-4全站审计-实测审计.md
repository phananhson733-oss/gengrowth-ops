## 一、⭐ 做得好的四件事

### 1.1 真的在爬，而且把配额说得很清楚

两次实测：

| 站点 | 检查页数 | 内链 | sitemap URL | 未收集 | 耗时 |
|---|---|---|---|---|---|
| gengrowth.ai | 100 | 1,445 | 87 | 22（全部 robots-disallowed） | 约 1 分钟 |
| www.astrologywiki.com | **630** | 2,551 | 558 | 2 | 约 2.5 分钟 |

两次都返回 `CRAWL COMPLETED`，并给出分项：`skipped 0 · blocked 0 · robots-disallowed N · errors 0`。

> 📌 **一处我先前的怀疑，已排除。** gengrowth.ai 返回整数 100，我一度怀疑存在隐藏的 100 页上限、与页面声称的「约 950 页」矛盾。用 astrologywiki 复测得到 630 页且状态仍是 `COMPLETED`，**说明没有 100 页上限，gengrowth.ai 确实只有 100 个可发现页面。**

### 1.2 遵守 robots.txt，并且能被验证

gengrowth.ai 的 22 个未收集 URL 全部是 `robots-disallowed`。核对站点 robots.txt：

```
Disallow: /*?*category=
Disallow: /*?*pillar=
```

**爬虫排除的正是这两条规则覆盖的 URL。** 顺带确认：这两条参数规则是 P0-2 审计中列出的站点侧问题（S 系列）之一，**现已修复**。

### 1.3 边界声明写得比多数商业工具狠

落地页「Not measured by this public synchronous audit」三条 + FAQ 八条，反复申明同一件事：

> **What the result is not**: It is not a site-quality grade, ranking forecast, **repair plan**, search-console report, or exhaustive crawl.

> **04 Does it provide recommendations or a fix list?**
> No. The public result records what was observed. **It does not produce remediation advice, priorities, diagnoses, or an action plan.**

> **07 Does an uncollected link mean the target is broken?**
> No. A target is recorded as an HTTP error **only when the crawler actually collected it** and observed a 4xx or 5xx final response.

第 07 条尤其值得记：**它主动堵掉了「没抓到 = 坏了」这个最常见的误读**——而这正是 P0-2 审计里那个爬虫 bug 造成的错误结论类型。

### 1.4 每条记录都给「观察数 / 受测数」

不是「105 个重复标题」，而是 `105 observed / 630 tested pages`。分母始终在场，读者能自己判断比例。这一点比 P0-1 的「All 45」好（见 P0-1 审计 4.1）。

## 二、🔴 最重要的一条：产品定位与推广承诺直接冲突

**这不是 bug，是两份文件对同一个工具的定义不一致。**

推广执行口径第五节给 P0-4（文中称 Website Health Map）的定义：

| 项 | 推广文档写的 |
|---|---|
| 用户原话 | **「我的网站先修哪三个问题」** |
| 对外承诺 | 3 分钟给出具体 URL、**影响、修复方法和验证方式** |

而 P0-4 产品本身的声明：

| 项 | 产品写的 |
|---|---|
| 落地页 | 不是 grade、不是 forecast、**不是 repair plan** |
| FAQ 03 | 不含健康分或评级 |
| FAQ 04 | **不产出修复建议、优先级、诊断或行动计划** |
| 结果区 | Records are **not scores, priorities, or instructions** |

**用户带着「先修哪三个」来，工具明确拒绝回答「先修哪三个」。**

这同时也和推广文档第八节自定的启动门槛冲突：

> 每个对外主推工具必须能让用户在 3 分钟内完成真实任务……**首屏给出 Top 3 行动**，并说明对象、证据、影响、下一步和验证方法

P0-4 **按设计**不满足这一条。

### 2.1 结论：不改产品立场，把「拒绝」变成漏斗的第一级

**产品拒绝给建议是对的，不改。**

「先修哪三个」里的"哪个最重要" = 影响 × 成本，而"影响"需要知道哪些页面真有排名和流量。P0-4 结构上不连 GSC、不执行 JS、不知道站点商业目标，**它拿不到"影响"这个变量，硬给排序就是编**。这与 P0-3 拒绝判定惩罚是同一种克制，而这种克制是这条产品线目前最主要的可信度来源。

**但「先修哪三个」是两个问题，只有一个需要 GSC：**

| 问法 | 需要什么 | P0-4 能否回答 |
|---|---|---|
| 修哪三个能带来最多流量 | 排名、曝光、点击 | ❌ 结构上不可能 |
| **哪三类问题影响的页面最多** | 只需要计数 | ✅ **已经算出来了** |

`180/558`、`107/630`、`105/630` 这些数产品早就有了，只是没排序（最严重的一条排在倒数第三，见四、4.2）。**按观察数降序排列是算术，不是判断**——它没有断言 180 比 107 更严重，只是把数大的放前面，不越过产品自己划的线。

### 2.2 落地形态

结果区末尾（当前是直接进入 FAQ）改为：

```
我们检查了 630 个页面，观察到 7 类问题：

  180 / 558   sitemap 页面没有任何内链
  107 / 630   重复的 meta description
  105 / 630   重复的 title
  ……

这些是我们从公开 HTML 里能核实的全部。

我们无法告诉你先修哪一个 —— 那需要知道哪些页面真的有排名
和流量，而那只存在于你的 Search Console 里。

  [ 连接 Search Console，按实际影响排序 → ]
```

### 2.3 这样处理同时成立四件事

| | |
|---|---|
| **产品诚实度** | 一句都没退让，边界反而说得更清楚 |
| **招募话术** | 「先修哪三个」有了诚实答案：三类**已经给了**，排序需要 GSC |
| **启动门槛** | 第八节「首屏给出 Top 3 行动」满足——Top 3 = 三类问题，行动 = 连 GSC |
| **核心指标** | 直接服务「20 人连接 GSC」，且是在用户最有动机的那一刻给入口 |

**P0-4 从"一个不完整的审计工具"变成"授权漏斗的第一级"。** 它是五个工具里仅有的两个匿名即用工具之一，**在漏斗里的真实位置是入口，不是终点**——当前的问题是它读完就没了。

### 2.4 配套的口径调整（不在本文档范围）

产品侧改动见九、A2 / A2b。推广口径侧需要两处调整：

| 文档位置 | 现在 | 调整为 |
|---|---|---|
| 第五节 P0-4 对外承诺 | 3 分钟给出具体 URL、影响、**修复方法和验证方式** | 3 分钟给出**影响页面最多的几类问题、逐条 URL 证据，并指出哪些判断需要接入 Search Console** |
| 第八节启动门槛 | 首屏给出 Top 3 行动 | 保留，补一句：对不接数据源的公开工具，Top 3 指"影响面最大的三类观察"，下一步动作可以是"接入数据源" |
| 第五节用户原话 | 我的网站先修哪三个问题 | **保留不变**——这仍是正确的进入动机 |

**状态：口径调整已确定由口头向上沟通，不再走文档更新。** 产品侧改动不依赖该沟通结果，可先行落地。

### 2.5 顺带的一条风险

真正的风险不只是"承诺不符"，还有**查询意图不匹配**：`free seo audit` 这个词的搜索者，期待的是 Ahrefs / Semrush 那种打分加修复清单——这是该词几乎全部竞品的形态。我们排上去后交付中立事实记录，跳出率会偏高。

2.2 的收尾同时缓解这一点：它把"我不给你打分"变成一个**有明确下一步的结局**，而不是一次空手而归。

### 3.2 🔴 唯一缺 `SoftwareApplication` Schema 的工具页

| 工具页 | SoftwareApplication | Offer | Organization |
|---|---|---|---|
| P0-1 seo-quick-wins | ✅ | ✅ | ✅ |
| P0-2 internal-link-audit | ✅ | ✅ | ✅ |

复现：

```bash
for u in seo-quick-wins traffic-drop-diagnosis seo-audit internal-link-audit; do

```

**讽刺的是，P0-4 是四个里最「像工具」的一个**——匿名、即时、输入 URL 就跑。而 `SoftwareApplication` 正是让 Google 理解「这是一个可交互 Web 工具」的那个 Schema。

### 3.3 ⚠️ `/tools` 在站内有四种叫法

| 出现位置 | 叫法 |
|---|---|
| `/tools` 的 Title | `Free SEO & Growth Tools` |


## 四、🔴 结果呈现的三个问题

### 4.1 `OBSERVED` 徽章在同一份报告里含义相反

两条记录并排看：

```
robots.txt resource
  Whether the crawler successfully fetched and parsed a robots.txt resource.
  [ OBSERVED ]   1 observed / 1 tested site resource        ← 好事：找到了

Repeated title text
  Inspected pages that shared the same normalised, non-empty title text.
  [ OBSERVED ]   105 observed / 630 tested pages            ← 坏事：105 个重复
```

**同一个徽章，两个相反的含义。** 差别只在于条件名称是中性描述（`robots.txt resource`）还是问题描述（`Repeated title text`）——前 2 条属前者，后 15 条属后者。

`NOT OBSERVED` 同理反转：`Title not present — NOT OBSERVED 0/630` 是好消息，但徽章读起来像是"没测到"。

**页面上没有任何术语说明。** 实测搜索整页文本，找不到解释 `OBSERVED` / `NOT OBSERVED` 含义的句子。

这对推广文档定义的核心 ICP（「团队没有资深全职 SEO」）是硬伤：**这批人恰恰是最需要徽章告诉他们好坏的人。**

### 4.2 17 条记录平铺，无优先级线索

astrologywiki 的实际结果：

| 状态 | 计数 | 条件 |
|---|---|---|
| OBSERVED | **180 / 558** | **Sitemap page without an observed HTML inlink** |
| OBSERVED | **107 / 630** | Repeated meta-description text |
| OBSERVED | **105 / 630** | Repeated title text |
| OBSERVED | 70 / 630 | Canonical target differs |
| OBSERVED | 48 / 630 | Redirect chain |
| OBSERVED | 32 / 630 | Noindex directive |
| OBSERVED | 30 / 630 | Multiple H1 elements |
| NOT OBSERVED | 0 / 630 | Non-2xx final response |
| NOT OBSERVED | 0 / 630 | Canonical link not present |
| NOT OBSERVED | 0 / 630 | Title not present |
| NOT OBSERVED | 0 / 630 | Meta description not present |
| NOT OBSERVED | 0 / 630 | H1 not present |
| NOT OBSERVED | 0 / 630 | Non-HTTPS final URL |
| NOT OBSERVED | 0 / 449 | Collected internal target returned 4xx/5xx |
| NOT OBSERVED | 0 / 630 | JSON-LD parse error |
| OBSERVED | 1 / 1 | robots.txt resource |
| OBSERVED | 1 / 1 | Sitemap resource |

**页面上的排列顺序是固定的检查顺序，不是严重度顺序。** `Repeated title text 105/630` 夹在 `Title not present 0/630` 和 `Meta description not present 0/630` 中间；最严重的 `180/558` 排在倒数第三。

所有行的字号、行高、徽章尺寸完全相同；数字用小号灰色等宽字体放在右侧——**信息量最大的内容在视觉上被降权了**。

这与 P0-2 审计第四节「为什么用户感受是『网址堆砌』」是同一类问题。

### 4.3 排序不违反它自己的立场

产品声明「Records are not scores, priorities, or instructions」，因此**不能**加严重度评分或建议。

但**按观察数从多到少排列，仍然是事实陈述**——它没有断言 180 比 107 更严重，只是把数大的放前面。同理，把 `0 observed` 的 8 条折叠成一句「8 项检查未发现问题（点击展开）」，也不构成判断。

**这是在不越线的前提下能拿到的最大可读性收益。**

## 五、🔴 没有导出，而产品自己提出的场景需要导出

落地页列了三个使用场景，第三个是：

> **03 Periodic comparison input**
> Run the same synchronous audit again and **compare the facts manually**; this free tool does not store history.

而实测：**P0-4 结果区没有任何导出、下载或复制功能。**

| 工具 | 落地页提及 CSV | 提及 export |
|---|---|---|
| P0-1 seo-quick-wins | 11 次 | 12 次 |
| P0-2 internal-link-audit | 4 次 | 9 次 |
| **P0-3 traffic-drop-diagnosis** | **0** | **0** |
| **P0-4 seo-audit** | **0** | **0** |

（P0-4 页面上 13 处 `download` 全部指爬虫的下载量安全限制，与导出无关。）

**「不存历史 + 建议手动对比 + 没有导出」三者不能同时成立。** 用户要执行产品自己建议的场景 03，唯一办法是把 17 条折叠记录逐条展开截图，跨两次运行肉眼比对 630 页的证据。

P0-1 和 P0-2 都有 CSV 导出，**说明这不是技术约束，是这两个工具漏了**。

提交后按钮变为 `Auditing the site…`，此后直到结果返回，界面没有任何变化。实测扫描 DOM：

```js
document.querySelectorAll('progress,[role=progressbar],[class*=progress]').length  // → 0
```

**零进度条、零 spinner、零动画、无已抓页数、无耗时。**

P0-1 / P0-3 也是只改按钮文案，但它们跑几秒（一次 GSC API 调用）。**P0-4 是唯一可能跑满 4 分钟的工具，反馈却最少。** astrologywiki 那次实测约 2.5 分钟，期间用户无法区分「在跑」和「卡死」。

页面自己已经把配额讲得很清楚（950 页 / 250ms / 4 分钟），**这些数字完全可以变成进度**：已抓 N 页、已用 M 秒。

## 七、出口：只有一个，但这一个选对了

结果区 86% 处有一张卡：

> **Inspect the site's internal structure**
> **Run an internal link audit** — The separate internal link audit records observed links, crawl depth, and candidate orphan pages within its current synchronous collection.

**这个导向是准确的**：本次最大的发现就是 180 个 sitemap 页面没有 HTML 入链，而 P0-2 正是孤岛页工具。比 P0-3 的页尾卡（写给未授权用户、且不含最该链的 P0-1）好得多。

但仍只有一个出口：

- 没有 P0-3 —— 而 astrologywiki 恰恰正在经历 90% 的点击下跌（见 P0-3 审计第九节）
- 没有 P0-1

**建议**：与 P0-3 的改法 D 同理，把出口挂到触发的记录上——`Sitemap page without an observed HTML inlink` 触发时给 P0-2，`Redirect chain` / `Canonical target differs` 触发时给 P0-3。

## 八、⚠️ P0-2 那两个爬虫 bug：本轮未能证实，也未能证伪

这是本次审计的一个**未完成项**，需要说明清楚，不能记成「已通过」。

### 8.1 测试设计

P0-2 审计发现两个爬虫 bug：

1. **HTML 实体未解码** —— `href="/blog?a=1&amp;b=2"` 被当成含 `amp;` 的幻影 URL
2. **子域名被当成同源** —— 用 `endsWith()` 而非精确 host 匹配

gengrowth.ai 同时具备触发条件（blog 有 `&amp;` 参数链接、站点链向 `app.gengrowth.ai` 子域名），所以选它作为测试站。

### 8.2 结果与失效原因

展开全部 26 个折叠块后扫描结果全文：

```js
(t.match(/amp%3B|amp;/gi)||[]).length        // → 0
(t.match(/app\.gengrowth\.ai/gi)||[]).length // → 0（页面自身导航链接除外）
```

**Bug 2 可以初步判定不存在**：结果中未出现任何 `*.gengrowth.ai` 子域名。

**Bug 1 的测试无效**。原因：站点 robots.txt 现已加入

```
Disallow: /*?*category=
Disallow: /*?*pillar=
```

而带 `&amp;` 的链接全部是这两类参数 URL。爬虫正确地遵守了 robots，**因此根本没有走到会触发该 bug 的路径**。核对确认这些链接仍存在于页面上：

```bash
curl -s "https://gengrowth.ai/blog?pillar=attribution" | grep -oE 'href="[^"]*amp;[^"]*"'
# → href="/blog?category=methodology&amp;pillar=attribution"
```

astrologywiki 一轮同样未出现 `amp;`，但该站未确认存在带 `&amp;` 的内链，不能作为反证。

### 8.3 下一步

需要一个**存在 `&amp;` 内链且未被 robots 屏蔽**的测试站点才能定论。在此之前，**P0-4 的实体解码行为按「未验证」记录**，不写入任何"已通过"的结论。

### 10.2 顺带查出的一条站点侧问题

## 十一、🔴🔴 2026-08-06 追加：一个正确性缺陷，比前面所有呈现问题都严重

> 本节由第十节的业务排查回溯产生。展开页面级证据逐条核实后发现，**P0-4 在一个处理正确的站点上报出了 105 个不存在的问题。**

### 11.1 页面级证据是平铺的，掩盖了真实模式

展开 `Repeated title text`（105 observed / 630 tested）后，每个 URL 单独成块：

```
https://www.astrologywiki.com/en/wiki/aries
  TITLE TEXT      Aries
  MATCHING PAGES  2

https://www.astrologywiki.com/wiki/aries
  TITLE TEXT      Aries
  MATCHING PAGES  2
```

**105 行，只对应 50 个不同标题。** 每行把相同的标题与相同的计数再抄一遍。

`MATCHING PAGES: 2` 这个字段本身就证明**工具已经算出了分组**，只是展示时拍平了。按组渲染应为 50 行：

```
Aries                                    2 pages
  /en/wiki/aries  ·  /wiki/aries
```

**后果**：这条记录里最重要的信息——「每个词条页存在两个 URL」——在当前展示下看不出来。**我是把 105 行提取出来做分组之后才发现的。** → **A10**

### 11.2 🔴 核实之后：这 105 个全部是假阳性

按分组结果逐条核实：

| 分类 | 数量 | 实际状态 |
|---|---|---|
| `/wiki/X` + `/en/wiki/X` 配对 | 约 96 | ✅ canonical 已收敛到 `/en/wiki/X` |
| 共用首页标题的 URL | 7 | ✅ canonical 已收敛到 `/` |
| **真实的重复标题问题** | **0** | |

核实命令：

```bash
for u in aries jupiter house-1; do
  for p in "/en/wiki/$u" "/wiki/$u"; do
    echo -n "$p → "
    curl -sL "https://www.astrologywiki.com$p" \
      | grep -oE '<link rel="canonical" href="[^"]*' | sed 's/.*href="//'
  done
done
# 两者均输出 https://www.astrologywiki.com/en/wiki/<u>
```

旁证：sitemap 只含 `/en/wiki/`（395）与 `/zh/wiki/`（126），无前缀形式 0 个；首页 12 条 wiki 内链全部指向 `/en/wiki/`；Google 实际收录的也是 `/en/wiki/aries`（已在 GSC 确认）。

**canonical、sitemap、内链、实际收录四者一致。这个站没有重复标题问题。**

### 11.3 为什么这条比前面所有问题都严重

**工具自己有一条 `Canonical target differs` 记录（70 / 630）** —— 它知道这些页面的 canonical 指向别处。**但重复标题检查没有使用这个信息。**

这不是呈现问题，是**正确性问题**：

| | |
|---|---|
| 产品的立身之本 | 「只记录实际观察到的事实」「不给评分、不给预测」 |
| 实际发生的 | 在一个处理正确的站点上，报出 105 个不存在的问题 |

一个用户按这份报告去"修复"105 个重复标题，会发现无从下手——因为它们本来就是对的。**这比排序错、徽章歧义严重一个量级**：前者让人看不清，后者让人看到假的。

`107 个重复 meta description` 几乎肯定是同一成因，须一并修。

### 11.4 修法

| 方案 | 做法 |
|---|---|
| **最低限度** | 分开计数：`105 observed, of which 105 canonicalised elsewhere` |
| **推荐** | 检测重复前先按 canonical 归并；仅当**多个 URL 各自 canonical 指向自己**且标题相同时才计为重复 |

**推荐方案不改变产品立场** —— 按 canonical 归并仍然是"记录观察到的事实"，只是把 Google 已经声明的规范关系纳入了观察范围。反而更贴近"我们只说数据支持的话"。
