# P0-2 内链审计 · 实测审计

## 零、一句话结论

**工具能跑通，边界意识和诚实度是这个品类里稀缺的。但两个爬虫 bug 导致 91% 的输出是误报；层级展示混用了三套逻辑，报不出「哪些页面埋得太深」这个最该报的事实。**

| 层级 | 结论 |
|---|---|
| 🔴 **Bug** | 两个，都在爬虫的 URL 处理上，**都会影响所有用户的站** |
| 🔴 **指标定义** | 缩进用 URL 路径、depth 用爬虫遍历层数（含 sitemap 种子），**三套逻辑混在一个视图里，报不出真实的点击深度分布** |
| 🟠 **表格设计** | 结构化但不可读，用户感受是"网址堆砌" |
| 🟠 **产品体验** | 信任建设很好，**行动建设完全缺失** |
| 🔴 **能力边界** | 只报「爬取副产品」（depth / inbound），**四个真问题一条没报**，其中两条读 meta 标签就能查 |
| 🔴 **站点侧** | 顺带查出 4 个 SEO 问题，**其中 2 条有官方文档逐字对应** |
| ✅ **该保护的** | 边界声明、解释限度、不替用户下结论 |

## 一、🔴 Bug 1：爬虫不解码 HTML 实体

### 1.1 现象

用 gengrowth.ai 跑出的 12 条 `Prioritized findings` 里，**11 条长这样**：

```
/blog?amp%3Bcategory=methodology&page=2 is at observed crawl depth 3
/blog?amp%3Bpillar=attribution&category=case_study is at observed crawl depth 3
/blog?amp%3Bpillar=customer_stories&category=methodology is at observed crawl depth 3
...
```

`amp%3B` = `amp;`。

### 1.2 根因

站点 HTML 是**正确的**：

```html
<!-- gengrowth.ai/blog?pillar=attribution 的真实源码 -->
href="/blog?category=case_study&amp;pillar=attribution"
```

按 HTML 规范，属性值里的 `&` 就应该转义成 `&amp;`。浏览器会解码回 `&`。

**我们的爬虫没解码**：

```
读到      /blog?category=case_study&amp;pillar=attribution
按 & 切分  → category=case_study
          → amp;pillar=attribution      ← 参数名变成 "amp;pillar"
重新序列化 → ?amp%3Bpillar=attribution&category=case_study
```

**与工具输出完全吻合。**

### 1.3 复现

```bash
curl -s "https://gengrowth.ai/blog?pillar=attribution" \
  | grep -oE 'href="[^"]*amp;[^"]*"' | sort -u
# 输出：href="/blog?category=case_study&amp;pillar=attribution" 等
```

### 1.4 影响

| 影响 | 说明 |
|---|---|
| **12 条 findings 里 11 条是误报** | 用户看到的待办清单 **91% 是假的** |
| **页面数虚增** | 服务器对未知参数返回 200，爬虫把幻影 URL 当成真页面收进 167 的计数里 |
| ⚠️ **影响面极广** | `&amp;` 是 HTML 里写 `&` 的**标准正确写法**。**任何有筛选 / 分页 URL 的站都会中招** |

### 1.5 修法

href 提取后先做 HTML 实体解码（`&amp;`→`&`、`&lt;`→`<`、`&#38;`→`&` 等），再做 URL 规范化。

> ⚠️ **要修的是爬虫，不是站点。** 如果有人看到这份报告去改 blog 模板，就修反了。

## 二、🔴 Bug 2：子域名被当成同源路径

### 2.1 现象

层级树里有个 `app` 节点：

```
app        入链 48 | 出链 0 | 深度 2
           标题：404: This page could not be found.
```

### 2.2 根因

全站实测：

```
href="/app..."（同源路径）        → 0 条
href="https://app.gengrowth.ai"  → 每页 1–3 条（右上角「Open GenGrowth」按钮）
```

**一条真正的 `/app` 同源链接都不存在。** 爬虫把子域名 `app.gengrowth.ai` 解析成了路径 `gengrowth.ai/app`，然后去抓，抓到 404 页。

推测是同源判定用了 `hostname.endsWith('gengrowth.ai')` 之类的宽松匹配。

### 2.3 复现

```bash
curl -s "https://gengrowth.ai/" | grep -coE 'href="/app[/"]'                    # → 0
curl -s "https://gengrowth.ai/" | grep -coE 'href="https://app\.gengrowth\.ai'  # → 3
curl -sL -o /dev/null -w "%{http_code}\n" "https://gengrowth.ai/app"            # → 404
```

### 2.4 影响

- 制造一个入链 48 的幻影 404 节点
- **违反工具自己声明的 `SAME ORIGIN` 契约**（页脚有这行字）
- ⚠️ **风险不止误报**：意味着爬虫可能爬到本不该爬的域名上，这是抓取边界问题

### 2.5 修法

同源判定改成**精确 host 匹配**（`hostname === seedHostname`），不要用 `endsWith` / `includes`。

## 三、⭐ 最重要的发现：`crawl depth` 的定义掩盖了真实问题

**这不是 bug，是指标定义的选择——但它决定了这个工具有没有用。**

### 3.1 用户的心智模型 vs 工具的实际逻辑

**用户期待的**（也是"内链层级"在 SEO 语境里的标准含义）：

```
/ 首页
├─ Free Tools / Blog / Pricing / Legal…      ← 首页链出去的
   └─ 各篇 blog                              ← /blog 链出去的
      └─ 文中指向其他 blog 或工具页的链接
```

**工具实际做的**：

| 展示要素 | 实际含义 |
|---|---|
| **缩进** | **URL 路径层级**（`/blog/xxx` 缩进在 `blog` 下，因为路径像，不是因为 `/blog` 链向它） |
| **Depth** | **爬虫遍历层数**，且 **sitemap 条目被当作爬取种子** |

工具自己在右侧详情面板承认了：

> *"Sitemap entries can be crawl seeds, so this is **not asserted as a homepage click count** or ranking prediction"*

**证据**：`affordable-seo-tools` 在首页出现 **0 次**，在 sitemap 里，工具标它 **depth 1**。

### 3.2 ⚠️ 一处自我更正

> **本文档初稿写过「从首页 3 跳只能到达 50 页，117 页不可达」。这个数字是错的，现予撤回。**
>
> 我那个对照脚本在 URL 规范化时**丢掉了 query string**，`/blog?page=2` 被当成 `/blog` 跳过，因此完全没抓到分页里的文章。
>
> **讽刺的是：我犯的正是我批评工具犯的那一类错误——URL 规范化没做对。**

**修正后的实测**（保留 query、解码 HTML 实体、严格同源）：

```
深度 1（首页直链）      25 个
深度 2（展开 /blog、/tools）  新增 27 个
深度 3（展开分页页）    新增 51 个
```

**大部分页面链接可达。真正的问题不是"不可达"，是深度分布。**

### 3.3 两种模型真正的分岔点

同样是 `/blog/xxx`，URL 路径深度全都是 2，但实际点击深度差很多：

| 页面 | URL 路径深度 | **实际点击深度** |
|---|---:|---:|
| `/blog/bounded-internal-link-crawl` | 2 | **1** ← 首页直接推荐 |
| `/blog/affordable-seo-tools` | 2 | **3** ← 首页→blog→page=2→文章 |
| `/blog/best-cheap-seo-tools` | 2 | **3** |
| `/blog/marketing-attribution-for-saas` | 2 | **≥4** |

**分岔的不是"树长什么样"，是"哪个页面被放在哪一层"：**

```
按 URL 路径                    按点击可达
/                              /
└─ blog                        ├─ 1跳: bounded-internal-link-crawl
   ├─ bounded-…        (2)     └─ blog
   ├─ affordable-…     (2)        └─ 2跳: blog?page=2
   ├─ best-cheap-…     (2)           └─ 3跳: affordable-seo-tools
   └─ marketing-…      (2)                   best-cheap-seo-tools
                                             ⚠️ marketing-… ≥4跳
```

**左边四篇看起来一模一样；右边一眼能看出哪篇被重点推荐、哪篇埋得很深。**

这个站的分页设计恰好把差距拉开了——`/blog` 只列 12 篇，其余 60 篇全在 `?page=2..6` 后面。**URL 路径完全体现不出这一层。**

> 📌 这也解释了 findings 里那条 `/blog/marketing-attribution-for-saas has limited observed internal support` —— 工具说了"内链支撑少"，**但没说它埋在 4 跳外**，而后者才是可行动的信息。

### 3.4 所以工具现在用的到底是哪种展现形式

**一个视图里混了三套逻辑**：

| 展示要素 | 用的逻辑 |
|---|---|
| **缩进（主）** | **URL 路径层级** |
| **缩进（回退）** | 路径父页未采集时，才挂到"已观测到的浅层内链父页"——这时才是链接关系 |
| **Depth 列** | **爬虫遍历层数**，且 sitemap 条目算作爬取种子 |

工具自己的说明就是这个混合的产物：

> *"Indentation follows the collected URL path where possible. When a path parent was not collected, the row is explicitly labeled as grouped under an observed shallower inbound page."*

**这段话之所以难懂，是因为它在解释一个三套逻辑拼起来的结构。统一成"链接可达"之后，这段解释就不需要了。**

### 3.5 为什么"发现"和"可达"必须分开

| | Sitemap 可达 | 链接可达 |
|---|---|---|
| 作用 | 让搜索引擎**发现**这个 URL | 让页面获得**内链支撑** |
| 一个只在 sitemap 里的页面 | 能被发现 | **没有任何内链指向它 = 孤岛** |

### 3.6 ⚠️ 依据分级（这一节请工程和内容同事都读一下）

**我最初的表述是「sitemap 只影响发现，不影响权重传递，权重只沿链接流动」。这句话有一半超出了官方依据。** 拆开如下：

#### ✅ Google 官方文档明说的

**① Sitemap 的定位是「发现 / 抓取」** —— [Sitemap 概述](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview)：

> "站点地图可帮助搜索引擎**发现**网站上的网址，但**并不保证** Google 能抓取站点地图中的所有内容并将其编入索引。"

同一页在「不需要 sitemap 的情况」里把二者对立：

> "您的网站**已在内部全面建立链接**。这意味着，Googlebot 可以**沿着首页的链接**找到您网站上的所有重要网页。"

**② 链接是排名信号** —— [Link best practices](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)：

> "Google uses links **as a signal when determining the relevancy of pages** and to find new pages to crawl."

**③ 每个重要页面都该有内链** —— 同页：

> **"Every page you care about should have a link from at least one other page on your site."**

#### ⚠️ 属于推论，不是官方结论

**「sitemap 不传递权重 / 权重只沿链接流动」** —— Google 官方文档**没有**讲过 sitemap 与 link equity 的关系。

这句话的依据强度：

| 依据 | 强度 |
|---|---|
| PageRank 按定义就是链接图算法，sitemap 里的 URL 不是文档间的链接 | 强（算法定义） |
| Google 从未说过 sitemap 传递任何权重 | 中（缺席证据） |
| Google 明说 sitemap 的 `priority` / `changefreq` 基本被忽略 | 中 |
| 行业共识 | **弱**（我们这个项目已经推翻过多条"共识"） |

**准确的表述应该是**：sitemap 的作用是发现（官方明说）；链接是相关性信号（官方明说）。sitemap 是否传递权重，Google 没说过它传递，也没有已知机制表明它会——**但这是推论。**

#### 📌 但产品改法不依赖那半句

即使「权重只沿链接流动」被推翻，下面的改法也不变：

- 工具叫 **Internal Link Audit**，本就该测内链
- Google 明说「你在意的每个页面都该有至少一条内链」
- **「哪些页面埋在 4 跳之外」本身就是用户想知道的事实**
- 现在的 depth 混了两种口径，导致这个事实被掩盖

### 3.7 建议改法

**① `depth` 拆成两个口径**

爬取时可以用 sitemap 补全覆盖，**但计算 depth 时只能沿真实链接走**：

```
发现（可用 sitemap）  ≠  可达性（只能靠链接）
```

**② 新增核心输出：点击深度分布**

```
点击深度分布（沿真实链接，不含 sitemap 种子）
  1 跳    25 页
  2 跳    27 页
  3 跳    51 页
  ≥4 跳   ⚠️ N 页  ← 这些拿不到多少内链支撑
  不可达  ⚠️ N 页  ← 只在 sitemap 里
```

**「≥4 跳」和「不可达」两栏才是可行动的输出**，比现在四个数字卡片加起来都有价值。

**③ 树的组织方式：从「URL 路径」改成「链接可达性」**

```
/ 首页
├─ 1 跳（25 页）
├─ 2 跳（27 页）
├─ 3 跳（51 页）
├─ ⚠️ ≥4 跳
└─ ⚠️ 不可达（只在 sitemap 里）
```

按 URL 路径缩进对扁平站没有信息量；**按可达性分层，一眼看出哪些页面埋得太深。**

**④ 缩进说明那段话可以删掉**

> ~~"Indentation follows the collected URL path where possible. When a path parent was not collected, the row is explicitly labeled as grouped under an observed shallower inbound page…"~~

**这段之所以难懂，是因为它在解释一个不该存在的设计。** 改成按可达性分层后不需要解释。

## 三之补 · 顺带查出的站点侧 SEO 错误（不是工具的问题）

### 分页页的 canonical 全部指向第一页

```
/blog          canonical → https://gengrowth.ai/blog
/blog?page=2   canonical → https://gengrowth.ai/blog   ⚠️
/blog?page=3   canonical → https://gengrowth.ai/blog   ⚠️
```

**但三页的内容完全不同**——page1 与 page2 的 12 篇文章**零重复**。

### ✅ 这条有 Google 官方文档逐字对应

[Pagination best practices](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)：

> **"Don't use the first page of a paginated sequence as the canonical page. Instead, give each page its own canonical URL."**

> "Give each page a unique URL. For example, include a `?page=n` query parameter, as URLs in a paginated sequence **are treated as separate pages by Google**."

### 影响

分页页被自己声明为 `/blog` 的重复版本 → Google 可能不索引它们、降低抓取频率 → **只从 page=2..6 链出的那 60 篇文章，内链信号被削弱**。

这个站 63 篇 blog 里只有 12 篇在第一页，**其余 51 篇全部依赖这批 canonical 错误的分页页**。

### 修法

`/blog?page=N` 的 canonical 改为**自引用**（指向 `/blog?page=N` 自己）。

> 📌 **一个连带观察**：P0-4 全站审计报过 `Canonical 目标不同 66/162`——**这批分页页很可能就在那 66 个里**。也就是说：
> - **P0-4 检测到了**（作为一个原始计数）
> - **P0-2 没检测**（不在它的范围内）
> - **两个工具都没告诉用户这意味着什么**
>
> 这同时印证了产品评审的两条结论：**停在观测没走到判断**，以及**工具之间不连通**。

## 三之补二 · 参数 URL 的完整实测（2026-08-05 追加）

### A. 先澄清一个常见误解：`?amp%3B...` 能打开，不代表它"存在"

**实测**：

```
/blog?这是我随便编的=12345    → HTTP 200，内容与 /blog 完全相同
/blog?xyzabc=nonsense&foo=bar → HTTP 200，内容与 /blog 完全相同
```

**原因**：查询字符串不是路径的一部分。服务器逻辑是「路径 `/blog` 存在 → 返回 200；参数不认识 → 忽略」。

**这是 HTTP 的普遍行为，不是本站缺陷。** 所以：

- ✅ 爬虫造出的 `?amp%3B...` URL 能打开 —— 因为**任何**参数都能打开
- ✅ 但它们**不存在于站点结构中** —— HTML 里写的是 `href="/blog?category=case_study&amp;pillar=attribution"`（正确转义），浏览器和 Googlebot（Chromium 内核）都会解码成 `&`
- ⚠️ **Google 看不到这批 URL，只有我们的爬虫造了它们，然后自己去抓，服务器照例返回 200，爬虫就当成新页面收进了 167 的计数**

### B. 站点侧实测出的四个真问题

#### B1 · `category` 筛选在有分页时不生效 → 真重复内容

```
/blog?page=4                        → 12 篇（agency-rank-tracking…）
/blog?category=methodology&page=4   → 12 篇（agency-rank-tracking…）  ← 完全相同
```

**不同 URL、相同内容、都可索引。**

#### B2 · ⚠️ 15 种筛选组合里 8 种返回 0 篇文章，且都是 HTTP 200

```
?pillar=attribution&category=case_study         → 0 篇
?pillar=attribution&category=weekly_review      → 0 篇
?pillar=customer_stories&category=methodology   → 0 篇
?pillar=customer_stories&category=weekly_review → 0 篇
?pillar=experiment_driven&category=case_study   → 0 篇
?pillar=growth_automation&category=weekly_review→ 0 篇
?pillar=seo_content&category=case_study         → 0 篇
?pillar=seo_content&category=weekly_review      → 0 篇
```

**✅ 这条有 Google 官方逐字对应的条款**（[Faceted navigation](https://developers.google.com/crawling/docs/faceted-navigation)）：

> **"Return an HTTP 404 status code when a filter combination doesn't return results.** … This should also be the case if the URL contains duplicate filters or **otherwise nonsensical filter combinations**, and nonexistent pagination URLs."

#### B3 · 筛选 URL 全部可索引，robots.txt 无任何参数规则

实测：`?category=`、`?pillar=`、`?page=` 全部**无 robots meta**，robots.txt 里也没有参数相关规则。

官方对无限 URL 空间的两条警告：

> **Overcrawling**：爬虫无法在抓取前判断 URL 有没有用，会先抓一大堆才发现没用
> **Slower discovery crawls**：抓取预算花在无用 URL 上，新的有用 URL 就发现得慢

#### B4 · canonical 策略对了一半

**所有变体的 canonical 都指向 `/blog`** —— 用同一条规则处理了两类完全不同的 URL：

| URL 类型 | canonical → `/blog` | 判定 | 依据 |
|---|---|---|---|
| **筛选 / 未知参数**（`?category=`、`?xyzabc=`） | ✅ **正确** | 官方认可的消重做法 | Faceted navigation 文档 |
| **分页**（`?page=2..6`） | ❌ **错误** | 官方明说要自引用 | Pagination 文档 |

⚠️ **两类还会纠缠**：`/blog?category=methodology&page=4` **既是筛选又是分页**，现在直接指向 `/blog`，导致第 4 页那 12 篇文章的内链信号被合并掉。

### C. 「任意参数返回 200」到底正不正常

| 情形 | 判定 | 依据 |
|---|---|---|
| 未知参数返回 200 | ✅ **正常**，HTTP 普遍行为，不用改 | — |
| **空结果组合返回 200** | ❌ **应返 404** | 官方明说 |
| 筛选 URL 可索引且无 robots 规则 | ⚠️ **应该管** | 官方给了三种办法 |
| canonical → 无筛选版（筛选类） | ✅ 可用，但官方说"长期效果不如 robots.txt / noindex" | 同上 |

**官方推荐的处理优先级**：

```
1. robots.txt 屏蔽参数模式（最有效）
2. 用 URL fragment（# 而非 ?）承载筛选 —— Google 不抓 fragment
3. canonical / nofollow —— "generally less effective in the long term"
```

### D. ⭐ 这一轮暴露的产品结论：工具只报「爬取副产品」

工具给出的 12 条 findings，**全部只有两类**：

```
· is at observed crawl depth 3          ← 爬虫遍历时零成本产出
· has limited observed internal support ← 入链计数，同样零成本
```

**而 B1–B4 四个真问题，一条都没报。**

| 现在报的 | 该报但没报的 | 检测成本 |
|---|---|---|
| crawl depth（遍历副产品） | **不同 URL 相同内容** | 需内容指纹比对 |
| inbound count（遍历副产品） | **空结果页** | 需数页面主体元素 |
| — | **筛选 URL 可索引** | ⚠️ **读一个 meta 标签，零边际成本** |
| — | **canonical 指向异常** | ⚠️ **同上，零边际成本** |

**后两条尤其值得说：爬虫已经把 167 页的完整 HTML 抓下来了，却只用了里面的 `<a href>`。** 读 `<meta name="robots">` 和 `<link rel="canonical">` 是零额外请求的。

**结论：工具当前的能力边界是「爬取过程中顺手能算的东西」，而用户要的"审计"恰恰主要由需要额外分析的部分构成。**

> 📌 顺带印证了产品评审的另一条：P0-4 全站审计**报过** `Canonical 目标不同 66/162`（这批分页页很可能就在里面），但只给了个计数；P0-2 不检测 canonical。**两个工具一个检测了不解释、一个不检测，用户两边都拿不到答案。**

## 四、表格：为什么用户感受是「网址堆砌」

### 4.1 六个具体原因

**① 副标题完全没有区分度**

每行是 URL（主）+ 页面标题（副）。但这个站大量页面标题**都是 `Blog — GenGrowth`**：

```
blog?amp%3Bcategory=methodology&page=2
  Blog — GenGrowth
blog?amp%3Bcategory=methodology&page=3
  Blog — GenGrowth
```

**副标题本该帮用户认出"这是哪个页面"，全一样之后用户只能读 URL —— 这就是"堆砌网址"的直接来源。**

（顺带：这与基线查到的 **71/162 页 Title 重复** 是同一问题的另一面。）

**② 三列数字无视觉编码**

`INBOUND / OUTBOUND / DEPTH` 全是同色同粗的灰数字。`6 · 32 · 3` 和 `117 · 12 · 0` 视觉等重，**用户必须逐行读数并在脑中比较，眼睛无法扫描**。

**③ 「层级树」名不副实**

这个站是扁平的：`/` 下挂 `app`、`blog`，然后 100 多个 blog 页平铺在同一层。**缩进只有一两级，树没提供信息，却占了左侧一大块宽度。**

**④ 排序是字母序**

`affordable-seo-software → affordable-seo-tools → agency-rank-tracking → ai-agents-for-sales → ai-search-visibility → ai-seo-audit → all-in-one-seo`

**用户关心的是"哪个有问题"，不是"哪个字母靠前"。**

**⑤ 默认就是全量**

筛选器有「全部 / 首页 / 候选孤岛 / 深层页面 / 其他」，但默认停在**全部 167 行**。

**⑥ 长 URL 换行打乱节奏**

`blog?amp%3Bpillar=attribution&category=case_study` 折成三行，行高失去规律。

### 4.2 根子上

**这个表在回答"我的站长什么样"，用户问的是"我该改哪里"。**

## 五、产品与用户体验

### 5.1 用户旅程

| 步骤 | 用户看到 | 问题 |
|---|---|---|
| 落地 | Hero + 输入框 | 副标题三个术语堆一句，讲的是爬虫实现不是用户的问题 |
| 提交 | **什么都没变** | ⚠️ **零反馈**。实测 2 秒后按钮文案未变、无进度、无骨架屏 |
| 出结果 | Report ready + 四个数字 | 见 5.2 |
| 找问题 | **先滚过 167 行表格**才看到 12 条 findings | ⚠️ **结论排在证据后面** |
| 看完 | 没有下一步 | ⚠️ **报告没有出口** |

### 5.2 四个数字里三个是过程指标

```
PAGES COLLECTED  167   ← 过程
HTML LINKS       2821  ← 过程
SITEMAP URLS     88    ← 过程
PRIORITIZED      12    ← 结果，但排最右、同样大小
```

而且 **167 vs 88 这个差值本身就是发现**（79 页被抓到但不在 sitemap），工具把两个数并排放着，**没有说出它们的关系**。

### 5.3 报告没有出口

滚完整个报告，**没有任何指向其他工具的入口**。唯一转化点是顶部导航的「Open GenGrowth」，与"我刚看完内链报告"这个上下文无关。

**免费工具跑完那一刻用户注意力最集中，而我们什么都没接住。**

### 5.4 核心矛盾：信任建设很好，行动建设完全缺失

**做得好的地方，全在建立信任：**

| 设计 | 传达 |
|---|---|
| `Collection status: Completed within the safety limits` | 不假装扫全了 |
| `INTERPRETATION LIMIT: …not asserted as a homepage click count or ranking prediction` | 不过度解读 |
| `STATIC HTML · SAME ORIGIN · TRANSIENT REQUEST · NO STORED REPORT` | 说清边界 |
| `These are editorial review prompts, not automatic changes` | 不替用户做决定 |

**这套克制在这个品类里很稀缺，是真正的差异化。但信任建立完之后，用户拿到的还是一堆事实。**

### 5.5 对照用户真实需求

痛点报告里的 Reddit 原话：

> *"this is genuinely tedious past 100 pages... **eating a whole afternoon**"*

**他要省掉那个下午。而我们把"手工翻 100 个页面"变成了"翻 167 行表格 + 读 12 条 findings"——下午没省掉，只换了形式。**

**真正省掉那个下午的输出：**

```
你的站有 117 个页面无法从首页通过链接到达
12 个深度 ≥3 的页面里，11 个是同一个模板问题 —— 修模板即可，不用逐个改
1 个页面（/blog/marketing-attribution-for-saas）几乎没有内链指向

最该做的一件事：从 /blog 列表页加一条链接到 marketing-attribution-for-saas
```

**四句话，用户十秒钟就知道该干什么。这些信息全都在报告里，只是没被说出来。**

### 5.6 两个被浪费的设计资产

**① 右侧详情面板做得很好但没人知道能点**

点行 → 显示该页 inbound / outbound / depth / sitemap + observed evidence + interpretation limit。**分层清楚，是整个报告里最好的模块。** 但没有任何"行可点击"的视觉提示，默认选中首页。

**② Hero 那张内链关系图是装饰性的**

它画的是假数据。**而这个工具最该有的就是真实的内链图谱**——孤岛节点一眼可见。竞品（Screaming Frog、Sitebulb）都有可视化。

**我们把可视化用在了装饰上，把数据用在了表格里。刚好反了。**

### 5.7 一个未决策导致体验缺一块

`TRANSIENT REQUEST · NO STORED REPORT` —— 报告关掉就没了。

意味着**不能保存、不能分享给同事、不能对比"改之前 vs 改之后"**。而"改完再测一次看有没有变好"**恰恰是这类工具最自然的复用场景**。

这直接对应交接文档里那个未决策：**「转化资产 vs 外链资产」**。走外链资产路线的话，可分享的结果页是必需的——**而且它同时解决了产品复用问题**。

## 六、✅ 必须保护的设计

迭代时不要弄丢：

1. **边界声明**（`STATIC HTML · SAME ORIGIN · TRANSIENT REQUEST · NO STORED REPORT`）
2. **解释限度**（`INTERPRETATION LIMIT`，明说什么不能推断）
3. **抓取状态诚实**（`Completed within the safety limits`，不假装扫全了）
4. **不替用户下结论**（`editorial review prompts, not automatic changes`）
5. **输入区消除顾虑**（`Free · No sign-up · No software to install · Any public website`）

> ⚠️ **提醒**：如果之后有人反馈"工具太难懂"，**正确的修法是加「下一步」层，不是加「评分」层。** 评分会把不可通约的观测压缩成一个数字，必然掺入我们并不掌握的假设——那会毁掉上面五条。
