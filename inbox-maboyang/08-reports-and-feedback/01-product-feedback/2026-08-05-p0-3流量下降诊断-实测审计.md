# P0-3 流量下降诊断 · 实测审计

## 零、一句话结论

**这是五个工具里产品做得最好的一个，超过 P0-1。但它有一个和 P0-1 完全相反的毛病：产品极强，落地页极弱。**

| 维度 | 结论 |
|---|---|
| **产品逻辑** | ⭐ **全线最高水位**：拒绝下结论的分支、三档证据分层、11 项检查全公开 |
| **认知诚实度** | ⭐ 「未检查 ≠ 检查了没问题」「窗口不可手调」两条应写进产品原则 |
| **可视化** | ⭐ **五个工具里唯一有图表的**（双轴时序 + 阴影对比窗口 + 可展开数据表） |
| 🔴 **匿名落地页** | **471 词**，四个真工具里最薄，只比未上线的 P0-5 多 140 词 |
| 🔴 **内容与产品脱节** | 招募主词是「我是不是被惩罚了」，落地页 `penalt` 出现 **0 次** |
| 🔴 **结果态阅读负担** | 1,935 词正文里 **93 处否定/限定，每 21 词一处** |
| 🔴 **结果态无出口** | 唯一的工具出口写给「还没跑的人」，且不含最该链的 P0-1 |
| ⚠️ **一处需核实** | `Average position is impression-weighted` 与我们自己的记录冲突 |

## 一、⭐ 必须保护的六项设计

这一节是整份文档里最重要的。P0-3 有几处做法是**整条产品线的最高水位**，改版时不能被"简化"掉。

### 1.1 「I could not tell」分支拒绝向任何方向下结论

两张状态卡（Manual action / Security issue）各有三个选项，第三个是 `I could not tell`。我两张都选了这个（我确实没打开过 astrologywiki 的 Manual Actions 报告，不该替它填状态）。

报告顶部的响应：

> **One answer is missing, and it is the one that matters**
>
> Until that page is settled, this report **will not tell you that you have been penalised and will not tell you that you have not.** Both would be claims about something we cannot see. The traffic observations below stand on their own — read them, but do not read a verdict into them.

这正是 `2026-08-03-p0-3新增降权诊断能力-产品需求.md` 里「『不是惩罚』是同等重要的输出」那一条，**实现得比需求文档写的更严**——它连"不是惩罚"也拒绝说。

同时，两张卡的答案被记为**用户的观察而非工具的判断**：

> Both are recorded as your observations, not as ours. Google publishes no interface for either page, so we have no way to verify them — which puts them on a different footing from the measured numbers below.

### 1.2 未检查 ≠ 检查了没问题

因为我没有勾选品牌词确认框，两个模块被跳过。报告的写法是：

> Brand vs non-brand queries — The query-level read did not run for this report, so this could not be computed. **It was not checked and found clear — it was not checked.**

**这句话应该刻进整条产品线。** P0-1 的 Q3/Q4（「All 45」被误读成真实分布）如果用这个口径，根本不会出现。

### 1.3 11 项检查全部公开，三种状态

结果区底部有一个折叠块：

> This run performed **11 checks and 3 triggered** — open to see all of them, including what came back clear and what could not be checked

展开后每条标 `Triggered` / `Clear` / `Cannot check`，且每条"查不了"都说明**为什么查不了**以及**去哪查**：

| 状态 | 检查项 | 说明 |
|---|---|---|
| Triggered | Sustained decline | 峰值后两个不重叠的周都低于维持阈值 |
| Triggered | Click-through change point | 曝光维持的窗口里点击骤降 |
| Triggered | Short visibility anomaly | 一小段天数相对自身星期几基线崩塌后反弹 |
| Clear | Site-wide visibility loss | 该 property 仍在记录曝光 |
| Cannot check | Decline concentration | 「本版本中集中度检查未接入 query 读取」，去 GSC Queries 标签页看 |
| Cannot check | Affected page availability | 本工具不抓页面，去 URL Inspection 查 |
| Cannot check | Single-page dominated decline | 本工具只读整站日汇总 |

**注意第五条**：产品在用户可见文案里承认自己有一处没接完（`not wired to the query read in this version`）。这种诚实度很少见，而且它把"没做完"和"没问题"清楚地分开了。

### 1.4 窗口不可手调，并且说明了理由

> Windows are chosen by change-point detection and **cannot be adjusted by hand. Moving a window moves the conclusion — that is picking an answer, not diagnosing one.**

这一条直接堵死了 SEO 报告最常见的自欺方式：调窗口调到出现自己想要的结论。

### 1.5 三档证据分层，且不混用

> Layered by evidence strength: an **observation** is a fact in your data, a **hypothesis** is an explanation the data is consistent with but cannot establish. **We do not blur the two.**

实际用到三个标签：

| 标签 | 用法 |
|---|---|
| `Observed` | 数据里的事实 |
| `Hypothesis` | 数据一致但无法确立的解释，单独成块 |
| `Data boundary` | 数据量不够，检查自我禁用 |

第三档的实例：

> **Seasonality cannot be assessed yet** `Data boundary`
> A year-over-year read needs the same season last year, and this property does not have it yet. **We do not estimate it.** This check turns itself on once the history is long enough.
> History available: 193 · History required: 395

**"不够就不算，而不是估一个"**，并且告诉用户什么时候会自动打开。

### 1.6 Google 更新时间线：主动压制自己的证据效力

> Context only, and **it does not count toward anything**. The detector works in whole weeks, so the event is a span rather than a date; announced updates roll out over weeks too. **In a typical year those windows cover a large share of the calendar, so an overlap is as likely to be coincidence as anything else.**
>
> That span does not overlap any update we have on file. **This is not evidence that nothing algorithmic happened** — Google adjusts ranking continuously, and only some of it is announced.
>
> Update list version **2026-08-04.v2**, last checked against Google's status dashboard on **2026-08-04**.

三件事同时做到：说明这条不计入结论、说明"没重合"不等于"没发生"、给出清单版本号与核对日期。

## 二、⚠️ 一处我自己的核对失误（更正）

**2026-08-05 早些时候我报告「P0-3 六个因素全覆盖，推广文档的对外承诺站得住」，方法是错的。**

我 grep 了整个 HTML，拿到 `manual action` 出现 19 次，据此判定覆盖。**实际上那 19 次全部在 `<script>` 和 JSON-LD 载荷里，可见正文是 0 次。**

正确的区分方式：

```bash
# 错的：整个 HTML，含 script 与 RSC 载荷
grep -oic "manual action" p03.html            # → 19

# 对的：先剥掉 script/style，再看可见正文
perl -0777 -pe 's{<(script|style)\b.*?</\1>}{}gis' p03.html \
  | sed 's/<[^>]*>/ /g' > p03_visible.txt
grep -oic "manual action" p03_visible.txt     # → 0
```

结论要分两句说：

- **降权诊断确实已上线，而且实现质量很高**（见一、）——这部分是授权后客户端渲染的，curl 拿不到；
- **但匿名落地页对它只字未提**（见三、3.3）。

> 📌 这是本轮审计里我第三次犯同类错误：P0-1 的 `hrefLang` 大小写、P0-2 批评爬虫时自己的 URL 规范化、这次的 script 载荷。共同点都是**没有先确认"我查的这个东西，是不是我要查的那个东西"**。三次都记在各自文档里。

## 三、🔴 匿名落地页只有 471 词

### 3.1 站内横向对比

| 工具页 | 净词数 | H2 | H3 | FAQ | `<details>` | 匿名可用 |
|---|---|---|---|---|---|---|
| P0-1 seo-quick-wins | 2,739 | 13 | 37 | 11 | 0 | ❌ |
| P0-2 internal-link-audit | 1,353 | 9 | 31 | 10 | 10 | ✅ |
| P0-4 seo-audit | 1,044 | 9 | 27 | 8 | 8 | ✅ |
| **P0-3 traffic-drop-diagnosis** | **471** | **4** | **10** | **3** | **0** | ❌ |
| P0-5 hidden-keywords（未上线） | 331 | 3 | 10 | 0 | 0 | — |

**P0-3 的落地页在结构上更接近未上线的 P0-5，而不是另外三个真工具。**

复现命令：

```bash
for u in seo-quick-wins traffic-drop-diagnosis seo-audit internal-link-audit hidden-keywords; do
  curl -s "https://gengrowth.ai/tools/$u" -o t_$u.html
  w=$(perl -0777 -pe 's{<(script|style)\b.*?</\1>}{}gis' t_$u.html \
      | sed 's/<[^>]*>/ /g' | tr -s ' \n' ' \n' | wc -w)
  echo "$u  $w 词  H2=$(grep -oF '<h2' t_$u.html|wc -l)  H3=$(grep -oF '<h3' t_$u.html|wc -l)"
done
```

> ⚠️ 注意：数出现次数必须用 `grep -o … | wc -l`。`grep -c` 数的是**行数**，而这些页面是单行 HTML，永远返回 1。我第一次跑就踩了这个，得到"P0-3 只有 1 个 H2"的错误结果。

### 3.2 关于 AstrologyWiki 那份工具页 SOP 的适用边界

`00-inbox/2026-07-09-工具落地页设计规范-sop-v1.0.md` 规定了 ≥2000 词、H3 ≥15、FAQ 8-10 条。**但它第六节的适用边界明确只列了 AstrologyWiki 的工具页和 51 词根扩站页，不含 GenGrowth。**

所以本节不拿那份 SOP 当硬标准，只做站内横向对比。**如果要把它升格为全公司标准，需要单独决策**——那是另一件事，不在本审计范围。

### 3.3 落地页与招募口径对不上

推广文档第五节给 P0-3 定的用户原话是：

> why is my website traffic dropping、**「我是不是被惩罚了」**

而落地页可见正文里：

| 词 | 可见正文 | 全文（含 script） |
|---|---|---|
| `manual action` | **0** | 19 |
| `penalt` | **0** | 5 |
| `demand` | **0** | 5 |
| `technical` | **0** | 4 |
| `ranking` / `CTR` / `index` / `seasonal` | 各 1 次，**全在同一句** | — |

那唯一一句是：

> Diagnosis — Supported explanations **such as** ranking, CTR, indexing, or seasonal changes—not a guessed single cause.

四个因素，还是举例式的 `such as`，而且是在讲"工具把什么分开"，不是在讲"你能得到什么"。

**这个工具最强的能力——降权判定，以及它拒绝下结论的那套设计——对所有没授权的人完全不可见。** 而「我是不是被惩罚了」恰恰是把人带到这个页面的那个念头。

推广文档给它的对外承诺（区分需求、CTR、排名、索引、技术和季节性）**产品做得到，落地页没说**。

## 四、🔴 结果态的阅读负担

### 4.1 量化

跑完之后页面从 471 词涨到 **2,944 词**（结果区本身 2,523 词；剥掉可展开的数据表后，纯叙述 1,935 词）。

| 指标 | 值 | 说明 |
|---|---|---|
| 结果区总词数 | 2,523 | 比 P0-1 整个落地页（2,739）还接近 |
| 纯叙述词数（去数据表） | 1,935 | |
| 句子数 | 88 | |
| 平均句长 | **22 词** | 英文商务写作常规目标 15–20 |
| 超 30 词的句子 | **14 句** | |
| **否定/限定词出现次数** | **93** | `cannot` / `not` / `does not` / `rather than` / `without` / `only` … |
| **平均每 N 词出现一处否定** | **21** | |

### 4.2 费劲的根子不是字多，是几乎每句都在做减法

**1,935 词里 93 处否定或限定，等于每 21 词就有一处。**

这不是文案毛病，而是产品最大优点的直接代价——它的立身之本就是"我不告诉你我不知道的事"，那就只能反复用否定句表达。随手几例：

> …this report **will not** tell you that you have been penalised and **will not** tell you that you have **not**.
>
> It was **not** checked and found clear — it was **not** checked.
>
> This is **not** evidence that **nothing** algorithmic happened.
>
> **Neither** Manual Actions **nor** Security Issues is among them.

单看每一句都对、都必要。**连着读 1,935 词，认知负担就上来了。**

### 4.3 阅读路径：前 37% 读完才看到第一个数字

按文本位置测算结果区的内容分布：

| 位置（占结果区） | 内容 |
|---|---|
| 0 – 37% | **元信息与边界**：报告基于你的两个回答 / 有一个答案缺失 / 我们能和不能确立什么 / Google 更新时间线 / 两个模块没算 |
| **37%** | **第一个真实数字出现（411）** |
| 41% | What we found · 4 |
| 46% | 首次出现 `-90%` |
| 56% | What to do next · 6 |
| 78% | 11 项检查（已折叠） |
| 95% | FAQ |
| 98% | 工具出口卡 |

测算方式：

```js
const t=document.body.innerText, r=t.indexOf('This report was built'), L=t.length;
const pos = s => Math.round((t.indexOf(s)-r)/(L-r)*100) + '%';
```

**"费劲"的来源不是总字数，是数字出现得太晚。** 前 37% 全部在讲这份报告的输入、边界和它不能做什么——每一句都对，但读的人此时还不知道自己站在哪。

### 4.4 结构问题：结论和限定条件是平权的

现在的排版里，"发生了什么"和"这个判断的边界在哪"用同样的字号、同样的段落形态、前后相邻排列。用户必须逐句读完才能分辨哪句是结论、哪句是免责。

**建议的方向不是删限定条件**——那会毁掉这个产品的核心价值——**而是把两者分层**。

P0-2 有 10 个 `<details>`、P0-4 有 8 个，**P0-3 的结果区只有 2 个**（数据表 + 11 项检查）。这套折叠机制在结果区几乎没被用上。

### 4.5 三条具体改法

#### 改法 A · 结论前置：顶部加一张摘要卡（→ T5a）

现在结果区的第一块是「This report was built on your two answers」——讲的是**输入**，不是结果。建议在它之前插入：

```
astrologywiki.com · 2026-01-25 起 193 天

  点击   411 → 42       -90%      峰值周 → 最近周
  曝光   20,626 → 4,982 -76%
  变点   2026-07-15 → 07-22（8 天）

  这是两次下跌，机制不同
  4 条发现 · 6 条待办 · 11 项检查中 3 项触发

  ⚠ 惩罚状态未确认 —— 本报告不会说你被惩罚了，也不会说你没有
```

最后一行是把「拒绝下结论」这件事提到最前面。它现在在 6% 处，写得很好，但被夹在元信息里读不出分量。

#### 改法 B · 用产品已有的标签驱动折叠（→ T5b，成本最低）

**产品已经把每一块内容分好类了** —— `Observed` / `Hypothesis` / `Data boundary` / `Cannot check`。不需要引入新的判断标准，直接把折叠状态绑定到现成分类：

| 现有标签 | 折叠状态 |
|---|---|
| `Observed` | 默认展开 |
| `Hypothesis` | 默认折叠（标签已经在了，只是现在和 Observed 一样铺开） |
| `Data boundary` / `Cannot check` / `did not run` | 全部收进一个统一折叠区：**「我们没能查的（N 项）」** |

按此规则，前 37% 里可下沉的有五块：

1. 「What we can and cannot establish about a penalty」的引言
2. Google 更新时间线整段（产品自己写了 `does not count toward anything`）
3. Brand vs non-brand queries（未算）
4. Where a fixed set of queries sits now（未算）
5. Seasonality（`Data boundary`）

**摘要卡上提 + 这五块下沉，用户在前 10% 就能看到数字。而且一个字都没有被删除** —— `It was not checked and found clear — it was not checked.` 这类句子全部原样保留在折叠区内。

#### 改法 C · 重复的否定表达压成标签（→ T5c，优先级最低）

1,935 词里 93 处否定，其中一部分是同一个意思说了多遍。建议同类免责**第一次出现时写全文，之后用标签**（如 `未检查`），全文放在折叠区或悬停中。

这条排在最后：改法 A 和 B 完成后，可能就不需要它了。

## 五、🔴 结果态没有出口

### 5.1 唯一的工具出口，是写给「还没跑的人」的

页面 91% 处（y=7502 / 全页 8246px），FAQ 右侧有一张卡：

```
PUBLIC TOOLS YOU CAN RUN FIRST
Start with a site check that does not require a connection.

  → Free SEO Audit
  → Internal Link Audit
```

**措辞是 `run first` / `Start with`，面向的是尚未授权的访客。** 但它出现在跑完 2,944 词报告之后。

一个刚被告知"你的 CTR 从 1.99% 崩到 0.85%"的人，读到页面底部，看到的是"先从一个不需要连接的站点检查开始"——对一个刚刚完成连接的人说的话。

### 5.2 最该链的 P0-1 没有链

结果区的头号发现是**点击率崩塌**（Stage 1 曝光 -4%、点击 -59%）。而 GenGrowth 里专门找 CTR 缺口的工具就是 **P0-1 SEO Quick Wins**。

**P0-3 诊断出了 CTR 问题，却没有链到那个 CTR 工具。**

更直接的证据是，报告的 "Do first" 行动里写着：

> Establish whether click-through fell because the query mix changed or because your results got worse… **take only the queries that already existed before the drop and check whether their click-through fell too.**

这段描述的操作，正是 P0-1 在做的事。**产品自己写出了下一步，却没给下一步一个链接。**

### 5.3 FAQ 三条全是"跑之前"的信任问题

| FAQ | 面向 |
|---|---|
| Can a public crawl diagnose a traffic drop? | 跑之前 |
| Is the Google connection read-only? | 跑之前 |
| Can it prove one root cause? | 跑之前 |

没有一条帮到正在读结果的人。

### 5.4 统一起来看

**整个页面底部（FAQ + 工具卡）都是为"未跑"状态写的，但它恰恰是"已跑"用户唯一会看到的部分。** 结果态复用了匿名态的页尾，没有自己的收尾。

这和 P0-2 审计 5.3 节「报告没有出口」是同一类问题，但 P0-3 更可惜：它不是没有出口，是**出口存在却指错了方向**。

### 5.5 三条具体改法

#### 改法 D · 把链接放进提出需求的那句话里（→ T4a，最强的版本）

报告的 "Do first" 已经写了：

> **Establish whether click-through fell because the query mix changed or because your results got worse.** The two have opposite fixes… take only the queries that already existed before the drop and check whether their click-through fell too.

**这段描述的操作，就是 P0-1 在做的事。** 出口不该等到 98% 处，应该就在这里：

```
Do first
Establish whether click-through fell because the query mix
changed or because your results got worse

  …take only the queries that already existed before the drop
  and check whether their click-through fell too.

  → Run SEO Quick Wins on this property              ← 新增
    It reads the same Search Console property and lists the
    queries whose click-through sits below your own baseline.

  Based on: This is not one decline, it is two ·
            Your biggest impression day converted far below
            your peak week
```

同理，另外三条也各有天然去处：

| 行动条目 | 应挂的出口 |
|---|---|
| Pull deploy records and CDN or server logs | P0-4 Free SEO Audit（抓取侧，且无需再授权） |
| `Cannot check` · Decline concentration | GSC Queries 标签页深链（产品自己已经在说"去那看"） |
| `Cannot check` · Single-page dominated decline | P0-2 Internal Link Audit |

#### 改法 E · 页尾那张卡改为按触发结果条件渲染（→ T4b）

当前是静态卡，且措辞面向未授权访客。建议改为：

- 标题：`PUBLIC TOOLS YOU CAN RUN FIRST` → **`WHERE TO GO NEXT`**
- 正文：`Start with a site check that does not require a connection` → 指向本次诊断的实际结果

| 触发的检查 | 导向 | 卡上文案 |
|---|---|---|
| `Click-through change point` | **P0-1 SEO Quick Wins** | Your click-through fell while impressions held. This finds which queries. |
| `Short visibility anomaly` | **P0-4 Free SEO Audit** | Those days need a crawl-side check. No connection required. |
| `Decline concentration` / `Single-page dominated`（Cannot check） | **P0-2 Internal Link Audit** + GSC Queries 深链 | We could not split this by page. Here is where that is checked. |

astrologywiki 本次触发的是「CTR 变点 + 短期可见性异常」，因此这张卡应给出 **P0-1 与 P0-4**。**而它现在给的是 P0-4 和 P0-2 —— 唯一最该给的 P0-1 反而没有。**

#### 改法 F · 位置从 98% 提到 78%（→ T4c）

页尾卡应移到 **"What to do next" 结束处**（约 78%），即 11 项检查折叠块之前。

理由：读完六条待办的人正处在"那我现在做什么"的状态，此时给出口最有效；而 11 项检查与 FAQ 都属于"想深究才看"的内容，放在出口之后不影响它们被找到。

## 七、⚠️ 一处需要核实的措辞

"Do not do" 里有一条：

> **Do not chase a rankings recovery because average position went up**
>
> **Average position is impression-weighted.** When high-ranking queries disappear the number rises on its own, without any of your pages having moved. Optimising against it means solving a problem you do not have.

**建议的动作是对的**（不要因为均位数字变化就去追排名恢复），而且对 astrologywiki 当前处境完全适用（曝光 -76%，大量查询消失）。

但 `impression-weighted` 这个定性**与我们自己此前的记录冲突**——我们记录的是 GSC 均位为按查询平均而非按曝光加权，并且当时把它列为"我们踩过的统计陷阱"。

我现在无法确定哪一边对，**因此本文不下结论**。

**建议**：对着 Google Search Console 官方文档核一次这句措辞。这是产品里一条明确的"不要做"，措辞错了会误导用户，而核实成本极低。

## 九、必须单独立项的业务发现：astrologywiki.com 点击 -90%

**这一节不是工具审计，是审计过程中跑出来的真实业务问题。**

| 窗口 | 周 | 点击 | 曝光 | CTR |
|---|---|---|---|---|
| **A 峰值周** | 2026-07-09 → 07-15 | **411** | 20,626 | 1.99% |
| **B 次周** | 2026-07-16 → 07-22 | 168 | 19,791 | 0.85% |
| **C 最近周** | 2026-07-30 → 08-05 | **42** | 4,982 | 0.84% |

- 点击 **-90%**，曝光 **-76%**
- 变点检测定位在 **2026-07-15 → 07-22**（8 天跨度）

### 9.1 工具的判断：这是两次下跌，机制不同

> **This is not one decline, it is two — with different mechanics** `Observed`
>
> 第一阶段曝光只掉 4%、点击掉 59%（点击率崩塌：人看得见你但不点）；第二阶段曝光才掉 75%（人看不见你了）。**Treating these as one event sends you to fix the wrong thing.**

### 9.2 另外两条 Observed

**单日最高曝光却几乎不转化**
2026-07-19，曝光 5,044（全期最高），点击 38，当日 CTR 0.75%（峰值周 1.99%）。工具的假设是"一批几乎不产生点击的查询涌入"，并明确标为 `Hypothesis`。

**两天可见性崩塌后反弹**
2026-07-31 → 08-01，曝光从该星期几正常的 1,872 掉到 **34**，两天后反弹到 1,343。工具把它和主跌**分开报告**（"a dip that recovered is not evidence of a sustained problem"），并建议去查部署记录和 CDN / 服务器日志。

### 9.3 建议

1. **今天就查 07-31 → 08-01 的部署与 CDN 记录** —— 这是唯一一个有明确排查路径的点
2. **打开 GSC 的 Manual Actions 与 Security Issues 页面**，把这两个状态确认掉（本次审计我选了「看不出来」，所以报告拒绝对惩罚下任何结论）
3. **按工具的 Do first 执行**：只取下跌前就存在的查询，看它们的 CTR 是否也跌了 —— 这能区分"查询构成变了"和"我们的结果变差了"，两者修法相反
4. 时间上，07-15 → 07-22 这个窗口与**外链冲刺计划**的执行期重合，需要一并核对

**C 窗口含 Search Console 未定稿的数据会偏低，但 411 → 42 不是数据延迟能解释的量级。**
