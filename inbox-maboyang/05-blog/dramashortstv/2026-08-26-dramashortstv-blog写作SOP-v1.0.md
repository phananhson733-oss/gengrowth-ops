1. **建卡与分级**：从关键词清单-40个.md 的排期建议表里取下一项，确认属于哪个内容类型（见二节六类模板），不需要 us_share 地区闸门这一步

4. **独立QA质检**（下详见六节）：5秒red-line扫视，不连贯盲发
5. **部署与内链**：内链到已发布的安全指南/App档案页，反链回对应枢纽页（演员图鉴枢纽页等）

## 三、写前搜证：四字段 + 安全边界（改造自变量预处理器v2.0）

原版给每篇文章要求 Entity / Friction / Logic / Content_Angle 四个字段，并用"占星科学边界"卡安全性。dramashortstv 保留四字段结构，**占星科学边界替换成短剧站自己的安全边界**：

### 3.1 四字段定义（对照短剧站场景重写）

| 字段 | 定义 | 短剧站案例 |
|---|---|---|
| **Entity** | 本篇的主权实体，同类型其他篇不得复用 | "DramaBox"（App档案页）/ "Marc Herrmann"（演员页）/ "DramaBox vs ReelShort"（对比页）|
| **Friction** | 真实用户痛点，必须有信源（Google真实SERP/App商店真实评论/Reddit），不能是自己拍脑袋想的 | DramaBox/ReelShort 退订投诉的真实用户评论原文 |
| **Logic** | 机制解释：这件事实际怎么运作 | 金币+订阅的付费模式怎么运作、演员的真实剧目怎么核实 |
| **Content_Angle** | 差异化角度：解决同一个Friction，别人的内容没做到的地方 | "查两款App的真实开发商注册信息+真实投诉模式"这个角度，reelpulse同款对比页没做 |

### 3.2 安全边界（取代占星科学边界，四条不能破）

1. **盗版关联词强制排除**：`[剧名]+dailymotion`、`免费看不付费`、`free coins`、`mod apk`——无论出现在哪种内容类型里，一律不能出现在正文或推荐链接里，这条判据比四问更前置，不需要走SERP检查直接排除（依据：选词验证.md 三节3.4/5）
2. **平衡测评框架，不做攻击性内容**：竞品/信任类内容（"is X legit"、对比测评）参照已验证过SERP排名靠前的调性（真实体验+价格+优缺点），不写"揭露骗局"式内容（依据：选词验证.md 三节3.2）
3. **内容诚实边界**：不夸大投诉代表性、不编造具体细节、区分一手信源（官方Fandom/Play商店listing/IMDb）和二手信源（聚合站/未署名转载）、明确标注未核实数据留给发布前核实（依据：DramaBox档案页/对比测评/演员页三篇已实证的写法）
4. **同名污染核查（演员类内容专属）**：写演员页之前必须查一遍真实Google搜索，确认这个名字有没有被其他同名人稀释；如果有，标题和首段必须明确限定"ReelShort actor"（依据：Evan Adams/Ben Armstrong的实测教训，见演员图鉴生产清单.md）

### 3.3 证据强度与中止规则（改造自 Evidence + Confidence + Abort）

- **四问全过**（近两年新域名/十万月访以下站/UGC位/AI摘要未完整答完）→ 正常推进
- **四问不过**（AI摘要已完整答完该问题）→ 该词不做主攻方向，可作为FAQ承接词或内链锚点，不单独开页（依据：C组#25 `best short drama apps` 的处理方式）
- **同名污染核查未过**（多个不相关同名人占据SERP主要位置）→ 标题/首段必须加限定词，不能假装没有这个问题
- **一手信源缺失**（官方渠道/App商店/IMDb都查不到）→ 明确标注"未找到公开信息"，不编造

## 四、六类内容的锁定模板

以下模板从已发布的5篇稿件反推，不是凭空设计。新写同类型内容时，结构、板块顺序照此执行，不随意增减。

🔴 2026-08-27 更新：这六节的结构现在也封装进了 `2026-08-27-dramashortstv-blog-system-prompt-v1.0.md` 的 State 3（六个分支 A-F），**实际生成时按那份文档的状态机执行**，本节保留作为人工阅读的说明版本，两边改动要同步。

### 4.1 安全指南聚合页（对照已发布的短剧App安全指南.md）

1. 标题（三选一）+ Meta description（150字符内）
2. 正文：直接回答"是不是骗局"这个核心问题（结论先行）→ 付费机制怎么运作 → 逐App要点 → 怎么避免踩坑
3. 数据诚实声明（哪些App有实测数据支撑，哪些只有通用框架覆盖）

### 4.2 App档案页（对照已发布的DramaBox档案页.md）

1. 关键词覆盖表（列出目标词+月搜+KD+AI摘要状态）
2. 标题三选一
3. 正文按子问题分块（每节标题就是一个问题，对应query fan-out逻辑）
4. FAQ（结构化数据用）
5. 🔴必须亲自核的事项（发布前必做清单）
6. 内容诚实边界
7. SEO执行说明（为什么这么选主攻方向）

### 4.3 对比测评（对照已发布的DramaBox vs ReelShort.md；v1.1 按 unifab 补丁四重写）

搜竞品名的用户已进入决策阶段，转化意图远高于信息词。这类内容按以下八节写，**顺序不动**：

| # | 板块 | 要求 |
|---|---|---|
| 1 | 快速结论 | 让读者 30 秒内知道选哪个。不能是"两个都不错" |
| 2 | 各自介绍 | 中立语气，不攻击（对应三节安全边界第 2 条）|
| 3 | 真实测试 / 对比数据 | 具体数值，有截图更好。数字必须标信源与采集日期 |
| 4 | **定价对比** | 金币包价格、单集解锁成本、订阅价与续订周期，逐项列 |
| 5 | 优缺点表格 | 缺点用具体场景描述，不用笼统批评 |
| 6 | **功能差异矩阵** | 三段式：**对方有我方没有**（诚实列出，这段最建立信任）／ 双方都有但差异在哪 ／ 我方独有 |
| 7 | **明确的二选一结论句** | 必须写成两句：`Choose [A] if you need X` / `Choose [B] if you need Y` |
| 8 | FAQ 8–10 条 + FAQPage schema | 见 5.6 |

额外两节（dramashortstv 专属，保留 v1.0 已有内容）：

- **四问核查**：选词规则 v1.2 的四问，附真实 Google 实测记录
- **与竞品同款内容的差异化说明**：SERP 里已有同款对比文章时必写

> 补丁四原结构第 7 段是「嵌入产品教程模块」，那是工具站设计（有计算器可演示）。dramashortstv 无工具页，该段不采用；其位置由本表第 7 项（二选一结论句）承接。

**执行红线**：竞品缺陷描述必须基于真实测试或公开用户评论，不能捏造。写法用「部分用户反映 X」并引用 Reddit / App 商店原文。

### 4.4 品牌剧单（暂定，未经实证，下次写这类内容时验证并回填此节）

推测结构：标题（接裸品牌词，不正面硬刚品牌词排名）→ N部剧的简介+亮点 → 内链导向对应剧集页

### 4.5 演员/角色内容（对照已发布的Marc Herrmann.md / Evan Adams.md）

1. Quick Facts表（姓名/生日/身高/其他身份等，逐项标注信源）
2. 正文：出道前经历 → ReelShort剧目列表（含播放量）→ 观看入口
3. 内容团队备注（不进最终发布稿）：信源交叉核实记录、发现的官方简介错误、图片版权待办、数据时效性提醒

### 4.6 题材枢纽页/读者视角桥接（暂定，未经实证）

推测结构（依据选词验证.md 3.6节fanficable.com案例）：第一人称"我作为读者/追剧者"视角，不是产品页写法，需要先确定"我们的读者人设"这个前置问题才能真正执行

## 五、通用写作规范（改造自System Prompt v4.5.2 + unifab 补丁）

以下规则不分内容类型，全部适用。

### 5.1 字数目标（v1.1 新增）

⚠️ **提案，需回测。** 补丁给的是 astrologywiki 的 T1 4,000–6,000 / T2 2,000–3,000，工具站与片库站不可直接照搬，以下按六类模板重定：

| 内容类型 | 目标字数 |
|---|---|
| 安全指南聚合页 | 2,500–4,000 |
| 对比测评 | 2,000–3,000 |
| App 档案页 | 1,800–2,500 |
| 题材枢纽页 | 1,500–2,500 |
| 品牌剧单 | 1,500–2,200 |
| 演员/角色内容（量产线）| 800–1,200 |

字数是**结果不是目标**——写够该写的内容自然到量。低于下限说明子问题没铺开；高于上限先查是不是有凑字数的段落。

> 对照：2026-08-28 已发布的《Are Short Drama Apps Safe?》正文 1,475 词，低于安全指南聚合页下限约 40%。原因是两个品牌小节的实质内容被删空（见 01-review-audit/2026-08-28-blog审计-短剧app安全指南.md）。

### 5.2 可读性

- 单段不超过 60 词，超过就拆
- 超过 300 词的板块，必须有至少一处视觉断点（编号列表/项目符号/子标题/引用块），不能连续 4 段纯文字
- 可枚举内容（步骤/排名/多个并列案例）用编号列表；并列特征/无排名的清单用项目符号；论证性内容用散文，不要硬拆成列表

### 5.3 标题与 H2/H3

**H2/H3：**
- 每个 H2 应包含目标词或相关长尾变体，不用 "Conclusion"/"Summary"/"FAQ" 这类光秃秃的通用标签
- 同一篇文章里 H2 的句式要有变化，不能全部用同一个开头结构

**标题公式（v1.1 新增，五选一）：**

| # | 公式 | 示例 |
|---|---|---|
| 1 | 具体承诺 | `What to Check Before You Pay` |
| 2 | 年份限定 | `Best Short Drama Apps in 2026` |
| 3 | 情绪钩子 | `The Coin Problem Nobody Explains` |
| 4 | 数字清单 | `7 Short Dramas Worth Finishing` |
| 5 | **数据化反差** | `90% of Viewers Get the Coin Math Wrong — Here's Why` |

第 5 种写法要点：百分比用具体数字，不用"大多数/很多人"；反差部分描述具体误区，不用笼统批评；结尾给正向暗示（Here's Why / The Fix / What You're Missing）。**数字必须有信源**，不能为了句式好看编一个。

### 5.4 禁用 AI 写作痕迹

继承自 Reddit/公众号侧已验证的六项自查（见 05-blog/reddit/2026-08-14-reddit发帖计划与素材库.md 1.1 节）：

1. 对偶格律（两句同构只换一个词）
2. 否定+肯定成对句式滥用
3. 破折号纠正式表达
4. 三重排比
5. 段末金句
6. 破折号密度超过 1–2 处

### 5.5 内链规则（v1.1 大幅扩充）

**数量与位置：**

| 规则 | 要求 |
|---|---|
| 数量 | 精修线 3–5 条 · 量产线 2–3 条（v1.1 把量产线下限从 1 提到 2）|
| **位置** | **正文前 20%（首屏内）必须有第一条**——此位置权重最高；中段一条；结尾一条。不要全堆在文末 |
| 链接目标 | 指向剧集页 / App 档案页 / 题材枢纽页本身，不指向"怎么看"类文章 |
| 方向 | blog → 枢纽页/剧集页；枢纽页底部反向推荐相关 blog，形成双向 |
| 单页出链上限 | **总出链 ≤ 15 条**（正文文字链 + 推荐卡组件 + 相关文章，全部计入）|

出链超过 15 条时，PageRank 在所有链出页面间均分，每条传的权重都变少。

**锚文本三维分布**（单目标页面维度）：

| 类型 | 比例 | 示例 |
|---|---|---|
| 精确关键词 | 20–30% | `DramaBox app` |
| 部分匹配 / 相关词 | 40–50% | `the DramaBox coin system`、`our DramaBox breakdown` |
| 自然语言描述 | 20–30% | `what we found when we checked it` |
| 无语义（"点击这里"）| < 10% | 尽量不用 |

**整站上限**：同一目标页面的精确匹配锚文本，全站不超过总页数的 10%。

**跨集群互链克制**：六类内容之间（演员页 ↔ App 档案页 ↔ 对比测评）属跨集群。

- 需有强语义关联才加，判断标准：**"读完这篇，读者真的会想看那篇吗？"**
- 单篇出链中跨集群比例 **≤ 20%**
- 不确定就不加，宁可少——乱链会稀释每个集群的主题信号

**组件链接不能替代正文静态链接**：推荐卡这类组件链接传语义信号但 PageRank 传递效率低，正文静态链接才是权重主通道。两者必须同时存在，不能用组件链接凑数量。

**其他：**
- 锚文本必须是描述性短语，禁止裸 URL 或 "here"/"click here"
- 不链接盗版/mod apk 相关站点（对应三节安全边界第 1 条）

### 5.6 Schema 规范（v1.1 新增）

每篇必须有：

| Schema | 要求 |
|---|---|
| `BlogPosting` | headline / description / image / datePublished / dateModified / author / publisher |
| `FAQPage` | 8–10 条，答案 ≤300 字符，**必须与页面可见正文逐字对应** |

**🔴 `author` 必须指向 Person 实体，不是 Organization。** 四个字段缺一不可：

```json
{
  "@type": "Person",
  "name": "[作者名]",
  "jobTitle": "DramaShortsTV Editor",
  "description": "[含专业背景的简介]",
  "worksFor": {"@id": "https://dramashortstv.com/#organization"},
  "sameAs": ["[作者的公开主页/社媒]"],
  "knowsAbout": ["Short Drama Apps", "Vertical Drama", "Streaming Platforms"],
  "alumniOf": [{"@type": "EducationalOrganization", "name": "[学校名]"}]
}
```

- `knowsAbout` → Google 评估 Expertise 的直接依据
- `alumniOf` → Trustworthiness 背书
- `sameAs` → 跨平台验证作者真实存在
- `worksFor` → 把作者绑定到 Organization，雇佣关系可核验

**不要写 "editorial persona, not a real individual" 这类声明**——主动声明非真实会直接削弱 EEAT。

> 现状：2026-08-28 已发布的那篇 blog，`author` 是 `{"@type":"Organization","name":"DramaShortsTV"}`，需改。演员图鉴是主力内容类型，这条影响整条线。

**验证方法**：`curl -s [URL] | grep -c "FAQPage"`，确认首字节 HTML 里就有，不是客户端渲染出来的。
