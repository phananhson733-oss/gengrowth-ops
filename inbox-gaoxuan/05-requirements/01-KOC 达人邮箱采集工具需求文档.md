> [!summary] 一句话结论
> 第一版优先支持把现有名单中的一整列 TikTok handle 或主页链接直接粘贴、上传或从表格导入，系统逐行读取账号、提取公开账号资料和公开商务联系方式，并将邮箱及处理状态写回对应达人。Hashtag/BGM 用于后续扩展新达人来源。

## 0. 本轮需要产品与开发优先完成的内容

本需求的重点不是指定技术方案，而是跑通下面这条业务链路：

```text
粘贴一批 handle/主页链接或上传现有表格
→ 识别输入类型
→ 将每一行转换为一个账号处理任务
→ 与历史达人库去重
→ 获取公开主页资料
→ 从 Bio 和公开外链寻找商务联系方式
→ 验证邮箱
→ 获取或判断地区
→ 与上次搜索做增量比较
→ 新达人优先展示
→ 人工审核
→ 加入独立的建联系统
```

第一版最重要的能力：

1. 直接处理运营已经整理好的批量 handle/主页链接名单；
2. 逐行抓取公开联系方式，并将结果准确写回原达人；
3. 记录公开联系方式的具体来源和验证状态；
4. 跨批次去重并显示历史建联状态；
5. 无法取得的数据明确标记，不编造结果；
6. Hashtag/BGM 发现作为后续扩展，不影响第一版交付。

# 一、为什么要做

目前寻找和整理 KOC 需要人工打开 Hashtag/BGM 页面、逐条查看发布者、复制 handle、检查 Bio、打开 Linktree 或个人网站寻找邮箱，并再次检查是否联系过。主要问题包括：

- 搜索结果会随时间变化，无法识别本周新增达人；
- 同一达人可能被多个 Hashtag/BGM 重复发现；
- 找到邮箱后无法追溯其来源；
- Bio 没有邮箱时不知道应该继续检查哪里；
- 地区、粉丝地区等数据的来源和可信度不清楚；
- 已经建联、拒绝或退订的达人可能再次进入名单；
- 每次搜索形成独立表格，无法沉淀成持续更新的达人库。

因此第一版先解决“我已经有达人名单，如何批量补齐公开邮箱”的问题，再扩展为通过 Hashtag/BGM 持续发现新达人的联系人数据库。

# 二、第一版范围

## 2.1 第一版只做

| 优先级 | 功能 | 说明 |
|---|---|---|
| P0 | 批量粘贴 handle/主页 | 支持从现有文档复制一整列，一行一个账号 |
| P0 | 表格导入 | 支持上传 CSV/XLSX，或读取 Google Sheet/飞书表格 |
| P0 | 单个 handle/主页输入 | 用于临时补充或测试 |
| P0 | 原表逐行回写 | 邮箱、来源、验证状态和失败原因写回对应行 |
| P0 | 搜索快照 | 保存每次搜索的时间、数量及结果 |
| P0 | 达人统一去重 | 同一达人只保留一条主记录 |
| P0 | 增量识别 | 标记 new/existing/updated |
| P0 | 公开邮箱提取 | 检查 Bio 和达人主动公开的外链 |
| P0 | 邮箱验证 | 标记有效、风险、无效或待确认 |
| P0 | 历史建联状态 | 展示未联系、已发送、已回复、拒绝、退订等 |
| P0 | 人工审核与交接 | 只有审核通过者才能加入建联名单 |
| P1 | 达人地区 | 输出来源、证据和可信度 |
| P1 | Hashtag/BGM 输入 | 从主题或音乐页面发现新的候选达人 |
| P1 | 视频/Photo 输入 | 反查发布账号 |
| P2 | 相似 Hashtag | 推荐相关主题词，由运营确认后再采集 |
| P2 | 定时重跑 | 每周重新扫描保存的 Hashtag/BGM |
| P2 | 粉丝地区占比 | 依赖 TikTok One、合规第三方或达人后台数据 |

## 2.2 第一版不做

- 不破解账号、绕过验证码、登录验证或平台权限；
- 不获取达人未公开的私人邮箱；
- 不使用泄露数据库；
- 不将系统猜测的邮箱直接认定为真实邮箱；
- 不承诺一次抓到 Hashtag/BGM 下的全部历史达人；
- 不将推断地区展示成确定事实；
- 不承诺普通公开页面可以取得粉丝地区百分比；
- 不自动向达人发送邮件；
- 不自动把所有发现者加入建联队列；
- 不无限采集、无限扩词或无限重试。

# 三、核心业务流程与节点说明

> [!important] 本章是第一版开发的主要依据
> 每个节点均说明做什么、怎么做、产生什么结果，以及数据大概从哪里取得。具体代码和供应商由技术评估。

## 3.0 第一版主流程：已有名单批量补邮箱

这是第一版必须优先跑通的流程。运营已经在 Excel、WPS、Google Sheet、飞书或其他文档中整理了达人名单，其中至少有 `handle` 或 `主页链接` 一项。

```text
运营复制一整列 handle/主页链接，或上传现有表格
→ 系统识别每一行属于 handle 还是主页链接
→ 为缺少主页链接的 handle 自动生成标准主页链接
→ 清理空行、错误格式和重复账号
→ 为每个有效账号建立独立处理任务
→ 逐个读取公开主页与 Bio
→ Bio 没有邮箱时继续检查达人主动公开的外链
→ 验证取得的邮箱
→ 将邮箱、来源、验证状态和失败原因写回原行
→ 显示本批次成功、未找到、失败和待人工审核数量
→ 运营审核后选择是否加入建联名单
```

### 支持的导入方式

| 输入方式 | 运营怎么操作 | 系统怎么处理 |
|---|---|---|
| 批量粘贴 | 从现有表格复制一整列或多列，粘贴到输入框 | 自动按换行和列拆分，一行生成一条记录 |
| CSV/XLSX 上传 | 上传现有达人表格 | 让运营选择哪一列是 handle、哪一列是主页链接 |
| Google Sheet | 提供表格或指定工作表 | 读取指定列，并把结果写回新增列或结果表 |
| 飞书多维表格 | 选择对应数据表和字段 | 读取 handle/主页字段并回写结果 |
| 单条输入 | 临时粘贴一个 handle 或主页 | 立即处理单个账号 |

### 最小输入要求

每一行至少满足一项：

- `handle`，例如 `@jessthemysticalcat`；
- `profile_url`，例如 `https://www.tiktok.com/@jessthemysticalcat`。

原表中的地区、粉丝数、标签、优先级、备注等字段应原样保留，系统不得覆盖运营已有内容。

### 建议写回原表的新增字段

| 字段 | 说明 |
|---|---|
| `normalized_handle` | 清理后的标准 handle |
| `normalized_profile_url` | 标准主页链接 |
| `public_email` | 公开取得的邮箱 |
| `email_source_type` | TikTok Bio/Linktree/个人网站/代理页面等 |
| `email_source_url` | 邮箱所在的具体页面 |
| `email_verification_status` | verified/risky/invalid/unknown |
| `contact_status` | public_verified/public_unverified/not_found 等 |
| `bio_text` | 最新公开 Bio，可选 |
| `creator_country` | 达人地区，如可取得 |
| `region_confidence` | 地区可信度 |
| `outreach_status` | 未建联/已发送/已回复/拒绝/退订/黑名单 |
| `processed_at` | 本次处理时间 |
| `processing_status` | pending/running/done/partial/failed |
| `failure_reason` | 没有完成时的具体原因 |

### 行号与回写规则

1. 每条导入数据生成稳定的 `import_row_id`；
2. 系统处理结果必须通过 `import_row_id` 写回原达人，不能因为排序或去重写错行；
3. 重复账号可共用一条达人主记录，但原表每一行仍需返回处理状态；
4. 运营原有列不得被覆盖，默认在右侧新增结果列；
5. 如果选择“输出到新表”，需要保留原始行号和原始 handle；
6. 任务中断后允许从未完成行继续，不重复处理全部名单；
7. 支持只重新处理 `not_found`、`failed` 或 `unknown` 的行；
8. 支持下载处理结果或同步回原表。

### 批量任务结果汇总

例如导入 1,000 行后，系统需要显示：

```text
原始行数：1,000
空行或格式错误：20
重复账号：80
唯一有效达人：900
找到公开邮箱：420
只找到代理邮箱：35
只找到联系表单：60
未找到公开联系方式：330
需要人工审核：25
处理失败：30
```

运营可以点击每个数量查看对应记录，不能只看到一个总成功率。

## 3.1 节点一：创建采集任务

| 项目 | 说明 |
|---|---|
| 操作人 | 运营 |
| 输入 | 第一版优先为批量 handle、主页链接或现有表格；后续支持视频、Photo、Hashtag、BGM |
| 做什么 | 保存原始输入、采集上限和筛选条件，创建唯一 `search_id` |
| 怎么做 | 粘贴一整列/多列账号，或上传表格并映射 handle、主页链接字段，点击开始处理 |
| 数据来源 | 运营提供 |
| 输出 | pending 状态的搜索任务 |
| 失败处理 | 格式错误时停止并提示支持的格式 |

建议保存：原始文件/表格、工作表名、字段映射、原始行号、是否只处理未完成行、粉丝范围、地区条件、是否排除已建联者、创建人和创建时间。

## 3.2 节点二：识别输入类型

| 类型 | 识别方式 | 下一步 |
|---|---|---|
| handle | `@` 或账号名格式 | 读取账号主页 |
| 主页 | TikTok 账号 URL | 读取账号主页 |
| 视频/Photo | 内容 URL，Photo 含 `/photo/` | 提取发布者 |
| Hashtag | URL 含 `/tag/` | 获取当前相关内容 |
| BGM | URL 含 `/music/` | 获取当前使用该音乐的内容 |
| 表格 | CSV/XLSX/Google Sheet/飞书 | 先映射字段，再逐行拆成账号任务 |
| 无法识别 | 不符合规则 | 人工确认 |

输出 `source_type`、`source_value`、`source_url`、识别状态及失败原因。无法识别时不能猜测类型继续执行。

## 3.3 节点三：获取 Hashtag/BGM 候选内容

本节点仅在输入为 Hashtag 或 BGM 时执行。

| 项目 | 说明 |
|---|---|
| 输入 | Hashtag/BGM 链接、采集上限 |
| 做什么 | 获取当前可访问的视频或 Photo 列表 |
| 怎么做 | 逐页读取，直到达到上限、没有更多结果或平台限制 |
| 数据来源 | TikTok 公开页面、平台允许能力、公司审核通过的数据服务 |
| 输出 | 内容 ID/链接、发布者、发布时间、发现来源 |
| 必须记录 | 请求量、实际量、是否完整、停止原因 |
| 失败处理 | 返回部分结果并说明失败环节，不能将 partial 写成 complete |

Hashtag/BGM 结果动态且可能有限，所以产品目标是保存本次快照并在下次识别增量，不承诺一次取得全部达人。

## 3.4 节点四：提取内容发布者

| 项目 | 说明 |
|---|---|
| 输入 | 视频或 Photo 链接 |
| 做什么 | 取得发布者 handle、主页及平台账号 ID（如可得） |
| 数据来源 | 内容公开页面、URL 信息、允许的数据服务 |
| 输出 | 标准化账号记录 |
| 失败处理 | 保留内容链接，标记 `manual_review`，不根据水印或评论猜测 |

## 3.5 节点五：与历史达人库去重

| 项目 | 说明 |
|---|---|
| 输入 | 账号 ID、handle、主页链接 |
| 做什么 | 判断首次发现、历史已有或资料变化 |
| 怎么做 | 优先账号 ID，其次标准化 handle 和主页链接 |
| 数据来源 | 本次候选名单 + 历史 `creators` 数据 |
| 输出 | `new` / `existing` / `updated` / `manual_review` |
| 失败处理 | 改名、同邮箱多账号等冲突进入人工审核 |

同一达人由多个来源发现只保留一条主记录，但所有 Hashtag/BGM/视频来源必须保存在关联记录中。同步查询其建联状态：未联系、已入队、已发送、已回复、合作中、拒绝、退订、黑名单。

## 3.6 节点六：获取公开主页资料

| 项目 | 说明 |
|---|---|
| 输入 | handle 或主页 |
| 做什么 | 读取当前公开账号资料 |
| 数据来源 | TikTok 公开主页、平台允许接口、合规第三方服务 |
| 输出 | 昵称、Bio、粉丝数、点赞数、视频数、认证状态、Bio 外链 |
| 失败处理 | 已取得字段照常保存，其余写 `unavailable`，不要整条判失败 |

每个字段要能区分：公开取得、授权数据、人工补充、推断或无法取得。

## 3.7 节点七：检查 Bio 中的公开联系方式

| 项目 | 说明 |
|---|---|
| 输入 | Bio 原文和主页公开信息 |
| 做什么 | 识别直接公开的邮箱或其他联系方式 |
| 怎么做 | 识别邮箱格式并保存其上下文 |
| 数据来源 | TikTok Bio |
| 输出 | 邮箱、来源主页、Bio 原文、发现时间、初始状态 |
| 没找到 | 进入公开外链检查 |
| 不确定 | 标记 `manual_review` |

## 3.8 节点八：检查达人主动公开的外部链接

| 顺序 | 数据位置 | 寻找内容 |
|---|---|---|
| 1 | Linktree/Beacons/Carrd | Email、Business、Contact、Collaborate |
| 2 | 个人网站 | Contact、About、Work With Me |
| 3 | 商务合作页 | 商务邮箱或表单 |
| 4 | 经纪公司/MCN 官网 | 代理邮箱、经纪人 |
| 5 | 达人主动链接的其他社媒 | 公开商务联系方式 |
| 6 | 联系表单 | 表单 URL 和适用对象 |

系统输出公开邮箱、代理邮箱、联系表单、仅私信或 `not_found`。每条邮箱必须保存具体来源 URL。页面打不开时记录 URL 和原因，不自动扩大到非公开来源。

## 3.9 节点九：验证并分类邮箱

| 项目 | 说明 |
|---|---|
| 输入 | 公开取得的邮箱 |
| 做什么 | 检查格式、域名及大致可投递状态 |
| 数据来源 | 公开 DNS 信息、公司审核的邮箱验证服务 |
| 输出 | verified / risky / invalid / unknown / manual_review |
| 失败处理 | 无结果写 `unknown`，不能直接写有效 |

| 联系状态 | 含义 | 能否自动进入建联 |
|---|---|---|
| `public_verified` | 公开且通过验证 | 可以 |
| `public_unverified` | 公开但未验证 | 人工确认后可以 |
| `agency_contact` | 公开代理邮箱 | 确认适用范围后可以 |
| `contact_form_only` | 只有表单 | 不进入邮件队列 |
| `social_dm_only` | 只有公开私信 | 不进入邮件队列 |
| `inferred` | 第三方推测 | 必须人工确认 |
| `invalid` | 验证失败 | 不可以 |
| `not_found` | 未找到 | 不可以 |
| `suppressed` | 禁止联系 | 不可以 |

## 3.10 节点十：获取或判断地区

| 优先级 | 数据来源 | 可信度 |
|---|---|---|
| 1 | 平台/授权数据明确地区 | verified |
| 2 | Bio 明确自述 | high |
| 3 | 个人网站/商务资料 | high |
| 4 | 多项公开信号一致 | medium |
| 5 | 仅语言、时区等推断 | low |
| 6 | 没有足够证据 | unavailable |

输出国家/地区、城市（如有）、来源、证据、可信度和更新时间。

粉丝地区占比大概可从 TikTok One/Creator Marketplace、合规达人数据平台、达人提供的 Audience Analytics 或人工上传截图取得。无授权数据统一写 `audience_data_status: unavailable`，不得用语言或评论样本生成精确百分比。

## 3.11 节点十一：与上次搜索做增量比较

示例：第一次 800 个达人；下一周 900 个，其中 750 个历史已有、150 个本次新增。

系统必须：

1. 保留两次搜索快照；
2. 不重新创建 900 条主记录；
3. 把 150 个标记为 `new`；
4. 默认新达人置顶；
5. 历史未建联排在已建联之前；
6. Bio、邮箱、粉丝数或地区变化时标记 `updated`；
7. 保存首次发现、最后发现及所有发现来源；
8. 显示历史建联状态；
9. 拒绝、退订、黑名单不得重新加入建联；
10. 支持筛选“本次新增且有邮箱”。

数据来自本次快照、历史搜索快照、`creators` 和 `creator_sources`。

## 3.12 节点十二：推荐相似 Hashtag

| 项目 | 说明 |
|---|---|
| 输入 | 种子 Hashtag、本次内容、达人公开近期内容 |
| 做什么 | 推荐可能找到相似 KOC 的其他 Hashtag |
| 怎么做 | 汇总共同出现标签、语义相关词和优质达人常用标签 |
| 数据来源 | caption/Hashtag、达人公开内容、历史搜索结果 |
| 输出 | 推荐词、理由、相关度、样本量、是否搜索过 |
| 失败处理 | 证据不足时不强行推荐 |

推荐词必须由运营勾选并设置上限后才能创建新任务，不能自动无限扩展。

## 3.13 节点十三：结果排序与人工审核

默认排序：

1. 本次新增 + 公开已验证邮箱；
2. 本次新增 + 公开未验证邮箱；
3. 本次新增 + 代理邮箱；
4. 本次新增 + 联系表单；
5. 历史已有但未建联；
6. 已建联；
7. 已回复或合作中；
8. 拒绝、退订和黑名单。

运营可以查看主页、联系方式来源、验证结果、地区证据、发现来源和历史建联，并批量加入建联名单、暂不联系或拉黑。

## 3.14 节点十四：交接给独立建联系统

运营点击“加入建联名单”后，系统再次检查邮箱有效性、联系方式来源、历史建联、退订、拒绝和黑名单。不通过者保留在达人库并显示原因。

交接字段至少包括 `creator_id`、handle、主页、称呼、email、邮箱来源、验证状态、地区、来源 Hashtag/BGM、建联状态、人工审核状态和备注。

# 四、状态、筛选与排序规则

| 状态 | 说明 |
|---|---|
| `new` | 本次首次发现 |
| `existing_uncontacted` | 历史已有但未联系 |
| `existing_contacted` | 已联系 |
| `replied` | 已回复 |
| `collaborating` | 合作中 |
| `rejected` | 已拒绝 |
| `unsubscribed` | 已退订 |
| `blocked` | 禁止联系 |
| `updated` | 资料发生变化 |

筛选至少支持粉丝范围、地区、联系方式类型、邮箱验证状态、来源 Hashtag/BGM、本次新增、是否已建联及人工标签。

# 五、默认数据结构

## 5.1 `discovery_searches`

保存 `search_id`、来源类型/值/链接、请求量、实际量、唯一达人数、新增/已有/更新数量、开始/完成时间、状态及失败原因。

## 5.2 `creators`

保存 `creator_id`、平台账号 ID、handle、历史 handle、主页、昵称、Bio、粉丝数、点赞数、视频数、认证、Bio 外链、地区、地区可信度、首次/最后发现时间、记录状态、建联状态及备注。

## 5.3 `creator_sources`

保存达人由哪个 `search_id`、Hashtag、BGM 或视频发现，以及首次/最后发现时间和出现次数。

## 5.4 `creator_contacts`

保存联系方式类型、邮箱、表单、代理信息、来源 URL/原文、验证状态、可信度、发现/验证时间、人工审核及禁止发送状态。

## 5.5 `audience_insights`

保存粉丝国家、年龄、性别分布、数据来源、数据日期和状态。没有授权数据时为空并标记 unavailable。

# 六、平台数据边界

- TikTok 公开结果可能变化或受限，能取得多少就记录多少；
- 必须显示请求量、实际量和完整性；
- 账号页抓不全时允许部分成功；
- 单个明确账号/视频链接优先于动态列表；
- 抓不到字段写 `待补数据/待确认`；
- 失败必须说明页面访问、翻页、主页读取、外链访问、验证或授权哪个环节；
- 公开网页采集和授权数据必须在字段层面区分；
- 技术应先确认平台条款、公司合规要求和供应商授权范围。

# 七、技术实现建议

| 环节 | 可选方向 |
|---|---|
| 界面 | 独立后台/飞书/Google Sheet |
| 调度 | 后端队列/n8n/Make |
| TikTok 数据 | 官方允许能力/合规第三方/公开页面 |
| 外链解析 | 页面解析器 |
| 邮箱识别 | 文本规则 + 页面识别 |
| 邮箱验证 | 合规验证服务 |
| 地区 | 授权数据 + 公开证据 + 可信度规则 |
| AI | Hashtag 推荐、相关度及分类 |
| 存储 | 关系型数据库，必须有稳定 `creator_id` |
| 输出 | 后台表格/CSV/Google Sheet/飞书 |

# 八、验收标准

1. 输入 20 个有效 handle，至少 90% 返回公开基础信息或明确失败原因；
2. Bio 明确含邮箱时提取准确率达到 95% 以上；
3. 外链有公开商务邮箱时保存邮箱及具体来源 URL；
4. 没有公开联系方式时返回 `not_found`，不得编造；
5. 同一达人多来源出现只产生一条主记录，但保留全部来源；
6. Hashtag/BGM 显示请求量、实际量、完整性和停止原因；
7. 同一 Hashtag 两次运行后正确区分新增、已有和更新；
8. 新达人可默认置顶，已建联状态正确显示；
9. 退订和黑名单不能重新进入建联名单；
10. 地区带来源和可信度；
11. 粉丝地区无授权数据时写 unavailable；
12. 相似 Hashtag 显示理由，且未经确认不自动采集；
13. 每条失败记录说明具体环节及人工补充方式；
14. 只有人工审核通过的联系方式能交接给建联系统。

# 十、当前结论

第一版最小可交付：

```text
批量粘贴 handle/主页链接或上传现有达人表格
→ 映射字段并逐行建立任务
→ 建立唯一达人记录并保留全部来源
→ 与历史达人库去重
→ 获取 Bio 和公开外链中的商务联系方式
→ 验证邮箱并记录来源
→ 标记地区可信度及历史建联状态
→ 将结果准确写回原行
→ 人工审核后交接建联系统
```

Hashtag/BGM 发现、相似 Hashtag 推荐和定时增量扫描作为下一阶段能力，在批量名单补邮箱流程稳定后再开发。
