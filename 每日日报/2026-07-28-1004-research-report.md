今天读什么｜别只看“任务完成”：给 Agent 建一张质量健康度仪表盘

### 1. 适合谁读 / 预计阅读时间
适合已经把研究、内容生产、线索整理、知识库问答或自动化动作交给 Agent，却仍只能凭“这次看起来不错/不太对”判断质量的团队。也适合开始关注模型成本、工具失败、人工返工，却不知道这些数字该怎么连起来的人。预计阅读约 10 分钟。

### 2. 为什么值得读
很多 Agent 上线后只有一个总开关：任务成功或失败。但“成功返回一段文字”不等于业务成功。它可能按时生成研究稿却漏掉来源，成功建了线索却重复建档，成功调用工具却绕了多轮无意义搜索，或把本应停在草稿的动作推进到错误状态。

传统监控擅长回答“服务是否存活、是否变慢、是否报错”，却很难回答“结果是否值得交付、是否遵循正确流程、是否正在过度消耗资源”。Anthropic 的 Agent 评测指南强调：离线测试、线上监控、用户反馈、人工抽查各有用途，不能用单一分数替代。OpenAI 的实践也把成本、时延、用户反馈和模型评审列为生产环境的常见信号。

真正需要的不是更华丽的大屏，而是一张能把“结果、过程、成本、风险”放在同一任务 ID 下的质量健康度仪表盘。它的目的不是监视模型，而是让团队知道该修提示词、工具、知识来源，还是业务规则。

### 3. 核心概念
**第一，结果指标与过程指标必须同时看。** 结果指标看交付是否被接收：研究稿是否可核验、草稿是否被采用、线索是否进入正确队列。过程指标看它怎么做到：工具路径、重试、耗时、token、错误和最终状态。只看结果难定位；只看过程，容易优化出一条“很省钱但没用”的路径。

**第二，成功率不是万能指标。** 把“HTTP 返回成功”“生成了文件”“进入下一步”拆开。内容任务可定义“必填结构完整、关键主张有出处、人工可直接采用”；增长任务可定义“身份已解析、未触达超频、只生成待审草稿”。这才是业务成功。

**第三，指标要按风险分层。** 内部摘要可抽样看质量；涉及外联、发布、写 CRM 或改数据的任务，还要看越权拦截率、审批等待时长、执行前后回读一致率。高风险动作不能被平均成功率掩盖。

**第四，告警应盯变化，而不是盯所有异常。** 一次工具超时未必值得叫人；某工具失败率持续上升、同类任务平均调用次数突然翻倍、人工打回率持续超出基线，才是该调查的信号。LangChain 也建议关注工具调用失败率和各工具的运行次数，而不只看时延与错误码。

**第五，轨迹要能转成改进样本。** 被打回、被人工改写或触发异常的任务，保留最小上下文：输入类型、版本、关键来源/工具、失败理由和最终处理。不要把整段对话当知识库；要把可复现问题转成测试样本、规则或模板。

### 4. 可复用方法
先给一条高频流程做“最小四层仪表盘”：

1）定义任务终点：为“竞品研究→内容草稿”写 2—3 个业务成功条件，而不是只记录“已生成”。  
2）固定任务链路：让任务 ID 贯穿触发、检索、模型调用、工具调用、人工修改和最终状态；敏感正文可不进指标库，只存必要摘要与引用 ID。  
3）每层只选 1—2 个指标：结果层看采用率/返工率；过程层看时长、工具错误率；成本层看单任务 token 或工具次数；风险层看拦截或回读不一致次数。  
4）先建基线再设阈值：连续运行一两周，按任务类型看中位数与波动范围；别一开始凭感觉规定“超过 30 秒就是故障”。  
5）每周只挑一个异常簇复盘，例如“引用缺失的研究稿”或“搜索超过 5 次的任务”，归因到提示词、工具、来源、规则或输入质量之一，并做一个可验证改动。

### 5. GenGrowth 可以怎么用
可从每日研究报告或 AI Builder 情报流试点。为每篇稿记录：是否按时产出、是否与近日报告重复、关键结论是否带公开来源、最终是否被频道保留/被人工改写、检索与成稿耗时。若“格式合格但重复率高”，优先改选题去重；若“来源齐但人工改写多”，优先改读者结构与表达；若“耗时猛增但质量未提升”，再检查工具循环和模型路由。

再把同一框架用于增长工作流：不要只报“生成多少线索”，还要报“多少条身份解析通过、多少条因规则降为草稿、多少条经人工确认进入下一步”。这样产量才不会伪装成增长。

### 6. 今日行动
选一个运行中的 Agent 流程，今天只补一张表：`任务ID｜业务成功条件｜最终状态｜人工是否改动｜工具次数/错误｜耗时｜风险结果｜版本`。收集 20 个任务后，不先追求总评分；先找一个高频、可修复的失败模式，把它写进下次运行前的检查项。
