今天读什么｜别把工具箱倒给 Agent：让它“先找能力，再做动作”

### 1. 适合谁读 / 预计阅读时间
适合正在把 Slack、飞书、CRM、网页搜索、表格、知识库、代码仓库接给 AI 的人。尤其适合这样的阶段：每接一个 MCP 或内部接口，Bot 看起来更全能，却开始变慢、选错工具、把参数填混。预计阅读约 10 分钟。

### 2. 为什么值得读
工具越多，不一定越聪明。传统做法是：任务一开始就把所有工具名称、说明、参数和示例一股脑交给模型。问题不只是 token 成本高，更是模型在一堆相似按钮里容易误选——“发私信”和“发频道公告”、“查客户”与“改客户”名字很近，实际影响却天差地别。

近期 OpenAI、Anthropic 都把“工具搜索”作为正式能力：先只展示少量高频、低风险的入口；当任务确实需要时，再在工具目录中定位并加载具体能力。Anthropic 的公开测试显示，大型 MCP 工具库的主要故障包含选错工具与参数；其方案在一个测试中把初始工具定义带来的 token 消耗显著压低，同时提升了大工具库任务的正确率。重点不是迷信某个 API，而是换一个产品设计：**工具目录负责被发现，工作上下文只保留本次真正需要的工具。**

### 3. 核心概念
**第一，目录、加载、授权是三层事。** 工具目录告诉 Agent“公司有哪些能力”；按需加载让它在本轮看见正确的名称、参数和返回结构；授权系统才决定它是否能对某个对象执行。能搜索到“发布文章”不等于获得发布许可。把三层混在一起，会造成“为了不让它误用，只好完全不给它看”的两难。

**第二，给工具按业务域分门。** 不要把 80 个函数平铺。可先按“研究取证、内容草稿、客户资料、项目协作、发布执行”分成清晰目录；每个目录用一句人话说明范围。OpenAI 建议优先以 namespace 或 MCP server 承载延迟加载的函数；目录描述是模型判断要不要进去的路标，不是营销文案。

**第三，默认常驻的只应是少数。** 保留 3—5 个每次都高频且安全的工具，例如站内搜索、读取任务状态、创建内部草稿。低频、专业、具副作用的能力——批量更新、发送、发布、删除——默认不把完整定义塞进上下文。需要时先搜索，再加载，再经过规则和审批。

**第四，工具搜索本身也会犯错。** 搜索结果只是一组候选，不是行动建议。相似名称、过时描述和跨项目同名工具都会误导模型。因此目录记录要有：稳定名称、适用场景、不能做什么、输入/输出摘要、风险级别、所属系统、版本与负责人。MCP 规范也强调客户端应把服务端的工具标注视为不可信，并在敏感调用前向人展示确认信息。

**第五，加载后也要可回收。** 一次任务中发现的工具不应自动变成永久可用集。任务切换、客户切换、进入高风险步骤或工具版本变化时，应重新过滤或清空已加载工具；避免上一位客户的能力、旧版参数说明或临时权限悄悄带到下一轮。

### 4. 可复用方法
先挑一条工具超过 15 个的流程试行，不必重构全系统：

1）盘点现有工具，给每个工具补一张“能力卡”：业务域、动作类型（读/草稿/写/发/删）、典型任务、禁用边界、风险级别、负责人。删除重复和含糊命名。  
2）设“常驻层”：只留少量真正高频的只读或内部草稿工具；其他进入可搜索目录。  
3）先做粗筛再精搜：根据任务类型、租户、用户角色、当前状态，确定可搜索的业务域；再让模型从该域找具体工具。不要让研究任务搜索到所有外联和删除能力。  
4）让搜索结果返回候选理由与工具版本；加载后再校验参数、对象范围和权限。写入、发送、删除必须生成变更预览并走原有审批，而不是因“工具刚被找到”而自动放行。  
5）做一组小评测：挑 20 条真实脱敏任务，比较改造前后四个数——首次选对工具率、参数校验失败率、初始上下文 token、完成时延。若工具很少、每次都会用到，反而不必增加搜索步骤。

### 5. GenGrowth 可以怎么用
可以为 AI Builder 工作流建立一个“增长能力目录”，而不是让每个 Bot 带着全套工具开场：

- **研究域**：搜索公开网页、读取已批准的知识材料、生成证据包；默认只读。  
- **内容域**：提取选题、生成多版本草稿、做品牌与来源检查；默认产出草稿。  
- **运营域**：查询线索状态、生成 CRM 更新建议、创建待审任务；不直接批量写入。  
- **执行域**：发布、外联、批量改数据等高影响能力；只有工作流已到“待执行”、对象范围已锁定、人工已批准时才允许被加载和调用。

这样，研究 Agent 不必理解发布后台的几十个参数，内容 Agent 也不会“顺手”看到客户触达工具；但需要交接时，下游仍能按任务状态发现恰当能力。目录同时成为新人和工具维护者的共同说明书：哪些能力存在、谁负责、什么场景不可用，一目了然。

### 6. 今日行动
选出你们当前最臃肿的一条 Agent 流程，今天只完成两件事：

- 列出全部工具，标记“每次常用 / 偶尔需要 / 高风险”；把名称相近却动作不同的工具单独拉出来复核。  
- 为其中一个业务域写 5 条能力卡，并设一条规则：默认只可搜索本域；跨域或产生外部副作用时，必须明确说明理由并进入审批。

一周后用真实任务对比：Agent 是否更少选错、上下文是否更短、审批是否更聚焦。若没有改善，不要立刻扩大目录；先检查工具名称和边界说明是否足够清楚。
