今天读什么｜多 Agent 不该先问“派给谁”，而要先问“谁对下一步负责”

### 1. 适合谁读 / 预计阅读时间
适合正在把研究、内容生产、线索整理、知识库问答或运营流程拆给多个 Agent 的人。尤其适合这种困惑：一个主控 Agent 既要回答用户、又要反复请专家帮忙；另一些任务却在不同 Agent 间来回转交，最后没人说得清该由谁给出最终结论、谁有资格继续执行。预计阅读约 10 分钟。

### 2. 为什么值得读
多 Agent 设计最常见的错误，是看见一个领域就新增一个“角色”，再让它们彼此互相转交。系统表面更专业，实际却增加了上下文复制、重复确认、权限扩散和调试难度。

更有用的分界不是“这个问题属于哪个领域”，而是：**这位专家是在提供一份受限的输入，还是应该接管接下来的对话与动作？** 前者是“把 Agent 当工具调用”；后者才是“交接主责”。OpenAI 的编排指南明确区分这两种模式：管理者若仍要对最终回复负责，应把专家作为有边界的能力调用；只有专家确实应拥有后续分支，才把控制权交出去。

这一区别会直接改变工作流质量。把所有专家都做成接管者，用户会被转来转去，最终口径容易漂移；把所有专家都藏成工具，又可能让主控在不具备政策、权限或长期状态的情况下勉强做决定。先界定责任，角色数量才有意义。

### 3. 核心概念
**第一，工具式协作：主控不换人，专家交结果。** 主控把一个定义清楚的子问题交给专家，例如“从 20 篇资料抽取已证实的定价变化”“把访谈按三类需求编码”。专家返回结构化证据包、评分或草稿；主控核验、综合并对最终输出负责。它适合并行检索、多视角审查、格式转换和一次性分析。

**第二，主责交接：换的是决策权，不只是提示词。** 当任务进入一个不同的业务阶段，新的 Agent 应负责接下来要问什么、可用什么工具、遵循什么政策，并可能持续与人交互。例如客户已经从“内容选题咨询”进入“需要安排会议”，日程 Agent 接管后不该只是回一段候选时间，而应负责补齐参会人、查忙闲、处理改期，直至交还一个确定状态。

**第三，按“结果所有者”选模式。** 只要最后仍需要协调者把多个输入合成一份交付，就优先工具式协作；只要后续判断、风险和对话都应由新领域负责，才交接。不要因为专家比主控懂得多，就默认把最终责任也交给它。

**第四，交接必须有入口、出口和回收条件。** 入口写清触发条件、传递的最小状态、对象范围与权限；出口写清成功状态、不能完成时的原因码，以及何时返回协调者或转人工。没有出口的交接很容易演变成 Agent 之间的“踢皮球”。

**第五，专长不是角色的充分理由。** OpenAI 建议先从一个聚焦 Agent 开始，只有当能力隔离、政策隔离、提示词清晰度或轨迹可读性确实改善时才增加专家。Anthropic 的多 Agent 研究复盘也提醒，多 Agent 的 token 消耗显著更高，且依赖密集、必须共享大量上下文的工作未必适合拆开。

### 4. 可复用方法
给任一现有流程做一次“责任归属图”，只需五步：

1）写出每个节点要交付的对象，而非角色名，例如“可引用证据包”“待审内容草稿”“已确认会议状态”。  
2）为每个对象指定唯一结果所有者：谁有权发布最终结论、谁能推进状态、谁承担失败说明。  
3）逐个问专家：它的输出会被主控综合吗？会，设计成工具调用，并规定输入/输出 Schema、预算和只读或草稿边界。  
4）若专家要持续决定下一步，则设计交接卡：触发条件、最小上下文、可用工具、禁止动作、完成/退回状态、超时路径。  
5）在轨迹中记录“为什么调用/为什么交接、交给谁、何时归还”。每周抽查 10 条运行：是否发生无效转交、是否有两个 Agent 同时认为自己负责、是否有主控代替专家越权决定。

### 5. GenGrowth 可以怎么用
以“把公开行业信号变成客户可读快报”为例：研究 Agent 可作为工具并行产出来源、事实和反例；主控内容 Agent 负责选择哪些事实能写入并合成快报；品牌/事实核验 Agent 也宜作为工具，给出通过、修改或证据不足的结构化结论。只有当客户主动要求继续沟通、需要排期或进入明确审批流程时，才把主责交给对应的会务、项目或审批工作流。

这样做的好处是：研究与审核不会悄悄获得发布权限；内容主控不会把“专家建议”伪装成已批准决定；每个阶段都能找到唯一负责人和可追溯产物。对于跨 Bot 协作，同样应把任务卡作为公开交接件，而非让不同角色共享私有上下文。

### 6. 今日行动
挑一条本周正在运行的流程，列出其中所有“转给某 Agent”的地方。给每一处打一个标签：`专家工具`或`主责交接`。若无法在一句话内说清“谁对下一步和最终状态负责”，先不要新增 Agent；补上结果所有者、入口和出口，再做自动化。
