今天读什么｜让 Agent 先交“变更集”，再动真实系统

### 1. 适合谁读 / 预计阅读时间
适合正在让 AI 整理线索、更新 CRM、发布内容、改表格、维护网站或写代码的人。尤其适合这样的场景：Agent 已经能把任务做完，但团队无法在动作发生前看清它究竟要改什么、影响谁、失败后如何收口。预计阅读约 10 分钟。

### 2. 为什么值得读
Agent 的风险常不在“答案写错”，而在它把一连串判断直接变成了现实世界的改动：新增了哪些客户记录、替换了哪段网页文案、给谁打了标签、删掉了什么字段。等人发现不对时，原始状态可能已经被覆盖，修正和复盘都会变得昂贵。

一个更稳的设计是把“理解任务”与“提交改动”拆开：Agent 先生成一份可审查的**变更集**，系统再校验、预演、批准并执行。它类似代码里的 Pull Request：重点不是让人逐条替 Agent 操作，而是让每次有副作用的工作，都先成为一个边界清楚、可对比、可拒绝、可回滚的对象。

GitHub 针对 Agent 生成的 Pull Request 提醒，审查能力不会随着 Agent 并发自动增长；当一个改动无法用一句话说明目的、没有计划、或同时碰了很多无关文件时，应先要求缩小范围。这个原则同样适用于增长工作流：一次“同步一下客户”若没有对象清单和字段差异，就不应进入执行。

### 3. 核心概念
**第一，变更集不是执行日志。** 日志说“已经调用更新接口”；变更集在执行前说明“准备把 A 表第 18 行的行业从 X 改为 Y”。它至少包含：任务目的、对象范围、操作类型（新增/修改/删除/发送）、前后差异、依据、预期影响、创建时间与版本。

**第二，计划、预演、提交是三道不同关口。** 计划回答“准备做什么”；预演（dry run）在不写入真实系统的情况下检查权限、字段、数量、冲突和依赖；提交才真正产生副作用。不要把“Agent 说将执行”当作“已验证可执行”。

**第三，审查应看差异，不该重读全过程。** 审查卡优先展示新增/删除/修改数量、受影响对象、关键字段的前后变化、异常项、引用依据与风险等级；原始检索、推理和工具轨迹保留可追溯入口即可。人应该判断业务意图是否正确，而不是充当手工数据库管理员。

**第四，执行前后都要设条件。** 执行前检查目标仍存在、版本未变、权限仍有效、数量未超限；执行后回读关键状态并记录回执。若有人已改过同一条 CRM 记录，旧变更集不能静默覆盖，而应标为冲突、重新生成或交人工处理。

**第五，可补偿不等于一定能撤销。** Temporal 的 Saga 模式要求为多步流程定义补偿动作，例如“创建草稿后发布失败”可把草稿标为撤回；但已发送邮件、已经被外部系统消费的通知通常无法真正收回。变更集必须在执行前标注补偿方式与不可逆边界，不能事后假设能回滚。

### 4. 可复用方法
先挑一条风险适中、频率较高的流程，例如“把活动报名者补充进 CRM”，用五步改造：

1. 限定一次任务的对象：输入名单、允许字段、最大条数与有效期；不接受“全部同步”这种模糊授权。  
2. 让 Agent 只产出结构化变更集：每条写 `对象ID、字段、旧值、新值、依据、置信度、风险`，低置信度项自动排除到待核队列。  
3. 运行预演：检查重复主体、必填字段、黑名单、权限和已有修改；输出通过、冲突、需补资料三类结果。  
4. 按影响分流：内部标签可批量批准；负责人变更、外联触发、删除和发布必须单独确认；超范围变更自动失效。  
5. 执行后回读并保存回执：记录成功对象、失败对象、幂等键和补偿入口；下一次只重试未完成项，不整批重跑。  

### 5. GenGrowth 可以怎么用
可把“变更集”做成 GenGrowth 工作流的统一中间层，而不是让每个 Bot 各自直接写系统。

- **内容生产**：先生成“文章/落地页更新包”——改哪些段落、引用何处、预计影响哪些链接；审核后再发布。  
- **线索运营**：先生成“CRM 更新与外联草稿包”——主体匹配依据、拟更新字段、是否会触发触达；默认只写草稿，不直接发送。  
- **情报沉淀**：先生成“知识库候选更新包”——新增事实、来源、重复风险、建议归属；通过再进入正式库。  

这样，内容、线索和知识库虽用不同工具，却共享同一种“先看差异、再提交、后可核验”的治理方式。

### 6. 今日行动
选出当前最容易误写的一条流程，为它做一页变更集模板。今天只增加三个字段：**对象范围、前后差异、执行后回读结果**。然后拿最近 5 个真实任务做预演：统计哪些变更因冲突、证据不足或范围不清而应被拦下。这个数字比“Agent 完成率”更能告诉团队，自动化是否真的可控。
