今天读什么｜别让 Agent 一路狂奔，先给它一张“停损表”

1. 适合谁读 / 预计阅读时间  
适合做 AI Builder、智能体工作流、内容生产自动化、研究助手、增长自动化的人读。适合把搜索、写稿、发消息、查资料、外部工具接进 Agent，但开始发现它有时会“越帮越忙”的团队。预计阅读时间 8 分钟。

2. 为什么值得读  
很多团队做 Agent，第一阶段追求的是“它能不能自己做更多事”；第二阶段真正冒出来的问题却是：它到底该做到哪里停。失控不一定是灾难级错误，而是一些慢性问题——多搜了十几轮、重复调同一个工具、在低价值步骤上烧掉模型预算、拿着不完整信息一路往前冲，最后结果看起来还行，成本却悄悄上去了。

最近几家公开资料把这个方向讲得很清楚。Vercel 在 2026 年 6 月更新的 AI SDK 指南里，已经把“最多跑几步”和“最多跑多久”写成配置。LangChain 把模型调用次数、工具调用次数做成中间件，强调这不只是性能优化，而是生产环境里的成本保护。OpenAI 在迁移到 Agents SDK 的实战文档里，把“请求里必须带预算”“涉及花钱或改生产状态的动作要审批”讲成标准边界。Anthropic 也反复强调：默认只读、敏感 Bash 和网络动作要额外批准，权限范围必须先画清。

一句话：更成熟的 Agent，不只是更会做事，而是更知道“做到哪一步必须停、停了以后怎么收”。

3. 核心概念  
第一，Agent 不是越自主越好，而是越自主越要有上限。没有上限的自主，更像无人看管的脚本，不像可信的数字同事。

第二，至少要给 Agent 画四条线：步数线、时间线、成本线、权限线。步数线限制它最多思考/调用多少轮；时间线限制一次任务最多跑多久；成本线限制模型调用和外部工具消耗；权限线决定哪些动作可以自动做，哪些必须停下来等人确认。

第三，停下来不是失败，而是能力。好的系统不是等跑爆了才报错，而是在到达阈值时“结束得明白”：给出当前最好结果、说明还缺什么、是否需要人工接手。

第四，工具可见不等于工具可自动执行。让 Agent 看见一个工具，和允许它不经审批直接调用，是两件不同的事。

第五，预算要按任务类型分层。查资料、写草稿、发外部消息、改数据库，不该共用同一张预算表。

4. 可复用方法  
如果你想给现有流程补一层最小“停损表”，可以直接用这五步：  
1）先只挑一条高频流程，例如“搜资料→成稿”或“线索研究→生成外联草稿”。  
2）为这条流程填一张小表：最多几步、最多多久、最多几次搜索、最多几次昂贵模型调用、哪些动作需要审批。  
3）把停止条件写成系统能力，而不是一句模糊提示词。能用 step limit、duration limit、model/tool call limit 的，尽量配置成硬边界。  
4）给超限后的默认出口：返回当前结果、降级到更便宜模型、转人工复核、或者只生成草稿不执行发送。  
5）把每次触发上限的原因记下来。连续一周后你会看见：到底是提示词太散、工具太多、还是流程拆分不清。

5. GenGrowth 可以怎么用  
对 GenGrowth，最值得先上“停损表”的，不是所有流程，而是三类：

第一，研究学习稿流程。限制“最多搜索 N 次、最多写作 N 轮、超过时直接进入人工定稿”，避免为了追求完整把成本越拉越高。  

第二，外联与增长自动化流程。涉及发消息、改 CRM、提交表单的动作，不该自动穿透到底，应该停在“生成建议 + 等确认”。  

第三，多 Bot 协作流程。Hermes、PM、Ops 之间的子任务如果没有时长、步数和交付边界，就容易互相转交、上下文膨胀。

6. 今日行动  
今天就挑一条你最常用 Agent 流程，补上一张最小预算表：  
- 最大步数：5 还是 8？  
- 最大时长：60 秒还是 5 分钟？  
- 最大搜索/工具调用次数：各多少？  
- 哪一步一旦涉及外发、写回、花钱，必须停下审批？

先别追求完美，只要把这四个数字和一个审批点写出来，你的 Agent 就已经从“会跑”进化到“可控”。
