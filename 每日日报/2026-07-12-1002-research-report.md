今天读什么｜把每次返工变成 Agent 的“不会再犯”清单

### 1. 适合谁读 / 预计阅读时间
适合正在做 AI Builder、智能体工作流、研究报告、内容生产、线索整理或增长自动化的人。尤其适合经历过这种循环的团队：Agent 某天把来源引错、漏了字段、工具调用顺序不对；大家花半天修好，过几天换了提示词、模型或工具，又在别处犯回同类错误。预计阅读时间 10 分钟。

### 2. 为什么值得读
很多团队已经有日志、截图和人工复盘，却仍然没有真正变稳。原因是这些材料大多停留在“这次发生了什么”，没有进入“下次改动前必须通过什么”的测试体系。于是每一次修复都像口头交代：人记得，系统不记得。

Anthropic 在 2026 年的 Agent 评测指南里给出一个很实用的方向：从人工本来就在检查的内容、用户反馈和 bug 队列中提取真实任务；早期只要 20—50 个来自真实失败的样本，就足以启动。OpenAI 也把过程记录（trace）和可重复运行的数据集区分开：前者适合定位一次工作流为什么失手，后者才适合比较提示词、模型、路由或工具变更有没有带来倒退。LangChain 的实践则把这条链路称为改进飞轮：异常运行进入审阅，提炼成测试样本，修复后加入回归集，防止老问题再次出现。

一句话：不要把一次失败只当事故单；要把它加工成下一次上线前的“不会再犯”检查项。

### 3. 核心概念
**第一，轨迹不是测试集。**  
轨迹记录一次任务里模型说了什么、调了哪些工具、耗时多久；它负责回答“问题在哪里”。测试集则把其中可复现的问题改写成清楚任务、输入和验收规则；它回答“改完后还会不会出问题”。两者要连接，但不能混为一谈。

**第二，能力测试和回归测试用途不同。**  
能力测试故意放进 Agent 目前还做不好的难题，用来寻找提升空间；回归测试收录已经修好的问题，目标应接近全通过。只做前者，改动容易伤到旧能力；只做后者，系统又缺少向上爬的目标。

**第三，评测应尽量验结果，不要死盯唯一路径。**  
同一份合格研究稿，可以用不同检索顺序完成；同一个客户问题，也可能有不同但有效的处理步骤。更可靠的检查是：关键字段是否齐全、引用是否可追溯、最终草稿是否进入正确状态、是否越过权限边界。只有安全或合规确实要求时，才检查特定工具或参数。

**第四，评分需要分层。**  
格式、必填字段、链接可打开、状态是否写回，优先用确定性规则；“解释是否清楚”“语气是否得体”“论证是否完整”可以用带明确量表的模型评审；抽样人工复核则用来校准前两层，防止自动评分本身漂移。别只设一个笼统的“质量 8 分以上”。

**第五，失败样本也要有优先级。**  
高频、影响大、容易复发的错误先入库；偶发且难复现的异常先保留轨迹和标签，别急着写成含糊测试。否则测试集会变成噪音仓库。

### 4. 可复用方法
可以用一张“失败→测试”卡，给现有流程补上最小闭环：

1. **收集**：每周从人工打回、用户反馈、工具报错和抽读轨迹中挑 3—5 个真实问题。  
2. **改写**：把抱怨改成可执行任务。不要写“报告不好”，而写“给定三篇来源，结论必须标出来源链接；证据不足时必须标记不确定，不能补造事实”。  
3. **验收**：每个任务写出输入、期望结果、禁止项和评分方式；先让人或参考答案证明任务本身可通过。  
4. **分类**：分别放进“能力待攻克”“已修复回归”“安全边界”三个小集合，避免一张表混用。  
5. **放行**：每次改提示词、换模型、改工具描述或路由前，先跑回归集；关键指标下降就暂停放量，回看轨迹定位原因。  

最初不需要购买复杂平台。一个版本化表格或 JSON 文件，加上可复跑的脚本和人工抽样，就能开始。关键不是工具多，而是每个失败是否真的被转成了下一次可验证的约束。

### 5. GenGrowth 可以怎么用
对“研究资料→学习稿→Slack 推送”流程，可先建立 15 条回归卡：是否避开近期重复主题、关键判断是否附公开来源、是否包含适合谁读/方法/落地点/行动、引用链接是否有效、正文是否没有把猜测写成事实。这样改日报提示词或换模型时，不用只凭感觉看一篇样稿。

对“线索研究→外联草稿”流程，回归卡可检查：公司和联系人是否匹配、是否把不确定信息标为待核、是否只生成草稿而非直接发送、是否符合品牌与合规边界。对有副作用的步骤，再额外检查真实终态，而不只相信 Agent 说“已完成”。

建议把每张卡都带上版本、来源（用户反馈/人工复核/工具失败）、影响等级和负责人。它既是质量资产，也是团队对“什么叫做好”的共同说明书。

### 6. 今日行动
选一条最常返工的 Agent 流程，找出最近 5 次人工修改或失败记录。今天只把其中 3 条改成可复跑的测试卡：明确输入、验收、禁止项和评分方式。下次修改提示词、模型或工具前，先跑这 3 条；若任一已修复问题重现，就不继续放量，而是先回看对应轨迹。
