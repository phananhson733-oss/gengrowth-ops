今天读什么｜别只验最后一句：让 Agent 用“工作底稿”交付可审查结果

### 1. 适合谁读 / 预计阅读时间
适合正在用 AI 做研究报告、内容选题、线索筛选、竞品跟踪或跨工具自动化的人。尤其适合遇到过这种情况的团队：Agent 最终写得很顺，但你不知道它查了什么、哪些判断只是推断、缺哪些资料；下一位同事或下一轮 Agent 只能从聊天记录里重新拼线索。预计阅读约 10 分钟。

### 2. 为什么值得读
很多工作流把“最终回复”当成交付终点。问题是，一段漂亮总结同时混进了事实、判断、遗漏与行动建议；人想复核时，只能重新翻网页和工具日志，系统想继续工作时，也会把整段自然语言重新塞进上下文。于是质量、协作和复用都依赖“这次模型刚好记得”。

更稳的做法是让 Agent 交付一组可审查的工作底稿：结论只是其中一份；另外留下主张—证据对应表、未决问题、结构化风险项和验证结果。OpenAI 最近的 Agent 改进示例把摘要、证据表、引用、风险清单和开放问题作为同一任务的必备产物；Anthropic 也指出，文件系统不只是存储，而是 Agent 可按需取用的上下文索引。

关键转变是：**不要把 Agent 当“会说话的答案框”，而要把它当能产生可回读工作件的协作者。** 人审核的是差异和证据，下一轮 Agent 读取的是已确认的底稿，而非一长段聊天回忆。

### 3. 核心概念
**第一，最终文案不是唯一产物。** 一次研究至少应分开保存：给读者的结论、每条关键主张的来源、尚未证实的缺口、以及本次规则校验的结果。四者混在一篇文章里，既难检查也难复用。

**第二，底稿要标注“已知”和“未知”。** 证据表不只记录支持材料，还应记录反例、来源日期、适用范围与置信边界；没有资料的字段写“未证实”，不能用流畅语言补上。这样未决项会成为下一步任务，而不是被遗忘。

**第三，产物契约比提示词更可靠。** 不只要求“请引用来源”，而是规定必须存在哪些文件、每条主张要有什么字段、哪些为空就不能通过。验证器应检查真实文件、引用是否存在、必填列是否齐全，而不是只相信模型自报“已核验”。

**第四，工作区是上下文的外部骨架。** 文件名、目录、时间和版本会告诉人和 Agent：什么是原始资料、当前结论、待审草稿与历史运行。只把所有内容堆进一个对话窗口，会让过期结果、失败日志与新任务互相干扰。

### 4. 可复用方法
以“某行业竞品研究”为例，先定义一个最小交付包，而不是先写长提示词：

1）`brief.md`：只放面向业务的结论、建议和明确限定条件。  
2）`claims.csv`：一行一个关键主张，包含主张、证据链接/位置、来源日期、反例、状态（已证实/待核/不支持）。  
3）`open_questions.md`：列出会改变决策但尚缺证据的问题，并注明下一步该查什么。  
4）`validation.json`：由脚本写入检查结果，例如是否有空来源、死链、重复主张、无出处数字或超出范围的动作。

再按“四步门”运行：先收集并写底稿；再基于底稿生成简报；随后执行确定性校验；最后才进入人工审阅或下一节点。人工优先看新增主张、冲突与未决项，不必重读全部原始材料。任务结束后保留底稿和版本，清理冗长临时日志；下次只按需回读对应文件。

### 5. GenGrowth 可以怎么用
- **研究报告**：每篇报告同时保留“主张—来源—反证—缺口”表。频道正文仍然易读，但后续选题、销售材料和客户沟通只能引用表中已证实项。
- **内容生产**：把内容草稿、事实核验表、品牌/敏感项检查、待人工确认项分开。发布节点只读取通过检查的版本，避免把创作过程中的猜测带到成稿。
- **增长线索**：让 Agent 输出候选名单、匹配证据、缺失字段和建议动作；不要直接把一段“高意向客户总结”写入 CRM。审核者看的是对象与依据的差异。
- **多 Agent 协作**：研究者交证据包，写作者交草稿，审核者交通过/退回原因；交接的是小而明确的文件契约，而不是整段上下文。

### 6. 今日行动
挑一条已有的低风险流程（建议从竞品研究或内容选题开始），本周只增加三个文件：`claims.csv`、`open_questions.md`、`validation.json`。先设五条硬规则：每条关键主张有来源；来源带日期；冲突不得静默合并；缺口必须显式列出；校验失败不能进入下一步。连续跑 10 次后，统计人工最常修改的三类问题，再把它们固化成字段或自动检查，而不是继续给提示词加长段补丁。
