今天读什么｜别让 Agent 一重试就做两遍，先给关键动作一张“重试安全卡”

1. 适合谁读 / 预计阅读时间
适合正在做 AI Builder、智能体工作流、增长自动化、内容生产、知识库沉淀的人读。尤其适合已经把搜索、发消息、写表格、发邮件、写库、发审批接进 Agent，但开始担心“超时后重跑，会不会把同一件事做两遍”的团队。预计阅读时间 10 分钟。

2. 为什么值得读
很多团队做 Agent，前半段解决的是“它能不能自己做更多事”；真正上线后，常见事故却不是它不会做，而是它失败后又做了一遍。一次超时、断线、重复点击或后台重启，都可能把“继续执行”变成“重复执行”：重复发外联、重复建任务、重复写记录、重复发审批，严重一点就是重复扣费或重复对外发送。

最近几条公开信号把这个方向讲得越来越清楚。OpenAI 在 Agents SDK 文档里，已经明确把“对话继续”和“暂停后恢复同一次运行”分开，并把副作用审批、后台运行、durable integration 讲成正式能力。Vercel 则把 durable execution 和 WorkflowAgent 做成基础设施：工具调用按步骤持久化，失败后从上一个检查点继续，而不是整条链路重来；AI SDK 7 还强调审批恢复时要重新校验原始参数，避免“批的是 A，执行成了 B”。Anthropic 另一边给了一个提醒：不要把所有风险都丢给审批弹窗，因为审批疲劳会很快出现，系统边界要先收紧。

一句话：更成熟的 Agent，不只是会重试，而是会“安全地重试”。

3. 核心概念
第一，能重试不等于适合重试。搜索网页、读取文档、重新拉状态，通常可以重复做；但发邮件、建记录、扣费、删数据、发外部消息，这些写动作不能把“再来一次”当默认答案。

第二，要区分“同一个意图”和“新的一次请求”。用户只想发出一次动作，但网络超时、页面刷新、Worker 重启时，系统很容易把它误判成新请求。解决这个问题的核心不是提示词，而是给任务和关键写动作分配稳定 ID。

第三，决策层和执行层最好拆开。模型负责判断“现在该做什么”；有副作用的动作，最好交给带幂等保护的执行层去做。这样就算上层重跑，底层也知道这是不是同一件事。

第四，检查点要落在步骤之间，而不是只留在聊天记录里。好的恢复不是“把整段历史重新塞回模型”，而是明确知道：做到哪一步、哪一步确认成功、下一步该不该继续。

4. 可复用方法
如果你想给现有流程补一层“重试安全卡”，可以直接用这五步：
1）先挑一条有真实副作用的流程，比如“搜线索→生成外联草稿→正式发送”或“整理资料→写回表格/知识库”。
2）把步骤拆成四类：读取、判断、写入、确认。只有写入类步骤，才必须带幂等键或人工确认。
3）给每次任务一个 task_id，给每个关键写动作一个 action_id 或 idempotency_key。重复到来时，不再重新执行，而是返回上次结果或当前状态。
4）把状态写到系统外：pending、running、succeeded、failed、needs_approval，不要只靠聊天上下文记住“刚才做到哪”。
5）为失败定义分层处理：读动作可静默重试；写动作先查是否已成功；高风险动作超时后宁可停下来等人，也不要整段重跑。

5. GenGrowth 可以怎么用
对 GenGrowth 来说，这很实用。
- 在增长自动化里，它可以避免同一条线索被重复触达、同一封外联消息被重复发送。
- 在内容生产里，它可以避免一次发布失败后把内容重复发到多个渠道。
- 在知识库沉淀和多 Bot 协作里，它可以把“谁创建了任务、谁已经执行、哪一步待审批”变成可恢复状态，而不是靠 bot 之间互相猜测。

6. 今日行动
今天就做一件事：挑出你们当前最容易“重试出事故”的那条 Agent 流程，把其中所有写动作列出来，然后逐个补三样东西——稳定任务 ID、幂等键、状态回执。哪怕只是先把“重复请求返回旧结果、而不是再执行一次”做出来，稳定性都会提升。
