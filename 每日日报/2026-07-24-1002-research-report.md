今天读什么｜别只给答案贴链接：给 Agent 建一张“主张—证据账本”

### 1. 适合谁读 / 预计阅读时间
适合正在用 AI 做行业研究、内容选题、竞品分析、销售材料、客户洞察或知识库问答的人。尤其适合遇到过这种情况的团队：报告末尾有一串来源，但你仍说不清某个数据、判断或推荐究竟由哪条材料支持；网页一更新、客户一追问，整篇稿子都得从头核对。预计阅读时间约 10 分钟。

### 2. 为什么值得读
“有引用”不等于“有证据”。Agent 常把网页、旧摘要、检索片段和模型推断混在一起，最后附几个链接。链接可能存在，却未必支持紧挨着的结论；数字、比较级和因果判断尤其容易写得像事实。

更可靠的做法是把最终稿拆成可核的最小单元：每一个重要主张都要能回到具体证据，并标明它是原文事实、基于证据的推断，还是尚待验证的问题。W3C 对来源追溯的定义包含产物、参与者与产生过程；OpenAI 的 Agent 示例则把事实账本、引用文件、证据覆盖检查和最终产物校验放在同一流程里。重点不是保存“搜过什么”，而是保存“这句话凭什么成立”。

### 3. 核心概念
**第一，主张不是段落。** “某产品适合中小团队”可能混有功能、价格、部署成本和适配判断。前几类可查事实，最后一类是带条件的建议；不要用一个笼统链接替整段背书。

**第二，证据强度有层级。** 官方文档、原始数据、客户公开案例通常强于二手解读；搜索摘要只适合找路，不应充当关键证据。来源还要带抓取时间、版本或页面标题，因为网页会变。

**第三，引用存在不等于支持成立。** 检查要问：来源是否真的说了这件事？数字、时间、对象是否一致？原文是否有相反限定条件？“相关”与“证明”是两回事。

**第四，不确定性也应结构化。** 对每项主张给出“已支持、证据不足、证据冲突、不适用”之一。证据不够时，保留开放问题或改写成条件性建议，不能由流畅文案把空白抹平。

**第五，账本不同于运行日志。** 日志记录 Agent 调了什么工具；账本记录最终哪条结论依赖哪份材料、由谁或哪个版本生成、后来是否被人工修订。前者排障，后者复核与复用。

### 4. 可复用方法
给现有“搜资料→成稿”流程加一层账本，可从五步开始：

1）划“必须核”的边界：数字、产品能力、竞品比较、客户案例、政策描述，以及会触发外联或决策的建议，全部进入账本。  
2）规定最小字段：`claim_id`、主张原文、类型（事实/推断/建议）、证据 URL 或文件 ID、原文位置、来源等级、抓取时间、状态、Agent 版本。  
3）先抽主张，再写长文：研究 Agent 输出“候选主张+证据”；写作 Agent 只能使用“已支持”的事实。  
4）发布前跑两道检查：规则检查字段、链接与日期；复核 Agent 或人工抽查高影响主张是否被原文真正支持。Anthropic 建议在链式流程的中间步骤加入程序化闸门。  
5）把失败变成样本：记录“夸大功能”“数字过期”“来源不支持结论”等理由码，加入下一次回归检查。

### 5. GenGrowth 可以怎么用
先从“AI Builder 信号→GenGrowth 选题简报”试起。研究阶段生成轻量证据表；每个选题只使用 3—5 条已支持事实，并把“值得写”的判断标为编辑建议，而非客观事实。编辑只需看高风险主张的原文摘录与链接，就能快速决定保留、降调或删除。

同一信号被改写成公众号、销售材料或客户洞察时可复用证据表，但必须重查时效与适用对象，不能直接复制旧结论。衡量的也不是引用数量，而是高影响主张的可追溯率、打回问题的可定位率和过期证据的重核率。

### 6. 今日行动
找一篇最近由 AI 协助完成的研究稿或内容草稿，圈出其中 5 个高影响主张。为每条填上“原始来源、原文位置、事实/推断/建议、状态”四栏；凡是找不到原文支持的，先改成待验证或删掉。把这张小表作为下次同类任务的输入与验收件。
