今天读什么｜别把 Agent 的脑子当仓库，给它一套“上下文工程”

1. 适合谁读 / 预计阅读时间
适合正在做 AI Builder、智能体工作流、内容生产、研究助手、知识库沉淀、增长自动化的人读。尤其适合已经发现：模型明明越来越强，但流程一长就开始跑偏、变慢、忘事、重复读同一堆资料的人。预计阅读时间 10 分钟。

2. 为什么值得读
过去大家常把问题归结为“提示词没写好”。但这两年的公开实践正在把重点往前推一步：真正决定 Agent 稳不稳的，往往不是某一句 prompt，而是每一步到底让它看见什么、不看见什么、把什么留在外面、什么时候再取回来。

Anthropic 直接把这个方向叫做“上下文工程”。他们在公开材料里给了两个很有代表性的信号：一是在复杂搜索评测里，记忆工具配合上下文编辑，相比基线带来 39% 的提升；二是在 100 轮网页搜索任务里，上下文编辑把 token 消耗降了 84%，同时让本来会因上下文耗尽而失败的任务继续跑下去。LangChain 也把常见做法总结成四个动作：写入、选择、压缩、隔离。Vercel 在 AI SDK 7 里把 runtime context、tools context、durable WorkflowAgent 做成正式能力；OpenAI 也明确区分“你的代码可见的本地上下文”和“模型真正看得见的上下文”。

一句话：下一阶段更值钱的 Agent，不只是会调工具，而是会管理自己的注意力。

3. 核心概念
第一，上下文不是越多越好，而是有限注意力预算。资料、历史消息、工具返回、规则、记忆、示例，都会抢模型的注意力；塞得越满，不代表越懂，反而更容易分心、冲突、遗忘。

第二，要区分两种上下文：给程序用的状态，和给模型看的信息。像 API Key、租户 ID、审批状态、运行计数，更适合放在运行时状态里；真正需要模型推理的内容，才进入提示和消息。

第三，成熟系统通常会做四件事：把重要进展写到外部工作台；只在需要时取回相关信息；把冗长历史和大工具结果压缩；把复杂任务拆给带独立上下文的子代理或独立执行环境。

第四，工具本身也是上下文工程的一部分。工具太多、描述重叠、返回结果太长，都会让 Agent 变笨。好的工具不是把底层 API 原样搬给模型，而是只返回高信号结果。

4. 可复用方法
如果你想给现有流程补一层最小“上下文工程”，可以直接用这五步：
1）先挑一条长流程，例如“搜资料→整理要点→成稿→归档”。
2）把信息分三层：必须当场看、可以外部暂存、根本不该给模型看。
3）先加一个外部工作台：比如 notes.md、任务清单、结构化 state，专门存进展、决策、待办。
4）给大结果加压缩规则：搜索结果只保留摘要，日志只保留头尾，旧步骤定期总结，不让原始长输出一路跟着跑。
5）遇到复杂分支时，不要让一个 Agent 背全场；把专题搜索、审查、整理拆成独立上下文的小任务，最后只交回压缩结论。

5. GenGrowth 可以怎么用
在 GenGrowth，最直接的落地点有四个。
第一，研究报告流：搜到的网页、播客、博客不要整段塞回主 Agent，先做证据卡和要点卡，再成文。
第二，内容生产流：标题候选、素材摘录、品牌口径、最终正文分层保存，避免每次改稿都把全量历史再喂一遍。
第三，增长自动化流：线索抓取、字段清洗、消息草稿、正式发送分开管理；敏感状态放运行时，不直接暴露给模型。
第四，多 Bot 协作流：Hermes、PM、Ops 之间只传最小必要包，别把整段上下文原样交接。

6. 今日行动
今天就做一件小事：找一条你们已经在跑的 Agent 流程，画一张“上下文去留表”。只回答四个问题——什么必须进模型、什么只放状态、什么要压缩、什么该交给子任务。哪怕只改这一张表，通常都比再补一段长 prompt 更有效。
