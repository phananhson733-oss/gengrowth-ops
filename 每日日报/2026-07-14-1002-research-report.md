今天读什么｜别让所有 Agent 同时开跑：给工作流一套“排队与让路”机制

### 1. 适合谁读 / 预计阅读时间
适合正在搭 AI Builder、研究助手、内容生产、线索处理或增长自动化的人。尤其适合遇到这类现象的团队：早上定时任务一到，多个 Agent 同时检索、调用模型、写入表格；平时好用的流程突然变慢、频繁报错，甚至互相拖垮。预计阅读时间 10 分钟。

### 2. 为什么值得读
Agent 工作流常被误解为“并发越高越先进”：同时开十个研究任务、几十次工具调用，好像自然会更快。但模型接口、网页服务、MCP 工具、数据库和人工审核队列都不是无限容量。任务涌入速度一旦超过下游处理速度，超时会触发重试，重试又制造更多请求，最后把一个局部拥堵放大成整条流程的故障。

AWS 在近期 Agent 编排材料中把并发、限流和背压列为生产级控制面：应分别限制工作流、单个 Agent、外部工具和模型层的消耗。Temporal 也建议把不同性质的工作拆进独立任务队列，避免一类耗时任务“饿死”另一类任务。GitHub 的 Agentic Workflows 则用并发组、超时、限速、写操作上限和人工审核叠加防护。共同结论是：稳定不是让 Agent 永不排队，而是让它在拥堵时有序地慢下来。

一句话：排队不是性能问题的补丁，而是把有限模型与工具能力分配给更重要工作的产品规则。

### 3. 核心概念
**第一，并发、吞吐和延迟不是一回事。** 并发是同时在跑多少件事；吞吐是单位时间真正完成多少件；延迟是每件事等多久。盲目提高并发，可能只让“同时等待接口响应”的任务更多，并不会提高完成量。

**第二，背压是下游说“先别再塞了”。** 当模型触发限流、网页抓取变慢、表格写入积压时，上游不应继续无节制地产生新任务，而应减速、暂存或合并。这比让每个任务各自报错再重试可靠得多。

**第三，队列必须分级。** 用户正在等待的问答、当天必须发出的报告、低优先级历史补录，不该挤在同一条队列。至少区分“即时”“当日”“后台”三档；把昂贵研究与轻量分类分开，避免长任务占满全部工位。

**第四，失败队列不是垃圾桶。** 同一任务超过重试预算后，应移入待处理队列，保留任务 ID、输入摘要、已完成步骤、失败原因和下一步建议。它的目的不是悄悄吞掉失败，而是让人或修复流程能安全接手。

### 4. 可复用方法
给一条现有流程补上“排队与让路”，可以从五步开始：

1）画出真实瓶颈：分别记录模型调用、搜索/网页工具、写入系统、人工审核每一步的等待时间和错误率；不要只看总耗时。  
2）划三档优先级：例如“用户即时请求 / 今日定时产出 / 可延后归档”，每档明确最长等待时间与超时后的处理方式。  
3）设置四层上限：全流程同时运行数、单 Agent 同时运行数、单工具每分钟调用数、单任务最大并行分支数。先保守，依据数据再逐步放宽。  
4）写清拥堵策略：队列变长时，是延后启动、合并相似任务、切到轻量路径，还是暂停入口；不要把“无限重试”当策略。  
5）建立例外出口：重试耗尽的任务进入失败队列；高风险写入仍停在审批前，不因“队列清空”而自动放行。

### 5. GenGrowth 可以怎么用
以“每日研究报告”为例，可把资料抓取和成稿拆开：抓取任务进入后台队列，并限制同一来源的并发；证据齐全后再进入写作队列；最终发布仍保持单一、可审核的出口。这样早高峰不会因为多篇报告同时检索而影响正在进行的用户请求。

在线索运营中，可以把“新线索入库后的字段整理”设为轻量、可批处理的后台任务；把“生成外联草稿”设为当日优先；任何正式发送则继续走人工审核。真正要被优先保障的不是“所有任务马上启动”，而是高价值任务能在承诺时间内拿到可信结果。

建议最少看四个指标：各优先级队列长度、排队等待时间、限流/超时次数、失败队列数量。若队列长期增长，先减少入口或提升瓶颈能力；若低优先级总被饿死，再调整配额，而不是让它与紧急任务抢资源。

### 6. 今日行动
选一条会同时触发多任务的流程，在白板或表格写下：入口、共享资源、三档优先级、每层并发上限、超过重试预算后的去处。先只给最脆弱的一个外部工具加“每分钟限额 + 失败队列”，运行一周后再看等待时间和错误率是否下降。
