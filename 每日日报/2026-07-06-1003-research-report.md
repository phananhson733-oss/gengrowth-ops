今天读什么｜别把 Agent 当全权限实习生，先给它一张“权限卡”

1. 适合谁读 / 预计阅读时间
适合正在做 AI Builder、智能体工作流、多 Bot 协作、内容生产自动化、知识库助手的人读。尤其适合已经把 Slack、文档、表格、邮件、网页工具接进 Agent，但开始担心“它能做很多事，可我不确定它该做哪些事”的团队。预计阅读时间 10 分钟。

2. 为什么值得读
过去很多团队做 Agent，先追求的是“能不能把工具接进去”。工具一旦接通，下一步常见误区就是：默认让同一个 Agent 拿到一整套权限，读能读、写能写、发消息也能发。Demo 阶段很顺，真正进业务后就会开始冒风险：提示词被污染时，影响范围被放大；一个本来只该查资料的 Agent，顺手就能改记录、发外部消息；换一个入口或 Bot 时，谁该拥有哪种能力也说不清。

最近几家的公开资料，正在把方向讲得更明确。OpenAI 在 connectors 与 remote MCP 文档里，把工具白名单、逐次审批、按工具跳过审批做成正式配置；Anthropic 在 trustworthy agents 研究里强调，用户必须明确决定 Agent 能做什么、不能做什么，而且不同动作应对应不同许可级别；Google A2A 则把 agent card 做成正式说明书，要求远程 Agent 对外声明自己的能力、技能和认证方式。你会发现，下一阶段更稳的 Agent，不只是“会调工具”，而是“先把能力边界写清楚，再让它做事”。

一句话：真正可上线的 Agent，不该像拿着老板全部账号的万能实习生，而应该像一个有岗位说明书、有权限范围、有审批规则的数字同事。

3. 核心概念
第一，权限不是工具数量，而是动作边界。同样是接入 Gmail，读邮件、起草回复、正式发送，风险完全不同。

第二，白名单比“相信模型会克制”更可靠。OpenAI 已经把 allowed tools 和 approval 做成正式能力：先限制它能碰什么，再谈它会不会乱碰。

第三，审批要细到动作级，而不是粗暴地“全开”或“全关”。Anthropic 给出的思路很实用：有些动作可以始终允许，比如读取日历；有些动作必须每次确认，比如发邀请、对外发送、删除或写回。

第四，远程 Agent 也要先亮身份。Google A2A 里的 agent card，本质上就是岗位卡：我是谁、会什么、怎么认证、有哪些技能。没有这层声明，多 Agent 协作很容易变成“能连上，但不可信”。

第五，权限最好是临时的、可撤回的。一次任务结束后就回收，通常比长期默认放权更安全。

4. 可复用方法
如果你想给现有流程补一层最小“权限卡”，可以直接用这五步：
1）先按任务拆 Agent，不要一个 Agent 包打天下。研究、写稿、归档、发送，尽量分角色。
2）给每个角色只配最小工具集，并区分读、写、发送、删除四类动作。
3）把高风险动作单独设成人工确认点，比如外发消息、写回 CRM、删除文件、改正式知识库。
4）给每个 Agent 写一张能力说明：用途、允许访问的数据、允许调用的工具、禁止动作、交付格式。
5）把日志和审批记录留出来，定期复盘：哪些权限从没用过，哪些动作总要人工兜底，就继续缩权或改流程。

5. GenGrowth 可以怎么用
对 GenGrowth 来说，这套方法特别适合多 Bot 协作。比如：研究 Bot 只负责搜集资料和生成学习稿，不直接发外部消息；Ops Bot 只负责低风险整理和草稿，不继承 PM/CEO 的高权限；真正涉及发布、回写、审批、对外触达的动作，再交给有明确授权的人或专门节点处理。这样做的好处不是“更保守”，而是更容易规模化：以后接更多工具、增加更多 Bot，也不会每加一个能力就把整套系统的风险一起放大。

6. 今日行动
今天就挑一条你最常用的 Agent 流程，做一次“权限盘点”：
- 写下这个 Agent 实际用了哪些工具；
- 标出哪些属于读取，哪些属于写入，哪些属于外发；
- 删掉 1 项它其实不必长期拥有的权限；
- 给 1 个高风险动作补上人工确认。

如果你做完这一步，很多“我总觉得它不太可控”的不安，通常会立刻下降一半。
