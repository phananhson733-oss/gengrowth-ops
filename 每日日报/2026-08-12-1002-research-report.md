今天读什么｜Agent 不怕重试，怕的是“做了但没回执”

### 1. 适合谁读 / 预计阅读时间
适合正在让 AI 自动整理线索、写入 CRM、创建任务、同步表格、生成内容草稿或调用外部接口的团队。尤其适合遇到过这种场景的人：页面显示“请求超时”，但你不知道客户记录到底有没有建成；任务重跑后，频道里多了一条通知，表格也多出一行。预计阅读约 10 分钟。

### 2. 为什么值得读
Agent 工作流最容易被低估的一类错误，不是模型答错，而是**结果不确定时的重复执行**。一次“创建线索”“发送提醒”会跨过模型、队列、网络和第三方系统。调用方可能在对方已成功写入后才断线；Worker 也可能已经完成动作，却在回传成功前崩溃。于是系统只看见“没有收到回执”，自然选择重试。

问题在于：网络语义通常只能保证“至少执行一次”，很难天然保证“恰好一次”。Temporal 明确提醒，Activity 成功后若 Worker 未及时把结果告知服务端，Activity 仍可能被再次执行；Stripe 和 AWS 的共同做法则是：让同一业务动作带着同一把幂等键重试，由执行端返回第一次的结果，而不是再做一遍。

这对 GenGrowth 很实际：重复发一封外联、重复创建一条 CRM 记录、重复发布一篇内容，伤害不只是一笔 API 成本，还会损害客户体验与数据可信度。**重试不应由“报错了”触发，而应由“能否证明尚未完成”决定。**

### 3. 核心概念
**第一，幂等不是“不重试”，而是“重复请求只有一次业务效果”。**  
例如“为线索 L 创建初次跟进草稿”无论提交三次，最终应只有一个草稿；后两次返回同一个草稿 ID 或“已存在”，而不是新建三个。

**第二，幂等键要代表业务意图，而非某次网络请求。**  
不要每次重试随机生成 UUID，也不要把邮箱、手机号等敏感信息直接拼进键。可用 `任务ID + 动作类型 + 对象ID + 版本` 形成稳定键，例如“本次活动、给这位联系人、生成第 2 版草稿”。当用户改了文案或对象范围，版本变化，才应成为新的动作。

**第三，回执是后续决策的依据。**  
每次有副作用的调用都应保存：幂等键、请求摘要、目标对象、执行状态、外部对象 ID、时间、错误类别和可回读链接。Agent 的自然语言“已完成”不是回执；第三方返回的对象 ID、数据库唯一记录或已发送消息 ID 才是。

**第四，未知状态不能直接当失败。**  
超时后至少有三种可能：根本没到达、对方已完成、对方仍在处理。正确步骤是先按幂等键或业务唯一条件查询，再决定恢复成功、有限重试，还是进入人工核对。把未知直接重跑，是重复事故的起点。

**第五，读取、草稿和不可逆动作要用不同策略。**  
查询通常可安全重试；建草稿可用幂等键并回读；发送、扣费、删除等高风险动作除幂等外还要缩小对象范围、限制次数，并在异常后优先核验。若下游根本不支持幂等或查询，宁可禁用自动重试、转人工，也不要赌“应该没发出去”。

### 4. 可复用方法
可为一条“AI 筛选线索→建草稿→写 CRM”的流程补一层最小执行账本：

1. 先列出全部副作用：新建、更新、发送、发布、删除、付费调用；每项指定业务对象与成功证据。  
2. 给每项定义稳定幂等键和版本规则；数据库对该键加唯一约束，或调用支持该字段的下游 API。  
3. 执行前先查账本：已有成功回执就直接复用结果；处理中则等待或轮询，避免并发双提交。  
4. 超时或 5xx 后先“查后写”：按键或对象唯一条件回读；仅在确认未完成时用指数退避重试，并设置次数和截止时间。  
5. 把终态写清：成功、未执行、待核验、可重试失败、不可重试失败；对“待核验”生成一张包含对象和预期影响的人工卡，而不是含糊地报错。

### 5. GenGrowth 可以怎么用
先从最容易造成重复的两条链路试点：一是内容生产中的“生成草稿→进入待审库”，二是增长运营中的“线索判定→更新 CRM→生成跟进草稿”。前者可用 `内容主题 + 渠道 + 版本` 防止同一选题反复入库；后者可用 `活动ID + 联系人ID + 动作类型` 防止重复建档和重复触达。

关键不在于先替换所有工具，而是让每次动作都能回答四个问题：**要影响谁？凭什么算同一次？成功证据在哪里？不确定时谁来决定？** 这些字段也能反过来成为质量仪表盘：重复拦截次数、未知状态占比、回读成功率、人工核验量，比“任务成功率”更早暴露流程问题。

### 6. 今日行动
选一条本周会执行的写入流程，花 30 分钟做一次盘点：

- 找出一个最怕重复的动作，例如“创建 CRM 线索”或“发送跟进邮件”；  
- 写下一条稳定幂等键公式，以及什么变化才算新版本；  
- 为超时设计固定分支：先查回执，再重试，仍不确定则转人工；  
- 用同一输入连续模拟两次，验收标准不是“第二次没报错”，而是外部系统只留下一个正确结果。
