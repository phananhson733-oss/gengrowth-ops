今天读什么｜别让 Agent 每次从零开始：给工作流加一层“可失效的复用层”

### 1. 适合谁读 / 预计阅读时间
适合正在做研究助手、内容生产、线索研究、知识库问答或增长自动化的人。尤其适合这类团队：同一公司、同一产品、同一份资料被不同 Agent 反复搜索、反复总结、反复花模型钱；但一谈“缓存”，又担心旧信息被当成新事实。预计阅读时间约 10 分钟。

### 2. 为什么值得读
很多 Agent 的成本与等待，不是来自真正困难的推理，而是来自重复劳动：每次都重新装入岗位规则、工具说明、品牌资料；每次都重新抓同一页面；每次都把已经核过的证据再总结一遍。

但“把答案存起来”并不是解法。研究结论会过期，客户状态会变，网页会更新，模型和提示词也会换。盲目复用会把昨天的正确答案变成今天的误导。

更成熟的思路是建立**可失效的复用层**：凡是重复、稳定、可追溯的输入或中间成果，优先复用；凡是时效敏感、范围不同、证据不足的内容，必须重新取证。它既不是长期记忆，也不是把旧回答直接复制给新用户，而是一套“先检查、再决定是否重做”的工作流规则。

OpenAI 的 Prompt Caching 把这种思路落到调用层：相同的长提示前缀可以复用，且可通过 `cached_tokens` 与 `cache_write_tokens` 观察实际命中。Anthropic 也建议让共享上下文保持一致，以提升批处理中的缓存命中。它们共同说明：复用应被度量，而不是凭感觉宣称“已经优化”。

### 3. 核心概念
**第一，缓存、记忆、事实库不是一回事。** 缓存的目标是减少重复计算，允许过期和清除；记忆用于保留长期偏好或决策；事实库则应保存可引用的原始资料与版本。不要把一段旧回答同时当作三者。

**第二，优先复用“中间成果”，少复用“最终结论”。** 例如“某官网页面在何时抓取、抽取出哪些字段、对应原文链接”可复用；“这家公司现在最适合做什么”应结合当前目标重新判断。对研究型 Agent，证据包通常比成文答案更耐用。

**第三，一条复用记录必须带四张标签。** 至少记录：适用对象与范围、来源/版本、生成时间、失效条件。缺少任一项，系统就无法判断这次能否安全使用。比如产品定价页可设较短有效期；品牌语气规范可设较长有效期；CRM 客户状态则每次都应回读。

**第四，缓存命中不是“相似就拿来”。** 除了语义相似，还要检查权限、租户、语言、任务目标和时间窗。不同客户的竞品研究即便问题相似，也不能共用私有输入或结论。缓存键应先隔离数据边界，再考虑相似匹配。

**第五，失效本身是产品能力。** 资料更新事件、超过有效期、模型/提示词版本变化、人工标记“证据有误”，都应触发失效或降级为“待复核”。不能确定是否新鲜时，默认回到原始来源，而不是自信复用。

### 4. 可复用方法
给一条高频流程加复用层，可从五步开始：

1）列出重复点：分别标出稳定指令、工具定义、网页/文档抽取、检索证据、最终文案，别把它们混成一个缓存。  
2）为每类内容定复用等级：可直接复用、可作为草稿、必须重新验证。  
3）给记录补“复用合同”：对象、来源 URL/版本、时间、有效期、失效触发器、权限范围。  
4）把检查放在昂贵步骤之前：先查是否已有合格证据包，再决定是否联网、调用强模型或重新生成。  
5）记录命中后的结果：节省了哪些调用、人工是否打回、是否因过期而重做。命中率高不等于价值高；错误复用率必须单独看。

### 5. GenGrowth 可以怎么用
可先在“行业/客户研究 → 内容选题包”这条链路试点。为每个公开对象保留一个证据包：官网与产品链接、抓取日期、关键事实、引用片段、适用主题、有效期。新任务先读取包，再只补查发生变化的部分；最后由 Agent 依据当前受众与目标重新写成公众号、销售材料或 Slack 简报。

这样能把“重复搜索”变成“增量更新”，同时保留来源与新鲜度边界。注意：对外发送、客户画像、CRM 状态和任何私有资料，不应跨客户复用，也不能只靠缓存结果决定行动。

### 6. 今日行动
挑选本周最常重复的一条流程，建立一个 10 条以内的“证据包清单”。每条只填：对象、来源链接、抓取时间、可支持的判断、有效期、何时必须重查。明天再让 Agent 先读清单、后做补查，并对比一次任务的耗时、工具调用数与人工返工情况。
