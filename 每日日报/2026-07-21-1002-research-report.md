今天读什么｜别把人当 Agent 的紧急按钮：把人工介入做成可恢复的异常队列

### 1. 适合谁读 / 预计阅读时间
适合正在做研究助手、内容生产、线索运营、客户沟通或内部流程自动化的人。尤其适合这样的团队：Agent 一遇到不确定、权限不足或高风险动作，就在 Slack 里扔一句“请确认”；人回晚一点，任务就丢了；人说“不同意”，系统又只能从头再跑。预计阅读时间约 10 分钟。

### 2. 为什么值得读
“人在回路中”常被理解成多加一个确认按钮。但如果所有犹豫、异常和写操作都丢给人，结果通常不是更安全，而是审批疲劳：人不知道为什么要看、该看什么、不同意之后会怎样；Agent 也不知道该暂停、改稿，还是终止。

更有效的设计，是把人工介入当作一条正式的**异常队列**：系统先自动处理低风险、规则清楚的部分；只有触发明确条件时，才生成一张可判断的“决策包”，保存当前进度，等待人给出批准、拒绝或修改；之后从原任务恢复，而不是把旧上下文重新拼成一段新对话。

这已是主流 Agent 运行时的共同模式。OpenAI 将高风险工具调用建模为可保存、可恢复的暂停运行；LangGraph 用持久化检查点支持暂停、人工编辑状态再继续；Anthropic 在真实业务模板中强调，结果进入下游、提交或对客户生效前，应保留人工复核与批准。重点不是让人替 Agent 做全部工作，而是让人的有限注意力只花在真正需要判断的地方。

### 3. 核心概念
**第一，审批、复核、补充信息是三种不同介入。**  
审批回答“能不能执行”；复核回答“这份结果是否可靠、哪里要改”；补充信息回答“目标或事实还缺什么”。把它们混成一个“确认吗？”弹窗，人和系统都会误解下一步。

**第二，触发条件必须前置且可解释。**  
不要让模型凭感觉随时打断人。可用四类硬信号：动作有外部影响（发送、发布、写 CRM）；证据冲突或关键字段缺失；金额、客户等级、品牌风险超过阈值；连续重试或预算接近上限。每次进入队列都要写明命中的规则。

**第三，人工看到的应是决策包，不是完整轨迹。**  
一张合格卡片至少包含：要做的动作、对象与影响范围、依据摘要及来源、Agent 的建议、可选项（批准/拒绝/编辑/转人工）、到期时间。原始日志留作追溯，但不应逼审批者阅读几十轮工具输出。

**第四，暂停必须可恢复。**  
保存任务 ID、版本、已完成步骤、待执行动作、输入快照和审批结果。批准后从检查点继续；拒绝则进入预设替代路径，例如只产出草稿、回到补充信息、或安全结束。切勿把“批准”当作一条新的用户消息后整条重跑。

**第五，人改过的内容是最有价值的训练信号。**  
记录被改了什么、为何拒绝、最终采用哪个选项。每周把高频理由转换成规则、模板、测试样本或更清楚的工具约束，才能逐步减少无意义打扰。

### 4. 可复用方法
给一条现有工作流加“人工异常队列”，可从五步开始：

1. 画出所有会打断人的节点，并按“可自动通过 / 必须人工判断 / 应直接停止”三类归档。  
2. 只保留 3—5 个明确触发器，例如“发送外部消息”“引用不足两条”“高价值客户”“写入失败两次”。  
3. 统一决策包模板：任务目标、当前结论、证据、拟执行动作、风险、推荐选项、截止时间。  
4. 给每个暂停点设置三个终态：批准后恢复、拒绝后降级、超时后安全停止；并记录恢复依据。  
5. 每周看四个数：介入率、批准率、平均等待时长、同类拒绝率。介入率高不一定坏，但若批准率接近 100%，说明规则可自动化；若拒绝率高，说明前置质量或边界设计有问题。

### 5. GenGrowth 可以怎么用
先从“线索研究 → 外联草稿”开始：资料搜集、公司归类、首版文案可自动完成；只有准备对外发送、目标为重点客户、或资料置信度不足时，才进入异常队列。审批卡只展示客户、拟发送渠道、核心卖点、证据链接、完整草稿和风险提示。批准后由执行层发送；拒绝后保留为草稿并记录修改原因，不自动重发。

内容生产也适用：Agent 可先完成选题、提纲、资料卡和初稿；涉及品牌敏感表述、未经核实的数据、正式发布时，再让编辑处理一张“发布决策包”。这样编辑不是从头校稿，而是在关键位置做选择。
