今天读什么｜别让 Agent 互相“转述”：让协作围绕交付件而不是聊天记录

### 1. 适合谁读 / 预计阅读时间
适合正在把研究、内容生产、线索跟进、知识库整理或增长动作拆给多个 Agent 的团队。尤其适合已经遇到过这种场景的人：三个 Agent 都“完成了”，但有人重复搜资料、有人漏掉边界，最后由一个总控 Agent 把结果重新概述一遍，反而把原始结论改错。预计阅读约 10 分钟。

### 2. 为什么值得读
多 Agent 的真正价值不是“角色越多越聪明”，而是把彼此无关的上下文、工具和任务并行隔离。但很多系统仍然让 Agent 靠不断互相发消息协作：研究员把一段自然语言总结交给写作者，写作者再把摘要交给审核者。每多一次转述，证据、版本、未决问题和责任边界就更容易丢失。

Anthropic 在其多智能体研究系统的复盘中发现，子 Agent 若没有清晰的目标、输出格式、工具/来源指引与任务边界，容易重复、遗漏或跑偏；其进一步建议让子 Agent 将成果保存为可独立存在的外部产物，仅把轻量引用交回协调者，以减少“传话游戏”带来的信息损失。LangChain 的多 Agent 评测也指出，总控重述子 Agent 结果会增加误差和 token 消耗。

它们共同指向一个实践：协作的最小单位不该是聊天消息，而应是可验收、可追溯、可复用的“交付件”。

这不是要求所有人先搭复杂数据库。先让每个 Agent 交出一张结构化任务卡或一份证据包，再由下游读取原件、只补必要说明，就能明显减少“看似协作、实际失真”。

### 3. 核心概念
**第一，消息是通知，交付件才是事实载体。**  
消息可以说“竞品研究已完成”；交付件应包含结论、证据链接或摘录位置、适用范围、未知项、版本、生成时间和下一步。下游依据交付件工作，而非相信一句“我查过了”。

**第二，分工按产物边界，不按人设名称。**  
不要只设“研究 Agent、写作 Agent、审核 Agent”。更清楚的拆法是：证据包、选题简报、草稿、事实核验单、待审批动作。若两个 Agent 交的是同一种模糊摘要，重复不可避免。

**第三，原始证据与解释分层。**  
一份合格交付件应分出：可验证事实、基于事实的推断、建议动作、仍待确认的问题。写作 Agent 可以改写表达，但不应把推断伪装成事实；审核 Agent 可以否决结论，也能回到证据定位。

**第四，交接要带“接收条件”。**  
交付件不是生成完就算成功。它必须声明下游能否接收：关键字段是否齐、证据是否可访问、冲突是否已标注、风险是否已转人工。未满足就回到补充队列，而非硬交给下一位。

**第五，尽量转发，不要二次转述。**  
对需要保持原意的研究结论、客户原话或审批理由，协调 Agent 应传递原始交付件链接/ID 与关键字段；只在面向读者时才重新编写。这样既降低失真，也让问题能回溯到具体节点。

### 4. 可复用方法
给一条“研究→内容→发布”流程加交付件协作层，可用五步：

1. 选一个最常返工的交界处，例如“资料研究交给写作”。  
2. 定义一张最小交付件：`任务ID、目标、结论、证据、推断、未知项、版本、状态、接收条件`。其中“证据”和“未知项”不可省略。  
3. 让上游只拥有自己所需工具和上下文；要求它把结果写入交付件，而不是把完整思考过程塞给下游。  
4. 给下游设置读取规则：优先读最新已通过的交付件；发现证据不足，只能标回“待补充”，不得自行补造事实。  
5. 为每次交接记录三项指标：重复检索率、因信息缺失退回率、下游改写导致的事实纠错率。先用一周数据找出最脆弱的接口。

### 5. GenGrowth 可以怎么用
可以把一篇行业内容的生产，拆成四份轻量资产：

- **研究证据包**：主题、目标读者、5—8 条可核来源、主张与不确定项；  
- **内容简报**：一个中心判断、读者痛点、不可越界的表述、可用案例；  
- **文章草稿**：只引用已支持主张，并标出待确认位置；  
- **发布检查单**：链接、品牌语气、敏感承诺、CTA、渠道和人工批准状态。  

协调 Agent 只负责派发、检查接收条件、汇总状态；它不替研究 Agent“复述证据”，也不替审核 Agent 放行。对增长自动化同样适用：线索研究交“客户画像卡”，外联 Agent 交“待发草稿”，执行层交“回执卡”。每个动作都能定位来源、责任与下一步。

### 6. 今日行动
选正在跑的一条内容或线索流程，今天不要新增 Agent，只做一件事：在最容易返工的交接处建立一张交付件模板。用最近 3 个真实任务回填，检查是否能回答：结论从哪里来？还缺什么？谁有资格接手？如果答不上来，先修接口，再谈扩充角色。
