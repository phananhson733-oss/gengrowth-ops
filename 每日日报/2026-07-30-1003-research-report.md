今天读什么｜别把“全权限 Bot”当捷径：给 Agent 发一次性能力凭证

### 1. 适合谁读 / 预计阅读时间
适合已经让 AI 查资料、整理线索、写内容、读写表格、创建任务或准备外联草稿的人。尤其适合这样的团队：同一个 Bot 同时拿着云盘、CRM、邮件、发布后台的长期权限；虽然日常方便，但一旦任务理解错了、网页里混入诱导文字，或某个工具参数出错，影响范围会远大于这一次任务。预计阅读约 10 分钟。

### 2. 为什么值得读
很多工作流谈“是否审批”，却忽略一个更早的问题：**Agent 此刻到底看得见哪些工具、能碰哪些对象、权限会持续多久？**

常见做法是给一个通用 Agent 配置一把长期有效的“万能钥匙”，再在提示词里提醒它谨慎。这对原型很快，对生产却很脆弱。OWASP 将这类风险归为“过度代理能力”：问题不只在模型会不会犯错，还在系统给了它不必要的功能、权限与自主性。OpenAI 也明确区分两件事：先决定 Agent 可见哪些工具；再为有副作用的调用设置审批。把两者混成一条“请小心操作”的提示，不能形成可靠边界。

更好的设计不是让 Agent 永远权限更低，而是把权限变成按任务、对象、动作和时间签发的**能力凭证**：它这次可以读取哪份资料、只能为哪个客户生成草稿、是否允许真正写入、多久后自动失效。模型负责提出动作；系统负责发钥匙、验钥匙和收钥匙。

### 3. 核心概念
**第一，工具可见性不等于执行许可。** 研究 Agent 根本不应看见“删除文档”“发送邮件”；即使能看见“更新 CRM”，也不等于可直接写入。可见性缩小误调用面，许可决定一次调用能否落地。

**第二，权限要同时限定四个维度。**
- **动作**：只读、建草稿、更新字段、发送、删除分别授权；“写入”不是一个权限。
- **对象**：限定客户 ID、项目、文件夹、表格行或允许域名，不能只写“可访问 CRM”。
- **范围**：限定可改字段、单次数量、金额/频率上限，以及是否允许附件或外链。
- **时效**：凭证在短时间或单次运行后失效，任务取消、规则变更或人工撤回时立即作废。

**第三，Agent 的自然语言意图不是授权。** “把这批客户同步一下”只是候选动作。系统应把它编译成结构化请求：`动作=创建草稿；对象=本次名单；数量≤20；到期=30分钟`，再用确定性规则核验。网页、邮件、文档里的文字也只能当数据，不能扩展这张凭证。

**第四，审批是签发高风险凭证，而不是点一个泛确认。** 审批卡应展示具体动作、对象范围、影响预览、有效期和回退方式。批准“给 A 客户创建一封草稿”不应顺带允许“向所有联系人发送”。批准后只签发最小范围的短期许可；超出范围重新申请。

**第五，执行端必须二次校验。** 不要只在模型前做一次检查。真正调用邮箱、CRM、云盘时，工具服务还要检查：凭证是否有效、动作/对象/字段是否匹配、幂等键是否已用、当前状态是否仍允许。这样即便旧任务恢复、模型重复调用或请求被篡改，也不应越权落地。

### 4. 可复用方法
从一条“研究线索→生成外联草稿→人工确认→发送”的链路开始，做一个最小能力表：

1）列出真实动作，而非系统名称：读取官网、保存证据、建联系人草稿、修改 CRM 标签、发送邮件、删除记录。  
2）逐项标出默认权限：读取可自动授权；建内部草稿限对象；外联、发布、删除、改权限默认无权。  
3）把模型输出改为“动作申请”，至少包含动作、对象 ID、字段差异、理由、预期影响与幂等键。  
4）由策略层返回四种结果：拒绝、只给只读凭证、签发一次性草稿凭证、进入人工审批。不要把底层服务账号直接交给模型循环。  
5）在执行回执中记录凭证 ID、规则版本、实际对象、前后摘要和失效时间；凭证本身不要进入日志或模型上下文。  
6）每周看三项：被拒绝的越界申请、过期/未使用凭证、人工批准后仍被二次校验拦住的请求。它们比“Agent 是否说完成”更能暴露流程边界是否合理。

### 5. GenGrowth 可以怎么用
先选风险和复用度都高的“内容线索→客户研究→外联草稿”流程：研究 Agent 仅获公开网页读取与证据包写入权；写作 Agent 只能读取已核证资料、写入草稿库；真正的邮件工具不向前两者暴露。运营人员批准某一批次后，系统只对该名单、该模板版本、该时间窗发出一次发送许可，并设置频率上限与撤销开关。

这样做不会让流程变慢，反而减少“这个 Bot 到底有没有资格做这件事”的临场判断。更重要的是，权限边界可成为产品化资产：把“可读资料范围、草稿规则、审批动作、执行回执”做成客户可见的控制台或服务交付清单，客户买到的不只是文案生成，而是一条可控的增长自动化链路。

### 6. 今日行动
选出当前一个拥有最多外部权限的 Agent，花 30 分钟完成一张四列表：它能做什么动作、能碰什么对象、谁批准、权限何时失效。然后立即做一个低风险改动：把一个不必要的写/删工具从该 Agent 的默认工具列表移除，或将其改为只生成待审批动作。最后用两条反例验收：任务要求处理 A 客户时，是否能触达 B 客户？审批过期后，是否还能重放调用？任一答案为“能”，就先别扩大自动化范围。
