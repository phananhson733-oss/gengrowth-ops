# 短剧数据采集迁移与发行管理平台需求文档（v5.0）

> 本文档是本功能的单一需求与设计依据。彪哥只需阅读这一份即可进入实施计划。
>
> v5.0 已于 2026-09-01 完成逐项方案确认。本文中的“已验证现状”不等于功能已经上线；只有通过第 14 节全部验收项后，才能声称正式交付。

## 1. 一句话目标

把“短剧发行管理”迁移为一套由公司持有的飞书多维表格，并通过现有 Social Bot 提供查询、人工维护、排期、数据同步和进度反馈；TikTok 采集历史继续存本地 SQLite，现有 Google/Social OS 流程保持不变。

## 2. 已锁定决策

以下结论已经确认，实施时不得重新解释成可选项：

1. **飞书多维表格是本功能的正式业务载体**，不再是“最好能上”的可选 P1。
2. **只替换短剧发行管理这个功能的 Google 业务表**。既有 Social OS、TikTok Daily Metrics 和其他 Google Sheet 流程不修改、不退役。
3. 正式 Base **新建**，不修复或复用历史试验 Base。旧 Base 不删除，只保留为只读历史。
4. 正式 Base 由公司成员以用户身份创建，放入公司共享空间或知识库；业务人员拥有正常协作权限，Social Bot 应用只取得最小必要 API 权限。
5. 正式 Base 只保留三张业务表：`账号台账 / 发布记录 / 选剧池`。每日指标历史继续只存 SQLite，不增加第四张“指标快照”表。
6. `选剧池`由人决策和维护。Pengman 或授权 Ops 可以通过明确的 Social Bot 指令维护；采集器、定时任务和自动推荐不得写其人工字段。
7. Social Bot 写操作采用实名 allowlist；其他群成员只读。
8. 自动采集每天北京时间 08:00 运行一次；授权人员可说“同步短剧数据”手动补跑。
9. 手动同步采用异步 `run_id` 模式：立即确认、后台单实例运行、可查询进度、完成后主动回复原会话。
10. 剧 ID 使用 `SD-000001` 形式的可读递增编号，创建后不可修改；现有 16 部剧在迁移时一次性补号。
11. 切换采用七天观察窗口：Base 成为唯一人工录入口，旧 Google 业务表只读，连续七天对账通过后再归档旧表。
12. 实现采用“**短剧专用 Runner + Social Bot Skill**”，不新增 Hermes 核心工具，不新增常驻 HTTP 服务。

## 3. 已验证现状（2026-09-01 只读审查）

### 3.1 当前 Google 业务表

源表：<https://docs.google.com/spreadsheets/d/1BbOcWUVrhRsnuSAs9LcyCuYWTrauPxtJWI12Esao7p0>

| 页签 | 当前实际业务记录 | 说明 |
|---|---:|---|
| 账号台账 | 11 | 粉丝数和数据日期通过 `IMPORTRANGE` 获取 |
| 发布记录 | 71 | 大量预填公式一直铺到空白行；实际业务行按日期/账号/剧/链接判定 |
| 选剧池 | 16 | 人工维护；共有 19 列，其中 I/J/L/N 是空白分隔列 |
| 采集数据 | 130 | `QUERY(IMPORTRANGE(...posts_latest...))` 的实时投影，不迁移 |

当前 Google Sheet 时区是 `America/Los_Angeles`，而采集快照日期使用北京时间。迁移后统一按 `Asia/Shanghai` 解释业务日期；TikTok 原始发布时间继续用带时区的 ISO 时间保存。

### 3.2 当前采集资产

源代码位于：

```text
inbox-pengman/tools/tiktok-public-capture/
```

现有能力：

- `collect_tiktok_public_data.mjs` 抓取 11 个账号和帖子公开指标；
- `persistence.mjs` 写 SQLite，并继续投影到 TikTok Daily Metrics；
- `feishu_sync.mjs` 面向另一张账号资产表，仅更新粉丝和粉丝同步时间；
- `reconcile_published_content.mjs` 面向 AstrologyWiki Markdown 生产记录，不是短剧发布记录适配器；
- `run_scheduled.sh` 当前写死 Pengman 机器路径，默认每天运行六次，且没有跨手动/定时入口的统一单实例锁。

因此：

- 不得把短剧多表逻辑直接塞进现有 `feishu_sync.mjs`；
- 可以复用采集器和 SQLite，但短剧 Base 投影必须使用新适配器；
- 发布匹配器只能复用经过抽取和测试的通用匹配思想，不能直接把现有 Markdown 写入器指向 Base。

### 3.3 历史飞书试验

`inbox-pengman/tools/short-drama-release-manager/` 是历史试验资产，不是生产入口。其旧 `--sync` 会先删除目标表全部记录再全量重建，并且“选剧池”只覆盖旧字段，不能用于人工维护的正式 Base。

历史试验脚本和 Base 保留证据，不删除、不继续运行、不作为回滚生产方案。

### 3.4 目标 Mac mini 与 Social Bot

只读审查确认：

- `ai.hermes.gateway-social` 正在运行，真实入口是飞书 `# social-assistant`；
- Social profile 已识别 Pengman、高璇、马博洋、Lynne、彪哥等 actor；
- 目标机器尚无短剧采集 `.env`、SQLite 或 `com.gengrowth.tiktok-public-capture` launchd 服务；
- 因此“Social Bot 可用”已验证，但“短剧采集已迁机”尚未发生。

## 4. 范围与非范围

### 4.1 本次必须交付

- 在公司共享空间创建正式飞书 Base；
- 建立三张业务表、关系、视图和字段权限；
- 一次性迁移 Google 三张业务表的全部有效记录和人工字段；
- 安全迁移 SQLite 与运行凭证到目标 Mac mini；
- 建立 `shortdrama_ctl` 唯一 Runner；
- 建立短剧专用 Social Bot Skill；
- 每天北京时间 08:00 自动采集和 Base 增量回填；
- Social Bot 查询、人工维护、排期、补链接、记录 RS 收益、手动同步和进度查询；
- `run_id`、单实例锁、结构化日志、审计和终态通知；
- 七天对账、回滚和真实 Social Bot 端到端验收。

### 4.2 明确不做

- 不迁移 `采集数据` 页；
- 不把每日帖子快照复制到 Base；
- 不修改或退役 TikTok Daily Metrics；
- 不修改现有 AstrologyWiki Social OS 的 Sheet、状态机或 Runner；
- 不建立网站、Dashboard Web App 或常驻 HTTP 服务；
- 不依赖飞书自动化/工作流触发采集；
- 不复用旧 Google → 飞书全量重建同步器；
- 不允许 Social Bot 自动生成正式选剧并写入选剧池；
- 不允许 Bot 物理删除业务记录；
- 不允许该流程 commit、push、reset 或清理 `gengrowth-ops`。

飞书目前[官方文档](https://www.feishu.cn/hc/zh-CN/articles/612376356355-%E4%BD%BF%E7%94%A8%E8%87%AA%E5%8A%A8%E5%8C%96%E6%B5%81%E7%A8%8B%E7%9A%84-webhook-%E8%A7%A6%E5%8F%91)已说明基础免费版支持 webhook 触发；v4.1 中“需要高级会员”的判断不再作为事实依据。本方案仍不用该能力，因为已锁定由现有 Social Bot 承担对话入口。

## 5. 总体架构

```text
Pengman / 授权 Ops
        │ 飞书自然语言
        ▼
现有 Social Bot (# social-assistant)
        │ actor 校验 + 短剧 Skill
        ▼
shortdrama_ctl（唯一 Runner）◄──── launchd 每天 08:00
        │
        ├── 单实例锁 + shortdrama_ops.sqlite（Job/Audit）
        │
        ├── 调用现有 TikTok Collector
        │       ├── tiktok_metrics.sqlite（完整历史事实源）
        │       └── 既有 Google/粉丝/生产记录输出保持原样
        │
        ├── ShortDrama Base Adapter
        │       └── 正式 Base（账号台账 / 发布记录 / 选剧池）
        │
        └── run_id 进度与终态 → 原飞书会话
```

### 5.1 组件职责

| 组件 | 只负责 | 不负责 |
|---|---|---|
| Social Bot Skill | 意图识别、actor 校验、固定命令路由、预览和结果转述 | 直接拼裸 Base API、猜测字段、绕过 Runner |
| `shortdrama_ctl` | 业务命令、字段白名单、锁、Job/Audit、Base 读写编排 | 抓 TikTok 页面、修改 Hermes 核心 |
| TikTok Collector | 公开数据采集、SQLite 历史、既有下游输出 | 维护人工业务字段 |
| Base Adapter | 三表结构校验、增量 upsert、读回核对 | 全表删除重建、覆盖人工字段 |
| 正式 Base | 当前业务状态和人工协作 | 保存每日指标历史 |
| SQLite | 采集历史、Job/Audit、可重建投影 | 作为 Ops 日常编辑界面 |

## 6. 飞书 Base 数据模型

### 6.1 表一：账号台账

主键：`账号ID`，取规范化 TikTok 用户名（去除 `@`、转小写），创建后不可修改。

| 字段 | 类型 | 所有者 | 规则 |
|---|---|---|---|
| 账号ID | 单行文本/主字段 | 系统 | 唯一、不可变 |
| 账号名 | 单行文本 | 人工 | 展示名称，默认等于账号ID |
| 主页链接 | 超链接 | 人工/系统 | 规范 TikTok 主页链接 |
| 粉丝数 | 数字 | 采集器 | 只接受完整采集结果 |
| 所属组 | 单选 | 人工 | 保留现有值 |
| 定位垂类 | 单行文本 | 人工 | 保留现有自由文本值 |
| 表现形式 | 单选 | 人工 | 保留现有值 |
| 状态 | 单选 | 人工 | 保留现有值 |
| 数据日期 | 日期 | 采集器 | 北京时间快照日期 |
| 指标同步时间 | 日期时间 | 系统 | 最近成功写入时间 |
| 同步状态 | 单选 | 系统 | `success / partial / failed` |

### 6.2 表二：选剧池

主键：`剧ID`，格式 `SD-000001`。编号只分配一次，不因剧名、日期或平台变化而改变。

| 字段 | 类型 | 所有者 | 规则 |
|---|---|---|---|
| 剧ID | 单行文本/主字段 | 系统 | 递增、唯一、不可变 |
| 剧名 | 单行文本 | 人工 | 必填 |
| 剧分类 | 多选 | 人工 | 将现有逗号分隔值拆成多选 |
| 上线日期 | 日期 | 人工 | 北京时间业务日期 |
| 生命周期 | 单选 | 人工 | 如 `新剧 / 在推` |
| 是否已排期 | 公式/汇总 | 派生 | 根据关联发布记录计算，不由 Bot 写 |
| 备注 | 多行文本 | 人工 | 保留原文 |
| 推荐理由 | 多行文本 | 人工 | 保留原文 |
| RS Boost 分类（待确认） | 多选 | 人工 | 保留字段名称和现有值 |
| 账号组 | 多选 | 人工 | 保留现有值 |
| 账号状态 | 单选 | 人工 | 保留现有值 |
| 平台 | 单选 | 人工 | ReelShort / DramaBox / ShortMax / TopShort / 其他 |
| 语言 | 单选 | 人工 | 保留现有语言选项 |
| 来源 | 多选 | 人工 | Reelshort榜单 / Google Trends / 至真选剧台，可扩展 |
| 推荐人 | 多选 | 人工 | 彭满 / 高璇 / 马博洋，可扩展 |
| 关联发布记录 | 双向关联 | 系统 | 一部剧可关联多条发布记录 |
| 归档状态 | 单选 | 人工 | `active / archived`，替代物理删除 |
| 创建人/创建时间/最后修改时间 | 系统字段 | 系统 | 审计使用 |

Google 的 I/J/L/N 空白分隔列不迁移。选剧池除 `剧ID`、派生关系和系统审计字段外，不接受采集器或定时任务写入。

### 6.3 表三：发布记录

主键：系统生成的不可变 `发布ID`，格式 `SR-000001`。一条发布记录关联一个账号和一部剧；非空 `Post ID` 必须全局唯一。

| 字段 | 类型 | 所有者 | 规则 |
|---|---|---|---|
| 发布ID | 单行文本/主字段 | 系统 | 唯一、不可变 |
| 日期 | 日期时间 | 人工 | 排期或业务日期，按北京时间解释 |
| 账号 | 关联账号台账 | 人工 | 必填 |
| 账号名 | Lookup | 派生 | 由账号关联带出 |
| 主页链接 | Lookup | 派生 | 由账号关联带出 |
| 剧 | 关联选剧池 | 人工 | 必填 |
| 剧ID/剧名/剧分类 | Lookup | 派生 | 由剧关联带出 |
| 剧ID（RS Boost） | 单行文本 | 人工 | 可选外部 ID |
| 视频链接 | 超链接 | 人工/采集器 | 人工值优先，采集器不得覆盖不一致值 |
| Post ID | 单行文本 | 人工/采集器 | 非空唯一，人工值优先 |
| 播放量/点赞/收藏/转发/评论 | 数字 | 采集器 | 最新完整值；`null` 不得写成 0 |
| RS收益 | 数字 | 人工 | 手动维护 |
| 备注 | 多行文本 | 人工 | 保留原文 |
| 发布状态 | 公式 | 派生 | 见下方状态规则 |
| 指标日期 | 日期 | 采集器 | SQLite 最新快照日期 |
| 匹配方式 | 单选 | 系统 | `manual_url / exact_post_id / account_time` |
| 匹配置信度 | 数字 | 系统 | 仅辅助匹配时填写 |
| 指标同步时间 | 日期时间 | 系统 | 最近成功写入时间 |
| 同步错误 | 多行文本 | 系统 | 只存可公开诊断，不含凭证 |
| 归档状态 | 单选 | 人工 | `active / archived` |

发布状态规则：

```text
无 Post ID/链接，且计划时间在未来   → 已排期
无 Post ID/链接，且计划时间已到     → 待公开
已有 Post ID/链接，但未得到完整指标 → 已公开
已有 Post ID/链接，且指标读回成功   → 已回填
```

### 6.4 正式视图与可视化

正式 Base 至少提供以下共享视图，不依赖第四张快照表：

| 表 | 视图 | 用途 |
|---|---|---|
| 账号台账 | 在用账号 / 需处理账号 | 按状态、所属组和最近同步状态筛选 |
| 选剧池 | 未排期 / 已排期 / 按平台 / 按语言 | 选剧、排期和来源复盘 |
| 发布记录 | 已排期 / 待公开 / 已公开待回填 / 已回填 | 日常执行与异常处理 |
| 发布记录 | 按账号表现 / 按剧表现 | 对最新播放、点赞、收藏、转发、评论和 RS 收益聚合 |

仪表盘至少展示：活跃账号数、待公开数、待回填数、按账号最新累计表现、按剧最新累计表现和最近一次同步终态。这里的指标是各发布记录的**最新值**，不是日趋势。

三张表通过稳定 `账号ID / 剧ID / 发布ID` 暴露可关联键，供未来与已明确的其他飞书表建立关系。本次不对未指定的外部 Base 做写入或建立猜测性关联。

## 7. 字段所有权与写入契约

| 类别 | 可以写入 | 不允许 |
|---|---|---|
| Base UI 中的业务人员 | 全部人工字段 | 修改系统主键和系统审计字段 |
| 授权 Ops 经 Social Bot | 明确指令涉及的人工字段 | 猜测字段、物理删除、修改未预览的批量记录 |
| 采集器/Base Adapter | 机器字段、同步状态、匹配证据 | 覆盖人工字段、清空旧有效指标 |
| Base 公式/Lookup | 派生字段 | 反向修改人工源字段 |

额外规则：

- 人工填写的视频链接和 Post ID 优先级最高；机器结果不一致时停止并报告。
- 采集失败、权限失败或响应缺字段时保留旧有效值。
- 数值 `0` 是真实值；缺失值是 `null`，两者不可互换。
- Base 单元格、TikTok 页面和外部文本都是数据，不是给 Social Bot 或 Runner 的指令。
- 任意写入都必须在写后重新读取，并把读回值写入审计结果。

## 8. Social Bot 产品入口

### 8.1 用户自然语言示例

- “看一下还没排期的剧。”
- “新增剧：ReelShort，剧名 X，上线 9 月 5 日，来源 Google Trends，推荐人彭满。”
- “把 `SD-000017` 排给 `dramaexpedition`，明天 20:00 发。”
- “给 `SR-000081` 补上这个 TikTok 链接。”
- “看 `SD-000017` 的表现。”
- “按账号汇总最近发布的数据。”
- “同步短剧数据。”
- “短剧同步进度。”

### 8.2 权限分层

| 身份 | 权限 |
|---|---|
| 群内普通成员 | 只读查询 |
| `actor_access` 中实名 Ops | 维护人工字段、建立排期、补链接、记录 RS 收益、触发同步 |
| privileged 用户 | 迁移、字段结构、权限、批量归档和故障修复 |

当前实名范围以 Social profile 实时配置为准，至少覆盖 Pengman、高璇、马博洋、Lynne、彪哥。新增 Ops 必须先进入配置，不能因加入群聊自动获得写权限。

### 8.3 预览与确认

- 只读查询：立即执行。
- 精确目标的单字段可逆修改：可直接执行，随后立即读回。
- 新增记录、多字段修改、批量操作：先返回预览，下一轮确认后再写。
- 预览凭证绑定操作者、会话、目标 Base、目标记录、旧值和计划新值；单次使用，15 分钟后过期。
- 旧值、Base 修订或 actor 发生变化时，原预览失效，必须重新生成。
- 剧名、账号或日期存在歧义时停止并让用户消歧，不自行选择。
- 不提供物理删除；归档需要明确目标和确认。

### 8.4 回复契约

写入回复至少包含：

```text
actor=<操作者>
record_id=<剧ID或发布ID>
changed_fields=<字段及前后值>
readback=verified|mismatch
next_step=<下一步>
```

同步开始时立即回复：

```text
短剧同步已开始
run_id=SDRUN-YYYYMMDD-HHMMSS
triggered_by=<操作者或 schedule>
state=running
```

终态主动回复：

```text
state=success|partial|failed
accounts_updated=<数量>
releases_updated=<数量>
manual_fields_changed_by_sync=0
errors=<结构化错误摘要>
next_step=<下一步>
```

`started` 不等于成功；没有终态、读回和计数时不得声称同步完成。

## 9. `shortdrama_ctl` Runner 契约

Runner 是唯一写入口。Social Skill、launchd 和人工诊断都只能调用其固定子命令，不允许直接拼裸 Base API。

Runner 命令面必须覆盖：

```text
shortdrama_ctl doctor
shortdrama_ctl migrate plan|apply|verify
shortdrama_ctl pool list|get|create|preview-update|apply-update|preview-archive|apply-archive
shortdrama_ctl release list|get|schedule|preview-update|apply-update|attach-post
shortdrama_ctl metrics by-drama|by-account
shortdrama_ctl sync start|status
```

实现要求：

- 目标路径和 Node 运行时均从安装时解析，不保留 `/Users/pengman/...` 硬编码；
- `shortdrama_ops.sqlite` 持久化 Job、actor、原消息路由、状态、步骤计数和审计；
- 定时和手动同步共享同一个跨进程锁；
- 重复触发返回现有 `run_id`，不启动第二轮；
- 连续写同一 Base 表时串行执行，单批不超过 200 条；遇到服务端限流时优先遵守 `Retry-After`，否则最多重试 3 次并采用递增等待，不能无限重试；
- 日志按 `run_id` 关联，并对 app secret、token、授权头和本地凭证路径做脱敏；
- 进程重启后仍能查询已持久化 Job 终态；
- 完成通知只能发回原始请求会话或已配置的运维会话，不能接受任意用户提供的 chat_id。

## 10. 采集与 Base 回填流程

```text
触发
  → actor/调度校验
  → 获取单实例锁
  → 创建 run_id
  → 运行现有 TikTok Collector
  → 先写 tiktok_metrics.sqlite
  → 既有 Google/粉丝/生产记录输出继续执行
  → Base Adapter 读取 SQLite 最新完整数据
  → 校验 Base schema 和字段类型
  → 账号增量 upsert
  → 发布匹配与增量 upsert
  → 写后读回
  → Job 终态与审计
  → Social Bot 原会话通知
```

发布匹配优先级：

1. 人工视频链接；
2. 精确 Post ID；
3. 唯一且高置信的账号 + 发布时间窗：有精确计划时间时要求同账号 ±6 小时内只有一个未占用候选；只有日期时要求该账号北京时间同一自然日内只有一个未占用候选。

账号和时间窗出现多个候选时返回 `ambiguous_post_match`，列出候选供人选择，不自动写入。

## 11. 错误与恢复契约

| 状态码 | 触发条件 | 系统动作 | 用户看到 |
|---|---|---|---|
| `already_running` | 已有活跃同步 | 返回现有 run_id | 当前任务和进度 |
| `capture_failed` | 采集未形成可信输出 | 不更新 Base 指标 | 失败阶段和重试建议 |
| `capture_partial` | 仅部分账号/帖子完整 | 只更新完整字段 | partial、成功/失败数量 |
| `base_auth_failed` | app scope 或资源权限不足 | 停止写入 | 缺少的权限和目标 Base |
| `base_schema_drift` | 字段或关系与确认 schema 不符 | fail closed | 漂移字段，不自动改 schema |
| `ambiguous_post_match` | 多个候选无法唯一关联 | 不写关联 | 候选列表和人工选择要求 |
| `base_rate_limited` | Base 返回限流 | 有界退避重试 | 未写范围和下次动作 |
| `readback_mismatch` | 写后读回不一致 | 不报告成功 | 目标记录和不一致字段 |
| `notification_failed` | 数据完成但消息发送失败 | 保留真实数据终态 | 进度查询显示通知失败 |

任何分页不完整、表读取失败或字段不可用都必须显示“partial/unavailable”，不能解释成有效零条。

## 12. 安全与权限

- Base 由公司用户创建，Social Bot 应用只授予三张目标表所需的最小权限。
- `.env`、Google 服务账号 JSON、飞书 app secret 和 token 通过安全通道迁移，禁止写入 Git、日志、回复和审计正文。
- Runner 只接受固定子命令、固定表 ID 和固定字段 schema，不接受任意 shell、URL、文件路径或 Base token。
- 所有写请求先做 actor 校验；权限错误不得自动降级为更高权限身份。
- 自由文本在写入 Base 前做长度和类型校验，但不得把业务文本当命令执行。
- 物理删除、全表清空、字段删除、关闭高级权限不属于普通 Ops 能力。
- 必须使用 Base 高级权限/角色或等价的字段保护，限制普通业务人员修改主键、机器字段和系统审计字段；若当前租户无法提供可验证的字段级保护，正式切换阻塞，不降级为靠口头约定保护。
- schema 更新和迁移 apply 仅 privileged 用户可执行，并在动作发生时再次确认。
- 旧 Google 表切换只读、正式 Base apply、launchd 安装和生产重启均是后续实施动作；本文确认不等于已经授权具体生产操作。

## 13. 迁移与七天切换

### 阶段 0：实施前检查

1. 确认目标 Mac mini 的真实用户名、仓库路径、Node、可选 yt-dlp 和网络。
2. 确认 Social gateway、actor_access 和原会话消息能力。
3. 由公司用户创建正式 Base，并提供真实 Base URL。
4. 读取 Base 返回的真实 app/table/field ID，不从旧 `.env` 猜测。
5. 读取迁移时 Google 三表实时记录数和字段结构。
6. 通过安全通道迁移 SQLite 与凭证，并验证文件大小、表结构和校验和。

### 阶段 1：备份和建表

- 备份 Google 三张业务表的值、公式、验证规则、格式和元数据；
- 备份旧 Base 试验资产的 URL/结构，仅作为历史证据；
- 建立正式 Base 字段、关联、视图和系统字段；
- 运行 `migrate plan`，只输出计划和差异，不写数据。

### 阶段 2：一次性迁移

- 迁移账号台账；
- 按当前选剧池可见顺序为现有剧分配 `SD-000001...`；
- 迁移选剧池全部人工字段；
- 为发布记录生成稳定发布 ID，并解析账号/剧关联；
- 不迁移 `采集数据`；
- 写后逐条核对主键、关系、人工字段和数量；
- 任何歧义行进入阻塞清单，不静默跳过。

### 阶段 3：切换

- Base 成为唯一人工录入口；
- 旧 Google 业务表切换为只读；
- TikTok Daily Metrics 和其他既有流程保持原样；
- launchd 改为北京时间 08:00 调用 `shortdrama_ctl sync start`；
- 手动“同步短剧数据”走同一 Runner 和同一锁。

### 阶段 4：七天观察

连续七天每天核对：

- 迁移批次记录保持完整；Base 当前数量等于“迁移基线 + 审计中新增 - 审计中归档”，不要求与只读 Google 总行数持续相等；
- 最新指标与 SQLite；
- 每轮机器同步前后人工字段哈希一致；观察期内经实名用户执行的人工变化以审计记录单独核对；
- 重复剧 ID、发布 ID、Post ID；
- Job 终态和原会话通知；
- 旧 Google 和其他 Social OS 流程无意外变化。

七天通过后只归档旧 Google 业务表，不删除；不退役 TikTok Daily Metrics。

### 回滚

若正式 Base 在观察期内不可用：

1. 暂停新 Base 写入和新 launchd 入口；
2. 导出观察期内 Base 新增/修改的人工字段；
3. 恢复旧 Google 业务表编辑权限；
4. 按审计记录补回观察期人工变更；
5. 保留 Base、SQLite、Job/Audit 和错误证据，不删除或清空。

## 14. 测试与验收

### 14.1 自动化测试

- ID 生成和唯一性；
- 字段类型、枚举和长度校验；
- 人工/机器/派生字段白名单；
- `null` 与 `0`；
- 发布状态计算；
- 精确和歧义匹配；
- actor 权限；
- 单次预览、过期和旧值变化；
- 单实例锁和重复触发；
- 分页、限流、partial 和 schema drift；
- 写后读回不一致；
- 通知失败但数据终态仍可查询；
- Skill 路由与 Runner 唯一写入口；
- 旧 Social OS 和现有采集输出回归。

### 14.2 迁移验收

- 执行时实时记录数与迁移读回数一致；
- 账号台账、发布记录、选剧池全部人工字段 100% 对齐；
- `剧ID`、`发布ID`、非空 `Post ID` 无重复；
- 账号和剧关系全部可解析，歧义记录为零或均有显式处置；
- `采集数据`未迁移；
- Base 时区和日期显示符合北京时间；
- 旧 Google 业务表有可恢复备份。

### 14.3 真实环境验收

至少完成：

1. 授权用户通过真实 `# social-assistant` 查询三张表；
2. 授权用户预览并确认一次多字段选剧池写入，随后读回；
3. 未授权用户尝试写入并被拒绝，Base 修订不变；
4. 手动说“同步短剧数据”，立即获得 run_id，最终收到原会话终态；
5. 观察一次真实北京时间 08:00 自然调度成功；
6. 制造一个安全的 partial/canary 场景，确认不覆盖旧指标和人工字段；
7. 七天内每轮同步均返回 `manual_fields_changed_by_sync=0`；实名用户的人工修改全部能在审计中解释；
8. 目标 Base、SQLite、Job/Audit、日志、Social 回复和旧流程读回全部一致。

只有完整观察到自然调度、真实 Bot 会话和 Base 写后读回，才能声称上线。单元测试通过、launchd 已安装、进程已启动或 Bot 回复“已开始”都不等于交付完成。

## 15. 优先级与实施顺序

| 优先级 | 交付 |
|---|---|
| P0 | 目标 Mac mini 环境、SQLite/凭证安全迁移、正式 Base 创建和 schema |

## 16. 完成定义

本需求完成必须同时满足：

- 正式 Base 位于公司共享空间，业务人员和 Social Bot 权限正确；
- 三表数据、关系和人工字段完整；
- 选剧池只能由人直接或经明确 Bot 指令维护；
- 每天 08:00 与手动同步都走唯一 Runner；
- Base 指标来自 SQLite 最新完整值，人工字段未被覆盖；
- Social Bot 查询、写入、进度和终态反馈可用；
- 七天对账通过且回滚可执行；
- 其他 Google/Social OS 流程无变化；
- 全部自动化和真实环境验收通过。
