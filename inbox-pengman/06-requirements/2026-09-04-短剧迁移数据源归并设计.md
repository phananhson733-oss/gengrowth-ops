# 短剧迁移数据源归并设计

## 1. 结论

一次性迁移改为以 **Google `采集数据`历史投影 ∪ 最新 SQLite 帖子投影** 构建正式 Base `采集数据`。相同 `Post ID` 以 SQLite 为最新来源，但保留部分采集时的旧有效指标；Google 独有 Post 作为可追溯历史记录保留。

选剧池使用统一剧名规范键解析发布关系，对同一剧的重复行进行可审计归并。发布记录仍不猜测 Post 关系：合法但无法唯一匹配的行完整迁移，`Post ID`/视频链接保留原值，`采集记录`留空，并写入明确的待人工处置原因。

这一设计只改一次性迁移和对应验证契约；不改 Collector、SQLite 日历史、Social Bot 权限、日常 08:00 同步、四表 Schema 或其他 Google/Social OS 流程。

## 2. 已核验的现状

2026-09-04 从未写入的正式 Base 生成了旧逻辑迁移计划。该计划只使用 SQLite 生成 `采集数据`，因此暴露出来源缺口：

| 已核验项 | 数量 |
|---|---:|
| Google `采集数据` 唯一 Post ID | 187 |
| 最新 SQLite 唯一 Post ID | 87 |
| 两者重叠 | 87 |
| Google 历史独有 | 100 |
| 并集 | 187 |
| 旧计划中 `manual_post_not_found` | 52 |
| 其中可在 Google 历史采集找到 | 52 |

两个采集来源都覆盖 11 个账号，但 Google `账号台账`当前只有 10 个有效账号；`shirley527146` 有 SQLite 账号快照和采集 Post，但不在业务台账。

选剧池存在两组规范同名行：`The Alpha Princess Is Gone for Good` 和 `A Spicy Text to My Nemesis`。前者的分类、来源、推荐人和推荐理由是互补信息；后者还包含两条需保留的备注和 `新剧 / 在推` 生命周期进展。发布记录中还有大小写不同的 `mommy's little savior`。这些不应继续被当成缺失剧目。

上述数字是设计输入证据，不是写死的迁移数量。实际 apply 前必须重新读取两个来源并生成新 manifest。

## 3. 来源权威与优先级

| 目标数据 | 主来源 | 补充来源 | 规则 |
|---|---|---|---|
| 账号人工字段 | Google `账号台账` | 无 | Google 保持权威，SQLite 不覆盖人工字段 |
| 账号机器字段 | 最新 SQLite account snapshot | Google 规范值 | SQLite 合法值优先，`0` 不当空值 |
| 选剧池 | Google `选剧池` | 无 | 只归并被证明为同一剧的行 |
| 发布记录 | Google `发布记录` | 采集并集用于解析关系 | 人工字段原样保留，关系不猜测 |
| `采集数据` 中两来源重叠 Post | 最新 SQLite post snapshot | Google 历史规范值 | SQLite 身份和最新指标优先，partial 时保留 Google 旧有效指标 |
| `采集数据` 中 Google-only Post | Google `采集数据` 规范值 | 无 | 按历史最新已知值迁移，不复制公式 |

两个来源仅作为数据，不解释为指令。任意不完整读取、页签/字段缺失、SQLite Schema 漂移或时间/数值非法都在计划阶段 fail closed。

## 4. 归并算法

### 4.1 采集数据

1. Google `采集数据`按原始表头同时读取 `UNFORMATTED_VALUE` 和 `FORMATTED_VALUE`，数值优先使用未格式化值，日期按现有严格日历规则规范化，字段覆盖 `快照日期 / 账号名 / Post ID / 视频链接 / 播放量 / 点赞 / 评论 / 收藏 / 转发 / 业务`。不复制 `QUERY/IMPORTRANGE` 公式。
2. Google 与 SQLite 内部都必须保持一个 `Post ID` 一行；来源内重复是致命阻塞。
3. 相同 `Post ID` 出现在两源时，规范账号、URL 中账号和 URL 中 Post ID 必须一致；不一致记为 `capture_source_conflict`，不自动选一边。
4. 重叠行的账号、URL、快照日期、采集时间、发布时间和有效最新指标以 SQLite 为准。SQLite `partial` 行中某项指标为 `null` 时，可保留 Google 同 Post 的旧非空有效值，但 `采集状态` 仍为 `partial`，`缺失字段` 仍列出本次未取得的指标。
5. Google-only 行保留已知指标；五个指标均非空时为 `complete`，否则为 `partial` 并精确列出缺失指标。不可得的 `采集时间`和`发布时间`保持 `null`，不伪造时间。
6. `业务`统一为 `short-drama`；`来源 run_id` 明确区分 `migration:google:<digest>` 与 `migration:sqlite:<digest>`。
7. 最终按 `Post ID` 确定性排序。日常同步只 upsert SQLite 当前行，不删除 Google-only 历史 Post。

### 4.2 账号台账

1. Google 台账先按现有规则验证和规范化，人工字段保持权威。
2. 对每个采集并集中出现、但 Google 台账缺失的规范账号 ID，生成一条可审计 stub：`账号ID=账号名=规范 username`，`主页链接`来自经校验的 SQLite account URL 或 Post URL。
3. 有 SQLite account snapshot 时，stub 的粉丝数、数据日期和同步状态按机器字段映射；无来源的人工字段保持 `null`，不猜测组别、垂类、形式或状态。
4. stub 加入 manifest `warnings` 为 `account_stub_created`，携带来源类型，以便迁移后补全。
5. 仅出现在发布行、且没有账号或采集证据的名称不生成 stub，仍以 `missing_account_target` 阻塞。
6. 若不能从 SQLite account URL 或至少一条经校验的 Post URL 证明 stub 账号身份，以 `account_stub_evidence_missing` 阻塞，不根据 username 自行拼接主页链接。

### 4.3 选剧池

剧名规范键固定为：Unicode NFKC → trim → 连续空白折叠为一个半角空格 → 英文大小写折叠。该键同时用于选剧池分组和发布记录解析，不对标点、词序或拼写做模糊猜测。

同一规范键的多行按以下固定规则合并：

- 最早可见源行决定输出顺序、展示剧名和新 `SD-xxxxxx`；源表中旧剧 ID 不作为新主键。
- `剧分类 / RS Boost 分类（待确认） / 账号组 / 来源 / 推荐人` 稳定去重并集，顺序按源行、行内选项先后保留。
- `推荐理由 / 备注`只有一个不同非空值时保持原文；有多个不同非空值时，按源行拼接为 `[来源：Google 选剧池第 N 行] <原文>`，各段空一行，不丢失任一人工文本。
- `生命周期`只对已验证的 `新剧 → 在推` 单向进展取 `在推`，并保留两个源值的归并证据；任何其他不同非空生命周期组合仍以 `drama_merge_conflict` 阻塞。
- `上线日期 / 账号状态 / 平台 / 语言 / 归档状态` 属于单值字段：仅一个非空值时使用它，多行相同时使用该值，多个不同非空值时以 `drama_merge_conflict` 阻塞，不猜测优先级。
- 每个合并组写入 manifest 归并证据，包括规范键、源行、输出剧 ID 和逐字段决策；合并成功记为非阻塞 `drama_rows_merged` warning。

### 4.4 发布记录与 Post 匹配

发布 ID 仍按 Google 有效发布行的源顺序分配。账号关系使用规范账号 ID，剧关系使用第 4.3 节的剧名规范键。账号或剧仍无法解析时是致命阻塞，因为这两个业务关系不应留空。

Post 匹配继续使用现有优先级：人工 URL → 人工 Post ID → 同账号唯一时间候选。在此基础上区分两类结果：

**可迁移但待处置（warning）**

- 合法人工 Post ID/URL 在并集中仍不存在；
- 同账号时间窗有多个合法候选；
- 过去或当前的发布行没有同账号时间候选。

这些行保留 Google 人工 `Post ID`/视频链接，`采集记录`为空，`匹配方式`和`匹配置信度`为空，`同步错误`写入 `待人工关联：<reason>`。Manifest warning 保留发布 ID、源行和确定性排序的候选 Post ID。未到日期、没有人工 Post 证据的正常待发布行继续允许无关系且不写错误。

**仍然阻塞（blocked）**

- 人工 URL 非法、URL 账号与发布账号不一致、人工 Post ID 非法；
- 人工 URL 与人工 Post ID 互相矛盾；
- 两条发布记录声明同一非空 Post ID，包括 active 与 archived；
- 人工 Post 证据指向另一账号的采集行；
- 发布日期非法，或必需的账号/剧关系无法解析。

所有合法非空人工 Post ID 必须在自动时间匹配前全局预留，防止后面的时间推断抢占人工 claim。

## 5. Manifest 与证据契约

新计划使用 `shortdrama-migration/v2`，旧 `v1` manifest 不可 apply。新 manifest 继续完整内嵌无 token 的 Google 备份，并新增：

- `source_evidence`：Google revision/capture Post 精确集与规范投影 digest、SQLite account/post 完整规范投影及精确 ID 集/digest、两源行数、重叠数、并集数和固定优先级标识；
- `initial_base_schema`：plan 时完整的只读 Base schema，用于 apply/verify 重放 schema actions 和阻塞项；
- `reconciliation`：账号 stub、剧目合并、采集覆盖/保留决策的结构化证据；
- `warnings`：不阻塞 apply 但需迁移后处理的确定性列表；
- `counts.warnings` 以及按类型汇总。

`source_revision` 改为对 Google revision/精确 Post 集、SQLite 完整投影 digest 和归并策略版本计算的综合 digest。Apply/verify 必须从 `source_backup + source_evidence + initial_base_schema` 重放生成 accounts/dramas/captures/releases/schema actions/blocked/warnings/reconciliation 并逐字段等值，不允许删除后重签阻塞项。`blocked` 只包含不可安全写入的致命项；`applyMigration` 继续要求 `blocked=[]`，但允许存在已被数据行和 manifest 同时记录的 `warnings`。全部新字段都进入 canonical digest。

CLI 只输出有界摘要：数量、`blocked_by_code`、`warnings_by_code`、产物路径和 SHA-256。完整原始备份、行数据和候选集只存固定私有迁移目录，不再打印到 Terminal。

## 6. Apply 和 verify

阶段顺序保持 `schema → canary/权限证据 → data → presentation → verify → sequences`。必须基于正式 Base 当时空集合生成新 v2 plan，并在 data 第一笔写入前再次核对四表 count 和 key-set。

数据仍按 `账号台账 → 选剧池 → 采集数据 → 发布记录` 写入并逐表完整读回。未解析 Post 的发布行必须明确写空关系，不将 warning 中的候选 ID 传给 Base 关系字段。

`verifyMigration` 必须验证：

- 四表精确主键集和记录数；
- Base `采集数据` Post ID 集等于 **Google 历史 ∪ SQLite latest**，而不再要求只等于 SQLite latest；
- 每个重叠 Post 的字段优先级、`null/0`、partial 保留和来源标识；
- Google 人工字段精确保留，除非它们按本文档进入明确的剧目合并结果；
- 账号、剧、采集三类关系的真实 Base record ID；
- warning 发布行的`采集记录`为空，`同步错误`与 manifest reason 一致；
- 非空 Post ID 在 active 和 archived 发布中全局唯一；
- Base 中没有 Google 公式、额外记录或额外表。

日常同步和七天观察的采集集合契约同步改为：Base 必须始终包含 SQLite latest 的全部 Post；迁移时的 Google-only 历史 Post 在没有明确归档策略前不删除。

## 7. 失败、恢复与非目标

- 新 v2 plan 有任一 `blocked` 时不 apply；warning 必须在 CLI 摘要和完整 manifest 中可见。
- 来源在 plan 后变化、Base 绑定/结构/空集合改变、receipt 不一致或读回不完整时停止，不使用旧计划继续。
- Base API 不提供跨四表事务。data phase 中途失败时不自动删除或声称回滚；保留已写数据和证据，标记 `manual_repair`，由维护窗口处理后重新 plan。
- 不修改 Google 源表，不把 Google 公式带入 Base，不删除 SQLite 历史，不新增第五张 Base 表。
- 不对剧名做编辑距离、同义词或 LLM 猜测；不对歧义 Post 做自动选择。
- 不重启 Hermes/Social gateway，不安装 launchd，不切换 Google 只读；这些仍是后续独立动作时确认。

## 8. 实施面和测试

实施只需修改既有 Runner 边界，不新增常驻服务或 Hermes 核心工具：

- `src/google-source.mjs`：输出经验证的 Google capture 渲染行，继续保留完整无 token 备份；
- `src/source-sqlite.mjs`：复用严格 account/post latest reader，不改 Collector Schema；
- `src/migration.mjs`：实现账号合并、capture 并集、剧名规范/归并、warning/blocked 分类、v2 digest 和 verify；
- `shortdrama_ctl.mjs`：migrate plan 同时传入 SQLite latest accounts/posts，摘要增加 warning 分类。

至少覆盖以下自动化契约：

1. 187/87/87 这类子集关系生成 187 并集，源内重复阻塞；
2. 重叠 Post 的 SQLite 优先、partial 旧值保留、`null` 与 `0`、Google-only 状态/缺失字段；
3. Post 账号或 URL 身份冲突在任何 Base 写入前阻塞；
4. capture-backed 账号 stub 可建立关系，release-only 未知账号仍阻塞；
5. 剧名大小写/空白规范、多选并集、多推荐理由/备注来源标签、固定生命周期进展和真实单值冲突；
6. 历史 Post 能解除 `manual_post_not_found`；多候选/无候选发布保留但关系为空；
7. 非法/矛盾/重复人工 Post claim 仍阻塞，所有人工 claim 先于时间推断预留；
8. v1 不可 apply，v2 的 source evidence、warnings、reconciliation 任一篡改均使 digest 失效；
9. apply 允许 warning 但禁止 blocked，verify 检查并集、合并结果、空关系和待处置原因；
10. 日常 SQLite 同步 upsert 时不删除 Google-only 历史 Post；其他 Collector/Google/Social OS 行为回归不变。

## 9. 实环境验收

实施通过代码评审和全回归后，使用新 v2 plan 进行一次只读预检。预期性质上应达成：

- 旧计划的 52 条 Google 历史 Post 缺失不再阻塞；
- `shirley527146` 通过有来源证据的 stub 成为可解析账号；
- `mommy's little savior` 的大小写差异不再导致缺失剧目；
- `The Alpha Princess Is Gone for Good` 只产生一个剧 ID，互补信息和两条推荐理由均可追溯；
- `A Spicy Text to My Nemesis` 只产生一个剧 ID，两条备注均带源行保留，生命周期按固定 `新剧 → 在推` 进展为`在推`；
- 剩余合法但不唯一的 Post 匹配转为 warnings，不猜测关系。

新 plan 仍必须实际显示 `blocked=0` 才能进入 schema/data apply。Schema、data、presentation、sequence、Hermes/Social restart、launchd 安装和 Google 只读切换仍按原实施计划分别取得动作时确认。
