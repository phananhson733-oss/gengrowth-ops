# Screen Studio 长录屏批量生成短视频自动化实施指南

> 本文件是待实施方案，不代表相关工具已经安装、完成试验或投入运行。目标是把一条无配音的 Screen Studio 长录屏，转成多条带旁白、字幕、Hook 和 CTA 的短视频，并保留人工选题、品牌判断和最终质检。

## 1. 目标与完成定义

### 1.1 目标输入

- 一条 Screen Studio 导出的长录屏，建议保留 1440p 或 4K 原始分辨率。
- 产品基本资料：一句话定位、目标用户、核心功能、允许使用的事实和 CTA。
- 目标平台与语言，例如 TikTok / Instagram Reels / YouTube Shorts，中文或英文。
- 可选：参考短视频、品牌字体、Logo、背景音乐、常用结尾卡。

### 1.2 目标输出

每次处理一条长录屏，输出：

1. 一份带时间点的录屏内容索引。
2. 5–10 个短视频候选方案。
3. Pengman 选择后的 3–5 个正式短视频方案。
4. 每条视频的 Hook、旁白、字幕、画面清单和 CTA。
5. 每条视频一份机器可读的剪辑计划 `edit_plan.json`。
6. 每条视频一份预览 MP4。
7. 兼容性验证通过后，每条视频一份剪映或 CapCut 草稿。
8. 一份自动质检报告和人工检查清单。

### 1.3 完成标准

一条短视频只有同时满足以下条件，才算自动化制作完成：

- 画面来自正确的录屏时间段，没有黑屏、隐私信息或明显加载等待。
- 旁白事实可核验，发音、节奏和画面匹配。
- 字幕时间正确，手机上可读，没有遮挡产品关键操作。
- 9:16 画面中的按钮、输入框和结果区域清晰可见。
- Hook、内容承诺和 CTA 与主生产记录一致。
- 已生成可播放的预览 MP4。
- Pengman 完成人工终审。

## 2. 实施原则

### 2.1 统一剪辑计划，多个输出端

不把业务逻辑直接写死在剪映或 CapCut 草稿中。先生成统一的 `edit_plan.json`，再由不同输出模块处理：

```text
Screen Studio MP4
→ recording_index.json
→ candidate_videos.json
→ Pengman 选择
→ edit_plan.json
→ Preview MP4 / 剪映草稿 / CapCut 草稿
```

这样即使剪映或 CapCut 升级导致草稿不兼容，前面的分析、脚本、配音和剪辑决策仍然可以复用。

### 2.2 一次关键人工选择，两次人工检查

推荐只保留三个必须由人完成的控制点：

1. **候选选择**：从 5–10 个候选中确认要制作的 3–5 个。
2. **脚本与事实确认**：确认 Hook、旁白承诺、产品事实和 CTA。
3. **成片终审**：确认画面、字幕、节奏、隐私和品牌表达。

其余素材抽帧、时间段整理、配音生成、字幕对齐、初剪和技术质检尽量自动完成。

### 2.3 接入现有 Social OS，不新建第二套生命周期

- 未被 Pengman 选中的候选只保留在候选结果中，不创建 `content_stage`。
- 每条被选中并准备生产的视频使用独立 `content_id` 和一份主生产记录。
- 脚本和剪辑方案准备期间保持 `content_stage: selected`。
- 自动化真正开始生成配音、字幕、初剪或草稿时进入 `producing`。
- 自动质检通过且人工终审完成后进入 `ready`。
- 只有存在真实 `published_url`、平台 ID 和实际发布时间后才进入 `published`。
- `analysis_status`、`render_status` 等只允许作为自动化运行日志，不能替代 `content_stage`。

## 3. 工具选择

| 工作 | MVP 推荐工具 | 备选 | 是否需要人工 |
|---|---|---|---|
| 视频信息检查 | FFmpeg / ffprobe | MediaInfo | 无 |
| 抽帧和代理视频 | FFmpeg | OpenCV | 无 |
| 画面理解 | 支持图像输入的视觉模型 API | 本地视觉模型 | 首轮检查结果 |
| 界面文字识别 | 视觉模型直接识别 | PaddleOCR / RapidOCR | 低置信度时确认 |
| 候选与脚本 | LLM + 固定提示词 | 人工编写 | 必须选题、审稿 |
| 配音 | 可返回时间信息的 TTS API | HeyGen、ElevenLabs、系统语音 | 首次确认声音 |
| 字幕对齐 | faster-whisper / whisper.cpp | TTS 原生时间戳 | 抽查专有名词 |
| 预览成片 | FFmpeg | Remotion | 无 |
| 剪映草稿 | pyJianYingDraft | 手工模板替换 | 兼容测试和终审 |
| CapCut 草稿 | pyCapCut | 手工模板替换 | 兼容测试和终审 |
| 技术质检 | FFmpeg + 自定义检查脚本 | 人工检查 | 最终终审 |

### 3.1 当前工具状态边界

- `pyJianYingDraft` 当前公开版本为 `0.3.0`，功能较完整，但新版剪映仍有模板读取、蒙版、轨道顺序和自动导出限制。
- `pyCapCut` 仍在从 `pyJianYingDraft` 迁移，模板和部分视频能力已经提供，批量导出仍标为迁移中。
- 两个项目当前文档都提示：macOS 可以安装并生成草稿，但生成草稿仍需 Windows 版应用导出。
- 因此第一阶段必须先做 5 秒草稿兼容性试验；在试验通过前，不能把“Mac 上自动生成并导出剪映/CapCut 草稿”写成已实现能力。
- 无论草稿是否兼容，FFmpeg 预览 MP4 都应保留，作为稳定的基础输出。

项目资料：

- [pyJianYingDraft](https://github.com/GuanYixuan/pyJianYingDraft)
- [pyCapCut](https://github.com/GuanYixuan/pyCapCut)

## 4. 详细实施步骤

## 步骤 0：一次性确定规则和完成兼容性 Canary

### 自动化要做什么

1. 检查本机 Python、FFmpeg 和目标草稿库是否可用。
2. 读取剪映和 CapCut 当前草稿目录位置。
3. 用一段 5 秒测试视频生成最小草稿，包含：
   - 一条视频轨道；
   - 一条音频轨道；
   - 一行字幕；
   - 一个简单缩放关键帧。
4. 分别尝试生成剪映草稿和 CapCut 草稿。
5. 保存测试日志、生成路径和错误信息。

### 需要的工具

- Python 3.11。
- FFmpeg / ffprobe。
- `pyJianYingDraft`。
- `pyCapCut`。
- 中国剪映桌面版和 CapCut 桌面版。

### Pengman 要做什么

1. 在剪映设置中确认草稿路径。
2. 在 CapCut 设置中确认草稿路径。
3. 分别打开测试草稿，检查视频、声音、字幕和缩放是否正常。
4. 手工导出一次，确认当前 Mac 版本是否真的可以使用生成草稿。
5. 从以下三条路线中确认 MVP 主路线：
   - A：剪映草稿 + 人工导出；
   - B：CapCut 草稿 + 人工导出；
   - C：FFmpeg 直接生成 MP4 + CapCut/剪映最终润色。

### 产物

- `compatibility-report.md`
- `jianying-canary/`
- `capcut-canary/`
- `canary-preview.mp4`

### 通过标准

- 至少一条路线能够稳定打开和导出。
- 如果两种草稿都失败，自动切换到路线 C，不阻塞后续 MVP。

## 步骤 1：导入和检查 Screen Studio 长录屏

### 自动化要做什么

1. 将原始录屏复制或链接到本次运行目录，不修改原文件。
2. 读取总时长、分辨率、帧率、编码和音轨情况。
3. 检测：
   - 是否完全无声；
   - 是否有损坏帧；
   - 是否存在长黑屏；
   - 是否存在长时间静止；
   - 横屏裁成竖屏后是否仍能看清产品界面。
4. 生成低码率代理视频，供后续快速分析。

### 需要的工具

- FFmpeg / ffprobe。
- 可选：MediaInfo。

### Pengman 要做什么

- 确认这条录屏可以用于公开内容。
- 确认没有客户资料、真实邮箱、密码、Token、后台数据或无关标签页。
- 如果存在敏感片段，提供需要排除的时间范围；自动化必须将其加入永久禁用区间。

### 产物

- `source-metadata.json`
- `proxy.mp4`
- `excluded_ranges.json`
- `preflight-report.md`

### 通过标准

- 视频可以完整解码。
- 所有敏感或不可用区间已经标记。

---

## 步骤 2：抽帧、画面变化检测和 UI 索引

### 自动化要做什么

1. 默认每 2 秒抽取一帧。
2. 在画面大幅变化、弹窗出现、页面跳转或结果加载时增加关键帧。
3. 识别每个阶段中的：
   - 页面或功能名称；
   - 可见按钮、输入框和结果；
   - 鼠标重点区域；
   - 页面跳转和操作完成信号；
   - 加载、错误、重复操作和无价值等待。
4. 将连续相同操作合并成一个功能片段。
5. 给每个片段记录置信度和风险。

### 需要的工具

- FFmpeg。
- 感知哈希或场景变化检测脚本。
- 支持图片输入的视觉模型。
- 可选本地 OCR。

### Pengman 要做什么

- 首次运行时快速检查自动生成的功能索引。
- 对“模型不知道这是哪个功能”的片段补一个名称。
- 确认哪些操作是对外最有价值的真实功能，哪些只是内部调试。

### 产物

- `frames/`
- `frame-analysis.jsonl`
- `recording-index.json`
- `recording-index.md`

### `recording-index.json` 最小字段

```json
{
  "start": 190.0,
  "end": 245.5,
  "feature": "生成报告",
  "visible_text": ["Generate", "Report"],
  "action": "点击生成并展示结果",
  "quality_score": 0.91,
  "privacy_risk": false,
  "notes": "中间有 4 秒加载等待"
}
```

### 通过标准

- 每个主要产品操作都有开始时间、结束时间和功能说明。
- 敏感区间和加载等待没有被标成可用卖点画面。

## 步骤 3：生成短视频候选

### 自动化要做什么

根据录屏索引和产品 Brief，生成 5–10 个候选。每个候选必须包含：

- 候选标题和内容角度。
- 目标用户和用户问题。
- 1–2 句 Hook 备选。
- 预计时长。
- 所需的原视频时间段。
- 为什么这些片段能够支撑内容承诺。
- 是否需要补录画面。
- 产品事实、CTA 和待确认项。

候选应覆盖不同意图，而不是只把同一段视频换标题：

- 产品总览。
- 单一核心功能。
- Before / After。
- 一步步教程。
- 常见错误或隐藏功能。
- 结果展示或速度证明。

### 需要的工具

- LLM。
- 固定候选生成提示词。
- `recording-index.json` 和产品 Brief。

### Pengman 要做什么

- 从候选中选出 3–5 个正式制作项。
- 删除价值弱、承诺过大或和账号定位不符的候选。
- 确认目标平台、账号、语言和 CTA。
- 只有这一步确认后，才为每条视频建立独立 `content_id` 和主生产记录。

### 产物

- `candidate-videos.md`
- `candidate-videos.json`
- 人工选择结果。

### 通过标准

- 每个被选中的候选都能由现有录屏画面真实支撑。
- 未选候选不进入正式生产，不生成配音和草稿。

---

## 步骤 4：生成并确认每条视频的 Brief 和脚本

### 自动化要做什么

对每个已选候选生成：

1. 一句短 Hook。
2. 旁白脚本。
3. 逐句画面对应关系。
4. 屏幕文字。
5. CTA。
6. 预计朗读时长。
7. 需要核验的产品事实。

脚本应从观众的问题或结果出发，避免把录屏机械描述成“现在我点击这里”。画面可以展示操作，旁白负责解释价值。

### 需要的工具

- LLM。
- 产品 Brief、候选方案和录屏索引。
- 现有统一内容 Brief 模板和主生产记录。

### Pengman 要做什么

- 确认 Hook 是否值得停留。
- 确认所有产品能力、效果和数据表达真实。
- 确认语气、语言、CTA 和最终脚本。
- 在主生产记录写入 `script_status: 已确认` 和确认版本。

### 产物

- 每条内容主生产记录中的确认 Brief 和脚本。
- `script.txt`
- `visual-beats.json`

### 通过标准

- 没有未经证实的效果承诺。
- 每一句旁白都有对应画面或明确的辅助视觉。
- 未确认脚本不进入配音和批量剪辑。

---

## 步骤 5：生成配音

### 自动化要做什么

1. 将已确认脚本提交给选定的 TTS 工具。
2. 使用固定声音、语速和情绪参数。
3. 保存音频、调用参数、成本信息和返回的时间数据。
4. 检查空白时长、峰值音量和总时长。
5. 如果旁白比目标时长过长，先生成返修建议，不自动删改已确认事实。

### 需要的工具

- 首选：能够 API 调用并返回稳定音频的 TTS。
- 可选：HeyGen、ElevenLabs 或其他已授权工具。
- FFmpeg 做音量和时长检查。

### Pengman 要做什么

- 第一次只需确认声音、语速、情绪和品牌适配。
- 抽查专有名词、产品名和英文缩写发音。
- 需要付费 API 时，明确授权预算和凭证保存方式；API Key 不写入仓库。

### 产物

- `voiceover.wav` 或 `voiceover.mp3`
- `voice-generation.json`
- 配音检查结果。

### 通过标准

- 发音正确、节奏自然、没有异常长停顿。
- 音频长度在目标时长允许范围内。

---

## 步骤 6：生成并对齐字幕

### 自动化要做什么

1. 使用最终配音重新转录或读取 TTS 时间戳。
2. 将长句切成适合手机阅读的短字幕。
3. 校对产品名、按钮名、数字和专有名词。
4. 输出 SRT 和结构化字幕 JSON。
5. 检查字幕重叠、空白和过长行。

### 需要的工具

- faster-whisper 或 whisper.cpp。
- FFmpeg。
- 字幕清洗脚本。

### Pengman 要做什么

- 抽查专有名词和字幕断句。
- 确认字幕语言和屏幕 UI 语言是否匹配。

### 产物

- `subtitles.srt`
- `subtitles.json`
- `subtitle-qc.json`

### 通过标准

- 字幕和声音基本同步。
- 字幕不遮挡产品关键按钮和结果区域。
- 没有拼写错误或超长字幕块。

---

## 步骤 7：生成统一剪辑计划

### 自动化要做什么

把脚本、配音时间、录屏索引和视觉节奏合并成 `edit_plan.json`：

```json
{
  "content_id": "gg-screen-demo-01",
  "source": "product-demo.mp4",
  "canvas": {"width": 1080, "height": 1920, "fps": 30},
  "voiceover": "voiceover.wav",
  "subtitles": "subtitles.srt",
  "segments": [
    {
      "source_in": 35.2,
      "source_out": 42.8,
      "timeline_in": 0.0,
      "speed": 1.25,
      "focus": {"x": 0.62, "y": 0.45, "zoom": 1.35},
      "purpose": "展示创建入口"
    }
  ],
  "hook_text": "30秒看懂这个产品",
  "cta": "Try it yourself"
}
```

计划生成时要自动处理：

- 删除加载等待。
- 根据旁白缩短或加速画面。
- 计算横屏录屏在 9:16 中的裁切和焦点。
- 关键点击前后保留足够观看时间。
- 禁止使用 `excluded_ranges.json` 中的片段。
- 记录所有自动决定的理由和置信度。

### 需要的工具

- LLM 或规则引擎。
- Python 时间轴处理模块。
- 前面所有结构化产物。

### Pengman 要做什么

- 正常情况下无需逐时间点编辑。
- 只在系统报告低置信度、隐私风险或需要补录时处理。

### 产物

- `edit_plan.json`
- `edit_plan.md`
- `unresolved-items.md`

### 通过标准

- 所有片段时间合法、不重叠、不超出源视频时长。
- 画面总时长与配音总时长匹配。
- 不包含敏感或禁用区间。

## 步骤 8：自动生成预览 MP4

### 自动化要做什么

1. 根据 `edit_plan.json` 裁切和拼接录屏。
2. 生成 9:16 画布。
3. 对重点区域进行缩放和平移。
4. 添加配音、字幕、Hook、CTA 和可选背景音乐。
5. 输出带时间码的内部审核版和干净预览版。

### 需要的工具

- MVP：FFmpeg。
- 需要复杂动态布局时：Remotion。

### Pengman 要做什么

- 查看预览，重点判断内容是否好看、好懂、节奏是否自然。
- 标记需要补录、换 Hook、换画面或调整停留时间的位置。

### 产物

- `preview-review.mp4`
- `preview-clean.mp4`
- `render-log.json`

### 通过标准

- 视频可完整播放，没有黑帧、花屏、音画断裂。
- 关键操作在手机尺寸下可读。
- 第一条路线 C 的 MP4 在此步骤已经达到可人工精修状态。

---

## 步骤 9：生成剪映或 CapCut 草稿

### 自动化要做什么

根据步骤 0 确定的主路线：

- 路线 A：用 `pyJianYingDraft` 建立中国剪映草稿。
- 路线 B：用 `pyCapCut` 建立 CapCut 草稿。
- 将视频、配音、字幕、Hook 和 CTA 放入独立轨道。
- 保存素材绝对路径、草稿路径和生成日志。
- 不自动覆盖同名人工草稿；新草稿名称必须包含 `content_id` 和生成时间。

### 需要的工具

- `pyJianYingDraft` 或 `pyCapCut`。
- 剪映或 CapCut 桌面版。

### Pengman 要做什么

- 打开草稿确认轨道顺序、字体、字幕、特效和素材路径。
- 完成必要的品牌润色和复杂特效。
- 在新版应用不兼容时，直接使用预览 MP4 继续，不等待草稿修复。

### 产物

- 剪映或 CapCut 草稿。
- `draft-generation-report.md`

### 通过标准

- 草稿可打开，素材不离线，时间轴结构正确。
- 草稿失败不会影响预览 MP4 和其他内容的批量处理。

---

## 步骤 10：自动质检和人工终审

### 自动化要做什么

技术检查：

- 分辨率是否为 1080×1920。
- 帧率和编码是否符合目标平台。
- 是否存在黑帧、静音、削波或异常长静止。
- 字幕是否越界、重叠或过长。
- Hook 是否在前 1 秒内出现。
- CTA 是否存在但不过长。
- 文件是否完整、可解码。

内容检查辅助：

- 列出所有数字、产品能力和效果承诺。
- 列出可能暴露隐私的帧。
- 对脚本、字幕和最终配音做文本一致性比较。

### 需要的工具

- FFmpeg / ffprobe。
- 自定义 QA 脚本。
- 视觉模型做风险帧复查。

### Pengman 要做什么

人工终审以下项目：

- 前 2 秒是否值得停留。
- 产品卖点是否真实且清楚。
- 画面焦点是否跟得上旁白。
- 字幕、颜色、字体是否符合品牌。
- 是否展示敏感信息。
- CTA 是否适合目标账号和平台。
- 是否需要在 CapCut/剪映中做最后润色。

### 产物

- `qa-report.md`
- `qa-report.json`
- 人工终审结果。

### 通过标准

- 自动 QA 没有阻断错误。
- Pengman 明确通过终审。
- 对应主生产记录可以更新为 `content_stage: ready`。

## 步骤 11：导出、归档和回写主生产记录

### 自动化要做什么

1. 将最终 MP4、SRT、封面、剪辑计划和 QA 报告放入同一 `content_id` 输出目录。
2. 记录最终文件校验值，避免误用旧版本。
3. 将生成路径、工具版本、运行时间和实际成本写入主生产记录的制作区块。
4. 保留最终输入、决策和日志；可重新生成的抽帧缓存可以后续清理。

### 需要的工具

- 文件归档脚本。
- 现有主生产记录。
- 平台发布工具只在另行确认已连接和授权后使用。

### Pengman 要做什么

- 在剪映或 CapCut 中完成最终导出，或确认 FFmpeg 输出就是最终版。
- 手工发布或使用当前已确认的发布路径。
- 发布后补充真实 `published_url`、平台 ID 和实际发布时间。
- 复盘后填写 `decision / next_test`。

### 产物

```text
output/screen-recording-multicut/YYYY-MM-DD-project/
├── source/
├── analysis/
├── candidates/
├── selected/
│   └── content-id/
│       ├── script.txt
│       ├── voiceover.wav
│       ├── subtitles.srt
│       ├── edit_plan.json
│       ├── preview.mp4
│       ├── final.mp4
│       └── qa-report.md
└── run-report.md
```

### 通过标准

- 每条内容只有一个当前主生产记录。
- 自动化产物可以通过 `content_id` 回溯。
- 未获得真实发布证据时不标记 `published`。

## 5. 人工工作总表

| 阶段 | Pengman 必须做的事 | 预计频率 |
|---|---|---|
| 初次设置 | 选择剪映/CapCut/MP4 路线，确认声音、字幕和品牌模板 | 一次 |
| 每条长录屏 | 确认公开权限和敏感区间 | 一次 |
| 候选阶段 | 从 5–10 个候选中选 3–5 个 | 每批一次 |
| 脚本阶段 | 确认 Hook、事实、承诺和 CTA | 每条一次，可批量 |
| 配音阶段 | 首次确认声音；以后只抽查发音 | 首次 + 抽查 |
| 预览阶段 | 判断节奏、清晰度和是否需要补录 | 每条一次 |
| 最终阶段 | 隐私、品牌和发布级终审 | 每条一次 |
| 发布后 | 补真实链接、平台 ID、时间和复盘 | 每条一次 |

不应要求 Pengman：逐帧标注整条长录屏、手工重新输入所有字幕、为每个候选建立主记录、重复维护另一张状态表。

## 7. 实施顺序

### Phase 0：兼容性验证

- 完成 5 秒剪映和 CapCut Canary。
- 确认 Mac 上实际能打开、修改和导出的路线。
- 失败时确定 FFmpeg MP4 为稳定主输出。

### Phase 1：单条视频端到端 MVP

- 输入一条代表性长录屏。
- 自动生成录屏索引和 5 个候选。
- 人工选 1 个。
- 生成脚本、配音、字幕、剪辑计划和预览 MP4。
- 完成人工 QA。

### Phase 2：一条长录屏生成 3–5 条

- 批量生成多个独立 `content_id` 输出。
- 复用相同声音、字幕样式和结尾 CTA。
- 检查不同视频之间是否重复过多。

### Phase 3：草稿输出和模板化

- 接入已通过 Canary 的剪映或 CapCut 路线。
- 建立一个受控模板，不覆盖人工草稿。
- 固定 Hook、字幕和 CTA 轨道规范。

### Phase 4：稳定运行

- 增加失败重试、成本记录、缓存和批处理。
- 把近期成功日志作为“已部署”的证据。
- 只有稳定运行后，才评估自动发布或更复杂的多平台变体。

## 8. MVP 验收测试

选择一条 5–15 分钟、无配音、包含至少三个产品操作的 Screen Studio 录屏，完成以下测试：

1. 自动识别至少 80% 的主要操作步骤。
2. 生成至少 5 个不完全重复的短视频候选。
3. 人工选择 3 个后，可以生成 3 条 20–60 秒预览。
4. 三条预览都不包含禁用或敏感区间。
5. 字幕和旁白基本同步，产品名无错误。
6. 关键 UI 在手机尺寸下清晰可读。
7. 至少一个剪映或 CapCut 草稿能够打开；若不能，FFmpeg MP4 路线仍然完成。
8. 每条输出都能通过 `content_id` 回溯脚本、原片时间段和 QA 报告。

## 9. 主要风险与处理

| 风险 | 处理方式 |
|---|---|
| 无声音导致模型不理解操作目的 | 结合 UI 文字、画面变化和一次人工功能命名 |
| 横屏 UI 裁成竖屏后看不清 | 高分辨率源文件、重点区域动态缩放、必要时上下布局 |
| Screen Studio 已经烘焙缩放动画 | 分析时识别现有缩放，避免再次过度放大 |
| 录屏出现隐私数据 | 预先标记永久禁用区间，QA 再做视觉检查 |
| TTS 时长与画面不匹配 | 优先调整画面速度和停留；改稿需重新确认 |
| 剪映/CapCut 更新破坏草稿 | 保留统一剪辑计划和 FFmpeg 稳定输出 |
| 新版桌面应用无法自动导出 | 人工导出，或直接使用 FFmpeg/Remotion 最终渲染 |
| 自动候选承诺超过产品能力 | 脚本事实确认作为强制人工门 |
| 批量视频内容过于重复 | 候选阶段按不同用户意图和不同证据片段去重 |
| API 成本或凭证风险 | 设置单次/单批预算，凭证不进入仓库，记录实际消耗 |

## 10. 当前结论

建议采用以下 MVP：

```text
视觉分析 + 人工选题
→ 自动脚本初稿 + 人工确认
→ TTS + Whisper 字幕
→ edit_plan.json
→ FFmpeg 稳定预览 MP4
→ 通过 Canary 的剪映或 CapCut 草稿
→ 人工终审和导出
```

第一项实际工作不是安装全部工具，而是完成“5 秒草稿兼容性 Canary”。它决定后续以中国剪映、CapCut，还是 FFmpeg MP4 作为主输出。无论结果如何，统一剪辑计划都应作为自动化的长期核心。
