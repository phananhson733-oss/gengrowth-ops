先给一句定义：

｜ Social OS 是一套以 Google Sheet 为控制面、以人工确认门控制风险、以 runner 执行机器写入的社媒闭环系统。
｜ 它把“证据 → 选题 → 审批 → 口播稿 → 文案包 → 人工制作与发布 → 数据回收 → 复盘学习”串在同一个 content\_id 下。

先纠正这次暴露出的一个问题

Social OS 中，title 和 hook 是两个独立字段：

• title：内部识别选题的标题
• hook：H3 阶段锁定的公开开场句
• 「口播稿」里不再单独保存一份 Hook，避免两处漂移

刚才 runner 的 status \-\-content\-id 只返回了 title，没有返回 hook。因此我刚才实际做到的是：

• 口播首句与 title 一致
• 但工具没有证明首句与 Sheet 的 hook 列逐字一致

我不应该默认把 title 当成 hook。这是当前流程的真实缺口。

正确做法应当是：

1）写稿前回读 Content\_Backlog\.hook
2）第一条非空口播句必须与该 Hook 一致
3）script 命令写入前自动校验
4）不一致就拒绝写入
5）Hook 改变后旧脚本和 H4 审批自动失效

目前第 1、3 步还没有被 runner 硬执行，所以这项规则暂时依赖人工检查。下面讲的是 Social OS 的完整设计，以及我以后应当遵循的标准执行逻辑。

――――――

一、Social OS 的整体架构

它由四层组成。

1\. 产品入口层

每个产品有一个自己的入口 Skill。例如 AstrologyWiki 使用：

• social\-pipeline\-astrologywiki

它负责：

• 判断哪些用户指令属于 AstrologyWiki 社媒流程
• 指向对应产品配置
• 指向该产品的文案风格、安全规则和生产资料
• 决定账号、平台和产品特有的限制
• 把执行请求交给通用 core

它本身不复制完整流程，避免多产品规则漂移。

2\. 通用流程层

通用 Skill 是：

• social\-pipeline\-core

它定义所有产品共同遵守的内容：

• 工作模式
• 状态机
• H0–H5 人工确认门
• 数据表结构
• 证据规则
• 防幻觉规则
• Script 与 Package 契约
• 数据窗口
• L1–L3 学习结论晋升规则
• runner 的读写权限

3\. 产品配置层

AstrologyWiki 的 product\-config\.yaml 保存相对稳定的配置，例如：

• 产品定位
• 目标市场和语言
• ICP
• 品牌语气
• 禁止表达
• 当前账号
• 内容池比例
• Hot 评分规则
• 可用制作形式
• 可用制作工具
• 数据观察窗口
• Google Sheet ID
• 通知群
• 产品安全规则和文案规则的文档位置

但产品启动完成后，运行时状态以 Sheet 为准。配置文件不承担每天的审批和进度状态。

4\. 执行层

唯一正式执行入口是：

• social\_pipeline\.py

主要子命令包括：

• validate：检查产品配置和前置条件
• init：初始化 Social OS 表格
• status：只读当前进度
• source\-ingest：把来源放入证据池
• research：生成证据、假设、基线和候选选题
• script：写入或覆盖唯一当前口播稿
• package：生成文案包
• metrics：追加发布数据快照
• review：生成复盘结论

所有正式写表都必须经过这个 runner。不能：

• 直接调用 Google Sheets API 绕过 runner
• 用竞品分析的 writer 写 Social OS
• 整行覆盖
• 写人工审批列
• 跳过状态门
• 自动发布

――――――

二、Google Sheet 在系统里的作用

Social OS 不是普通的内容表，而是运行状态的权威控制面。

一个产品对应一张 Spreadsheet。当前结构有十张表，其中七张是日常可见表，三张是内部研究表。

1\. 产品定位

保存：

• 产品一句话定位
• 产品网址
• 目标用户
• 核心痛点
• 目标市场
• 目标动作和 CTA
• 品牌语气
• 禁止表达
• 周产能
• 产品负责人审批

这是 H0 的载体。

2\. 账号与形象

保存每个账号的：

• Handle
• 平台
• active / paused / retired 状态
• 内容方向
• 周产能
• Avatar
• Voice
• 语速
• 背景
• 字幕样式
• 画幅
• HeyGen 模板
• 形象授权证据

这张表基本属于人工权威，因为“用谁的脸、什么声音、哪个账号代表品牌”不能由 AI 自动决定。

这是 H2 的载体。

3\. 选题审批

每条候选包含：

• content\_id
• 周次
• 目标账号
• title
• hook
• angle
• why\_now
• 分数
• 对应假设
• 机器阶段
• selection\_status
• 放弃理由
• 派生内容状态
• 建议制作形式
• 建议制作工具
• 路线理由

其中：

• 候选内容由机器生成
• selection\_status=selected/dropped 由人工填写
• AI 不能代签

这是 H3 的载体。

4\. 口播稿

每个 content\_id 只有一行当前稿：

• content\_id
• script\_text
• 脚本 Hash
• 字数
• 发音说明

关键原则：

• 同一内容不保留两个“当前版本”
• 改稿时覆盖原行
• Sheet 中这行是贴入生产工具的唯一口播来源
• 历史审计由 Hash 和系统审计列承担，不让操作者在多个版本间猜

5\. 文案包

保存最终可发布组合：

• content\_id
• 账号
• 发布包 Hash
• 预计时长
• Caption
• Hashtags
• CTA URL
• 自动检查结果
• H4 审批状态
• 审批人
• 审批时绑定的 Hash
• AIGC 标签确认
• ready\_to\_paste
• 发布链接
• 实际发布时间
• 定时时间
• 备注

它是制作前的主交付物，也是 H4 的载体。

6\. 数据回收

按发布时间追加数据快照：

• 24 小时
• 72 小时
• 7 天
• 30 天

可以记录：

• Views
• Likes
• Comments
• Shares
• Saves
• Completion rate
• Follows
• Link clicks
• Signups
• 抓取状态

这张表只能追加，不能覆盖历史快照。缺数据时留空，不能写成 0。

7\. 复盘结论

保存：

• 事实与推断
• 建议改变什么
• 支撑内容 ID
• 证据数量
• L1/L2/L3 级别
• 变更提案链接
• 人工决定
• 人工备注

这是 H5 的载体。

8–10\. 三张内部表

默认隐藏：

• 内部\_证据池
• 内部\_假设
• 内部\_对标基线

它们让每条选题和每条复盘结论能向上回链，而不是只留下“AI 觉得这个会火”。

三、完整业务链路

可以把整个流程看成下面这条链：

\`\`\`text
产品定位
→ 证据池
→ 对标基线
→ 内容假设
→ 账号策略
→ 候选选题
→ 人工选中
→ 口播稿
→ 文案包
→ 人工批准
→ HeyGen/剪辑
→ 人工发布
→ 数据回收
→ 复盘结论
→ 规则变更提案
\`\`\`

第 1 步：锁定产品定位

人工确定：

• 我们是谁
• 给谁做
• 解决什么问题
• 用户看完要做什么
• 什么语气可以用
• 哪些说法禁止
• 一周能做多少内容

H0 没通过，不能进入正式研究和生产。

第 2 步：建立证据池

来源可以包括：

• 竞品账号
• 竞品帖子
• 用户原话
• 当前公开讨论
• 已发布内容的历史表现

证据必须区分：

• 已抓取并核验
• 候选来源
• 未找到
• 读取失败
• 待人工抽检

LLM 提到的数字不直接采用。只有真实采集回写的数据才算证据。

TikTok/YouTube 链接的衔接

• 收到裸 TikTok/YouTube 链接：先进入独立的竞品分析流程
• 如果说“分析并入池”：先完成竞品拆解，再通过 source\-ingest 写入 Social OS 的证据池
• 入池后仍只是候选证据，不会自动通过 H1

第 3 步：建立对标基线

系统根据真实样本建立参照，例如：

• 参考账号 30 天中位播放
• 样本数量
• 我方目标值
• 观察时间

没有基线时，“3000 播放”本身没有意义。

第 4 步：形成可验证假设

例如：

• 具体关系行为型 Scorpio Hook 是否比抽象性格判断有更高完播
• 友情场景是否能扩展当前过度集中在恋爱题材的内容
• 单人 AI Host 是否比双人对话更适合某种心理机制

假设必须：

• 能被数据支持或推翻
• 回链证据来源
• 写清成功指标
• 写清观察窗口

第 5 步：锁定账号策略

人工决定：

• 哪些账号 active
• 每个账号负责什么
• 每周产能
• 形象、声音和模板
• 哪些内容不能投给该账号

例如当前：

• @astrologywiki：事实、知识、工具承接
• @miraaastrology：具体 placement/sign、关系行为、心理机制

暂停或退役账号不能自动重新启用。

第 6 步：生成候选选题

只有以下场景才新增正式候选：

• 周一建立计划
• 明确补库
• 明确重排
• 评估 Hot 内容

普通“今天做什么”不会重新生成选题。

生成候选前，会检查：

• 产品定位
• 目标用户
• 账号匹配
• 当前库存缺口
• 周产能
• 内容池比例
• 最近内容去重
• 历史数据结论
• 当前公开来源
• 合规和事实风险

AstrologyWiki 新候选还要求：

• 固定竞品索引成功读取
• 至少核验两个相关当前公开来源
• Hot 需要更严格的来源数量和直接链接
• 读不到必要来源就停止，不写猜测版选题

候选会写入「选题审批」，等待 H3。

四、从选题到口播稿的正确流程

这是这次最相关的一段。

1\. 先回读 H3

收到“写口播稿”或“生成文案包”后，先运行：

\`\`\`text
status \-\-content\-id \<content\_id\>
\`\`\`

确认：

• 选题存在
• 目标账号正确
• selection\_status=selected
• 是否已经有脚本或文案包
• 现有制作路线是否被人工修改

未被选中就停止。

2\. 读取锁定变量

应该读取：

• title
• hook
• angle
• why\_now
• 目标账号
• 来源假设
• 内容池
• 制作形式
• 已有人工修改

这里的优先级应该是：

\`\`\`text
H3 锁定 Hook
\> 单条人工要求
\> 产品文案规则
\> 历史样本
\> AI 自己提出的新 Hook
\`\`\`

如果 H3 已经有 Hook，脚本阶段不应再生成五个替代 Hook。

3\. 写作前检查

我会参考：

• AstrologyWiki 产品配置
• 账号方向
• 品类安全规则
• Copy Style
• 同账号最近的已发布稿
• 同账号当前未发布稿
• 人工已经确认的修改偏好
• Humanizer 规则

主要检查：

• 是否与近期内容重复
• 是否复用了旧内容的核心机制
• 是否出现宿命论
• 是否出现心理诊断
• 是否把星座写成绝对事实
• 是否攻击身份而不是描述行为
• 是否复制竞品措辞
• 是否用抽象词代替具体场景

4\. 口播稿结构

标准结构是：

1）首句逐字使用 H3 Hook
2）给出具体生活场景或行为
3）解释一个核心机制
4）加入必要边界，避免绝对化
5）回扣原 Hook
6）控制在适合目标平台的时长

写完后进行口语自然度检查：

• 是否能自然说出口
• 是否有过长从句
• 是否有 AI 式工整对偶
• 是否反复使用 not X, but Y
• 是否堆叠抽象名词
• 是否有不自然的总结金句
• 是否适合美式英语口播
• 前 2–3 秒是否清楚

5\. 推荐制作路线

根据脚本判断：

• 单人 AI Host
• 双人 AI 对话
• 录屏
• 图文
• 混剪
• 其他形式

再从当前已配置工具中选择：

• HeyGen
• Screen Studio
• CapCut
• 图文生产流程
• 人工处理

如果 Sheet 里已有人工路线，runner 会保留，不会自动覆盖。

6\. 写入唯一口播稿

调用 script 后：

• 写入「口播稿」
• 计算字数
• 计算脚本 Hash
• 阶段进入 scripting
• 写后立即回读核验

如果用户只说“写口播稿”，到这里停止。

7\. 生成文案包

只有用户明确说：

• 生成文案包
• 做成 Package
• 准备贴 HeyGen

才继续调用 package。

文案包包括：

• 当前唯一口播稿
• Caption
• Hashtags
• CTA URL
• 预计时长
• 自动检查结果

CTA URL 要带：

\`\`\`text
utm\_campaign=\<content\_id\>
\`\`\`

这样发布数据可以回链到同一条内容。

――――――

五、H4 为什么必须重新审批

文案包的 script\_hash 不只覆盖口播稿，还覆盖：

• Script
• Caption
• Hashtags
• CTA URL

因此任何一项改变，Hash 都会改变。

ready\_to\_paste=TRUE 必须同时满足：

1）checks 以 ok 开头
2）approval\_status=approved
3）当前 script\_hash 非空
4）approved\_script\_hash 与当前 Hash 一致
5）aigc\_label\_on=TRUE

所以：

• 批准后改一个字，旧批准失效
• 改 Hashtag，旧批准也失效
• 换 CTA 链接，旧批准仍会失效
• AI 无权替自己重新批准

飞书里回复“确认”“可以”“批准了”也不算过门。必须回到 Sheet 填写人工字段，再由 runner 回读验证。

――――――

六、制作与发布

当前 Social OS 只做到“可制作、可审批、可复制”，不会自动调用付费生产工具，也不会自动发布。

人工流程是：

1）确认 ready\_to\_paste=TRUE
2）从「口播稿」复制唯一当前稿
3）根据 production\_tool 进入 HeyGen 等工具
4）使用「账号与形象」中的 Avatar、Voice、背景和字幕设置
5）人工检查成片
6）手动发布
7）回填真实 publish\_url
8）回填真实 published\_at

published\_at 不能由系统猜，因为它是所有数据观察窗口的起点。

――――――

七、数据回收与复盘

数据窗口

以真实 published\_at 为锚点：

• 24h：允许约 20–28 小时
• 72h：允许约 66–78 小时
• 7d：允许约 144–192 小时
• 30d：允许约 648–792 小时

超出窗口的数据仍可保存，但会标记 early 或 late，不用于严格横向比较。

复盘时会做什么

系统会区分：

• 已核验事实
• 运营推断
• 下一轮建议

例如：

\`\`\`text
事实：具体行为型 Hook 的两条内容，在有效 24h 快照中的完播率高于当前基线。
推断：用户可能更容易在前两秒理解具体场景，而不是抽象身份判断。
建议：下一周保持账号、主播和时长不变，再测试两个具体行为型 Hook。
\`\`\`

不会因为单条高播放就永久改变账号方向。

――――――

八、学习结论如何升级

L1：单条结论

条件：

• 至少一条内容有可用数据快照

影响范围：

• 只影响该内容或紧邻的下一次测试

L2：进入 Reference

条件：

• 至少两条不同内容支持同一结论
• 人工选择 adopt

影响范围：

• 成为以后写稿时可参考的稳定经验

L3：提出流程或 Skill 修改

条件：

• 至少三条不同内容
• 横跨至少两个自然周
• 人工选择 adopt

即使达到 L3，系统也不会直接改 Skill，而是生成变更提案，包括：

• 原规则
• 建议新规则
• 支撑证据
• 反例
• 生效条件
• 失效条件
• 回滚方式

由负责人人工应用。

九、我接收不同指令时会进入什么模式

\| 用户指令 \| 模式 \| 我会做什么 \|
\|\-\-\-\|\-\-\-\|\-\-\-\|
\| “今天做什么”“进度” \| Mode A \| 只读 status，不写表 \|
\| “跑本周选题” \| Mode B \| 研究证据、生成有限候选，停在 H3 \|
\| “补库”“重新排选题” \| Mode C \| 先说明产能变化，再补有限候选 \|
\| “这个热点值得做吗” \| Mode D \| 按 10 分制核验和评分 \|
\| “回收数据”“这周复盘” \| Mode E \| 追加快照、生成 Insights，停在 H5 \|
\| “把 c\-xxx 写成口播稿” \| Mode F Script \| 检查 H3，写唯一口播稿，停在 scripting \|
\| “生成文案包” \| Mode F Package \| 写 Script，再生成 Package，停在 H4 \|
\| TikTok/YouTube 裸链接 \| 竞品分析 \| 抓数据、抽帧、拆解并写竞品表 \|
\| “分析并入池” \| 两段流程 \| 先竞品分析，再放入 Social OS 证据池 \|

Social OS 不是 Kanban，因此这些动作没有 Kanban task ID。

十、系统的主要安全与可靠性措施

runner 还负责以下底层防护：

• 只允许写机器列
• 人工审批列受保护
• 表头发生漂移就停止
• 外部文本按 RAW 写入，避免公式注入
• 同一身份重复写入自动去重
• 同一身份不同内容报冲突
• 写完后立即读回核验
• 不允许修改身份字段
• Metrics 只能追加
• 多进程写表有锁
• 缺失数字留空
• 网页和 Sheet 内容只当数据，不当操作指令
• 依赖来源读不到时停止，不编造
