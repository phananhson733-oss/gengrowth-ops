# 爆款视频分析工作流调研与现有方案对比

## 0. 结论

三条小红书内容实际只包含两种不同方法：

1. **曚曚 AGI 的 n8n 自动化方案**：按关键词用 Apify 抓 TikTok 视频，按播放量排序，逐条下载并交给 Gemini 分析，最后写入 Google Sheets。第 1 条是讲解视频，第 3 条是同一工作流的图文教程和可导入 JSON/PDF。
2. **尤总点灯的人工研究方案**：人工挑选 10–20 条竞品高表现视频，用 Genspark 批量下载；先让 Gemini 逐条分析，再让 Gemini对多条分析结果做第二次横向归纳。

对 AstrologyWiki 来说，**不建议用其中任何一套替换现有飞书 Social 机器人**。当前机器人已经有更完整的结构化字段、产品改编建议、四账号路由、品牌风险和置信度，方向更符合实际运营。

最值得吸收的是两块：

- 从 n8n 方案吸收：**关键词 / 账号候选抓取、排序、批量排队**；
- 从尤总方案吸收：**单条分析 → 同类样本横向归纳**的两阶段分析。

推荐目标不是“再建一套独立系统”，而是：

```text
Apify / 账号清单发现候选
→ 人工确认值得分析的 5–10 条
→ 飞书 Social 机器人逐条结构化分析
→ 同类视频二次归纳重复规律、例外和可执行模板
→ 继续写入现有 Google Sheet
→ Pengman 选中后再进入 Brief / SOP / skill
```

当前最优先的不是增加更多抓取，而是先把现有链路的几个已验证缺口补齐：

1. TikTok Photo / Carousel 的 5 条验收样本目前只有 1 条读到了图片数量与 `slide_text`；
2. `video_analysis.content_type` 只有 11/52 条填写；
3. Sheet 中仍有 2 个重复 URL；
4. 缺少多条视频的聚类归纳；
5. 外部 n8n JSON 使用的 `gemini-2.0-flash` 已于 2026-06-01 关闭，不能原样导入生产。

## 2. 方法一：曚曚 AGI 的 n8n 自动化方案

### 2.1 实际工作流

```text
手动执行 workflow
→ Config：Apify Key / Gemini Key / Top N / Prompt / 抓取数量
→ Set Keywords：输入一个关键词
→ Apify TikTok Scraper：抓取指定时间范围和地区的视频
→ 按 views 降序
→ Limit Top N
→ Loop Over Items 逐条处理
→ 从 TikTok 视频 URL 下载文件
→ 上传 Google Drive
→ 从 Google Drive 再下载到 n8n binary
→ Gemini Files API 建立上传
→ 上传视频
→ 固定等待 50 秒
→ Gemini 分析
→ Code 节点用正则解析文本
→ 追加写入 Google Sheets
```

PDF 中的默认设置：

| 配置 | 默认值 |
|---|---:|
| 关键词 | `AI learning tool` |
| 地区 | `US` |
| 时间范围 | `THIS_WEEK` |
| Apify 抓取数 | 15 |
| Top N | 20 |
| Gemini 模型 | `gemini-2.0-flash` |
| 每条上传后等待 | 50 秒 |
| 执行方式 | Manual Trigger |

### 2.2 它分析什么

作者的 Prompt 要求 Gemini 输出：

- `ContentType`：UGC faceless / UGC with face / professional；
- `Category`：Tutorial / Review / Challenge / Vlog / Q&A 等；
- `Hook`；
- `VisualHook`；
- `Transcript`；
- `Captions`；
- `AudioType`；
- `CTA`；
- `Tone`；
- `Analysis`。

Google Sheets 还记录 Apify 抓到的：

- 发布时间；
- 播放、点赞、评论；
- hashtag；
- 视频 URL、TikTok 页面；
- 视频标题；
-账号粉丝；
- cover。

### 2.3 优点

1. **从发现到入表是完整闭环**  
   不需要运营先手工收集每条视频，适合探索一个新关键词。

2. **视频文件确实交给多模态模型**  
   不是只把 caption 发给 AI，所以理论上能看到画面、字幕并听到音频。

3. **输出字段足够直观**  
   Hook、Visual Hook、Transcript、CTA、Tone 很适合快速筛选。

4. **结构适合低代码交接**  
   节点、凭证、字段映射和 Prompt 都集中在一个 workflow 中，容易看懂。

### 2.4 关键问题

#### A. 这个 PDF 不能在今天原样运行

它调用 `gemini-2.0-flash`。Google 官方文档显示该模型已于 2026-06-01 关闭，必须换成当前受支持模型并重新测试。

这不是“以后可能过期”，而是当前硬阻塞。

#### B. Google Drive 中转不是技术必需

作者说“API 不支持 URL 分析视频”，这部分基本正确：Gemini 不能直接拿任意 TikTok 页面 URL 当视频文件。

但当前流程：

```text
TikTok URL → n8n 下载 → Google Drive 上传 → n8n 再下载 → Gemini 上传
```

中间的 Google Drive 不是 Gemini 的必要要求。n8n 已经拿到 binary 后，可以直接传 Gemini Files API；较小的短视频还可以直接以内联数据发送。

Drive 只在“需要人工复核或长期留档”时有价值。否则会带来：

- 两次额外传输；
- 更多失败点；
- Drive 文件积压；
- 隐私和保留周期管理；
- 执行时间增加。

#### C. 固定等 50 秒不可靠

官方示例要求查询文件状态，直到 `ACTIVE`，失败时处理 `FAILED`。

PDF 只固定等待 50 秒：

- 小文件可能浪费时间；
- 大文件或排队时 50 秒可能不够；
- 没有明确区分处理失败和仍在处理。

按默认 15 条视频计算，仅等待节点就至少需要 750 秒，即 12.5 分钟，还未包含 Apify、下载、Drive、Gemini 和 Sheet 时间。因此“几分钟完成”不适用于默认批量设置。

#### D. “Top 20”与“只抓 15 条”互相矛盾

`videosCount = 15`，`getTop = 20`。排序后最多只有 15 条，Top 20 不会产生 20 条结果。

#### E. “爆款”只按原始播放量定义

当前排序没有控制：

- 账号粉丝规模；
- 发布时间和内容年龄；
- 同账号日常基线；
- 互动率；
- 分享 / 收藏；
- 付费投放；
- 大号历史权重。

结果会天然偏向大账号和发布时间更早的内容。它能找“这个搜索结果里播放高的”，但不能自动证明“这是可复制的爆款机制”。

#### F. Prompt 输出是自由文本，不是真正结构化 JSON

流程要求“一行一个字段”，再用正则解析。

风险包括：

- Gemini 轻微改名就会产生空字段；
- 多行 Transcript 或 Analysis 可能只保留第一行；
- 没有 schema 校验；
- 没有保存原始模型响应用于排错；
- 失败时把多个字段都写成 `Analysis failed`，难以区分抓取、下载、上传、处理或解析失败。

当前 Gemini 已支持 JSON Schema 结构化输出，生产版本不应继续依赖易碎的文本正则。

#### G. API Key 放在普通 Config 节点

PDF 把 ApifyKey 和 GeminiKey 作为普通字段写在 workflow 中。这样容易出现在：

- workflow 导出；
- n8n execution data；
- 调试截图；
- 日志。

应改成 n8n Credentials、环境变量或密钥管理，不应作为可见 Set 节点值。

#### H. 没有去重和分析版本

workflow 只向 Sheet `append`：

- 同一链接重跑会重复；
- Prompt 或模型升级后无法区分版本；
- 人工修正和 AI 重跑之间没有覆盖规则；
- 没有 `run_id`、`failure_stage` 或 `source_checked_at`。

当前 AstrologyWiki Sheet 已经出现两个重复 URL，这正是 append-only 无唯一键会产生的实际问题。

#### I. 它只做单条分析，没有真正做“规律”

虽然营销文案说可以找到爆款规律，但 JSON 的实际流程是逐条分析后直接入表，没有：

- 同类视频聚类；
- 重复模式出现次数；
- 反例；
- 账号基线比较；
- 跨视频汇总；
- 用自家发布结果验证。

它交付的是“批量单条拆解”，还不是可靠的“爆款规律模型”。

### 2.5 当前适合怎样使用

可以把它当作：

- 一个可学习的低代码原型；
- 关键词找候选的参考；
- Apify → 排序 → 队列 → 多模态分析的架构示例。

不建议：

- 直接导入后填 Key 就跑；
- 让它替代现有飞书机器人；
- 把播放 Top N 直接称为可复制爆款；
- 在未加成本上限、去重和人工确认前每天定时跑。

## 3. 方法二：尤总点灯的 Genspark + Gemini 方案

### 3.1 实际工作流

```text
进入竞品 TikTok 账号
→ 人工选 10–20 条播放 / 点赞较高的视频
→ 保存每条链接
→ 用 Genspark 的 Download for Me Agent 下载到云端
→ 再下载到本地
→ 每条视频单独上传 Gemini
→ Prompt 1：逐条拆 Hook / 画面 / 剪辑 / 留存
→ 完成多条单条分析
→ Prompt 2：只总结重复出现的共同规律
→ 输出可直接复用的内容打法和执行清单
```

### 3.2 两段 Prompt 的核心

#### Prompt 1：单条视频

要求：

- 用 3–5 个步骤说明视频在讲什么；
- 拆前 1–3 秒 Hook；
- 识别提升吸引力的关键画面；
- 解释留存机制；
- 输出 3 个可直接复用的套路；
- 重点分析画面、文字和剪辑，不只是复述内容；
- 不要泛泛而谈。

#### Prompt 2：跨视频归纳

要求：

- 不再分析单个视频；
- 找出最常出现的 5 个成功套路；
- 总结 Hook 的共性结构；
- 总结画面和剪辑的共性；
- 总结留存逻辑；
- 把视频归成 3–5 种内容类型；
- 只总结重复出现的规律；
- 不复述任何单个视频；
- 结论必须具体、可执行。

示例最终报告包含：

- 三类内容类型；
- 最有效的 Hook；
- 0–3 秒、3–15 秒、15–30 秒的执行清单；
- 转化段；
- 音乐和剪辑标准。

### 3.3 优点

1. **样本选择有人判断**  
   人先决定竞品和代表视频，避免系统抓到大量无关搜索结果。

2. **先单条、再横向归纳**  
   这是三条内容里分析方法最成熟的一点。单条视频不能证明规律，第二次归纳至少要求重复出现。

3. **Prompt 对视觉和留存更敏感**  
   它明确要求看画面、文字、剪辑和前 1–3 秒，而不是只总结视频讲了什么。

4. **最终输出可用于制作**  
   按时间段给动作清单，比泛泛的“这个 Hook 很好”更容易交给内容制作。

### 3.4 问题

1. **手工成本高**  
   找视频、收链接、下载到云端、再下载本地、逐条上传，10–20 条会产生大量机械操作。

2. **同样存在不必要的中转**  
   Genspark 云端 → 本地 → Gemini 可被自动化下载和直接上传替代。

3. **只有爆款样本，存在幸存者偏差**  
   如果只分析高表现视频，不放入同账号普通表现的视频做对照，模型无法判断哪些元素是爆款独有，哪些只是该账号固定模板。

4. **没有结构化表格和数据版本**  
   画面中展示的是 Gemini 对话报告，不是长期可筛选的数据库。

5. **没有产品和品牌约束**  
   Prompt 能提炼“可复用套路”，但没有 AstrologyWiki 当前方案中的：
   - 四账号适配；
   - 产品承接；
   - 版权风险；
   - 宿命化 / 绝对预测风险；
   - 证据置信度；
   - 不可复制因素。

6. **“重复出现”仍可能被模型主观判断**  
   第二段 Prompt 没有要求：
   - 每条规律由几条视频支持；
   - 支持视频 ID；
   - 反例；
   - 置信度；
   - 是否只来自同一账号。

### 3.5 当前适合怎样使用

最适合把它的两阶段方法接入现有机器人：

```text
现有 video_analysis 多条记录
→ 按账号 / 主题 / 形式 / 时间窗聚类
→ 汇总器只读取同一 cluster
→ 输出“规律 + 支持数 + 反例 + 可执行模板”
```

不需要继续用 Genspark 作为必经下载工具。

## 4. 现有飞书 Social 机器人方案

仓库方法论定义的当前流程是：

```text

+ AI 关键词扩展
+ 飞书机器人结构化拆解
+ Google Sheet 留档
+ Pengman 筛选
```

### 4.3 当前方案明显强于外部方案的地方

1. **不是只回答“为什么爆”**  
   会同时回答“能不能为 AstrologyWiki 所用”。

2. **有不可复制因素**  
   会区分真人 IP、版权素材、宿命化、夸大承诺、品牌不符和样本量不足。

3. **有四账号路由**  
   外部两套方法没有“官方 / AI 占星师 / 热点 / 普通爱好者”的明确落点。

4. **有产品承接**  
   会写具体的 birth chart、Sky Map、工具页或内容 CTA，而不是只给内容套路。

5. **有证据披露**  
   抓不到时会写 `待补数据/待确认`，不会默认把每个 AI 结论当事实。

6. **已经形成长期资产**  
   数据进入 Sheet，再进入 Brief、SOP、skill 和发布复盘；不是一次性的 Gemini 对话。

- 只有 `wealthyastrogirl` 一条：
  - `content_type = carousel`；
  - `photo_count = 13`；
  - 有部分 `slide_text`。

因此，需求文档写的“5 条中至少 3 条成功”尚未由当前 Sheet 证明。

更需要注意：

- 需求文档 frontmatter 写 `updated: 2026-07-25`；
- 正文写“功能已于 2026-07-25 前上线完成”；
- 本报告核验日期是 2026-07-23。

按当前日期，这个完成声明来自未来日期，不能作为已经验收的证据。建议在 2026-07-25 实测完成后再保留 `status: done`，或先改成 `implemented_pending_acceptance`。

#### B. `content_type` 回填不足

需求要求所有成功内容都有 `content_type`，实际只有 11/52 条填写。风格标签回填已完成，但内容类型回填没有同步完成。

#### C. 有重复 URL

两个视频 URL 各重复一行：

- `angelic_oracle/video/7626740251087719694`
- `promentalityx/video/7654674644355550478`

这会污染：

- 样本计数；
- 风格统计；
- 后续规律归纳；
- “多少条支持这个模式”的结论。

#### D. 缺少多样本汇总

当前 Sheet 单条分析很丰富，但仍主要依靠 Pengman 手工从 52 条中发现共同规律。多链接输入虽要求横向结论，但 Sheet 没有持久化：

- cluster；
- 模式支持数；
- 反例；
- 模式置信度；
- 分析版本。

#### E. `high` 置信度的口径需要更严

52 条中：

- high：36；
- medium：14；
- low：2。

但很多记录缺 likes、comments、shares、发布时间或完整画面。建议把：

- 数据获取置信度；
- 内容理解置信度；
- “为什么高表现”的因果置信度

拆开。当前单一 `analysis_confidence` 容易把“视频内容读得清楚”和“已证明它为什么爆”混在一起。

## 6. 推荐的新工作流

### 6.1 原则

1. 继续让 Google Sheet 做当前在线竞品数据的唯一事实来源；
2. 飞书机器人继续做链接入口和主分析器；
3. n8n / Apify 只负责“发现候选和排队”，不直接把所有抓到的视频都分析；
4. 只有人工确认的 5–10 条才进入多模态分析；
5. 多条归纳必须基于同类 cluster，不能把不同账号、题材和形式混在一起；
6. 规律必须带支持数和反例；
7. 机器人不得直接生成最终 Brief，Pengman 确认后再进入内容生产。

### 6.2 推荐链路

```text
输入模式
├─ A：单条视频 / Photo 链接
├─ B：多条已选链接
└─ C：关键词 / 竞品账号发现

C 模式：
Apify 抓元数据
→ 规范化 URL / TikTok post ID
→ 去重
→ 按时间窗、账号基线、互动率、播放速度做候选排序
→ 只把候选卡发给 Pengman
→ 人工选择 5–10 条

A / B / 已确认 C：
下载一次到临时存储
→ 直接上传当前受支持的 Gemini 模型
→ 轮询文件状态直到 ACTIVE / FAILED
→ JSON Schema 结构化单条分析
→ 保留 observed facts / inference / missing data
→ upsert 到 video_analysis
→ 不覆盖人工标签

多条同类记录：
按 account / topic / primary_style_tag / time_window 分 cluster
→ 二次归纳
→ 输出重复模式、支持数、反例、适配账号、可执行模板
→ Pengman 确认
→ 写入 format analysis / Brief / SOP / skill
```

### 6.3 候选排序不要只看播放量

第一版可以用简单分层，不必做复杂预测模型：

```text
候选优先级 =
同账号相对播放表现
+ 互动率
+ 分享率（如可见）
+ 发布时间校正
+ 与 AstrologyWiki 账号路线的相关性
```

推荐同时保留：

- 高表现样本；
- 同账号普通表现对照；
- 至少一个“同形式但没爆”的反例。

这样第二阶段才有资格判断“哪些元素可能与高表现相关”。

### 6.4 单条分析的推荐输出

继续复用当前 `video_analysis`，但模型输出应明确分三层：

```yaml
observed:
  visible_text:
  transcript:
  scene_timeline:
  public_metrics:
interpreted:
  hook:
  retention_mechanism:
  structure:
  cta:
operational:
  replicable_elements:
  non_replicable_elements:
  adaptation_for_product:
  recommended_account:
  risk_note:
evidence:
  data_confidence:
  content_confidence:
  performance_causality_confidence:
  missing_fields:
```

重点：不要再用“分析置信度 high”同时代表所有层级。

### 6.5 多条归纳的推荐输出

每条模式必须包含：

| 字段 | 说明 |
|---|---|
| `pattern_name` | 模式名称 |
| `support_count` | 支持样本数 |
| `supporting_urls` | 支持链接 |
| `counterexamples` | 反例链接 |
| `shared_hook` | Hook 共性 |
| `shared_visual` | 画面共性 |
| `shared_retention` | 留存共性 |
| `what_not_proven` | 不能从当前样本证明什么 |
| `recommended_account` | 四账号路由 |
| `actionable_template` | 可直接测试的结构 |
| `confidence` | 低 / 中 / 高 |

建议第一版只有 `support_count >= 3` 才进入“重复模式”；否则标为候选观察。

## 7. 最小改动清单

### P0：先修现有链路

1. **Photo 验收重跑**
   - 重新跑 5 条有效 `/photo/`；
   - 5 条都写 `content_type`；
   - 至少 3 条有真实图片数量、首图 Hook、页面结构和 CTA；
   - 不允许仅根据用户摘要补完整分析。

2. **补 `content_type`**
   - 回填当前 52 条；
   - 普通视频写 `video`；
   - Photo 写 `photo` 或 `carousel`；
   - 不确定写 `unknown`，不要留空。

3. **加唯一键并去重**
   - TikTok 使用 `platform + post_id`；
   - YouTube 使用 `platform + video_id`；
   - 重跑改为 upsert，不再 append 新行；
   - 保留人工确认标签。

4. **增加失败阶段**
   - 最小只增加 `failure_stage` 和 `error_detail`；
   - 可选值：`page_access / media_extract / transcript / ocr / metrics / model / parse / writeback`。

5. **分开置信度**
   - 保留现有 `analysis_confidence` 兼容旧表；
   - 新增或在内部结果中区分 `data_confidence`、`content_confidence`、`causality_confidence`。

### P1：加入两阶段分析

1. 多条输入先逐条入表；
2. 用相同账号 / 主题 / 风格生成 `cluster_id`；
3. 只对同类 cluster 做二次归纳；
4. 输出支持数、反例和模板；
5. 横向结果写到单独 `pattern_analysis`，不要塞进某一条视频行。

### P2：加入 Apify 候选发现

1. 第一版仅手动触发；
2. 每次只跑一个关键词或一个账号；
3. 配置单次最大条数和最高花费；
4. 只抓元数据，不自动下载全部视频；
5. 人工确认后再分析 5–10 条；
6. 验证稳定后再考虑周度调度。

### 暂时不要做

- 爆款预测 9 分自动提醒；
- 上千条视频的黑箱评分；
- 每天自动抓所有账号；
- 自动生成并发布脚本；
- 未经人工确认就把模式写入 SOP / skill。

原因：当前连 Photo 验收、去重和 `content_type` 都还未稳定，先扩预测会把数据质量问题放大。

## 8. 验收建议

### 单条分析

- 10 条普通视频至少 7 条完成；
- 每条成功记录有 `content_type`、Hook、结构、CTA、风险、产品适配和账号路由；
- 同一链接运行两次不新增重复行；
- 重跑不覆盖人工标签。

### Photo / Carousel

- 5/5 正确识别；
- 3/5 以上真实读取图片数量和顺序；
- 3/5 以上提取首图 Hook、页面推进和最后 CTA；
- 失败能精确到 `failure_stage`；
- 不根据 caption 猜未读取页面。

### 多条归纳

- 输入 10 条同类视频；
- 每条先有独立记录；
- 汇总只报告至少 3 条支持的模式；
- 每个模式列出支持 URL 和至少一个反例或“未发现反例”；
- 明确“观察到的重复”不等于“已证明的因果”；
- 输出一个适合四账号之一的具体测试模板。

### 候选发现

- Apify 一次抓取不超过配置上限；
- 有明确单次成本上限；
- 候选排序不只使用 raw views；
- 人工未确认前不下载和分析视频；
- 抓取失败不影响已有单条链接分析入口。

## 9. 最终判断

### 应该保留

- 现有飞书机器人和 Google Sheet；
- 当前丰富的产品适配、风险、四账号字段；
- 人工判断“值不值得研究”的门；
- 从 Sheet 到 Brief / SOP / skill 的沉淀链路。

### 应该吸收

- n8n 方案的 Apify 候选发现和批量排队；
- 尤总方案的“逐条分析后再归纳”；
- Gemini 的直接视频多模态分析；
- 时间段式可执行清单。

### 应该淘汰

- `gemini-2.0-flash`；
- Drive 的强制双重中转；
- 固定等待 50 秒；
- API Key 明文 Config；
- 自由文本 + 正则解析；
- 只按原始播放量选 Top N；
- append-only 无去重；
- 把多条单条分析直接叫作“爆款规律”。

一句话决策：

> **保留现有飞书机器人作为分析主干，新增“Apify 候选发现层”和“同类样本二次归纳层”；不要原样导入 PDF workflow。**
