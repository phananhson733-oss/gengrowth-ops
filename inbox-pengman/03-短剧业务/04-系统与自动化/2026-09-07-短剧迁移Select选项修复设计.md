# 短剧迁移 Select 选项修复设计

**日期：** 2026-09-07  
**状态：** 已批准设计，待实施计划  
**适用范围：** `inbox-pengman/tools/short-drama-release-manager`

## 1. 背景与现场证据

正式 Base 的 data phase 在第一张表“账号台账”的首个批量创建请求中失败：

```text
POST /open-apis/base/v3/bases/:base/tables/:table/records/batch_create
HTTP 200, code 800030005
```

失败后对四表做了全量读回，账号台账、选剧池、采集数据、发布记录均为 0 条，主键集合均为 `SHA256(JSON([]))`，因此没有部分写入，也不需要清理。

根因是 schema 与 record write 契约不闭合：Base v3 的 Select CellValue 只能引用字段中已经存在的 option name；当前“所属组”和“表现形式”的 `options=[]`，但首批账号记录会写入 `A纯切片`、`AstrologyWiki` 等值。选剧池的剧分类、生命周期、语言、来源也存在相同问题。另有四条迁移剧记录使用 `MoboReels`，不在已确认的平台闭集 `ReelShort / DramaBox / ShortMax / TopShort / 其他` 内。

## 2. 目标与非目标

### 2.1 目标

1. 迁移 plan 从最终规范化数据中确定性提取当前所需的可扩展 Select 选项。
2. Schema phase 在四表仍为空时，只追加缺失选项，并做完整读回。
3. Manifest 的 replay、schema action digest 和 receipt 绑定覆盖这些选项，禁止手改 manifest 绕过。
4. Data phase 在第一条记录写入前一次性验证全部 Select 值均可解析，避免跨表部分写入。
5. 将已知旧平台值 `MoboReels` 规范化为 `其他`，保留可追溯证据。
6. 运行期遇到未知可扩展选项时 fail-closed，不隐式修改 schema。

### 2.2 非目标

- 不修改 Google Sheet、SQLite、Collector、Hermes、launchd、角色权限或 Social Bot 命令面。
- 不把 Select 字段改成文本字段。
- 不在普通记录 create/update 中自动创建选项。
- 不复用或编辑现有 manifest、schema receipt、canary receipt、permission attestation。
- 不实现新的 Social Bot “管理选项”命令；未知选项由后续独立、显式批准的管理员 schema 操作处理。

## 3. 方案选择

采用 **manifest 驱动的可扩展选项追加**。

未采用的方案：

- **硬编码当前选项：** 会把可扩展业务词表变成代码闭集，每次增加来源或分类都需要发版。
- **飞书 UI 手工补选项：** 无法由 manifest 重放或由 receipt 证明，恢复和审计都不可靠。
- **record write 隐式新增选项：** 一条普通业务写入会同时改变 schema，扩大权限和并发风险。

## 4. 字段策略

在字段定义中增加纯策略标记 `optionPolicy: "manifest_append"`，只允许以下八个字段使用：

| 表 | 字段 | 类型 |
|---|---|---|
| 账号台账 | 所属组 | 单选 |
| 账号台账 | 表现形式 | 单选 |
| 选剧池 | 剧分类 | 多选 |
| 选剧池 | 生命周期 | 单选 |
| 选剧池 | RS Boost 分类（待确认） | 多选 |
| 选剧池 | 账号组 | 多选 |
| 选剧池 | 语言 | 单选 |
| 选剧池 | 来源 | 多选 |

固定闭集字段继续使用当前 `options` 契约；二者不得混用。`RS Boost 分类（待确认）`和`账号组`本次没有非空迁移值，因此当前 plan 不为它们生成选项 action；未来 migration source 出现非空值时，必须按同一策略生成 action。日常记录写入仍不允许隐式扩展。

## 5. 平台规范化

迁移规范化只接受两类平台输入：

1. 已在固定闭集中的值保持不变。
2. 精确旧值 `MoboReels` 映射为 `其他`。

每条映射生成确定性 warning：

```json
{
  "code": "platform_mapped_to_other",
  "table": "选剧池",
  "source_row": 47,
  "drama_id": "SD-000044",
  "source_value": "MoboReels",
  "target_value": "其他"
}
```

任何其他非空未知平台都生成 blocking diagnostic，不静默归为“其他”。原始值继续保存在签名绑定的 `source_backup` 中；manifest 业务行只写规范值“其他”。Replay 必须重新得到完全相同的行与 warning。

## 6. Manifest 与 Schema action

### 6.1 选项提取

从最终规范化的 `accounts` 和 `dramas` 行中提取八字段的非空 option name：

- 字符串必须已规范化、非空、无控制字符。
- 多选数组内部不得重复。
- 提取顺序使用最终行顺序中的首次出现顺序，保证稳定且保留业务可读顺序。

### 6.2 现有字段

对于已存在的目标 Select 字段：

```text
after_options = before_options + missing_required_options
```

- `before_options` 使用 Base 完整 schema readback 中的现有名称顺序。
- 已有名称原序保留；缺失名称按首次出现顺序追加。
- 不删除、不改名、不主动重排已有名称。
- 现有字段类型或 single/multi 属性不符时直接 `base_schema_drift`。
- 仅当存在缺失名称时生成 action。

Action 固定结构：

```json
{
  "id": "options:账号台账:所属组",
  "kind": "update_select_options",
  "table": "账号台账",
  "field": "所属组",
  "field_id": "fldBQrflrU",
  "phase": "storage",
  "before_options": [],
  "after_options": ["A纯切片", "BL剧鉴赏专家（？", "B生活", "C测试"],
  "spec": {
    "canonical": {"multiple": false, "name": "所属组", "type": "select"},
    "kind": "single_select",
    "name": "所属组",
    "optionPolicy": "manifest_append",
    "phase": "storage"
  }
}
```

`assertManifest()`必须验证 exact keys、八字段 allowlist、field ID、无空白/重复选项、`before_options` 为 `after_options` 前缀、至少新增一个选项，以及 replay 后 action 完全相同。`schema_spec_sha256`继续包含全部 `schema_actions`，从而绑定选项内容。

### 6.3 缺失字段

若一个 `manifest_append` 字段尚未创建，原 `create_field` action 必须携带从源数据派生的初始选项，并由固定客户端 body 构造器生成字段定义。不得先创建空 Select 再等待 data phase 失败。

## 7. Schema apply 与恢复

新增窄客户端接口：

```js
updateSelectFieldOptions(baseToken, tableId, fieldId, tableName, fieldName, options)
```

约束：

- 只允许八个 `manifest_append` Select 字段。
- 拒绝固定 enum、非 Select、空白或重复名称。
- 客户端自行构造完整字段 PUT body；manifest 不能传任意 JSON 到 API。
- 固定调用 `PUT /open-apis/base/v3/bases/:base/tables/:table/fields/:field_id`。
- 响应 field ID 必须与请求一致；ignored fields 或 malformed response 均失败。

字段更新是全量 PUT，只允许在 manifest 已证明四张迁移表全部为空、且 presentation phase 尚未执行时进行。当前需要写入的六个目标字段均为空选项，因此不会重建已有 option ID；另外两个策略字段本次无值、无 action。若中途已有 action 成功，恢复时重新 plan：已存在的 option name 作为新的 `before_options`，只规划剩余缺口。由于恢复仍发生在空表和 presentation 之前，验收以 option name、字段类型与 single/multi 属性为准。

应用每个 action 前必须重新读 schema：

- 当前值等于 `before_options`：执行 PUT。
- 当前值已经等于 `after_options`：视为 action 已完成，只读回。
- 当前值两者都不等：`schema_revision_drift`，停止。

PUT 后完整读回的 option name 必须精确等于 `after_options`，否则不生成 schema receipt。失败时不回删已经追加的选项；重新 plan 是唯一恢复入口。

## 8. Data phase 预检

在 `applyData()` 调用任何 Repository 之前执行全局 Select coverage 检查：

1. 当前 live schema revision 必须等于 schema receipt 的 post revision。
2. 固定 enum 字段中的每个非空值必须属于固定闭集。
3. 八个可扩展字段中的每个非空值必须存在于 live Base 字段 options。
4. 其他 Select 字段出现非空未知值时失败。

任一缺口返回 `base_schema_drift`，details 只包含 table、field 和缺失 option name，不发送任何 record write。现有 Repository 层校验继续保留，形成第二道防线。

日常 `createRecords` / `updateRecords` 同样在 record POST 前取得完整当前字段目录，并验证所有 single/multi Select option name。未知值返回稳定的本地校验错误，record mutation 次数必须为 0。该检查只读取 schema，不创建选项；固定 enum 还需同时通过静态闭集校验。

## 9. 测试设计

所有实现遵循 RED → GREEN → REFACTOR。

### 9.1 Migration

- 八个策略字段全部参与规划；按当前真实源词表生成恰好六个 `update_select_options` action，另外两个空值字段不生成 action。
- 已有额外 option name 被保留，缺失项只追加一次。
- Schema apply 后用同源重新 plan，option action 数为 0。
- 部分 action 已完成时，重新 plan 只包含剩余字段。
- 篡改 `before_options`、`after_options` 或平台映射结果，即使重算顶层 SHA，也因 replay/schema spec 不一致失败。
- 八字段任一必需 option 缺失时，data preflight 在账号写入前失败，四个 Repository 写调用均为 0。
- `MoboReels` 全部映射为“其他”并生成 warning；其他未知平台进入 blocked。

### 9.2 Feishu client

- 精确验证 PUT 路径和完整 Select body。
- 固定 enum、非 allowlist 字段、重复/空白 option 均在网络前拒绝。
- 响应 field ID 不一致、ignored fields、readback 缺项均失败。
- Record create/update 只允许完整当前字段目录中存在的 option name；未知动态值或实际目录缺少的固定值均在 record POST 前拒绝。

### 9.3 CLI 与集成

- Schema adapter 只路由固定 option action。
- Schema receipt 的 manifest SHA、action spec SHA 与新计划一致。
- 内存端到端覆盖 `plan → option actions → schema apply/readback → replan=0 actions`。
- 模拟 Base v3 对不存在选项返回 `800030005`，证明修复前 RED、补齐后 record batch 可通过。

## 10. 上线与证据链

修复合并且全量测试、静态检查、独立评审通过后：

1. 保持 Google 源暂停，连续读取确认 source revision 稳定。
2. 生成全新 manifest；不得编辑旧 JSON。
3. 核对 `blocked=0`、平台业务行无 `MoboReels`、warning 与 option actions 精确。
4. 经动作时确认执行 Schema phase，完整读回本次六个非空字段的 options，并确认八字段策略、四表空集和角色权限未变。
5. 生成新 schema receipt、canary receipt 和 permission attestation。
6. 按新 counts 再取得一次 data phase 动作时确认。
7. Data 成功后执行独立 verify，再进入 presentation 与 sequence phases。

旧 plan `migration-plan-20260907-110158.json` 及其 schema/canary/permission 证据均不可复用。

## 11. 成功标准

- 正式 Base 仍保持四张目标表，无额外表或字段。
- 八个可扩展 Select 字段均受 manifest_append 策略约束；其中本次六个非空字段包含当前迁移所需全部 option name。
- 固定 enum 未被扩大，`MoboReels`仅以“其他”进入业务行且原始证据可追溯。
- Data preflight 能在首笔写入前发现任何选项缺口。
- 新 data phase 精确写入新 manifest 的四表数量并完成逐表读回。
- 未修改 Google Sheet、Collector 行为文件、Hermes、launchd 或角色权限。
